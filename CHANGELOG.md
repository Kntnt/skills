# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/) and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed

- The test suites stand in for a binary through one shared helper. A test that has to fake something an engine shells out to — `gh`, so far — writes the stand-in and gets back the environment that makes it the one that runs, instead of spelling out for itself the executable-in-a-directory-placed-first-on-`PATH` dance. The commit engine's suite carried three copies of that dance; the orchestrate engine being built next talks to the tracker through `gh` for its whole working life and would have added more. Nothing a user can observe changes, and no test's meaning changes — the same tests assert the same things, from one helper instead of three copies.

## [0.8.0] – 2026-08-19

### Added

- `/tldr` — summarise what was just said, and keep replies short by default. Typed bare it takes everything the agent has written since you last spoke, plus whatever earlier context that range needs to make sense, and gives it back in three parts: what happened, what the agent decided on your behalf, and what needs you. All three always appear, and the empty forms are the point — *nothing needs you* is the sentence the reader came for, and a section that shows up only sometimes puts them back to scanning for it. Decisions taken along the way and decisions the reader still has to make are never in the same section, because sorting those two piles is the whole service; until now they arrived mixed into one stream and the reader had to do it themselves. The summary is written at the altitude of somebody who was not watching, in short numbered paragraphs running continuously across the three sections, so a detail can be asked for by number rather than paid for by everybody. It answers in the language the reader was using rather than the one the agent happened to write in, and anything typed after the command is a free-form instruction in any language — `all` widens the range, `engelska` names a language, `bara säkerhetsdelen` narrows the focus. It refuses to pad: a reply already short enough is said to be short rather than summarised into something longer than itself, and a range a compaction has taken a piece out of is reported as such, because *nothing needs you* is worth reading only from somebody who saw all of what they claim to have read. `/tldr --on` switches on TL;DR mode, so the brevity and the closing verdict arrive without being asked for; `--user` makes it standing, `--status` reports both scopes and any staleness, and `--off` takes it back. The issue asked for a Claude Code output style and that is not what was built: output styles exist in one harness, their command was removed in v2.1.91, and being part of the system prompt they cannot take effect in the session that asks for them — so the mode is a managed block in whatever context file the running harness already loads, as `delegation`'s is, and it takes effect on the turn that switches it on. It has no project scope, deliberately: brevity is how one person likes to read, and a committed block would impose it on everyone who clones the repository. It is built from named prohibitions rather than from *use your judgment*, which is the first instruction to erode twenty turns into a session, and the three-part template appears under the mode only above a structural gate — more than one list, more than three paragraphs, or a reply reporting work the reader did not watch — because three headings wrapped around a one-line answer is how a standing instruction earns being turned off. It governs what the agent says to you and never what it writes into files, so this repository's own dense prose is left alone. It is also the first skill here with no dependencies at all, so it runs no dependency check and works on a machine without `uv`. Architecture Decision Records 0048 and 0049 state the rules, and 0012 records what a skill with nothing to declare does instead of checking.

- `/kntnt select` reads you a skill's full help before you decide whether to have it. Ask for any row on the list and you get the manpage that skill ships — read from your own copy where you have one, and fetched from the collection where you do not — so deciding whether to enable something never means installing it first, which is the shape the question always had and never the shape the answer did. The path is derivable rather than published: `category` is already a catalog field and the origin serves a skill's files where the repository ships them, so nothing new is uploaded to make this work. Where you have no copy and the collection cannot be reached, you are told that, rather than shown an empty page or one the agent composed out of what it could see — a manpage is a file somebody wrote and reviewed, and the whole value of printing it is that it is not being improvised. Asking is not answering: nothing is written on either side and the list is still open, which is what lets the question be asked in the middle of reading rather than instead of it. Architecture Decision Record 0044 states the rule, and the Collection terms *Select* and *Help* name what moved where.
- `/kntnt select` can be answered without a list. `--on <skill>` and `--off <skill>` name skills directly and open none, as often as there are names and in either combination in one invocation, so a machine can be set up with nobody at the list — until now the only way to change what was Enabled was to read a list and answer it, which a provisioning script cannot do. They apply a change and never a whole set: a skill you do not name keeps the state it had — files included, so a deviating one is not quietly re-copied over your edit under a command that named something else — and a script that mentions one name can never silently disable another, which is precisely what a list read as a whole-set assignment would have done to it. What a named skill needs comes with it, resolved to the whole chain before anything is written and minus whatever already satisfies it, so `--on release --yes` enables `push` and `commit` as well and a project gains no second copy of a dependency global already supplies; an `--off` name stands against that resolution rather than being put back by it, and what it leaves unsatisfied is reported. `--off` deletes files, so the script refuses it without `--yes`, as every deletion in this collection is refused. `--yes` given with neither of them is an instruction of its own: open no list, enable nothing that was not already enabled, and put what you have into good order — refresh what deviates, repair what is incomplete. That asymmetry with Update, where `--yes` does enable the collection's new entries, is deliberate: there you pointed the verb at the collection, here nobody was asked *do you want this skill*, and an unattended run that answered it yes would place instructions into every harness you have that nobody has read. Run against a catalog read from the stored snapshot it refreshes nothing at all and says why, since nothing on such a list can be judged deviating. The delta is the script's arithmetic and not the agent's — it reads the base off the disk and walks the chain itself — because a set computed in prose is a set computed differently on a bad day, and the whole point of these forms is the run where nobody is there to notice. Architecture Decision Record 0043 states the rules, and the Collection term *Select* names what they belong to.
- `/kntnt select` shows what a skill needs and settles it before it writes anything. A skill that needs another one of this collection is shown locked while that other is unchecked, and the row names the missing skill, so the list carries the structure between skills rather than hiding it behind the answer — until now the catalog was a graph printed as a flat list, and the first sign that a skill needed another was that skill refusing to work once you had it. Check a locked row anyway and what it needs comes with it: the whole chain is resolved before the write, and you are asked one yes/no question naming exactly what would be added, once for the closure however deep it goes, so checking `release` where you have neither `push` nor `commit` is a single yes rather than one question per level — the decision was one decision, and being charged three times for it is the thing that makes people stop reading the questions. Nothing reaches the disk until that question is answered, and `--yes` answers it, so a selection that implies additions still completes unattended. The walk itself is the script's, not the agent's: the payload carries the resolved closure on the row that needs it, and the rendering names what the payload names, because a chain walked in prose is a chain walked differently on a bad day and the failure would be silent — a skill enabled without something it needs looks exactly like one that has everything. In a project, a skill already enabled globally satisfies the dependency where it stands and no second copy is proposed, which is what the layer model has said all along. Unchecking a skill that another checked skill depends on is reported and allowed: you are told what you left unsatisfied and the answer stands, because the answer is the whole checked set for the layer and a manager that quietly put the dependency back would be answering for you — `apply select` carries the same account under `unsatisfied` afterwards, read off the layer once the run is over rather than off the answer, so a dependency whose files never landed is reported as absent rather than counted as present because you named it. Architecture Decision Record 0047 states the rule, and the Collection terms *Dependency*, *Satisfied*, and *Unsatisfied* name what a row is judged by.
- `--dry-run` on every changing verb. `/kntnt enable`, `/kntnt disable`, `/kntnt update`, and `/kntnt uninstall` given the flag run for real — the same code, the same transport calls, the same reading of the disk afterwards — against a temporary home seeded with this collection's own files, which is deleted when the run ends. What comes back is the verb's own outcome, `intended`, `confirmed`, and `failed` read off that home's disk, and nothing in any directory of the layer has moved. Until now the only way to see a change before it happened was the plan half of `plan`/`apply`, and a plan describes intent: it is composed before the transport has been asked for anything, so it cannot report what the transport did with the files, and the run that follows is the first time anybody finds out. A second account of the verb is kept true by remembering to keep it true, and when the two disagree the user is shown the wrong one. This is possible because the transport respects an overridden `HOME`, which was measured rather than assumed: an install with `HOME` redirected landed entirely inside the temporary tree and the real home was untouched. The sandbox is seeded with the manager and every skill carrying this collection's marker, in each directory the layer covers, and with nothing else — without the seed every dry run would report installing what you already have, and another collection's files are never touched by any verb here, so copying them in would buy nothing and would hide the one thing worth seeing if a verb ever did touch one. It has a package cache of its own, so the first dry run in a session downloads the transport afresh and takes noticeably longer than the run it previews; the report says so, because an unexplained pause in a command whose whole promise is that nothing happens is exactly where somebody reaches for the interrupt. Every subcommand accepts the flag, including the ones that cannot act on it: the agent's forwarding is prose and therefore unreliable, and a forwarded flag must never be the thing that breaks a run. It is the expensive, full-fidelity preview and not a routine pre-flight — each of those verbs still confirms before it writes, and that confirmation is not a dry run; the flag does stand in for that confirmation on the dry run itself, since a preview you asked for by name has nothing outside its own sandbox to agree to. Architecture Decision Record 0042 states the rule and what it rests on, and the Collection term *Sandbox* names the temporary home.
- Every skill of this collection answers `--help` with a manpage shipped beside it, and `-h` and a bare `help` reach the same file. `agents-md`, `delegation`, `commit`, `push`, and `release` each carry a `help.md` next to their `SKILL.md`, written for the person holding the skill: what it does, what it takes, what it will not do, and what it depends on. Until now a skill asked for help re-emitted its own Arguments and Steps — instructions written for an agent, handed to a user as documentation, and regenerated on every run, so it drifted the first time the steps changed and drifted silently, because there was nothing to diff. A file is a thing a reviewer can read and a thing a skill can print without deciding anything. What it buys the user is that a skill in front of them can be asked what it does without their having to remember which collection it arrived from. Architecture Decision Record 0044 states the rule, and it binds every skill added later, not only these five. The point of a separate file is that the skill itself gets shorter, so four of the five lost the `## Arguments` section that only restated their own Steps: what the user needs is in the manpage, what the agent needs is in the Steps, and neither pays for the other. `delegation` keeps its own, because those are parse rules the agent carries out rather than a description of them. Architecture Decision Record 0046 states that rule for every skill written later, and 0016 is where it comes from: audience decides placement, and a file that points does not copy.
- Every catalog entry carries a content digest of that skill's directory as the collection ships it, computed over the sorted relative paths and the contents of the files, so that a rename, an edit, an added file, and a removed file each change it. Nothing changes on your machine yet: no command reads it and none behaves differently for it. What it buys is the question the manager has never been able to answer honestly — are the files on disk the files the collection ships — and that is more than a version number could have answered, since a truncated install and a hand edit both leave a version exactly where it was. It is generated when the catalog is generated, so there is no number to bump and no release step to remember, and the suite fails on a catalog that has fallen behind the skills it describes. It ignores exactly `__pycache__/` and `*.pyc`, from one list applied on the generating side and the reading side alike: the collection's tree carries the maintainer's own bytecode cache and an installed skill carries the one running it created, and a single artefact's worth of disagreement would have every skill with a script reporting itself as deviating forever — a signal that is always on being a signal nobody reads. Architecture Decision Record 0041 states the rule, and the Collection terms *Digest* and *Deviating* name what it establishes and what a mismatch means.
- `/kntnt select` — one verb where you both read what the collection has and change it. It prints the catalog as a list grouped by category, one row per skill: a checkbox that is checked when the skill is Enabled in the layer you are targeting, the skill's one-line description, and any capability it requires of the harness, so you know before choosing that it may refuse to work where you are. You answer in one sentence of plain text, changing several skills in a single reply rather than walking a menu, and you are asked to confirm once before anything is written. Until now the everyday act of changing what is Enabled was *read a list under one verb, then retype names from it under another*: Status printed a list, Enable and Disable took names, and the list you had just read was not the thing you acted on. Reading is never a side-effecting act — an answer that changes nothing writes nothing: no refresh, no repair, no touching of files to make the disk agree with a list you only wanted to look at. A skill whose files reached only some of the harnesses the layer covers is shown checked and marked incomplete, which is the truth rather than a rounded version of it, and confirming the list repairs it; there is no partial state, because a skill is Enabled or Disabled and incompleteness is a fact about the disk that no answer of yours could ever have selected. A skill whose files differ from the ones the collection ships is marked **deviating**, never *out of date* — the comparison sees two states and no history, so it cannot say which way the difference runs, and outside a project copy that has fallen behind the commoner cause is an edit of your own — which is why the offer to re-copy says in the same breath that the local changes are overwritten. Where the collection cannot be reached the list comes from the copy stored beside the manager and says so, and nothing on such a list is called deviating or current and no re-copy is offered from it: those digests describe the collection as of the last `/kntnt update`, so a refresh made from them could push a skill toward a revision the collection has already left. There is no Effective form: without `--project` the list is global, with it the project layer alone, and a skill already Enabled globally is marked as such rather than shown unchecked — this layer holds no copy of it to uncheck, and checking the row would give you a second one. The list closes by counting the skills on disk that carry this collection's marker and no longer appear in the catalog, and points at `/kntnt update`, which is the verb that takes those off. The script emits a payload and the agent renders it; there is no interactive picker and there will not be one, for the reasons Architecture Decision Record 0045 measured. Architecture Decision Record 0043 states the rule, and the Collection term *Select* names the verb.

### Changed

- `/kntnt update` reports each new catalog entry and asks whether to enable it, and `--yes` answers that question yes. Until now it named the new skill and left it there, so learning about it and acting on it were separated by a second command and by whatever happened in between: the reason to want the skill arrived at the one moment you were already thinking about the collection, and the way to get it did not. The question is asked once for the whole run, worded so that a plain yes ends it, and a no leaves every new entry disabled — `/kntnt select` is still where you change your mind. This reverses what the collection promised before, and the cost is real rather than argued away: an unattended `update --yes` — a cron job, a provisioning script, a skill forwarding your arguments unread — can now place instructions you have never read into every harness you have. What buys it is that `--yes` means one thing everywhere. The alternative was a flag that answers every question except this one, which is not a rule anyone can hold: you would carry a list of the questions it does not reach, and the exception was unenforceable exactly where it mattered, since a skill passing your arguments through cannot know which of them the manager would decline to honour. Every name such a run enabled is in its report, under `enabled` beside the `intended`, `confirmed`, and `failed` account every placement gets, and the files go through the same verified path as any other: `enabled` is what the answer asked for, and whether it landed is read off the disk afterwards like every other change — a new entry that never landed is named in `failed` and fails the run rather than being reported as installed. Dependencies and capabilities are re-checked across it afterwards, so a new skill that needs something you do not have says so; it is enabled on its own and what it lacks is reported, because a skill you had already chosen to leave disabled is not this question's to answer. `/kntnt select --yes` is the deliberate opposite and stays as it is — no list, and nothing enabled that was not enabled already: the unattended run that can add a skill is the one you pointed at the collection's own new entries. Architecture Decision Record 0007 records the trade and keeps the original reasoning beside it, so what was decided is *is one coherent flag worth an unattended install of unread instructions* rather than *should new skills be silent*.
- `/kntnt update` refreshes what has moved and leaves the rest alone. It compares each enabled skill's digest against the collection's and calls the transport only for the ones that differ, so the report finally carries information: *twelve of twelve refreshed* was equally true of a machine where every file was wrong and one where nothing had changed since the morning, and what you get now is the names that moved, with the ones already carrying the collection's own files listed apart from them. The plan half says the same thing before you confirm it, since a plan promising twelve refreshes ahead of a run that copies two describes a different verb. Skipping is safe for the same reason the refresh goes through `add` rather than the transport's own `update`: a digest that matches means the directory is byte-identical to what the collection ships, so there is nothing there to fetch — and `add` empties and replaces the whole directory, which is what makes *a file the collection dropped is gone, a file it changed is replaced, a file it added is present* true of every refreshed skill after one call. This is the opposite of the transport's own skip, which compares `SKILL.md` alone and infers a directory from one file. A skill whose files cannot be judged is refreshed rather than skipped — the question is open and fetching is what Update was asked for — which is where it parts company with `/kntnt select --yes`, where re-copying on no evidence would discard your edit under a command that never named the skill. The manager is refreshed every run whatever any digest says: it is no catalog entry, so no digest describes it, and the verb that repairs everything else has to be able to reach itself. Where the collection cannot be reached nothing is refreshed at all, and the run says so instead of reporting a refresh it did not perform: the files move through the same origin the catalog could not be read from, so comparing digests first would be a careful decision about which skills to fetch in front of a fetch that cannot happen. Dependencies and capabilities are still re-checked across everything enabled afterwards, not only across what moved, so a refresh that broke a prerequisite still tells you. Architecture Decision Record 0028 states which skills are handed to `add`, 0041 states what the digest establishes and what a fallback catalog does not, and the Collection term *Update* names the verb.
- The test double standing in for the transport resolves the global layer through `HOME`, as the real one does, instead of through a variable of its own. Nothing on any machine changes; the double is used only by this repository's own suite. What it buys is that a dry run which escaped its sandbox fails the suite: a double reading its own variable would have landed inside the sandbox whether or not the manager had redirected the one that actually decides where the real transport writes, and the test would have passed while the real thing wrote into your home.
- The manager's own files separate by kind, on the same rule: agent instructions per verb under `steps/`, a manpage per verb under `help/`, and `help.md` as the manager's own manpage. `/kntnt help <command>` prints that command's manpage, and bare `/kntnt` prints the manager's, as before. The manager's help stopped being a string held inside its script and became the file it ships, so there is one place to read it and one place to change it — and *where is the help* has a single answer whether the thing being asked is a skill or a subcommand. Nothing has to be done on any machine: `/kntnt update` places the new files.
- The test double standing in for the transport models `npx skills add`'s wipe: it empties a skill's directory before it copies, so a file left under an installed skill and an edit to one of the skill's own files are both gone after a re-add — the behaviour the real transport was verified to have. Nothing on any machine changes; the double is used only by this repository's own suite. What it buys is the postcondition a refresh is about to state — the skill on disk is the skill the collection ships and nothing more — which could not be tested at all against a double less capable than the thing it stands in for. Architecture Decision Record 0028 carries the rule, and its own history is the mirror image: the double was once *more* capable than the real transport, and the suite stayed green while the collection could not be updated.
- The flag table is settled and stated where the user meets it. Each verb's manpage now documents exactly the flags that verb takes — `select` and `update` take `--project`, `--yes`, and `--dry-run`, `uninstall` takes the last two and no `--project`, and `help` takes none — and the manager's own manpage no longer says `--dry-run` is *accepted everywhere*, which was true of the script's parser and was never true of the verbs you type. Help now says so rather than swallowing a flag it has no meaning for: `/kntnt help --yes` is told the verb takes no flags, instead of printing the page as though the flag had been honoured, because a flag accepted and ignored is what teaches that flags sometimes do nothing. The line the surface now draws is between the script and the grammar — the parser stays permissive so a flag the agent forwards on its own can never be the thing that breaks a run, while the pages state what each verb actually takes. `--help` and `-h` are untouched: they are how help is reached, not flags handed to it.

### Removed

- `/kntnt help <skill>` is withdrawn; `/kntnt help <command>` and bare `/kntnt` are unchanged. It required remembering that a skill had arrived through this collection, which is exactly the fact a user should not have to hold — and the two things it was actually used for both have better routes now. Reading about a skill you have is `/<skill> --help`, answered by the skill itself whichever collection it came from. Reading about one you do not have is `/kntnt select`, which is where that decision gets made anyway. A second way to the same text is a second thing to keep true, and this one asked the wrong question of the person typing it. The manager documents its own verbs and no skill; a name it does not document is refused with both routes named, so nobody is left holding a command that no longer answers. Nothing has to be done on your machine: `/kntnt update` places the new files. Architecture Decision Record 0044 states the rule.
- `/kntnt status`, `/kntnt enable`, and `/kntnt disable` are withdrawn, and `/kntnt select` is all three of them. Their steps files and their manpages go with them, so `/kntnt help status` is an error rather than a page describing a verb that no longer answers; nothing has to be done on your machine, since `/kntnt update` places the new files. What is lost with Status is the union view — what applies in this working directory, global and project merged into one report — and it is given up deliberately: a list you answer has to be one layer's, or an answer would have to say which layer it meant, and the project layer cannot subtract from global anyway. What is lost with Enable and Disable is the transcription step and nothing else. A skill that refuses for want of another skill of this collection now names Select as the way to get it, rather than a verb that is no longer there.

### Fixed

- `--dry-run` in a project now previews the run it stands in for. The temporary home it runs against holds both layers where the layer being previewed is a project, so a skill that needs another one you already have globally is no longer offered a second copy: until now the preview looked at a machine with nothing on it, and reported placing dependencies the real run knows better than to place — and every dependency judgment the preview made, `unsatisfied` included, was read off that same empty global layer. Seeing it is not touching it: the global directories are copied into the temporary home like the project's own, and nothing outside it moves. A run previewing the global layer still seeds global alone, because a global run reads no project, and a directory the real run never looked in has no business being there. Architecture Decision Record 0042 carries the rule the temporary home is seeded by.
- `/kntnt update` now reports the run it actually made when the transport refuses a skill. Until now such a refusal ended the command with an error and no report at all, so a skill the collection had withdrawn could be deleted from your machine with nothing to say it had happened, and the new catalog entry the same run had just told you about was never offered again — the copy of the catalog it compares against had already been overwritten, and that difference is the whole of what makes an entry new. The copy is now written after the work instead of before it, and held back only where a new entry the run was told to enable did not land, so a refused refresh or a refused withdrawal still advances it: those are found again by the digest and by the disk, and freezing the copy for their sake would only leave the fallback describing an older collection than the one the origin just answered with. A refused placement is reported as a skill that did not change, with the directories to look in, and the run still exits non-zero.
- A damaged copy of the catalog stored beside the manager no longer takes every command down with a traceback. It is read as no copy at all — a run with nothing to compare against reports nothing new, and one that can reach the collection carries on as though the copy had never been there — and the file is now written in one move rather than in place, so an interrupted update cannot leave half of it behind. Until now a snapshot truncated by an interrupted run made every verb fail with a Python traceback, including the `/kntnt update` that would have replaced the file, and the only way out was to delete it by hand. The path table the manager ships beside itself was read the same unguarded way and now fails with the manager's own message naming the file, since that one has no fallback to fall back to.
- A catalog the origin serves but cannot be parsed is reported rather than thrown. It used to reach the user as a Python traceback when the origin was a checked-out collection, since only the network read was guarded — and as *could not be fetched* when it came over HTTP, which sends you looking for a connection problem that is not there. Both now say the catalog at the origin is corrupt, and every verb still falls back to the copy stored beside the manager, as it does for an origin that cannot be reached at all. How the origin is addressed — the local path, the raw.githubusercontent URL, the pair of failure messages — now lives in one place that both the catalog and a skill's manpage are read through, so the two cannot drift apart.
- `/kntnt uninstall --project` now says why it is refused. The flag has never been accepted there — uninstall clears this machine, and a working directory's copies are checked into that repository and stay — but the refusal came from the argument parser and read `unrecognized arguments`, which reports that a flag is unknown where what the user has to learn is what the verb would have done. It is refused ahead of the parser now, in the verb's own terms, so the message names the machine it clears and the project it never reaches rather than leaving that to be inferred from a usage dump.

## [0.7.0] – 2026-08-18

### Added

- `/kntnt uninstall` — take this collection off this machine in one gesture. It removes every catalog skill enabled globally from every harness present in your home directory, and then the manager itself, last and through the transport, so your harness's own uninstall has nothing left to do. The manager goes only where everything else really left — a run that leaves a skill behind keeps `kntnt`, since it is the one verb that could still remove it — so `kntnt` among the confirmed removals is the whole report. Installing was one command and removing was none: the behaviour existed, but only as a side effect of dropping a harness from a list that has since been retired, and uninstalling by hand meant working out which directories held what. It takes no `--project`, and that is the decision rather than an omission: a skill in a working directory is checked into that repository and travels with it, so whether it stays is that project's decision — those copies are never touched, and the report says so rather than letting anyone believe the machine is clean while a repository still carries them. `--yes` is the gate, as on Disable. What it removes is what the catalog names, so the report says whether that list came from the collection or from the stored copy — the usual remedy of running it again is only available while the manager is still installed. Architecture Decision Record 0040 states the rule and the two things that follow from a manager deleting itself, and the Collection term *Uninstall* names the verb.
- Tests that pin the release version-bump: a nested JSON `"version"` must not be rewritten instead of the top-level one, a TOML `version_scheme` must not be read as the version, and a failed bump must write nothing.
- CI on push to `main` and on every pull request: ruff, mypy, and pytest. Tool settings live in `pyproject.toml`.

### Changed

- The Manager stops asking which Harnesses to target and stops recording an answer. Enable, Disable, and Update work out where to write on every run: every Harness with a home in the layer being acted on — `~/.claude`, `~/.config/opencode` and their like for Global, `.claude`, `.crush` and theirs for a Project. A Harness installed after an earlier Enable is reached by the next Update with nothing to configure in between, and every call to the transport names the full set rather than a subset. With no Harness detected, the shared `.agents/skills` directory alone is written to — never a directory for a Harness that is not installed. In the Project layer a Harness whose skills directory is not hidden (`skills`, `data/skills`) is not detected at all, because that name belongs to the repository as readily as to a Harness. What is lost, and was weighed: there is no longer a way to keep the collection out of one Harness you have; the remaining control is to not Enable the skill at all. Architecture Decision Record 0035 states the rule and its boundary, 0005 is rewritten now that it is trivially true, and 0014 is marked retired. The new record is numbered 0035 rather than 0031 because 0031–0034 were spent on `plan` and `execute`; a withdrawn number is not reissued, or a reference written against the old release would silently point at something else.
- Status reads `--project` like every other verb. Bare, it reports Global: every Catalog skill with its state on this machine, Disabled ones included. With `--project` it reports the Effective set for the working directory — everything Enabled in Global plus everything Enabled in this Project — and each skill says whether it comes from Global, the Project, or both; a skill Enabled in neither is left out, because it does not apply here. `--project=off` is the bare form, as everywhere else. Naming skills narrows either form and changes nothing else. Until now Status ignored the flag and reported both layers in two columns, which made it the collection's one inconsistent verb. The payload loses its per-layer `global` and `project` fields for one `state` per skill, a `source` in the flag form, and a `reports` field naming which of the two questions was answered — *what does this machine have* or *what applies here* — so no reader has to guess which report it is holding. Architecture Decision Record 0038 states the rule and why the flag form reports Effective rather than the Project layer alone; 0004 is corrected where it claimed Status always reports both layers.
- `status`, and every plan and apply payload, report the `directories` they act on instead of a list of Harnesses. There is no longer a list to report. Status names only the layers its report covers, so the bare form names Global alone.
- The README no longer names collections this one depends on. It listed four as essential while every Catalog entry declared `"externals": []`, and nothing in the repository referred to any of them — `plan` and `execute` had been the only skills ever to declare an External. The section is now one list of recommendations, offered as a courtesy. A skill that genuinely needs another collection declares it and says so when it is run, which is where a dependency belongs and where it cannot drift.

### Removed

- `/kntnt setup` and the Harness list it wrote. The subcommand, its skill body, its `--harness` arguments, the file under `~/.config/kntnt/`, the rebuild that reconstructed it, and the *Harness list is unsatisfied* failure state are all gone, along with the Collection term for the list. Nothing needs deleting on your machine: the stale `harnesses.json` is simply never read again. The Collection term *Detected Harness* replaces it.
- `plan` and `execute`, added in 0.6.0, are withdrawn. The premise — that work is best carried from Ticket to code through a file under `plans/` written by one skill and built unattended by another — did not hold, and a skill that does not earn its place is better removed than kept. `plans/`, Architecture Decision Records 0031–0034, and the Collection terms *Ticket*, *Plan*, *Land*, and *Drift* go with them. If either is Enabled on your machine, `/kntnt update` deletes it for you — see the first entry under *Fixed*; nothing has to be removed by hand. The six improvements below came out of that experiment and stand on their own.

### Fixed

- A skill the collection has withdrawn now leaves the disk. Update fetches the Catalog before it decides anything, so only what the current Catalog still carries is refreshed and every name that has left it is deleted from the layer being applied — through the same removal Disable uses, and without asking, because a withdrawn skill can no longer be updated, supported, or reached by any other command. Each one is reported alongside the new entries: `removed` now names the skill and what the disk showed — `removed` where the files are gone, `failed` with the directories its files survive in. A failure belongs to that skill and not to the run, so the rest of the refresh still happens and the report is still printed. The `--yes` gate Disable requires does not apply here: that gate stands in for a question, and this deletion asks none. Until now Update resolved its work from the Catalog it was about to replace, so a withdrawn skill was still Enabled, still in the refresh list, and still asked of a transport whose source no longer carried it: the run died with the transport's raw error and no JSON at all, and the files stayed where Disable refused the name and Status no longer listed it (issue #5). Architecture Decision Record 0037 states the rule and its asymmetry with 0007, and the Collection term *Withdrawn* names it.
- Update works out what has been withdrawn by looking at the disk instead of at the copy of the catalog stored beside the manager. A skill installed from this collection carries a `metadata.kntnt` block in its own frontmatter, so one that carries it, sits in the layer being applied, and is not in the catalog the collection answers with is one the collection has withdrawn — and it is removed, whatever any local file remembers. Until now the withdrawn set was the difference between the stored copy and the collection, and that copy is a sidecar of the manager: any run of the transport that re-copies `kntnt` replaces it, including a run of Update that refreshed it and then died, and including `npx skills update` invoked by hand. Once it had stopped naming a skill, nothing could establish the skill was ever ours, the difference was empty forever, and the files stayed where no command of this collection could reach them (issue #20). Machines left in that state — `plan` or `execute` on disk after the catalog had already moved past them — are recovered by one `/kntnt update`, with nothing to remove by hand. Two things the sweep never touches: `kntnt` itself, which is no catalog entry, and any skill without the marker, so another collection's skills and your own are left exactly as they are. Where the collection cannot be reached nothing is deleted at all — a stale list does not get to decide which files go — and `catalog_refreshed: false` says so. Reading a skill file the sweep cannot decode, or has no permission to open, answers *not ours* rather than ending the run. The `absent` verdict is gone from `removed`: a withdrawn skill this layer never held is not reported, because there was nothing here to remove. Catalog generation now refuses a skill whose frontmatter carries no `metadata.kntnt` block, since a skill shipped without the marker could never be swept. Architecture Decision Record 0037 is amended with the rule and with why a diff cannot carry it, and the Collection term *Withdrawn* says how one is found.
- Status and Enable read the Catalog from the collection instead of from the snapshot that shipped beside the Manager. A skill published upstream is listed the next time Status runs — Disabled, as ADR-0007 requires — and can be Enabled in that same invocation, with no `/kntnt update` in between; a skill the collection has withdrawn stops being listed at all. Until now the list was replaced only by Update, so it answered *what did the collection contain when this machine last updated*, and a user had no reason to run the one command that would have told them otherwise: an installation still on 0.6.0's snapshot offered `execute` and `plan` as though they could be Enabled, months after they had left the repository (issue #3). Where the collection cannot be reached the verb still completes from the stored copy and says that it did — `status` carries `catalog_refreshed`, the boolean Update already reports, and its skill body now says the list may be stale rather than presenting it as current. Update remains the only command that replaces the stored copy, because it is the difference between that copy and the collection that tells a new skill from a withdrawn one. Architecture Decision Record 0039 states the rule and why the write stays where it is, and the Collection term *Catalog* names it.
- Enable, Disable, and Update no longer report the plan they handed to the transport as the outcome. Each one reads the disk afterwards — the same presence test Status decides Enabled with, in the same layer and the same directories — and reports what it finds: `intended` is what the verb set out to do, `confirmed` what the disk showed, and `failed` the rest, each entry naming the skill and the directories that contradict it. Anything in `failed` exits non-zero, including a run where other skills succeeded, and the payload is still printed so the user learns which skill and where. This replaces the `changed` list of Enable and Disable and the `refreshed` list of Update. A transport that removes nothing and exits 0 used to be indistinguishable from one that did the work — that is how a Disable of two skills reported both as changed and left both on disk (issue #7) — and it is now a legible error. Architecture Decision Record 0036 states the rule.
- Release version bump now reads and writes by one rule per format: the top-level JSON `"version"`, and `[project]` / `[tool.poetry]` in TOML. A file that cannot be rewritten unambiguously aborts the whole bump so nothing is left half-written.
- `git status` paths in the commit plan are no longer C-quoted: porcelain is read with NUL separators, so a file named `skäl.md` is shown as itself.
- Catalog generation refuses a skill whose frontmatter `name` is not its directory, or whose description is empty or a YAML block-scalar indicator the parser cannot read.
- `CONTRIBUTING.md` now names this Collection, points at `skills/<category>/<skill>/scripts/`, and lists the same four checks CI runs.

## [0.6.0] – 2026-08-17

### Added

- `plan` — turn Tickets, or a design settled in conversation, into Plans under `plans/`. `/plan #12 #17` plans those Tickets whatever labels they carry, `/plan "<description>"` plans work with no Ticket behind it, and bare `/plan` shows a picker of the open `ready-for-agent` Tickets with the conversation's settled design as its first row. The External `improve` writes each Plan; the skill then makes the batch a queue by numbering it, resolving `**Depends on**` across old and new Plans, recording each Plan's Ticket, and writing `plans/README.md`.
- `execute` — build the Plans under `plans/` unattended. One at a time, `improve` builds each in an isolated worktree and renders the verdict, and every approved Plan is Landed on the branch the run started on — squash-merged, then committed through `commit` so the changelog gets one entry per Plan — before the next is dispatched. Drift is checked once against the run's base, after which the invariant that `HEAD` stands where the run left it is what separates the run's own commits from a third party's. A blocked Plan is set aside with everything that depends on it. It commits and stops: no push, no tag, no release.
- Architecture Decision Records 0031 (Plans are written by one skill and built by another), 0032 (Land each approved Plan before the next one starts), 0033 (Drift is checked once, before the run), and 0034 (an unattended skill asks only yes or no), and the Collection terms *Land* and *Drift*.
- The Collection terms *Ticket* and *Plan*. A Ticket is a unit of work in the issue tracker, named so that no skill is bound to one tracker's own vocabulary; a Plan is a file under `plans/` describing one unit of work, self-contained enough that an agent with no other context can carry it out.
- `plans/` — six implementation plans and their index, from an audit of the two Python engines. Nothing is fixed yet; the plans describe the work. They cover a version bump that can rewrite a nested `"version"` field instead of the real one and still report success, `git status` output parsed so that any path with a non-ASCII byte reaches the user C-quoted, the absent continuous integration that would keep the passing tests, linter, and type checker passing, and Catalog generation accepting an entry whose name or description cannot do its job.

## [0.5.0] – 2026-08-17

A skill declares `capabilities` in its frontmatter, `check` reports each one with a sentence to confirm and a fix, and the agent answers — no script can, since the Manager cannot know which Harness invoked it. Unknown Capability names fail when the Catalog is generated. Status, the Enable picker, and Update surface them.

The mode text drops the hard-coded `haiku < sonnet < opus < fable` ladder and the Fable pricing note for a rule each harness resolves against its own models, and covers the case where subagents can be spawned but their model cannot be chosen. `~/.claude` and Claude Code's scratchpad directory become the general thing they were examples of.

## [0.4.0] – 2026-08-17

### Added

- `--yes` is accepted by every verb of every collection script, and means the same thing everywhere: answer yes rather than ask. `agents-md` gained the flag; `kntnt` and `ship.py` previously advertised it and then died with `unrecognized arguments` when it was passed.
- Architecture Decision Records 0027 (bare `/kntnt` is Help), 0028 (Update re-adds), and 0029 (`--yes` means assume yes).

### Changed

- Bare `/kntnt` is now Help instead of Status. Status is reached as `/kntnt status`.
- `/kntnt disable` requires `--yes` on its apply step, because it deletes files and a script cannot prompt.
- Status spells out that it reports every Catalog skill, Disabled ones included, and points at `/kntnt update` when an expected skill is absent.
- `/kntnt update` says whether it managed to refresh the Catalog, so a failed fetch is visible rather than silent.

### Fixed

- `/kntnt update` refreshes the collection. It called the transport's `update`, which compares `SKILL.md` and skips a skill whose `SKILL.md` is unchanged — so any revision that touched only a sidecar was never delivered, and `delegation` could not reach the Catalog at all. Update now re-adds, and writes the Catalog to the running Manager's own directory, which the transport need not reach.
- The test double for the transport modelled `update` as an unconditional copy, making it more capable than the real thing and hiding the bug above.
- `apply setup` builds its removal list in a stable order rather than from an unordered set.

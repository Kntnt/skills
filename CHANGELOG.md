# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/) and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- The Catalog has a second entry type, and `/kntnt select` lists it as a second group. Until now the collection could install a Skill and nothing else, so a thing that is not a Skill had only one way in: attach it to an invented Skill purely to obtain a checkbox, which is a lie told to the Catalog to get past the fact that the Catalog had one shape. A **Feature** is a Catalog entry that owns Harness Integrations and nothing else — no Harness loads it, the transport never moves it, it has no directory in any skills tree, and nothing depends on it. It ships inside the Manager, which is the one directory always installed and always addressable by a hook, and it is Enabled and Disabled at the two seams that already install and remove what an Enabled Skill owns, with no new verb: a separate `setup` was considered and rejected because it splits *what do I have enabled* across two places, and ADR-0010 survives because nothing is left for a setup step to collect — a Feature asks the user nothing, it only writes. A Feature's row carries what it writes and where, generated from the Feature's own page and repeated in the single confirmation Select already asks before writing anything, because a row that edits a file the user owns and reads has to say so before the checkbox rather than after the run; a Feature no Detected Harness can serve is locked and says so rather than being hidden (ADR-0030). It is Global only, for the reason ADR-0160 gives capture — an owned entry is keyed by owner inside a Harness's own configuration, so a Project Enable and a Global one would write and remove each other's — and `select --project` carries the sentence saying so in place of a checkbox that could never change anything. Uninstall tears every Feature down first, while the Manager whose directory their hooks name is still there to do it, and Update re-converges the Enabled ones after a refresh has replaced the tree their script and their installed prose both come from. Update never adopts a new Feature, even under `--yes`: what it would write is instructions into a file the user reads (ADR-0173, amending ADR-0090).
- The Collection installs a `session-cleanup` Feature, which leaves the machine as the session found it. An agent session starts a dev server, writes a scratch directory, runs a container — and then the session ends and every one of those outlives it. Asking afterwards which of them belongs to the agent is a question nothing on the machine can answer: a process list cannot tell the agent's dev server from the user's, and a machine running several agent sessions at once cannot tell one session's work from another's at all. The judgement is cheap at exactly one moment, so the Feature installs two things that only work together — a fenced block in each Harness's own global instruction file asking the agent to record what it starts, and a session-lifecycle hook that stops exactly what was recorded. Either alone is worse than neither: the block without the hook asks for a record nothing reads, and the hook without the block reads an empty manifest forever while looking perfectly healthy, so both go in and come out together. Nothing outside a manifest is ever touched; a recorded process is stopped only while its recorded start time still matches what the machine reports, so a reused process id names something else and is left alone; the process group goes only where the recorded process leads one, a follower sharing a group with the agent's own shell; and a recorded path is deleted only where it resolves, symbolic links followed, strictly inside a temp root, so a line naming `/` cannot do what it says. The sweep runs at a session's start as well as at its end, which is what covers a hard kill, a crash, and a Harness whose end event is weak — a manifest whose terminal is still alive elsewhere is skipped, one sharing this terminal or whose terminal is gone is swept, and one older than a day is the backstop. It acts and records rather than reporting, the hook running while the user's screen is disappearing: every action is a line in `~/.kntnt/session-cleanup/cleanup.log`, including a session that ended having recorded nothing, which is the one thing worth watching because recording is the single step of the design that depends on an agent remembering to take it. It exits zero whatever happened, a cleanup that breaks a shutdown being worse than a leak. Serves Claude Code, Codex, and OpenCode; on Codex the hook is reported gated until that Harness's own trust review is accepted (ADR-0157).
- The Collection installs a `statusline` Feature, a two-line Claude Code status line. The first line is where you are — the working directory, a marker when you are standing in a linked worktree including one made by hand, the branch or the abbreviated commit of a detached head, Starship's own working-tree vocabulary, and any git operation left in progress. The second is the run: the model, its reasoning effort, the context window coloured green, amber and red, and each subscription window Claude Code puts on stdin with the time it resets. It reads what the Harness hands it plus one `git status` under a one-second timeout, and it calls no network service, reads no credential, and starts no background work — a status line runs on every render, so anything it did it would do again a moment later. `statusLine` is a single-valued setting rather than a hook table, so it cannot hold two: where it already runs a command that is not this collection's, that command is named on the row before the checkbox and the one confirmation Select already asks asks whether to replace it, and nothing is written until the answer is yes (ADR-0174). Checking the row is the user saying they want this status line, so answering that with *no, something is already there* would hand them an outcome they did not ask for and no way forward from the list they are standing in; refusing outright was the first draft's mistake, and the correction is a question rather than a different verdict. `--yes` is that answer and no flag of its own is added: it is one more thing asked in the one confirmation Select already puts before writing, and what keeps it from replacing a status line nobody meant to replace is that `--yes` alone enables nothing — `select --yes` with no name is `--as-is`, which Enables nothing that was not already Enabled, so a held setting is only ever reached by an invocation that also names the Feature. A Feature held off for want of that answer is reported under `held` rather than `failed`, nothing having been attempted and nothing broken, so no exit code moves on a question nobody was asked. Nothing is kept of what is replaced: a private ledger goes stale the moment the setting is edited by hand and a removal restoring a value the user has since replaced is worse than one that restores nothing, which is why the question says so before it is answered. Serves Claude Code, and says so on its row in a Harness that has no status line.

### Changed

- The Collection Library's integration mechanics now cover two more kinds of owned state, so that a Feature supplies its owner identity and the command to run rather than learning three Harnesses' file formats (ADR-0076). An owner may write a fenced block of prose into a Harness's global instruction file — `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, and OpenCode's own `~/.config/opencode/AGENTS.md`, the last confirmed against that Harness's documentation rather than assumed from a sibling's, because a block written where the Harness does not read it is an install that looks successful and does nothing. The ownership identity travels inside what is written, as `<!-- <owner> begin -->` and `<!-- <owner> end -->`, so removal takes exactly that fence and prose nobody fenced as ours is never touched; a file left holding half a fence is refused and named rather than converged, everything between two fences being the user's file and this collection deleting only what it can see both ends of. An owner may also take a single-valued setting, where taken means the slot was free or already ours and a slot somebody else holds is reported taken rather than overwritten or remembered. An owner may now also name the lifecycle moments it wants of one Harness instead of taking that Harness's whole set, a name that Harness does not have being dropped rather than written, so a feature acting on a session's beginning and its end installs two entries rather than three and a health check counting them says healthy rather than degraded. Several records about one Harness fold into the one record that Harness earns — the entries add up, the details join, and the state is the weakest of them — because a reader told that two records disagreeing about one Harness is itself the finding must never be handed two records that are simply about two things.


## [0.22.1] – 2026-09-05

### Changed

- A run whose frozen snapshot can select nothing invokes Model Selector once, not once per wave. Every wave, and every amend, repair, rebuild, and wave fix within one, sent the orchestrating session through `/model-selector context` and `/model-selector route`, each invocation loading that Skill's instructions, its routing reference, and its schemas into context again; on a Harness whose snapshot carries no profile, a rejected profile, no adapter able to express a point, or no safe candidate, every one of those answers was the same inheritance the first batch had already come back with — measured on the maintainer's own seat as roughly 100 KB of prose per wave for an answer the run already held. The engine's `route` verb now takes `--inherit` with one `--request` per role: where every decision the frozen account holds inherits for one reason that is the snapshot's own, it copies that decision under each new name, changed in nothing else, and extends the account exactly as a routed response would have, so a claim, an amend, and the report find the decision where they always did and an observation imports with the same provenance. The plan and every route report the fact as `routing.frozen_inheritance`, and the Skill reads it there rather than judging reasons itself. The first batch of a run still goes through the Interface, because freezing the snapshot is what establishes what it can select; a run that selected anything, an inheritance the request itself earned (`insufficient_evidence`, which an objectively checked request escapes), a verdict name, an escalated fix round, a mismatched lock, and a dry run are each refused and routed through the Interface as before. The decision stays Model Selector's own: this Skill emits no routing content of its own and reconstructs no rule (ADR-0172, narrowing ADR-0085 and ADR-0133).
- The wave check reads the wave it merged and not the whole branch. Every wave's check read the integrated branch from the run's base to its head, so the reading grew with the run — a three-wave run read its first wave three times and its second twice — on the main seat every verdict inherits, which made it the run's dearest reading; the evidence ledger says the check earns its place, six of the eight waves it records having ended in mechanical findings no green gate saw, so what was out of proportion was the range and not the reading. The brief now carries `<since>`, the commit the run branch stood at when this invocation's last wave check passed clean: every commit from there to the head is the wave's, each file those commits touch is read with its surrounding text, and the branch before it is not read again for its own sake — the check goes there only where the wave's commits point, the registry a new record joined, the release section a new entry was added to, whatever cites a file whose lines the wave moved, and the prose anywhere in the tree asserting what the wave has made false, found by searching for the change and then reading what the search turned up. Every round of one wave's check carries the same `<since>`, so a rerun after a fix still reads the whole wave, and an invocation holding no clean pass of its own — the first wave, and the first wave of a resumed run — falls back to the plan's `base` and reads the run's whole work exactly as before. The four kinds of defect looked for are unchanged, and so is the gate, which still runs whole on the branch as it stands (ADR-0171, narrowing ADR-0072).
- The test suite runs across every core. The pytest gate in the contributing guide and in CI now provisions `pytest-xdist` and runs with `-n auto`: the suite spends most of its wall time waiting on the subprocesses its tests spawn, and it measured 4 min 51 s serial against 1 min 01 s parallel on fourteen cores, every test passing either way. A builder, a verifier, and a wave check each run the gate, so an unattended run paid the serial time at least three times per ticket and once more per wave; the same four commands are still the gate, and only the last of them got faster. A suite check pins the flag in both places so neither can drift back to serial alone.
- The `rework` branch is source material rather than a successor. The ground-up rebuild on that branch was to take over `main` once complete; on 2026-09-05 the direction was reversed, because `main` had moved too far to be taken over. `main` is the surviving branch, `rework` is read-only, nothing is merged in either direction, and what is worth bringing over lands on `main` in ordinary `ready-for-agent` tickets that each name the rework commit they re-implement. The five pipeline Skills built there stay parked until asked for, `/orchestrate` remains the collection's ticket runner, and the tickets of the rebuild are its closed history. The temporary section of `AGENTS.md` says so and stays until the branch is deleted.

### Fixed

- A Skill's Harness integrations now install and tear down however the agent that invoked the Manager reached it. The Manager's two integration seams ran a Skill's declared script from whatever directory the invoking agent happened to be standing in, and a Global Update replaces the Manager's own installed tree while the same run is still going — the Manager is no Catalog entry and has no Digest to compare against, so it joins every Global refresh unconditionally, and where the staged tree differs, publication swaps the new one into place and unlinks the retired one before any Skill is asked to install or tear down what it owns outside its own directory. The invoking directory was therefore gone by the time those seams ran, and `uv` failed with its own *No such file or directory* before reaching the declared script at all. The failure then hid: a failed install or teardown is reported per Skill and never raised (ADR-0090), so the command still exited zero and every Skill still landed while the integrations a Skill owns were never written, or never removed. Both seams now run the script from `home()` — what the Manager already resolves Global paths against, what no run of this collection removes, and a directory the script has no use for anyway, the seam handing it everything it needs on the command line — identically in both layers and with no layer argument to take, the Project layer installing no integration at all (ADR-0160). A machine with no home to resolve raises `RuntimeError` rather than the `OSError` a missing directory would be, so that failure joins what the two helpers already report per Skill rather than becoming a new way for either to raise. `docs/coding-standard/python.md` now carries the rule together with the reason it exists — a process outlives its own working directory, and a run that replaces directories can destroy the one it is standing in — and the suite holds every shipped `subprocess` call to naming the directory it runs in or saying in the comment above it why it inherits one.
- Capture's lifecycle hook no longer reports a failed session start and a failed turn in the Harness that runs it. A Harness reads what a hook it owns writes on standard output as its own protocol, and the `hook` action wrote this feature's internal diagnostic object there — the same object a person gets running the script by hand — so Codex refused it over fields belonging to nothing it knows (`hook returned invalid session start JSON output`, `unexpected map key`) and surfaced `hook: SessionStart Failed` and the same for `Stop`, while the hook itself ran, did its work, and exited zero. Claude Code ignores fields it does not know and OpenCode's plugin never reads the channel at all, which is why this reached a Harness that parses it before anything reported it. It is the failure ADR-0090 rules out in the sentence that matters — a capture that breaks a session is worse than no capture — arriving as a measurement feature that makes the Harness look broken in every session, which is a measurement feature the user turns off. The object now leaves on standard error, unchanged in every field and in its fail-open shape, and standard output stays empty on every path the hook can take. The move is unconditional: a Harness and a person invoke the identical command line, so a rule telling them apart would be a second mode to get wrong, and a person piping the script reaches the same object with `2>&1`. Nothing else moves — `status`, `purge`, `install-integrations` and `remove-integrations` answer on standard output as they always have, and the command this collection installs is byte for byte the one it installed before, since Codex keys its trust decision over the hook entry as written and an argument added here would re-gate the hook. `references/run-capture.md` states the rule beside the fail-open one it belongs with.
- An installed hook entry now carries the timeout its own Harness accepts for that moment, so Codex stops reporting a clamp on every session. Every entry this collection installs asked for ten seconds, for every Harness and every lifecycle moment, and a Harness's own ceiling is neither of those things: Codex honours what it is asked for at `SessionStart` and at `Stop`, holds a session-end hook to three seconds whatever it is asked for, and names that clamp in `hooks/list`'s `warnings` — established from the Harness as installed (codex-cli 0.153.4, driven through `codex app-server`) at 999, 10, 5, 4 and 3 seconds in turn, the last of which it honours with the warnings array empty. Nothing was being truncated: session end is the one place in the hook path permitted to reach the network (ADR-0167), its refresh's network portion is hard-capped at two seconds against a monotonic deadline, and a whole session-end invocation with every source forced due and fetched over the real network measured 1.1 to 1.7 seconds — about a second of margin under the ceiling, which is now written beside the choice so an author raising that budget can see what it may not exceed. Codex's session-end entry therefore asks for three and every other entry carries the ten it carried before. Claude Code exposes nothing that answers what it would honour the way `hooks/list` does, so its value stays what it is installed with rather than what it was told, and OpenCode loads a plugin module carrying no timeout at all — both recorded in the same comment, reported rather than guessed. An installed Codex integration needs no new trust review over this: its session-end entry hashes identically whatever timeout is asked for, the same `currentHash` at 999 as at 3, because the hash is taken over the clamped entry. No record is earned, and neither ADR-0090's rule for a Harness whose lifecycle cannot carry the contract nor ADR-0157's for a gate this collection will not forge is reached — the work fits inside what every Harness here allows.
- A Skill that owns Harness integrations is no longer asked to remove them from the Project layer, so unchecking one in a working directory stops taking away what a Global Enable owns. The gate was built on one half of a mirrored pair: `placement_integrations` attempts nothing off the Global layer and names the reason, while the removal call had no such gate — an uncheck ran a Skill's declared teardown over whatever the run's own layer held, and a withdrawal ran it over the copies staged from that same layer's targets. The shipped `capture.py` answers `remove-integrations` by rooting at the user's own home rather than at the layer it was invoked from, because the entries it owns are the machine's, so a Project-layer run cleared every owned entry in every supported Harness on the machine. Nothing said so: a teardown is reported per Skill and never raised (ADR-0090), the run exited zero, and the Global Enable that owns the integration was left standing and describing a machine state that no longer existed — a user who unchecked a Skill in one project, or whose project-scoped Update dropped a Skill the collection had withdrawn, silently stopped measuring everywhere. ADR-0160 had already decided it, in the sentence that gated the placement: an owned entry is keyed by owner inside a Harness's own configuration, so a Global and a Project Enable of the same Skill would write and remove one another's single entry, and measurement is a property of the machine rather than of a working directory. Only the removal half was never built, and no Project-layer teardown can ever have been removing something a Project-layer run installed, that layer installing nothing. `removal_integrations` is now the mirror of `placement_integrations` — the same parameters, the same `attempted` beside a `note`, the directories coming from the caller because the two hold different ones, and its own note constant rather than a widening of the placement's, a run that installs none and a run that removes none being two different things to say. `teardown_integrations` keeps its signature and its plain list, and both callers reach it through the gate: the one in `remove_skills` and the one a withdrawal reaches in `refresh_outcome`. Every verb emits what it emitted before, Uninstall's failure branch included, where the answer's records go through as the bare list that branch has always carried; the one payload that changes is the one that has to, a Project-layer withdrawal's `removed` record no longer carrying an `integrations` key, because nothing was attempted and an empty list attached in its place would be the report claiming otherwise. The Skill's own disclosure now says which layer it means: `help.md`, `SKILL.md` and `references/run-capture.md` state that a Global Disable removes every entry the integration owns, and that a Project-layer uncheck or withdrawal removes none.
- Every changing verb now reports what became of the Harness Integrations a Skill owns, and two of them stopped throwing that answer away before it could be reported. Select's removals and Uninstall both tore integrations down and then rebuilt their outcome from `intended`, `confirmed` and `failed` alone, so the teardown's own answer never left the process; where a removal had already failed, Uninstall emitted it under `integrations`, the key that means a placement on every other path; and a transport that refused after the teardown had already run lost it altogether as the exception unwound. Both paths now carry it under `removed_integrations`, in the shape the removal gate returns — the per-Skill records beside that layer's own `note` — always present, its `attempted` empty only where nothing was torn down, and held outside the call that can raise, because a run that pulled a Skill's hooks out of a Harness and then failed has changed the machine, and silence about that is the one outcome ADR-0036 leaves unavailable. Uninstall reports both of its teardowns, the collection's Skills and then the Manager's own, in that one list, and no longer names either of them `integrations`. Update gains the same key, carrying the withdrawal gate's `note` with an empty `attempted`, its per-Skill records already sitting beside each withdrawal in `removed`. Nothing had ever told the agent to say a word about any of it — no step file and no help page mentioned integrations at all — so a failed install was never named, a Codex integration written to disk and held inert behind that Harness's own trust review was reported as installed and working, and a run whose files all landed was called clean while a feature the user believes is on did nothing. The one report contract is now written as the same sentences in each of the three step files: a failure named per Skill in the payload's own words and cut only where the Manager already cut it, records read per Skill and per Harness so a Skill the Manager asks once per directory that holds it is one finding rather than several and a disagreement between its copies is one disagreement, a `note` passed on wherever it is not null, a per-Harness entry that removed nothing left out as the converged state it is, and a run like that not called clean though it raised nothing and exits zero. What only a placement can produce — a gated integration reported present and not yet active with the whole of the `detail` that activates it, and the count of Harnesses no adapter serves, as a count and never as names — is written beside that block in the two files whose verb can place, and not in the file whose verb cannot. All three help pages gain a `## FILES` section saying that these verbs write and remove state outside a Skill's own directory, which deleting that Skill's files does not reach.

## [0.22.0] – 2026-09-05

### Added

- The Collection installs a `tldr` Skill, which explains the answer just given to somebody who did not follow it. `brief`'s bare form reframes a reply for the person who owns the outcome and assumes they are following along, so every rule in its perspective is subtractive; a user who did not follow an answer needs the opposite, and shortening a wall of jargon leaves a shorter wall of jargon. The new Skill's own perspective text says so: the preceding answer is treated as correct but pitched at the wrong reader, never as bloated — its usual input is an article, a research answer, a requested explanation, review output or a long design discussion, each long with reason. It gives the background the original assumed, keeps ordinary technical terms because the reader is a senior developer who delegated the work rather than somebody new to software, and unpacks only what is local to this work — names coined in the answer, project abbreviations, identifiers. Every reply closes by naming what the user must do, decide or answer, and where nothing is required of them it says that explicitly rather than omitting the line. The range is the preceding assistant output and whatever earlier context it would be unintelligible without; never a pasted document, a file or tool output pointed at. An empty range is reported and nothing is written, and a range compaction has truncated is reported as such. The perspective text is the Skill's own rather than the Library's, a shared store being for what more than one Skill reads. Its grammar is the Skill name and an optional instruction — no subcommand, no flag — so `/tldr bara säkerhetsdelen` and `/tldr -- bara säkerhetsdelen` are one invocation with one meaning (ADR-0169, narrowing ADR-0103). `brief` is untouched.
- Model Selector now keeps its own public sources current without being asked. Discovery existed and was correctly designed — `update` revalidates provider indexes on a cadence and reports what it finds — but every turn of it was manual, so the machine could sit weeks past every cadence answering from a model list nobody had revisited, silently and confidently. The lifecycle integration the Skill already installs now carries one bounded pass at a session's end: `scripts/refresh.py` conditionally re-retrieves the non-commercial sources that are due, by ETag or Last-Modified with a content hash as the fallback, and records each source's own check state. It interprets nothing — no page is parsed for meaning, no model is started, and no capability fact, benchmark fact, evidence record or derived frontier is created, changed or rebuilt by it. The unattended pass establishes that something moved; a person's next `update` establishes what. Maintenance stops at the money: model and release indexes, first-party capability sources and benchmark release indexes are refreshed, while commercial terms, gateway rate cards and any source kind or address the pass does not recognise are never retrieved unattended and are reported as due instead — an unattended pass may change what a model is judged capable of, never what it is judged to cost. The pass costs one connection at a time, no retries and a total of two seconds, and a pass that fails, times out or finds no network surfaces nothing, changes no fact and leaves every unfinished source due. `status` is the one surface it reports on, naming `/model-selector update` for each source it may never retrieve and saying plainly when no source state exists at all; `route`, its response schema and Orchestrate are untouched (ADR-0167, narrowing ADR-0090).

### Fixed

- A capability rank now comes from the local evidence ledger and the shipped seed together, and a main seat no benchmark scores no longer empties routing. Model Selector's ranking read `data/seed-evidence.jsonl` and nothing else, so a main seat with no evaluation row in that file left every mapping and every adapter spec out of the derived context and routing inherited on every request, silently — measured as eight mappings for three seats the seed scores and none for one released after it, with seed membership the only variable. That put a ceiling on the whole point of the Skill: a model released after the shipped seed could never be the main seat, and nothing the user does reaches it, the seed being a file inside the Skill. The ranking now reads `evaluation-configurations.jsonl` beside the seed, resolving an evaluation row's model through a validated `ModelVersion`'s `model_version_key` or an `AliasBinding`'s `model_reference_key` so an alias-backed model with a published score is ranked, and bridging benchmark identity on the `seed_id` an import preserves. One rule settles the merge — the ledger supersedes the seed for the same model and benchmark, no timestamp arbitrating, since an imported row keeps the seed's own retrieval time. The comparison benchmark is selected on candidate coverage alone: whether it also scores the main seat is no longer a condition, which is what keeps the fix from restoring mappings that all carry a null rank and empty the pool one step later. A configured main seat nothing has scored keeps every mapping, publishes `main_seat.model_capability` as `null`, and suspends the model dimension of the authority ceiling rather than acquiring one — no predecessor's score is inherited, no unranked seat is treated as the top of the ladder, and no rank is synthesised from cost. The deliberation dimension binds unchanged, a candidate the comparison never ranked stays excluded as `capability_rank_unavailable`, and a main seat absent from the profile still empties the mappings as it always did (ADR-0166, narrowing ADR-0083 and ADR-0136).
- A release `update` has validated is admitted as a candidate without a manual `config edit`. The gate read `validation_status` on the profile, which `update` writes the ledger and is forbidden to rewrite, so a newly adopted model stayed excluded and no verb said so — the second symptom of the same defect, and what made `profile-management.md`'s promise that a release "remains excluded until `/model-selector update` validates it" aspirational rather than true. An enabled selection is now admitted when the ledger records its model, as a validated `ModelVersion` or as an `AliasBinding` whatever its resolution status; the profile's own member stays required on every selection and stays the answer for a model the ledger has never seen, which is what keeps a fresh install working before its first `update` (ADR-0166).
- A stored `config.json` that no longer validates is now reported as rejected rather than treated as a profile nobody ever wrote. Model Selector's context derivation answered `None` for three different situations — no file, a file it could not read, and a file that failed the profile contract or its reference integrity — so a machine that had run `setup` and had every channel and selection on disk was routed as though it had none: no mappings, no adapters, an evidence ledger of any size reaching no decision, and every delegated role inheriting the main seat with `missing_profile` while the user saw runs that worked. The reading now distinguishes three states, and absence is `config.json` not existing and nothing else: a present file that cannot be read, cannot be decoded, decodes to something other than an object, fails the contract, or holds a selection that resolves to no configured access channel is rejected. A rejected profile carries the reason it was rejected — the read or decode failure, the failing schema path beside the constraint it broke, or the unresolved channel reference — and names re-running `setup` as the way back; it carries no revision, a stored profile being able to fail the contract on that very member. The rejection rides in the frozen snapshot, which is where a caller reads it back, and route inherits on it with its own reason token, `rejected_profile`, so a run rendering routing reasons renders the distinction rather than inferring it. No migration is written and that is the decision: the shapes that predate the contract diverge structurally from it, the profile is a short interview `setup` recreates, and a migration would have to guess at shapes nobody wrote down. Context still starts no setup, performs no network access and writes nothing in all three states, and the evidence ledger, read independently of the profile, survives a rejected profile intact (ADR-0165, narrowing ADR-0136).
- `references/evidence-ledger.md` now documents the benchmark prior that `update` actually writes. The reference described a required `EvaluationConfiguration` record as a run's configuration fingerprint — a shape nothing in the Collection stores as a row — while the rows in `evaluation-configurations.jsonl` hold an independent published measurement of a model at a configuration and were named by nothing: neither `score` nor `benchmark_key` nor `model_key` appeared anywhere outside the rows themselves. The record is documented under the name every stored row already carries, with all thirteen of its members, and its model key is stated as holding either a validated `ModelVersion`'s `model_version_key` or an `AliasBinding`'s `model_reference_key`, which is what makes an alias-backed prior joinable. `AliasBinding` gains its own full member list, the fingerprint is no longer listed among the required records and is described where it is actually carried — inline on every `RunObservation` — and `## Keys` gains the `evaluation_key` and `configuration_hash` recipes, which re-derive every key already stored. No store is renamed, no row is rewritten, and nothing `update` writes changes.
- `SourceState` is documented with the thirteen members its rows carry, in place of one line of prose that named one of them. The six `kind` values are written as the closed enumeration they are, `status` gains the fifth value `not_due` that the rows already carried and no document mentioned, `etag`, `last_modified` and `content_hash` are named as the conditional-retrieval validators they are and may be null, `finding` is stated to be human-readable prose that nothing parses, and `## Keys` gains `source_key = sha256(uri)`. ### Changed

- `/brief` is a mode and nothing else: `/brief on`, `/brief off`, `/brief status`, no flag, and a bare `/brief` refused as an incomplete form. The reframing job it used to carry on that bare form has moved to `tldr`, and every form now names the state it produces rather than silently toggling one. **The mode belongs to the conversation it is typed in.** It holds until `off` or until that conversation ends, and nothing is written anywhere — no settings key, no style file, no managed block in a context file, no scratch state, in any Harness — so two windows open on the same project hold independent states, another project is untouched, and no later session starts with it on. That is the point of the change: the mode is a property of the work in front of you, and a window driving a build wants the file-level detail the window running a design discussion wants gone. `--user`, `--yes`, the persistence scope, `references/persist.md` and the managed block, the staleness report and the confirmation before writing all go with it, and `status` now reports one bit for this conversation instead of two scopes and a verdict. An Output Style is declined for the third time and the reason is now on the record: it is read from a settings file and fixed at session start, so two windows on one project cannot hold different states, which is the whole requirement. Measuring a cadence from the look would push every due date forward at every session end, which is the defect this work exists to fix.
- `source-states.jsonl` is documented as what it always was: mutable check state holding one row per source, updated in place with no superseding history. The evidence ledger's append-only rule is stated as covering the evidence stores and not this one.

A refusal is read by a calling Skill as *start nothing*, so Model Selector refuses only what the caller itself got wrong — a malformed request or snapshot, an ambiguous or unavailable lock, an explicit point above the ceiling — and reports the state of the world by inheriting with a stated reason instead. The new token is its own rather than a reuse of `unavailable_selection_controls`, the two being different facts about a run: no complete adapter can express a safe point, against no configured candidate was safe to route to. Orchestrate recognises it with its own constant and states it in a run-level line of its own, so a run whose decisions all inherit for one of the two causes says which. `empty_safe_candidate_set` remains a stable refusal code for a Harness that cannot inherit at all (ADR-0166).
- `unknown_main_seat_ceiling` no longer refuses an automatic request. It answers a snapshot whose `deliberation_capability` is null — fixed portable ordinals no derivation omits, so only a hand-built snapshot presents one, which is the caller's own error — and an exact `--model` lock under a seat nothing scored, that being the one request whose whole point is a model chosen against the seat's own authority. A deliberation lock is answered exactly instead, the dimension it names still binding. Discovery runs weekly while the only index that can score what it discovers runs monthly, so a newly adopted main seat was unrankable for up to a month by construction; suspending the ceiling and expediting what makes it apply again are one design. Only those sources are made due — the model and release indexes are not (ADR-0166).

### Removed

- The stable request-decision refusal code `invalid_profile` is retired. A rejected profile now inherits instead, because Orchestrate reads a route refusal as *start nothing* and a profile gone stale would otherwise cost an unattended run every ticket in it, where inheritance costs that run its optimisation and nothing else. - The Collection installs a `case-study` genre, for an account of what a named customer did, told largely in that customer's own words. It states that the interviewee's words carry the substance and the writer's prose the structure. It states that a section is readable from a cold start, and names why a linear draft fails that in its later sections and not its early ones: by the fourth section the writer holds three sections of context the arriving reader does not. It states that a visual element is used where the information genuinely has that form and never as relief for the eye, because a scanner stops at everything set off from the prose and an element carrying nothing is a stop that pays nothing — a page decorated for scanability scans worse than the plain page it was made from. It states that the sense of address comes from verbs, situations and questions that are genuinely the reader's rather than from a pronoun, the failure being prose that describes a category the reader happens to belong to, and it leaves which pronouns a language has to that language. A review half ships beside it, and the test suite's floor names both.

It states the parts and their order: beneath the title a short opening fixing what the report covers, what it was written to do and the period it speaks to, so a reader coming back months later learns from that alone whether their question belongs to this document; then the body; and, from about five thousand words or wherever the reader asked for one, a front-loaded summary carrying the whole of it, with a shorter report carrying none — a threshold that settles whether the part exists at all and says nothing about how long any part runs. The heading rule grew rather than gaining a second beside it: headings are named for what they hold and better for what they found, so that a reader running down the contents has met the case before reading a section, a heading never withholds what its section holds to make somebody open it, and the levels divide without numbers, the upper taking the thematic area and the one beneath it the part that one section settles. Such a request resolved to the default genre, which imposes no convention and is written for text that stands on its own, and produced a text with no content declaration, no promise, and nothing to click for. The genre states what a teaser owes that reader: a declaration from which they can say what the source actually holds and whether it is theirs, in the source's own particulars rather than a field's general terms; a promise the source text keeps, settled on arrival against what the reader was led to expect rather than against what was literally said, and costing not this click but the next one; an arc compressed into the whole of the text rather than laid over its parts, stopping short of its own resolution; and an action naming what the click delivers rather than the act of clicking. - The ABT technique now states the three ways its arc is actually realised, where it previously stated one arc governing a text and conceded nesting in a single clause. An arc may be nested — a section, an anecdote, or a passage inside any of the three parts may carry a complete arc of its own, and what makes it subordinate rather than a second arc is where it leaves the reader: it turns on something the governing complication has already raised and hands the reader back to the part it sits in, size deciding nothing. An arc may be iterated — told once simplified so the reader has the shape and once in full so they have the substance, both passes turning on the same complication and reaching the same consequence, the second owing what the first left out, a second pass that only lengthens the first being repetition in the shape of a structure. And a text may open in medias res, which is an outer arc enclosing the whole piece: the scene is the complication, the bridge revealing what the scene was begins the consequence, and the rest of the text carries an arc of its own inside it. That variant is stated precisely enough that its characteristic failure is avoidable — the setup is carried by the scene itself, a setup laid out before the scene making the device an ordinary opening with an anecdote in front of it, and a setup omitted altogether forcing the bridge to carry a fact dump that spends the tempo the scene had bought. One arc still governs, the concession clause it used to carry having grown into the nesting requirement rather than being stated twice beside it, and the review half diagnoses each variant's failure without introducing a target of its own.
- The PAC technique now says at what scale its arc applies, how visible it may be, and when a section carrying part of it is complete rather than unfinished. The arc's unit is the section and not the whole of a long document: a text short enough to be read at a sitting carries one arc, and a long analytical document ordinarily carries one per large section, where a document built instead around a single premise tests it once and everything before the test is evidence for a claim the reader has had no occasion to weigh. Unlike the narrative arc beside it, this one is allowed to show — a reader who came for the reasoning is following the path from what is known to what it settles, and being able to see where they are on it is part of why they believe the conclusion; what is forbidden is the labelling, a section named for the part it is rather than for what it found. It states, for each way a quotation may be set, what the punctuation and capitalisation around it have to do: the run-in joint, punctuated by whether the quoted words are introduced as an utterance or are a grammatical part of the host sentence; the surrounding sentence's stops, which are one stop and not two, with a reporting clause bound to the utterance rather than standing as a sentence of its own; the block, whose setting off is the whole of the mark, so enclosing marks state the quotation twice and marks inside it are the source's; and reported speech, where a turn takes a paragraph of its own and a turn continued across paragraphs is marked as the same turn, because a new paragraph is what a change of speaker looks like there. It states that a modification, an omission and an error preserved from the original are each marked where they occur, unmarked all three reading as the source's own words — the single thing a quotation guarantees. It states that a spelled-out abbreviation takes ordinary capitalisation, capitals being a property of the abbreviation rather than of the words behind it, so the backwards reading that produces *Search Engine Optimisation* asserts a proper name the text does not have. And it states that a list holds one convention throughout, which one following from whether the items are complete sentences or fragments completing the sentence that introduces them, with the correction made at the departing items and a list genuinely of both kinds left to a pass that may rewrite an item. What turns on the language stays with the language: the glyphs, which side of a closing mark a stop falls on, how speech is conventionally set, and how a continued turn is marked are deferred to the resolved language's own mechanics scope, and no rule added here is one an installed resource already holds.
- The base contract now states the voice this Collection writes in, so a draft that satisfies the contract in full reads as this Collection's rather than merely as competent prose. A new `Voice` section holds five requirements, each stated once: that the text argues without blame, beginning from the reader's own impulse and following where it leads instead of charging them with a failing they cannot answer — the requirement reaching the framing as much as the words, since a reader hears condescension in how a point is set up; that importance is left for the reader to conclude from what is put in front of them, so that where another writer would raise their voice this text is often silent; that humour is an undertone which never points at itself, a draft that feels as though it is trying to be warm having already overshot; that a metaphor is used only where the material carries one, and is then the only one the text uses; and that a rhetorical question is the material's or nobody's. Three craft rules a reader can check are stated beside them: a body text stands without its paratext, so a reader holding the body and not the headline, standfirst or subheadings meets no pronoun, definite form or reference that only those resolve — the ordinary case, since a headline is often written by somebody else and changed after publication; an abbreviation is introduced by its full form before it is used alone, and one occurring once or twice is better not introduced at all; and an insertion takes the mark that matches its weight, the parenthesis dampening, the comma neutral and the dash amplifying, with the single dash a different tool again and the dash's form on the page left to the language. ## [0.16.0] – 2026-08-25

### Added

- A ticket may now declare, on a line of its own body opening `Builds alone`, that it shares its wave with no other ticket, and `/orchestrate` honours it. Such a ticket is a Solo Ticket: the planner places it in the first wave its blockers admit it in and gives that wave to it alone, its otherwise admissible siblings falling to the wave behind it, while ordering, ceilings, and blocking behave exactly as before. The plan names every such ticket under `solo` and carries `builds_alone` on the ticket itself, so a report says both that a ticket rides alone and that its own body is why. An author writes the line where the ticket's subject is a repository-wide invariant — a rule every shipped file is under, which the ticket rewrites or newly enforces — because a blocking edge names a ticket, and what such a ticket excludes is every new instance a concurrent sibling would write, which does not exist when the tickets are written. ADR-0099 is the record; it also names the rejected alternative, a tracker relation of the shape *exclusive over surface X* (issue #118).

### Changed

- The post-merge wave check under `/orchestrate` now judges a finding by whether fixing it requires somebody to decide something, rather than by whether every gate command passed. A failing command may be reported mechanical — and fixed on the branch like any other coherence finding — only under a constructive obligation: the finding names the command, states the exact correction as the file, the symbol or surface, the text as it stands and the text as it must stand, and names the decided thing that correction restates, so a fixer that has not read what the checker read applies it without deciding anything. A gate failure that cannot be written down that way is the stop it always was, beside a finding that requires choosing between two tickets' intents. Because the mechanical claim is a claim of full determination, such a finding buys exactly one fix round: the named command still failing when the check reads the branch again stops the run even where that round changed things, a different command failing is a new finding with its own single round, and the loop's existing bounds — it ends when a round finds nothing, and a round that changes nothing stops the run — are unchanged. From the second round on the re-check is handed what earlier rounds of the same wave's check explicitly declined, each with the ground it stated, and a declined finding is re-raised only on grounds the earlier reading did not have, named in the verdict, so a round no longer wins by speaking last. The fixer is confined to the findings' determined edits, may re-run the one named command and report what it said without anything being decided by it, and is told in words that the coder is never the finder or tester. ADR-0098 is the record; it supersedes the half of ADR-0072 that stopped the run on any failed gate (issue #117).

## [0.15.0] – 2026-08-25

### Added

- `/proofread` corrects one supplied text's mechanical language errors and nothing else. It corrects spelling, grammar, punctuation, agreement, inflection, duplicated and missing words, and the locale's own conventions for dates, numbers, currency, and quotation, and it preserves wording, meaning, tone, register, structure, factual content, formatting, code, links, and metadata — frontmatter byte for byte, and the text's own choice wherever more than one form is correct, because a preference is not an error. A genuine decision parks the ticket exactly as plan-time parking does — the question written on it, the ready label returned to triage, the claim released, no outcome recorded — and the wave carries on without it. Work tried and found wanting goes where it went before, the failure path the amend fronts. Nothing in the triage addresses the developer: the run acts between waves, reports once at the end, opens with what is done and what the developer must do, and states findings as a list of statements rather than questions awaiting answers. ### Fixed

- A subagent no longer ends its turn waiting on a command it started, which unattended is a run that dies where it stands. Every brief `/orchestrate` hands out tells its subagent to run the project's full verification itself, and none of them said what to do when a command outlives the subagent's patience: in one interviewed run the integration suite takes over twelve minutes, and this was that run's dominant failure mode — one ticket's builder ended its turn three times with the suite still running and nothing committed, a verifier ended its turn twice the same way, and a later builder twice more, each of them rescued by the orchestrating session arming a background wait by hand because a human happened to be watching. With nobody watching, every one of those turn-ends is a dead run: the subagent has neither finished nor failed, so nothing comes back to wake it and the night is spent standing still. All six briefs — `brief.md`, `verify.md`, `repair.md`, `repaired.md`, `wave.md`, and the `amend.md` that arrived with the amend — now carry one paragraph beside their verification instruction, in one wording so a subagent cannot learn the rule in one role and miss it in another: start a long command in the background, wait on its completion with whatever waiting facility the harness gives, and never end the turn while it runs, waiting being part of the work rather than idleness to yield in. `SKILL.md`'s build and verify steps name the complementary rule the orchestrator needs, since a stop it reads wrongly costs the ticket anyway: a subagent found waiting on a command it started has neither finished nor failed, and is resumed with that command's result rather than recorded — a verdict that was not reached is not a fail (issue #75).

- A ticket the run recorded failed and that was closed afterwards is in the report again, where it used to be in none of the five lists. The report promises that every ticket in scope appears exactly once and that the outcomes partition the scope by construction, but the two halves of that scope are read separately — the open half off the open listing, the closed half by a reader that kept only closed tickets whose last engine marker was the done outcome. A ticket recorded failed and then finished and closed by a person, or auto-closed by the tracker off a commit trailer once the branch reached the default branch, which working the default branch directly now makes ordinary, was in neither half: absent from the open listing because it is closed, and skipped by the closed reader because its last marker is failed rather than done. It was the run's — the run claimed it, built it, and wrote an outcome on it — and the report lost it without a word, which happened in the field and left the tracker as the only true account of that night. The closed reader is `tickets_recorded` now, its name following its meaning, and it skips only a ticket carrying no engine marker at all: a closed ticket is reported under the outcome as it stands with the last marker winning, exactly as the open half is already read, and its commit, what it collided with, and where its work stands render as for any other recorded ticket. The reasoning that justified the old filter narrows to what it is actually true of — a closed ticket bearing no marker of this engine's was never the run's to account for, and stays outside the report. A report that silently drops a ticket undermines every other line of it, which is the whole of what a report has to trade on (issue #81).

- A line in a ticket prescribing the delivery channel — a pull request, a push, a release — is no longer read as an acceptance criterion under `/orchestrate`, because delivery is the run's boundary: the run integrates into the branch, and publishing is the developer's move after it. The old reading was unsatisfiable by construction — the brief forbids a builder to push, the verifier checks every criterion with none excluded, so a ticket ending *deliver as a PR against the default branch* could only fail, the builder forbidden to do the one thing the sentence asks and the verifier failing the ticket for the builder's obedience. In one interviewed run this was the first stop of the night: the first ticket built correctly and was failed on exactly that line, at a ceiling of one where a failure stops everything, so one sentence about delivery ended a twelve-ticket run at ticket one, with two sibling tickets carrying the same sentence behind it and the developer's fix being to edit the clause out of three issue bodies by hand. Both criteria-reading briefs — `references/verify.md` and `references/repaired.md`, which checks both colliding tickets' criteria under the same rule — now state the exclusion in one wording: the verifier notes the clause in its report and takes its verdict from the rest. `references/brief.md` gives the builder the mirror sentence, a delivery instruction being not a requirement to build toward and not a decision to stop over — the work is delivered by being integrated (issue #82).

- Two `isolate` calls that overlap no longer reserve the same record number: the whole read-modify-write that produces a reservation happens under an advisory file lock, and the in-flight reading it derives from now reads the reservation files themselves rather than a caller's pre-lock list of open working trees. The defect was observed rather than reasoned — the session that verified #76 started four `isolate` calls concurrently in one wave and all four reserved the same number, precisely the collision the verb exists to prevent, one level up from where it was fixed — and nothing forbade the overlap: the sequential contract the engine assumed was stated nowhere, and the reader most likely to break it, an agent generally instructed to batch independent tool calls, is exactly the one the Skill is written for. The engine takes a lock rather than the Skill taking a vow, a contract stated only in prose being one an orchestrator breaks while following its other instructions correctly, and one that cannot reach a second session at all. The lock lives at `allocation.lock` under the git common directory, beside the working trees and reservations the run already keeps there, so two sessions working the same repository contend for the same file; a caller finding it held waits rather than fails, the work behind it being bounded and short and a refusal turning solved contention into a ticket with nowhere to build; it is released when the holding process exits, so a run killed mid-allocation strands nothing; and nothing else about `isolate`'s answer moves — the same ticket isolated again gets back the same reservation and the same scratch directory, under contention exactly as without it (issue #84).

- The brief an amending builder is given now carries every rule the first builder's does, and the suite holds the invariant rather than whoever writes the next ticket. `references/amend.md` carried neither the reservation paragraph — take the number the run reserved rather than reading the registry — nor the run-owned files paragraph, so an amending builder worked from less than the builder whose work it took over, in the same working tree, able to mint a duplicate record number or append straight to a run-owned file: the two collisions those rules exist to remove. Neither omission was careless, which is the point — each rule arrived in a ticket that listed the files to change, and the amend brief was either not yet written or not among them, so every new rule had to find every brief and every new brief every rule, by hand, with nothing failing when one of them did not. The two paragraphs are now in `amend.md` worded byte-identically to `brief.md`'s, fill-in instructions included, and the invariant is pinned beside the test that already pinned the waiting rule: which briefs go to a code-writing subagent and which rules those must carry are each declared in one place; the check quantifies over the briefs the reference directory actually holds rather than over a list of names, so a brief added later is covered from the moment it exists; and a brief that is genuinely exempt is exempt visibly, its reason stated, so a reader checks a stated exemption rather than noticing an absence (issue #85).

Most of the rules did exist, in records written for a reader deciding architecture rather than one writing a file, and exactly one existed nowhere but inside a test: a manpage carries an `## Options` section even where the skill has no flags at all, written *none, and none is missing*, so a reader learns the emptiness is deliberate rather than a section nobody wrote. `docs/coding-standard/skills.md` gathers them — the frontmatter fields the Catalog reads, the flat `kntnt.`-prefixed `metadata` namespace with string values, `compatibility` naming exactly the binaries the declaration holds and a soft requirement named there in prose and deliberately not in it, the dependency preamble present exactly where there is something to check, the manpage's sections and the one grammar its `## Options`, its `## Synopsis`, and `argument-hint` share, and where a file the body opens on demand lives — stating each once and citing the record that carries its reasoning rather than arguing it again. Where the suite does not in fact hold one of them, the module says so at the rule and marks it *held by hand*: the `## Help` heading as against the route the section carries, the four dependency lists being written out on a skill the suite does not name one by one, an on-demand file under `references/` in a skill the same list does not name, and the manpage sections other than `## Synopsis` and `## Options`. A contributor told *every rule here is enforced* would read a green fourth check as the form confirmed, and for those four it is not. `AGENTS.md` gains a line pointing at it and `CONTRIBUTING.md`'s coding-standard step names it, so an agent or a contributor meets it before writing anything. The contract stays written twice on purpose, and the module's preamble says why: a contributor who has not yet written anything cannot be helped by an assertion message, and a contributor whose suite has just gone red cannot be helped by a document they did not know to read. So every test pinning a rule about a skill's own shipped files now fails with the rule and its reason in a phrase, the record where there is one, and the path to the module — where before it failed with the heading it could not find, or a path, or a path and a key, the reasons all sitting in docstrings that are not shown when an assertion fails. The sweep takes in the pins on individual skills' bodies as well as the ones quantified over the collection — the `/commit`, `/push`, and `/release` bodies, `/delegation`'s capability declaration and the mode text it ships, and the line of its manpage saying an incomplete form is refused with the synopsis. It is bounded to a skill's own files: the Manager's own tests keep their messages, however bare, and so do the tests that use a shipped file as a fixture for the parser rather than to enforce a rule on its author, and the guards that only check the sweep found something to judge. The stale-record-number sweep now reads the coding standard and the suite too, so a citation in a message or in the module is held to the same check as one in the prose (issue #69).

- A test now fails when the README and the Catalog stop naming the same skills — when the Catalog carries an entry no `### <name>` section under Usage describes, and when a section describes a skill the Catalog does not carry. Both lists are authored by hand and neither is generated from the other, the collection's stance being that a text a reviewer can diff beats a regenerated one, so until now the only thing keeping them together was whoever remembered. They agreed at the time this was written because the change that prompted it updated them by hand. The paragraph closing that part — which skills need which binaries and which Capabilities — stays uncovered and cannot be covered without generating it, which is the thing ruled out; the gap is stated in the test a reader would otherwise take as covering the whole pairing, and in the standard module (issue #69).

### Changed

- The `metadata` block every skill carries is now what the Agent Skills specification says `metadata` is: a map from string keys to string values, one level deep. It was a nested map holding four lists with a boolean beside it, and a reader outside this collection does not refuse that — it coerces it, so `agentskills read-properties` answered with the dependency lists flattened into a Python repr like `"{'binaries': ['git', 'uv']}"`. Nothing could read `binaries`, `skills`, `externals`, or `capabilities` back out of that, and nothing warned, because a string is a legal value. Each list is now one space-separated string under its own key — `kntnt.binaries: "git uv"` — which is how the specification's own `allowed-tools` carries a list for the same reason, and an empty list is an empty string that means the same thing to every parser. The marker that says a skill is this collection's moves with the shape: it is any `kntnt.` key at all rather than a block, so a skill with no dependencies is marked by writing its four lists empty, and `/tldr` no longer needs an empty mapping spelled out to be recognisably ours. `internal: true` becomes `kntnt.internal: "true"`, because the specification asks for reasonably unique key names and `internal` bare is a key every collection has equal claim to; a reader that hid a skill from ordinary discovery by looking for the bare key will no longer find one here. The catalog is unchanged in every field a user or a skill reads — the same four lists for the same seven skills — and only the digests moved, because the files did. ADR-0061 is the record this implements; ADR-0060 loses the paragraph that corrected `/tldr` to `kntnt: {}` (issue #52).

- The manager reads a skill's frontmatter with PyYAML instead of the restricted YAML subset it carried, so what it accepts is what YAML accepts. `description: >` works — a description may run over lines, where generation used to refuse the folded form because the subset yielded a lone `>` as the whole value — and the parser that reads other collections' skills is one that is exercised by everybody rather than only here, which is where issue #48's kind of defect was hiding. The subset was there to keep the script dependency-free, and `uv` was always a hard dependency of every skill in the collection, so it was buying portability nobody needed. What it did buy is real and is being given up on purpose: with a cold `uv` cache **and** no network, a script that declares a dependency does not start, so in that one state the collection's skills fail at their dependency check rather than running. One run with the network up warms the cache for good. Contributors run two of the four checks with the package named — `uvx --with types-PyYAML mypy …` and `uv run --with pytest --with pyyaml pytest` — because neither goes through the script that declares it.

- Every skill of the collection now refuses what its grammar does not allow, which is the other half of the rule the manager took on: an undeclared flag, an invalid combination, and an incomplete form are one error rather than three behaviours, answered with what was wrong, the `## Synopsis` section of the skill's own `help.md` verbatim, and a pointer to `/<skill> --help` for the page in full. Validity is judged against the invocation rather than the skill — a flag is allowed where it has a function on the run you typed — which is why `/delegation status --yes` is now an error: `--yes` answers a confirmation, `status` writes nothing and asks for none, and the grammar was flat where the flag was not. `delegation`'s synopsis and `argument-hint` carry that split, and `/delegation user` with no state prints the synopsis and stops instead of asking which of `on`, `off`, or `status` you meant. That last one settles a contradiction rather than changing settled behaviour: the skill's arguments asked while its steps stopped, and the half the agent executes is the true one. The reason the ask existed survives untouched — a file in your home configuration or a committed file in a shared repository is never flipped off an inferred state, and an error infers nothing either. `agents-md`, `commit`, `push`, and `release` were audited for both classes and came back clean on both, and each now states the rule where the agent that enforces it reads it, since a skill with no script has no parser to make strict. `orchestrate` and `tldr` were brought to the same shape for the same reason.

- The manager refuses an unknown subcommand and a flag the verb does not take, and answers both the same way: the error, the synopsis of whatever was actually addressed, and where to read that page in full — and nothing else, with a non-zero exit. `/kntnt updat --yes` used to be re-read silently as `help --yes`, so a typo ran a different verb and the rest of the line became its arguments; it is now an error naming `updat` alone, and nothing after the unknown word is parsed or reported. `/kntnt help --yes` used to be the page with a note above it and is now an error too, because a flag accepted and ignored is what teaches a user that flags sometimes do nothing. The grammar is the one the manpages already documented — `select` and `update` take `--project`, `--yes`, and `--dry-run`, `uninstall` the last two, `help` none — and the rule binds the three subcommands no user types as well: `manpage` and `check` take none of them, and `catalog` keeps `--dry-run` by genuinely acting on it where it writes. The synopsis an error prints is the `## Synopsis` section of a shipped manpage, taken whole and verbatim — the verb's own page where a known verb was named, the manager's own where the word was not one of its subcommands — so nothing in the script is a second grammar free to drift from the page the pointer leads to. `uninstall --project` loses its bespoke message and goes through that one path like every other disallowed flag, the reason the verb has no project form staying in `help/uninstall.md`, which the pointer reaches. `--help`, `-h`, and bare `/kntnt` are unchanged: they are the route into help rather than flags on a verb. In the suite one table now drives both halves of the rule — a user-facing verb is checked against its manpage and against the parser, an internal subcommand against the parser alone, rather than being published as user documentation to satisfy the check — and the dependency gate every skill runs first is pinned flagless, so a stray flag there is caught in the suite rather than in a broken `/commit`. ADR-0059 is the record this implements; ADR-0050 loses the clause that said `--yes` reaches every verb of an engine.

- A change the transport refuses now tells the user why. `apply update` and `apply select` read a refusal off the disk rather than raising it, so that the run still reports the withdrawals it had already made — and that reading cost the transport's own account of what it declined and why, which is the one thing nothing else on the machine knows. It is written to stderr, verbatim and whole, under a line naming whose words they are; the payload on stdout gains no field and loses none, and the exit codes are what they were. Both mirrors do it, placement and removal alike, but a removal only where the disk check still leaves a failure: a transport that grumbled while removing the files anyway is exactly what that check exists to absorb, and that run stays clean and silent. The `update` and `select` steps tell the agent to hand the message on, and no longer say to report the failure *whatever the transport reported* — true of its exit code, and misread as *never mind what it said* the moment there is something to pass along.

- What a skill's agent opens only when the situation arises now lives in `references/`, the directory the Agent Skills specification recommends for it, instead of sitting flat in the skill's root. Fourteen files moved — `gates.md`, `placement.md`, and `writes.md` in `agents-md`, `mode.md` and `persist.md` in `delegation`, `mode.md`, `persist.md`, and `shape.md` in `tldr`, `changelog.md` in `commit`, and the five subagent briefs `brief.md`, `verify.md`, `repair.md`, `repaired.md`, and `wave.md` in `orchestrate` — and every pointer into them moved with them, including the one `/release` follows across into `commit`. A brief is read at one step and handed to somebody else, which is the same thing `agents-md` does with `gates.md` and not what the Manager's `steps/` is, so it goes where the rest of what a body opens on demand goes. Nothing about conformance changes: the specification calls those directories recommendations, and the collection validated as it stood. What changes is that a root no longer mixes the one file a user reads with the files only the agent opens, so a reader who has never seen this collection can tell which is which without being told, and can tell it the same way here as anywhere else. Three deviations stay, and are now recorded rather than merely true: `help.md` stays in each skill's root, because `select` fetches it from the origin at an address derived from the Catalog (ADR-0044); the Manager keeps `steps/` and `help/`, `steps/<verb>.md` being the procedure the agent carries out rather than documentation it consults, which is the line ADR-0046 draws; and `catalog.json` and `harness-paths.json` stay in the Manager's root, because an installed Manager fetches the Catalog from `skills/kntnt/catalog.json` and `update`, the verb that would deliver any fix, is the one that cannot run without it. The suite now follows both pointer shapes the collection uses and fails on the first that resolves to nothing, so a half-done move is caught here rather than in somebody's session. ADR-0063 is the record this implements, and it binds every skill added later; ADR-0046 names the moved files at their new paths (issue #54).

- `/orchestrate` now briefs a subagent with the ticket as the tracker holds it rather than with the body alone: the body it was filed with, followed by every comment on it since, oldest first and each one attributed and dated. Both subagents get it — the one that builds and the one that verifies — from the same field of the same plan entry, so a criterion the builder was given is a criterion the verdict is taken against. It matters because a ticket is a thread and `/triage` writes its agent brief as a comment by instruction: the settled decision, the desired behaviour, and the acceptance criteria all arrived nowhere, so a triaged ticket reached its builder as its untriaged self, ending in questions triage had already answered, and reached its verifier told to check acceptance criteria the ticket it was shown did not carry. Nothing refused and nothing warned. Both templates now say that where a comment contradicts the body the later text stands, and both keep the rule they already carried — the ticket is pasted whole, never summarised. What a run wrote on the ticket itself is left out, the outcome it recorded and the note it leaves before a rebuild being the engine talking to its next self; the two readings the engine makes of a comment are untouched, and a ticket nobody has written on is briefed exactly as it was. ADR-0065 is the record, and it draws the line the engine's boundary stance was always about: a marker is read only where the engine wrote it, and prose is relayed to a subagent rather than interpreted here (issue #62).

### Removed

- `/orchestrate` no longer refuses to run on the repository's default branch, nor on a repository where nothing can say which branch that is. A run works the branch the developer left it on, whichever branch that is, and which branch that is is not the Skill's to second-guess. The rule described somebody else's workflow rather than this one: every commit in this repository's history is on `main`, so the refusal bought no safety here — it made the Skill unusable without first inventing a branch that exists only to satisfy the check and merging that branch back by hand, which is the same commits on the same line of history one step later. Both places that asked go, the chain that decides whether a plan is `ready` and the guard at the top of the merge, and the plan's JSON is otherwise as it was: `ready`, `reason`, `branch`, and `default_branch` all stay, `default_branch: null` included, and only which conditions clear `ready` changed. A working tree holding work nothing has committed is now the only thing a run refuses about the state it starts in, and that refusal is untouched at both of its own call sites. `/release` still refuses to bump anywhere but the default branch: it commits, pushes, tags, and cuts a release, so it must ship from the published line, while a run publishes nothing. ADR-0064 is the record, and it states the price as well — a run on the default branch has no fork point to bound the closed half of its report by (ADR-0058), so it asks that question whole and leans on the full-page guard (issue #61).

### Fixed

- The dependency gate every skill runs first no longer answers exit 0 with two empty lists for a skill whose declaration it cannot read. `skill_deps` reads the four lists out of the `metadata` keys prefixed `kntnt.`, and a frontmatter carrying no such key came back as four empty lists — which is what a skill genuinely requiring nothing comes back as, so a manager meeting a shape it does not know reported nothing missing and handed the agent no capability to confirm. Both halves of the gate, gone without a word: reproduced against the released manager with two skills identical but for the shape of their `metadata`, each declaring a binary that cannot exist and the `subagents` capability, where the nested shape answered exit 2 with both and the flat one answered exit 0 with neither. Exit 0 is the go-ahead every skill's body is written against, so the skill runs. `check` now refuses instead, with exit 2 and the reason on stdout — the one non-zero answer every body documents a response to — carrying an entry of the same three keys any unsatisfied dependency carries, naming the skill, the fault, and `/kntnt update` as the remedy that brings the manager and every enabled skill to one revision. `apply update` asks the same question of every skill the layer holds and reports the answer rather than raising it, the withdrawals and placements of that run being already on disk by the time the re-check runs (ADR-0036), which also closes the case where a value the manager already refused would have taken the whole report down with it.

  The state is reachable, which is what decided the shape of the fix. `apply select` is the verb that reaches it: the manager is no catalog entry, so nothing in `select_change` names it, and a user enabling one skill on a machine that has not run `/kntnt update` since the shape changed gets the new shape beside the old manager. So does `apply update --project`, a project layer holding no manager of its own and its skills' checker falling back to the global one. `apply update` on the global layer refreshes the manager first and leaves the machine consistent, `apply uninstall` only removes, the three `plan` verbs write nothing outside a sandbox, and `help`, `manpage`, `check`, and `catalog` write no skill at all — eight verbs, which is the whole parser and therefore the whole list. What made this survivable to write in the first place is that *cannot read* and *is not ours* were the same observation: `collection_block` answering `None` is how the sweep tells a stranger's skill from one of ours, and refusing on it would refuse every skill on the machine this collection did not write. The two come apart at the caller — nothing but a skill of this collection invokes the checker — so the gate reads that answer as *ours, and unreadable* while the sweep goes on reading it as *not ours*. `carries_marker` is untouched and still answers rather than raises about any file at all. ADR-0068 is the record this implements; it cannot reach a manager already installed, and it says so, the residual hazard for this one migration being named there rather than fixed (issue #68).

- A skill's `## Arguments` section no longer restates what its own Steps already say, and the record that took those restatements out no longer describes a collection that has moved on under it. ADR-0059 needed each body to state the grammar the skill accepts and the one refusal that answers everything else, and `## Arguments` is where that went — which is why every skill carries the heading again where ADR-0046 had removed it from four of them. The grammar line and the refusal pass ADR-0046's own test, the agent parsing against the one and carrying out the other; the per-flag bullets that came back beside them do not, all ten of them saying what a Step of the same file says — `agents-md`'s `path` default is its step 3, `release`'s bump precedence is its step 4 and in more detail than the bullet gave, and every `--yes` is the step that waits. They are gone from `agents-md`, `commit`, `push`, and `release`, leaving the shape `/orchestrate` and `/ready-for-agent-check` already had, and no manpage is touched: `help.md` is the file written for the reader who wants a flag described, and it carries all ten. `delegation` and `tldr` keep their entries, which are parse rules rather than descriptions and are what their first step has nothing to carry out without. ADR-0046's count — four skills lost the section, one kept it — is corrected in the shape ADR-0017 uses, the claim named as what the record first gave, rewritten to what is true, and pointing at ADR-0059; its decision was never about the heading and stands unchanged.

- `/tldr` cited ADR-0029 for the flag-refusal sentence its siblings cite ADR-0059 for — the record ADR-0059 withdrew the tolerance clause from — so the skill named, as its authority for refusing a stray flag, the record that used to say a stray flag is tolerated. The sweep for stale numbers could not have caught it: it reads no skill body at all, and 0029 has a file either way, so the citation would have resolved wherever it was wrong. A new assertion reads every shipped `SKILL.md` and fails where the flag-refusal paragraph closes on any record but ADR-0059, keying on the opening clause all of them share rather than on a sentence `delegation` states at greater length. It is narrow on purpose and says so in its own docstring: whether a citation is apt needs knowing what the cited record carries, which is a reading and not a comparison, and what a test can hold is one rule written in one wording everywhere it appears (issue #66).

- Catalog generation now says which of three things is wrong with a skill's marker, instead of reporting all three as a marker that is missing. A `metadata` that is not a mapping — `metadata: hello` — reaches the same empty result as a skill carrying no `metadata` at all, and was refused with the message written for the second, which pointed at a marker while what was wrong was the line the keys would have hung under. A `kntnt.` key holding something other than a string was worse than a wrong message: it passes the test for a marker, and the value was then coerced with `str()` on the way in, so a `kntnt.binaries` written as a YAML list — the shape habit reaches for, and the shape every skill carried before the flattening — became `["['git',", "'uv']"]` in the catalog, a dependency list nobody declared, with nothing warning because a string is a legal value. That is exactly the loss ADR-0061 refused to let a reader outside this collection take, taken here instead. The three now answer separately and each says what is true: `metadata` is a list and not a mapping, no `metadata.kntnt.*` key is there at all, or `metadata.kntnt.binaries` is a list and not a string. `skill_deps` refuses that third one rather than reading through it, so the dependency check every skill runs first fails on it too instead of reporting dependencies the file does not declare. What is deliberately unchanged is `carries_marker`, which still answers rather than raises about any file at all: a skill whose marker is present but unreadable is still recognisably this collection's and can still be withdrawn, which is why generation is the only place the refusal can live. That gate — generation refuses, and `CONTRIBUTING.md` step 4 regenerates the catalog before anything ships — was load-bearing and pinned by nothing; a test now holds it against every malformed form (issue #48).

- Two rules of the skills coding standard are now held against every skill the collection ships, instead of against the skills a literal in the suite happened to name. The four dependency lists were read off five skills by name, and the reading itself could not see the failure it was there to catch: `skill_deps` resolves a `kntnt.` key nobody wrote to an empty list, which is exactly what a skill requiring nothing declares, so a skill dropping `kntnt.externals` outright was indistinguishable from one declaring it empty — and for the three skills the literal did not name, not even that much was looked at. The guard now discovers every `skills/<category>/<skill>/SKILL.md` and reads the four keys themselves out of `metadata`, so an omission fails where a resolved list could never have failed. Placement of a file the body opens only when the situation arises was further behind: the map it was held against was a hand-written table of skills and their files, `/ready-for-agent-check` had never been added to it, and its `references/review.md` could have moved into the skill's root without a word. That guard discovers the files too, on what a skill ships rather than on what somebody remembered to list — a skill ships its body, its manpage, its engine where it has one, and the files its body opens on demand, so every Markdown file that is neither `SKILL.md` nor `help.md` is one of the last kind and belongs under `references/` (ADR-0063). Nothing a skill has to satisfy moved and no shipped skill turned red: both rules were already stated and already kept, by whoever remembered. Both were marked *held by hand* in `docs/coding-standard/skills.md` and no longer are. The `## Help` bullet there loses a claim that was untrue in the same way: the suite does not pin the route that section carries, because the two tokens it looks for — `$HERE/help.md` and `--help` — are named again by the refusal clause every body has to carry, so a body whose `## Help` section is deleted outright still carries both and stays green (issue #70).

- The two rules `docs/coding-standard/skills.md` still marked *held by hand* are settled, both as requirements, and a third claim on the same sentence is settled as the convention it always was. A manpage carries six sections — `## Synopsis`, `## Description`, `## Options`, `## Notes`, `## Dependencies`, and `## See also` — of which the suite read two for every skill: the synopsis a refusal quotes verbatim, and the options the grammar is checked against. The other four were kept by whoever remembered, so a page shipped without a `## Description` failed nothing and was still wrong. All six are now held present on every manpage the collection ships — each skill's own, the manager's, and each of the manager's per-verb pages under `help/` — found rather than listed, and the manager's `steps/help.md` is not one of them, being the agent's instructions for the `help` verb rather than a page anybody reads. Presence is the whole of what the check buys and the standard now says so instead of implying more: a `## Description` of one word passes, and whether a section was written for a reader is a review's judgement and no test's. Five shipped pages departed from the rule and are corrected — the manager's own manpage and its four verb pages carried no `## Dependencies` at all, and each now states what that page's verb actually requires: `uv` everywhere, `npx` and network access where files move through the transport or the catalog is fetched from the collection, and nothing beyond `uv` for `help`, which prints pages off the disk and is the one verb that still answers on a machine that is offline. The `## Help` section of a body was unheld for a different reason: the suite asserted that a body names `$HERE/help.md` and answers `--help`, and the refusal clause every body has to carry names both tokens already, so a skill whose `## Help` section was deleted outright — a skill that can no longer be asked what it does — stayed green. The route is now read out of that section rather than out of the body at large, which requires the heading and pins the route to it in one assertion, and it reaches the manager's body as well as each catalog skill's. No shipped body changed: every one already carried the section. `## Arguments` is settled the other way, as a convention, because two shipped pages depart from the heading and are the better for it — `/orchestrate` puts the arguments it takes under *Aiming the run* and `/ready-for-agent-check` puts its own under *Scope*, and both name their content better than the generic word would. Nothing checks that heading, and the standard no longer reads as though something did. Each new guard was watched failing on a mutated page or body and passing once it was put back, and the file the manager keeps in `steps/` stayed green throughout, which is what tells the manpage rule from a glob for every `help.md`. No *held by hand* mark is left standing anywhere in the module, and the paragraph that explained the mark now says what remains true without it: where the suite holds less of a rule than the rule says, the module says so where the rule is stated (issue #71).

## [0.9.0] – 2026-08-19

### Added

- `/orchestrate` — read the issue tracker and work the run it makes of it. Every open ticket carrying `ready-for-agent` is in scope, laid out in the waves their blocking edges put them in and worked against the branch you are already on; a ticket without that label never appears, because a ticket without it is unfinished thinking and unfinished thinking is never built. Wave one is what may start now and each later wave is what the one before it unblocks, an edge being the tracker's own blocked-by relation or, where a ticket carries none, a `Blocked by` line in its body naming other tickets — a blocker already closed names work that exists and blocks nothing. Where no ticket is workable at all, the run says so and starts nothing rather than turning over a frontier that never grows, and `--dry-run` reads the same plan without starting anything either. Each ticket goes the same way. It is claimed on the tracker before any work on it starts — the tracker's own assignment relation, so a second session you start in parallel sees it taken and skips it, and a ticket a person has taken is left alone for the same reason. It is built by a subagent with its own context window, so a long run does not degrade as one context fills, briefed with the ticket's body as it was filed rather than a summary of it, the parent spec whose testing decisions are read before any test is written, the instruction to build test-first, the commit convention, and the fact that nobody is watching — which makes a genuine decision something to stop and report rather than guess at. `--model` names the model those subagents run on, so mechanical work can run cheaper than judgement work. It is then verified by a second subagent that never saw the building session and is told nothing the builder claimed: that one runs the project's full verification itself and checks each acceptance criterion against the repository as it now is. Its verdict is what closes the ticket, together with the commit that carries the work, and no flag, argument, or circumstance skips it — a run that can report success it cannot support is worse than no run at all. A ticket that fails verification is written down as failed and left open and claimed, and is never retried, because the conditions of a rerun would be identical and so would the outcome; its work is never reverted and stays where it was built, to be looked at. Where that is the run branch itself, the run stops there rather than building the next ticket on unverified code. A run refuses on the repository's default branch — and on a repository where nothing can say which branch that is, rather than guess at it — and nothing is pushed, tagged, or released. The run closes the loop on itself, because every outcome is written on the ticket it belongs to and that is where the next plan reads it back from: a ticket already recorded is never offered again, and a ticket whose blocker failed comes back stranded — not workable, since the work it builds on does not exist, and not missing from the account either, which is exactly what a loop tracking only what it can start drops without saying so. It ends with one report rather than a running commentary, so a night is read in one sitting, and every ticket in scope is in that report exactly once under one of five outcomes: done, failed, conflicted, stranded behind a failure, and never on the frontier — the last being everything the run never had a chance at, whether held by a cycle, by open work outside the run, by another session's claim, or by the run stopping before its wave came round. The account carried conflicted from the start, before integration existed to produce one, rather than growing a pile later. There is no sixth grouping and no ticket in two of them, because a ticket a run drops in silence is one you would not know to pick up. Everything deterministic about a run lives behind one seam, the engine's command line, so the skill behaves identically in every harness rather than being sharp where one vendor's orchestration primitive exists and vague everywhere else; ADR-0050 records that decision and what it replaces, and ADR-0051 records why an outcome is remembered on the tracker rather than in the run — the developer looks at the ticket, an outcome written in two places can disagree with itself, and reading it back off the tracker leaves the plan a function of the tracker alone, the same in a fresh session as in the one that recorded it. Re-invoking the skill continues an interrupted run rather than restarting it, and there is no resume flag to remember or forget. An interruption — the machine slept, the session was killed, the laptop closed — costs the tickets that were left rather than the ones that were built: what a run recorded is on the tickets themselves, so a fresh session reads a finished ticket as finished exactly as the session that closed it did, and the ticket the run was on when it stopped is picked up again rather than left standing as taken. That last part is what a claim alone cannot give. The claim is the tracker's own assignment relation, and a run of yours that stopped mid-ticket leaves the same login on it as a second run you started in parallel does — so without something more the ticket reads as somebody else's and the interrupted work goes nowhere. A run therefore keeps a note of what it has claimed in whatever per-session scratch directory the harness provides, passed to the engine as `--state-dir` on every verb, and a claim that note accounts for is its own to resume while every other claim is left alone. The note is remembered and never relied on: its absence — a new session, a cleared scratch directory, a machine restart, or a harness with no such directory to offer — is not an error, and the run rebuilds what it needs from the tracker and the branch and reaches the same account as the session that did the work. The plan says which tickets it is resuming, and both the note and the report name the commit the run's work sits on top of — read off the branch every time rather than out of the note — so a night reads as one diff from there to the head of the branch. ADR-0052 records that decision and what it costs: a run rebuilding its state cannot tell an interrupted claim of yours from one a run you started in parallel is holding right now, a login being all either leaves behind. The run is also aimed rather than always taking the whole tracker. Typed bare it works every open ticket carrying the label, as before; name a ticket and it works that one alone, so a single ticket is picked up without replaying the graph; name a spec and it works that spec's children, so tickets from an unrelated effort in the same tracker are neither planned nor touched. Which of the two a reference named is the tracker's answer and not the agent's reading of it: a reference the tracker files children under is a spec, and a spec is never itself built even where it carries the label, because what has children is the shape of other work rather than work; where the tracker files none, a ticket naming it as its parent settles it, that being the other way the ticket breakdown writes the relation and the same relation-then-body order every edge is read in. Anything else the tracker can answer for is a ticket. A reference nothing can resolve — a number the tracker does not know, something that is not a number, one written in another tracker's `owner/repo#number` terms, or two references where a run has one scope — is named as such and nothing is started, because dropping it would work the whole tracker under an argument that asked for part of it and picking a reading would work tickets nobody named. The dry run reads the run you aimed, and so does the report, which accounts for what you named rather than for a tracker the run never had. ADR-0053 records what a scope does not do: it narrows the set the same questions are asked of and changes no rule about any ticket in it. A named ticket still waits for the work that blocks it rather than being built on top of code that does not exist, and a ticket whose outcome a run has already recorded is still settled — to build it afresh you clear that outcome on the ticket, one gesture where the outcome lives and where you are already looking, rather than through a flag whose meaning has to be remembered. Relaxing either rule for a named ticket would make the rules a function of how the run was started, and both would fail quietly rather than loudly. The run is no longer one ticket at a time either. `--at-once` caps how many tickets are built at the same time, so concurrent test suites do not overload the machine and fail for the wrong reason, and the tickets that are workable now are worked together up to that ceiling rather than one after another — a ticket never waits on an unrelated ticket, and a run is never slower than its graph requires. The ceiling carries the isolation decision with it, because isolation is not an independent choice: above one, each ticket is built in a working tree of its own, on a branch of its own, cut from where the run branch stands and kept under the repository's own git directory, so the developer's working tree is exactly as they left it and `git status` says nothing about a run in progress; at exactly one, nothing is isolated and nothing is merged, which is the behaviour already delivered and what makes a small run cost no integration work at all. ADR-0054 records that decision and why a second flag for isolation would only ever be answered one way. Work is integrated at each wave boundary rather than at the end, because a ticket in a later wave is blocked by one in an earlier wave and therefore builds on that code: each verified ticket is merged into the run branch as its wave completes, and the project's full verification then runs once on the branch as it then stands, which is the only place two tickets that pass alone and fail together are caught. A failure there stops the run rather than spending the remaining hours building on broken code, and the tickets it never attempted are named in the report under never on the frontier rather than dropped. A merged ticket's working tree and branch are taken away and a failed or conflicted ticket's are kept, so the machine ends tidy except for the failures, which stay inspectable — and the report says where each one stands. A collision at the merge leaves the run branch exactly as it was, and is repaired before it is reported, because two tickets that both added an import should not cost a full rebuild: the run branch is merged into the losing ticket's own branch and settled there, so the branch the developer comes back to never carries a resolution nobody has checked, and a second subagent that did not make that resolution verifies it against both tickets' acceptance criteria — the way a repair fails quietly being to keep one ticket's criteria by dropping the other's. On a pass the ticket merges and closes as any other does, its branch now carrying the very commits it collided with, so it cannot collide again. Where it does not verify, the repair is thrown away with the working tree that holds it and the ticket is built once more from nothing on top of the work it collided with, which is code somebody meant rather than a stitched-together guess. That rebuild is the only rerun the run performs and happens at most once per ticket, so a collision that keeps coming back is recorded rather than built through the night; nobody is asked to resolve anything mid-run. A collision neither the repair nor the rebuild settled is recorded conflicted and reported with the ticket it collided with, that pair naming a blocking edge the ticket breakdown was missing, which is how one run improves the next one. ADR-0055 records why the repair is settled on the losing ticket's branch rather than on the run branch, and why a rebuild is the one exception to a failed ticket never being retried. Nothing is pushed and the default branch is not modified, which the merge refuses again on its own account rather than trusting the plan that came before it.

Help now says so rather than swallowing a flag it has no meaning for: `/kntnt help --yes` is told the verb takes no flags, instead of printing the page as though the flag had been honoured, because a flag accepted and ignored is what teaches that flags sometimes do nothing. The line the surface now draws is between the script and the grammar — the parser stays permissive so a flag the agent forwards on its own can never be the thing that breaks a run, while the pages state what each verb actually takes. `--help` and `-h` are untouched: they are how help is reached, not flags handed to it.

### Removed

- `/kntnt help <skill>` is withdrawn; `/kntnt help <command>` and bare `/kntnt` are unchanged. It required remembering that a skill had arrived through this collection, which is exactly the fact a user should not have to hold — and the two things it was actually used for both have better routes now. Reading about a skill you have is `/<skill> --help`, answered by the skill itself whichever collection it came from. Reading about one you do not have is `/kntnt select`, which is where that decision gets made anyway. A second way to the same text is a second thing to keep true, and this one asked the wrong question of the person typing it. The manager documents its own verbs and no skill; a name it does not document is refused with both routes named, so nobody is left holding a command that no longer answers. Nothing has to be done on your machine: `/kntnt update` places the new files. Architecture Decision Record 0044 states the rule.
- `/kntnt status`, `/kntnt enable`, and `/kntnt disable` are withdrawn, and `/kntnt select` is all three of them. Their steps files and their manpages go with them, so `/kntnt help status` is an error rather than a page describing a verb that no longer answers; nothing has to be done on your machine, since `/kntnt update` places the new files. What is lost with Status is the union view — what applies in this working directory, global and project merged into one report — and it is given up deliberately: a list you answer has to be one layer's, or an answer would have to say which layer it meant, and the project layer cannot subtract from global anyway. What is lost with Enable and Disable is the transcription step and nothing else. A skill that refuses for want of another skill of this collection now names Select as the way to get it, rather than a verb that is no longer there.

### Fixed

- `--dry-run` in a project now previews the run it stands in for. The temporary home it runs against holds both layers where the layer being previewed is a project, so a skill that needs another one you already have globally is no longer offered a second copy: until now the preview looked at a machine with nothing on it, and reported placing dependencies the real run knows better than to place — and every dependency judgment the preview made, `unsatisfied` included, was read off that same empty global layer. Seeing it is not touching it: the global directories are copied into the temporary home like the project's own, and nothing outside it moves. A run previewing the global layer still seeds global alone, because a global run reads no project, and a directory the real run never looked in has no business being there. Architecture Decision Record 0042 carries the rule the temporary home is seeded by.
- `/kntnt update` now reports the run it actually made when the transport refuses a skill. Until now such a refusal ended the command with an error and no report at all, so a skill the collection had withdrawn could be deleted from your machine with nothing to say it had happened, and the new catalog entry the same run had just told you about was never offered again — the copy of the catalog it compares against had already been overwritten, and that difference is the whole of what makes an entry new. The copy is now written after the work instead of before it, and held back only where a new entry the run was told to enable did not land, so a refused refresh or a refused withdrawal still advances it: those are found again by the digest and by the disk, and freezing the copy for their sake would only leave the fallback describing an older collection than the one the origin just answered with. A refused placement is reported as a skill that did not change, with the directories to look in, and the run still exits non-zero.
- A damaged copy of the catalog stored beside the manager no longer takes every command down with a traceback. It is read as no copy at all — a run with nothing to compare against reports nothing new, and one that can reach the collection carries on as though the copy had never been there — and the file is now written in one move rather than in place, so an interrupted update cannot leave half of it behind. Until now a snapshot truncated by an interrupted run made every verb fail with a Python traceback, including the `/kntnt update` that would have replaced the file, and the only way out was to delete it by hand. The path table the manager ships beside itself was read the same unguarded way and now fails with the manager's own message naming the file, since that one has no fallback to fall back to.
- A catalog the origin serves but cannot be parsed is reported rather than thrown. It used to reach the user as a Python traceback when the origin was a checked-out collection, since only the network read was guarded — and as *could not be fetched* when it came over HTTP, which sends you looking for a connection problem that is not there. Both now say the catalog at the origin is corrupt, and every verb still falls back to the copy stored beside the manager, as it does for an origin that cannot be reached at all. How the origin is addressed — the local path, the raw.githubusercontent URL, the pair of failure messages — now lives in one place that both the catalog and a skill's manpage are read through, so the two cannot drift apart.
- `/kntnt uninstall --project` now says why it is refused. The flag has never been accepted there — uninstall clears this machine, and a working directory's copies are checked into that repository and stay — but the refusal came from the argument parser and read `unrecognized arguments`, which reports that a flag is unknown where what the user has to learn is what the verb would have done. It is refused ahead of the parser now, in the verb's own terms, so the message names the machine it clears and the project it never reaches rather than leaving that to be inferred from a usage dump.

## [0.7.0] – 2026-08-18

### Added

- `/kntnt uninstall` — take this collection off this machine in one gesture. It removes every catalog skill enabled globally from every harness present in your home directory, and then the manager itself, last and through the transport, so your harness's own uninstall has nothing left to do. The manager goes only where everything else really left — a run that leaves a skill behind keeps `kntnt`, since it is the one verb that could still remove it — so `kntnt` among the confirmed removals is the whole report. Installing was one command and removing was none: the behaviour existed, but only as a side effect of dropping a harness from a list that has since been retired, and uninstalling by hand meant working out which directories held what. It takes no `--project`, and that is the decision rather than an omission: a skill in a working directory is checked into that repository and travels with it, so whether it stays is that project's decision — those copies are never touched, and the report says so rather than letting anyone believe the machine is clean while a repository still carries them. `--yes` is the gate, as on Disable. What it removes is what the catalog names, so the report says whether that list came from the collection or from the stored copy — the usual remedy of running it again is only available while the manager is still installed. Architecture Decision Record 0040 states the rule and the two things that follow from a manager deleting itself, and the Collection term *Uninstall* names the verb.
- Tests that pin the release version-bump: a nested JSON `"version"` must not be rewritten instead of the top-level one, a TOML `version_scheme` must not be read as the version, and a failed bump must write nothing.
- CI on push to `main` and on every pull request: ruff, mypy, and pytest. Tool settings live in `pyproject.toml`.

### Changed

- The Manager stops asking which Harnesses to target and stops recording an answer. Enable, Disable, and Update work out where to write on every run: every Harness with a home in the layer being acted on — `~/.claude`, `~/.config/opencode` and their like for Global, `.claude`, `.crush` and theirs for a Project. A Harness installed after an earlier Enable is reached by the next Update with nothing to configure in between, and every call to the transport names the full set rather than a subset. With no Harness detected, the shared `.agents/skills` directory alone is written to — never a directory for a Harness that is not installed. In the Project layer a Harness whose skills directory is not hidden (`skills`, `data/skills`) is not detected at all, because that name belongs to the repository as readily as to a Harness. What is lost, and was weighed: there is no longer a way to keep the collection out of one Harness you have; the remaining control is to not Enable the skill at all. Architecture Decision Record 0035 states the rule and its boundary, 0005 is rewritten now that it is trivially true, and 0014 is marked retired. The new record is numbered 0035 rather than 0031 because 0031–0034 were spent on `plan` and `execute`; a withdrawn number is not reissued, or a reference written against the old release would silently point at something else.
- Status reads `--project` like every other verb. Bare, it reports Global: every Catalog skill with its state on this machine, Disabled ones included. With `--project` it reports the Effective set for the working directory — everything Enabled in Global plus everything Enabled in this Project — and each skill says whether it comes from Global, the Project, or both; a skill Enabled in neither is left out, because it does not apply here. `--project=off` is the bare form, as everywhere else. Naming skills narrows either form and changes nothing else. Until now Status ignored the flag and reported both layers in two columns, which made it the collection's one inconsistent verb. The payload loses its per-layer `global` and `project` fields for one `state` per skill, a `source` in the flag form, and a `reports` field naming which of the two questions was answered — *what does this machine have* or *what applies here* — so no reader has to guess which report it is holding. Architecture Decision Record 0038 states the rule and why the flag form reports Effective rather than the Project layer alone; 0004 is corrected where it claimed Status always reports both layers.
- `status`, and every plan and apply payload, report the `directories` they act on instead of a list of Harnesses. There is no longer a list to report. Status names only the layers its report covers, so the bare form names Global alone.
- The README no longer names collections this one depends on. It listed four as essential while every Catalog entry declared `"externals": []`, and nothing in the repository referred to any of them — `plan` and `execute` had been the only skills ever to declare an External. The section is now one list of recommendations, offered as a courtesy. A skill that genuinely needs another collection declares it and says so when it is run, which is where a dependency belongs and where it cannot drift.

### Removed

- `/kntnt setup` and the Harness list it wrote. The subcommand, its skill body, its `--harness` arguments, the file under `~/.config/kntnt/`, the rebuild that reconstructed it, and the *Harness list is unsatisfied* failure state are all gone, along with the Collection term for the list. Nothing needs deleting on your machine: the stale `harnesses.json` is simply never read again. The Collection term *Detected Harness* replaces it.
- `plan` and `execute`, added in 0.6.0, are withdrawn. The premise — that work is best carried from Ticket to code through a file under `plans/` written by one skill and built unattended by another — did not hold, and a skill that does not earn its place is better removed than kept. `plans/`, Architecture Decision Records 0031–0034, and the Collection terms *Ticket*, *Plan*, *Land*, and *Drift* go with them. If either is Enabled on your machine, `/kntnt update` deletes it for you — see the first entry under *Fixed*; nothing has to be removed by hand. The six improvements below came out of that experiment and stand on their own.

### Fixed

- A skill the collection has withdrawn now leaves the disk. Update fetches the Catalog before it decides anything, so only what the current Catalog still carries is refreshed and every name that has left it is deleted from the layer being applied — through the same removal Disable uses, and without asking, because a withdrawn skill can no longer be updated, supported, or reached by any other command. Each one is reported alongside the new entries: `removed` now names the skill and what the disk showed — `removed` where the files are gone, `failed` with the directories its files survive in. A failure belongs to that skill and not to the run, so the rest of the refresh still happens and the report is still printed. The `--yes` gate Disable requires does not apply here: that gate stands in for a question, and this deletion asks none. Until now Update resolved its work from the Catalog it was about to replace, so a withdrawn skill was still Enabled, still in the refresh list, and still asked of a transport whose source no longer carried it: the run died with the transport's raw error and no JSON at all, and the files stayed where Disable refused the name and Status no longer listed it (issue #5). Architecture Decision Record 0037 states the rule and its asymmetry with 0007, and the Collection term *Withdrawn* names it.
- Update works out what has been withdrawn by looking at the disk instead of at the copy of the catalog stored beside the manager. A skill installed from this collection carries a `metadata.kntnt` block in its own frontmatter, so one that carries it, sits in the layer being applied, and is not in the catalog the collection answers with is one the collection has withdrawn — and it is removed, whatever any local file remembers. Until now the withdrawn set was the difference between the stored copy and the collection, and that copy is a sidecar of the manager: any run of the transport that re-copies `kntnt` replaces it, including a run of Update that refreshed it and then died, and including `npx skills update` invoked by hand. Once it had stopped naming a skill, nothing could establish the skill was ever ours, the difference was empty forever, and the files stayed where no command of this collection could reach them (issue #20). Machines left in that state — `plan` or `execute` on disk after the catalog had already moved past them — are recovered by one `/kntnt update`, with nothing to remove by hand. Two things the sweep never touches: `kntnt` itself, which is no catalog entry, and any skill without the marker, so another collection's skills and your own are left exactly as they are. Where the collection cannot be reached nothing is deleted at all — a stale list does not get to decide which files go — and `catalog_refreshed: false` says so. Reading a skill file the sweep cannot decode, or has no permission to open, answers *not ours* rather than ending the run. The `absent` verdict is gone from `removed`: a withdrawn skill this layer never held is not reported, because there was nothing here to remove. Catalog generation now refuses a skill whose frontmatter carries no `metadata.kntnt` block, since a skill shipped without the marker could never be swept. Architecture Decision Record 0037 is amended with the rule and with why a diff cannot carry it, and the Collection term *Withdrawn* says how one is found.
- Status and Enable read the Catalog from the collection instead of from the snapshot that shipped beside the Manager. A skill published upstream is listed the next time Status runs — Disabled, as ADR-0007 requires — and can be Enabled in that same invocation, with no `/kntnt update` in between; a skill the collection has withdrawn stops being listed at all. Until now the list was replaced only by Update, so it answered *what did the collection contain when this machine last updated*, and a user had no reason to run the one command that would have told them otherwise: an installation still on 0.6.0's snapshot offered `execute` and `plan` as though they could be Enabled, months after they had left the repository (issue #3). Where the collection cannot be reached the verb still completes from the stored copy and says that it did — `status` carries `catalog_refreshed`, the boolean Update already reports, and its skill body now says the list may be stale rather than presenting it as current. Update remains the only command that replaces the stored copy, because it is the difference between that copy and the collection that tells a new skill from a withdrawn one. Architecture Decision Record 0039 states the rule and why the write stays where it is, and the Collection term *Catalog* names it.
- Enable, Disable, and Update no longer report the plan they handed to the transport as the outcome. Each one reads the disk afterwards — the same presence test Status decides Enabled with, in the same layer and the same directories — and reports what it finds: `intended` is what the verb set out to do, `confirmed` what the disk showed, and `failed` the rest, each entry naming the skill and the directories that contradict it. Anything in `failed` exits non-zero, including a run where other skills succeeded, and the payload is still printed so the user learns which skill and where. This replaces the `changed` list of Enable and Disable and the `refreshed` list of Update. A transport that removes nothing and exits 0 used to be indistinguishable from one that did the work — that is how a Disable of two skills reported both as changed and left both on disk (issue #7) — and it is now a legible error. Architecture Decision Record 0036 states the rule.
- Release version bump now reads and writes by one rule per format: the top-level JSON `"version"`, and `[project]` / `[tool.poetry]` in TOML. A file that cannot be rewritten unambiguously aborts the whole bump so nothing is left half-written.
- `git status` paths in the commit plan are no longer C-quoted: porcelain is read with NUL separators, so a file named `skäl.md` is shown as itself.
- Catalog generation refuses a skill whose frontmatter `name` is not its directory, or whose description is empty or a YAML block-scalar indicator the parser cannot read.
- `CONTRIBUTING.md` now names this Collection, points at `skills/<category>/<skill>/scripts/`, and lists the same four checks CI runs.

## [0.6.0] – 2026-08-17

### Added

- `plan` — turn Tickets, or a design settled in conversation, into Plans under `plans/`. `/plan #12 #17` plans those Tickets whatever labels they carry, `/plan "<description>"` plans work with no Ticket behind it, and bare `/plan` shows a picker of the open `ready-for-agent` Tickets with the conversation's settled design as its first row. Drift is checked once against the run's base, after which the invariant that `HEAD` stands where the run left it is what separates the run's own commits from a third party's. A blocked Plan is set aside with everything that depends on it. It commits and stops: no push, no tag, no release.
- Architecture Decision Records 0031 (Plans are written by one skill and built by another), 0032 (Land each approved Plan before the next one starts), 0033 (Drift is checked once, before the run), and 0034 (an unattended skill asks only yes or no), and the Collection terms *Land* and *Drift*.
- The Collection terms *Ticket* and *Plan*. A Ticket is a unit of work in the issue tracker, named so that no skill is bound to one tracker's own vocabulary; a Plan is a file under `plans/` describing one unit of work, self-contained enough that an agent with no other context can carry it out.
- `plans/` — six implementation plans and their index, from an audit of the two Python engines. Nothing is fixed yet; the plans describe the work. They cover a version bump that can rewrite a nested `"version"` field instead of the real one and still report success, `git status` output parsed so that any path with a non-ASCII byte reaches the user C-quoted, the absent continuous integration that would keep the passing tests, linter, and type checker passing, and Catalog generation accepting an entry whose name or description cannot do its job.

### Fixed

- An owned integration converges on the moments its owner wants, so an owner that narrows that set is no longer told the write it just made did not take. `install` visited only the moments it was asked for and then counted the owner's entries across every moment, so a machine reconverged to a narrower capture — four Claude Code moments down to two, three Codex moments down to one — met `failed` with *the integration is not on disk after writing*, the opposite of what had happened, while the stale entries stayed exactly where they were and only `remove-integrations` followed by `install-integrations` by hand would clear them. Every moment the Harness's own file actually holds is now swept, a hand-edited entry at a moment this collection never installs at included, so an owner ends up holding exactly the moments it asks for and no state with more entries than wanted outlives an install; an event key emptied of everything goes, and another owner's entries at a moment being cleared are left as they were. What was cleared is named in a `removed` key of the record's own, which `fold` carries across a folded record, rather than in `detail`, where a sentence on an installed record already means *present and not yet active* to every reader of these records. `health` given a Harness holding a different number of entries than the owner wants now names the moments carrying an entry and the moments wanted, in place of a null detail or a claim about a file it has just read.

- `remove-integrations --harness=<name>` clears that Harness and leaves the others as they were. All three scripts answering the Manager's seam accepted the flag for installation and discarded it for removal, so `capture.py remove-integrations --harness=codex` took the owner's entries out of Claude Code and OpenCode as well and reported having done so — a caller reading the two seam words as symmetric lost an integration it never named. Naming no Harness still means every supported one, which is the Manager's own call, a Harness a Feature does not serve is reported as its install already reports it, and `docs/rules/skills.md` states what each of the two words takes instead of saying both are asked once per Detected Harness.

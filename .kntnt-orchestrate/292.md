Under `## [Unreleased]`, in `### Changed`:

- `/orchestrate` classifies each ticket into one of the eight Work Kinds when it routes it, instead of filing every building role as `implement` and every wave fix as `mechanical`. A ticket that rewrites a Skill's prose, one that decides a schema and one that fixes a failing test were routed and measured as the same job, and the eight kinds exist for the one property that tells them apart: how much intelligence the work needs. On 2026-09-05 eight of nine routed verdicts failed on `SKILL.md` and wording work — evidence pooled under one kind cannot tell that apart from the code the same seat handles well, and a selection made from it cannot either. The orchestrating session has read every body and thread before it routes, so that is where the classification is made: it names the kind on each building request — `build-<n>:<kind>`, and again on an amend, a repair and a rebuild, none of which inherits it — while a wave fix stays `mechanical` and takes none, its finding already naming the change. The engine refuses a building request that names no kind rather than guessing one, being unable to read a ticket at all. The vocabulary reaches the session through the plan rather than through Model Selector's private data: `selection.py --kinds` prints the eight kinds with the sentence that tells each from the others, `plan` carries them as `kinds`, and the run report renders the kind beside every routed decision.

CHANGELOG.md

### Changed

- Model Selector's `capture` now follows the Skill's own Enabled state and asks for nothing beyond it. Enabling the Skill through the Manager installs this feature's owned lifecycle integration into every supported Detected Harness of the Global layer, at the same seams — `add_skills` and `refresh_outcome`, reached from `select` and `update` — that already place and refresh a Skill's files: a Skill declaring `metadata.kntnt.integrations` now answers a second word, `install-integrations`, the mirror of `remove-integrations`, and installing twice changes nothing. Disabling the Skill removes every owned entry exactly as before. A Project-layer Enable installs no integration and the Manager's report says so in one line, because an owned entry is keyed by owner inside a Harness's own configuration and a Global and a Project Enable of the same Skill would write and remove one another's single entry. Only a Harness the Collection Library has an adapter for is ever attempted; the rest of a Detected-Harness list — seventy-odd of the seventy-six `harness-paths.json` now names — is reported as a single count naming the supported set rather than one row each. What remained of the `capture` command — `--on`, `--off`, `--status`, `--harness=<name>`, the consent statement, and `help/capture.md` — is gone from the Skill's body, help, frontmatter `argument-hint`, and argument grammar; `/model-selector status` gains a section reporting integration presence per Harness this collection has an adapter for and the capture store's size in bytes, staying read-only. No Seat is supplied at installation any more — the `--seat` argument, the configured-seat fallback, and the `seat` key in the capture configuration are gone, because the Seat is read from the Harness's own record of the finished session. The disclosure of what Enabling installs and retains, and what Disabling removes, moved to this Skill's own `help.md`, read in full before Select answers (ADR-0160, superseding ADR-0090's opt-in paragraph).

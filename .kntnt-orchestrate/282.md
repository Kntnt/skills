### Fixed

- An Update whose Feature re-convergence failed says so. A refreshed Manager is a refreshed Feature — the script a Harness's hook table names and the prose a Feature's block carries both come from the tree the run has just replaced — so `apply update` re-converges every Enabled Feature and emits what became of each one under a `features` key of its own. `skills/kntnt/steps/update.md` never told the agent to read that key: an agent following the steps exactly reported the run off the keys beside it, which answer for the Skills alone, so a Feature whose integrations did not come back was reported to nobody, and because the exit code is the Skills' too, the command returned zero and the user was told the run had succeeded. The steps page now carries a step of its own for it, placed between the Skills outcome and the Harness Integrations report, in the order `steps/select.md` already reads its payload in: a Feature's `intended`, `confirmed` and `failed` are read from `features` and never from the keys beside it, a non-empty `failed` names the Feature and the `harnesses` it was asked about and the run is not called clean whatever the exit code says, a `held` entry names the setting of the user's own that holds the Feature and says that `/kntnt select` with that row confirmed is what replaces it, and a `note` that is not null tells a user who ran Update in a project that their Features were not touched there rather than leaving them believing they were refreshed. The integration records the same key carries are left to the integrations step, which already reads them.

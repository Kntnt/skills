CHANGELOG.md

- Codex and OpenCode integrations are now verified against what those Harnesses actually read rather than assumed from a sibling's. Codex's own `hooks.json` — confirmed live against the installed binary (`codex app-server`, `initialize` + `hooks/list`) — turns out to accept the same PascalCase event names (`SessionStart`, `Stop`, `SessionEnd`) and the same nested matcher-group entry Claude Code's `settings.json` does; the camelCase, flat `handlerType`/`command` shape a first pass at this adapter wrote instead belongs to the app-server protocol's own runtime view, not to the config file, and was silently never read. What Codex actually needed was its trust review handled: it holds a newly written hook back from running until a human clears it, and installation reported success regardless. A Codex integration this collection writes correctly is now reported `gated` — present, not yet active, naming what the user does to clear the review — rather than `healthy`, and this collection forges no trust decision or trust record on the user's behalf. The OpenCode plugin now redirects its event onto the invoked command's own standard input instead of running it with only `--event=<type>` and no payload, which carries the session identity OpenCode nests inside the event and, verified directly against Bun's shell, keeps the child from inheriting the session's own standard input — the one thing that let a fail-open hook reading standard input to end-of-file block on it (ADR-0157).

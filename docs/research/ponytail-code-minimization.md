# Ponytail and smaller generated implementations

## Question and scope

Does Ponytail reduce code mainly through one Skill, and could this Collection adopt that mechanism without importing the entire project?

Inspected on 2026-09-19 at commit [`e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156`](https://github.com/DietrichGebert/ponytail/commit/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156), release 4.10.0. This analyzes source and published measurements, not an independent benchmark. No upstream scripts were executed or Collection contracts changed.

## Finding

The hypothesis is substantially correct. The code-minimization policy lives in one ordinary [`skills/ponytail/SKILL.md`](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/skills/ponytail/SKILL.md): 120 lines and 6,637 bytes in a repository with 166 tracked files. A compact instruction-only counterpart, [`AGENTS.md`](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/AGENTS.md), is 32 lines and 2,593 bytes. These counts were taken from the pinned checkout, including frontmatter and blank lines where present.

There is no code-reduction engine hidden in the runtime. The shared [instruction builder](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/hooks/ponytail-instructions.js) reads that Skill, removes frontmatter and examples for inactive intensity levels, and returns the remaining prose. The agent itself chooses and writes the smaller implementation. However, some scripts are directly relevant: they make the policy reach sessions and subagents reliably. Their contribution to delivery must not be confused with an algorithm that transforms generated code.

## What changes the implementation

The Skill gives the agent an ordered decision procedure before implementation: establish whether the current requirement needs new code; search the existing codebase for a solution; try the standard library; try native platform facilities; try an already installed dependency; then consider a short direct implementation. It tells the agent to stop at the first adequate choice instead of designing additional layers. Concrete examples make that procedure actionable: a browser date input can satisfy a date-selection requirement without a custom component and its supporting dependencies. This is avoided implementation, rather than merely compressed formatting. The full policy also rejects speculative abstractions and configuration. [Source: core Skill](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/skills/ponytail/SKILL.md).

The qualification is as important as the ladder. The current Skill requires reading affected code and tracing the actual flow first; for bug fixes it specifically asks the agent to find every caller and repair the shared cause. It preserves explicitly requested behavior, validation at trust boundaries, handling that prevents data loss, security, accessibility, and needed hardware calibration. This limits the tempting but invalid interpretation that a smaller incomplete patch counts as success. [Source: core Skill](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/skills/ponytail/SKILL.md).

Upstream's later [comprehension experiment](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/results/2026-06-22-issue-245-217-comprehension.md) reports that an operational instruction to find callers improved root-cause fixes where a general instruction to understand the flow did not. Its separate reuse probes showed both baseline and Ponytail reusing the existing helper, so that experiment did not demonstrate an additional benefit from the reuse rung. These are useful clues about instruction design, with the limits of small, author-run experiments.

The policy also contains choices that should not be copied wholesale: a preference for one-liners and the fewest files, strong limits on explanation, a single runnable check for nontrivial logic, and an `ultra` level that challenges requested scope. These are independent policy decisions, not technical prerequisites for preferring existing facilities. [Source: core Skill](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/skills/ponytail/SKILL.md).

## What the surrounding repository does

| Part | Role in the outcome |
| --- | --- |
| Core Skill and compact rule copies | The behavioral policy the model follows. |
| Lifecycle hooks and runtime/configuration helpers | Inject policy, track active intensity, propagate it to supported subagents, and handle host differences. |
| Platform manifests, adapters, and generated copies | Distribute or expose the policy through different hosts. |
| Review, audit, debt, gain, and help Skills | Separate user workflows; the core implementation policy does not call them to generate code. |
| Benchmarks, tests, examples, and maintenance scripts | Measure or maintain the product; they do not minimize a user's implementation at runtime. |

The first two rows are linked explicitly in the [activation hook](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/hooks/ponytail-activate.js), [subagent hook](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/hooks/ponytail-subagent.js), and [hook configuration](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/hooks/claude-codex-hooks.json). The configuration declares session-start, subagent-start, and user-prompt handlers. Ordinary prompt handling is not unconditional reinjection on every host; the [mode tracker](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/hooks/ponytail-mode-tracker.js) changes mode and has specific behavior for Qoder and Cursor. A bare Skill's persistence instruction is therefore not equivalent to a verified host-level activation mechanism.

The [MCP server](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/ponytail-mcp/index.js) retrieves the same instructions; the [review](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/skills/ponytail-review/SKILL.md) and [audit](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/skills/ponytail-audit/SKILL.md) Skills report simplifications without applying them. Neither is a code optimizer.

## What the published reduction establishes

The [June 18 agentic report](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/results/2026-06-18-agentic.md) compares real Claude Code sessions using Haiku 4.5 on 12 feature tasks in a pinned FastAPI/React template, with four runs per task and treatment. The reported date-picker means are 404 added lines for baseline and 23 for Ponytail; color picker is 287 versus 23; title search is 44 versus 44. The reduction concentrates where native facilities can replace substantial custom implementations.

The headline approximately 54% reduction is consistent with the ratio of sums of the published task means: 2,217 baseline lines versus 1,015 Ponytail lines, a 54.2% decrease. It is not the arithmetic mean of each task's percentage reduction; that is approximately 35.4% using the rounded table values. Larger baseline implementations contribute more to the aggregate. These calculations reproduce the table's arithmetic, not the underlying runs. [Source data: June 18 report](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/results/2026-06-18-agentic.md).

Several limits matter before interpreting this as equivalent functionality for less code:

- **The old 80–94% headline is not the current aggregate.** Upstream acknowledges that its earlier single-completion baseline included conversational material and inflated the gap. [June 18 report](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/results/2026-06-18-agentic.md).
- **Feature completeness is not established by the line counter.** In the current harness, fixture tasks receive `correct = 1` when added source lines exceed zero, and `safe = 1` unconditionally. Bash execution is disabled and agents are told not to run servers, databases, or browser verification. A separate [completeness judge](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/agentic/complete.py) exists, but its scores are not published alongside the headline in the June 18 report. [Scoring and execution source](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/agentic/run.py).
- **The metric is added source lines, not all created code or net maintenance cost.** The diff scorer ignores deletions, excludes recognized tests, lockfiles and generated files, and includes source comments. Test classification is a naming heuristic. [Metric implementation](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/agentic/run.py).
- **The safety result is a separate small experiment.** The report's 100% means 20/20 checks across five security tasks; the short YAGNI/one-liner prompt passed 19/20. It is evidence about those checks, not a security guarantee for the feature implementations. [June 18 report](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/results/2026-06-18-agentic.md).
- **The benchmark does not isolate delivery from wording.** Ponytail is loaded as a plugin, while the short control is appended prompt text. There is no reported comparison between identical complete rules delivered with and without the hooks. The current runner resolves an installed plugin directory, defaulting to an available cache version rather than pinning the measured policy to the source checkout. [Runner](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/agentic/run.py).
- **Reproduction requires new work.** Raw agentic workspaces and results are not tracked in the inspected tree; the runs directory is [explicitly ignored](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/.gitignore). The headline covers one model and small samples, with four timed-out feature cells disclosed. The current policy also includes changes made after that report. [Report](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/results/2026-06-18-agentic.md), [later policy changes](https://github.com/DietrichGebert/ponytail/blob/e3ba2aa6f1e6f0bc4d69eb09c9f0d0a93af56156/benchmarks/results/2026-06-22-issue-245-217-comprehension.md).

The evidence supports avoided overbuilding on suitable tasks, not universal reductions, verified completeness for every feature, or equivalence between a smaller policy and the plugin.

## Fit with this Collection

The Collection already requires YAGNI, KISS, reuse without indiscriminate abstraction, appropriate defensive guards, and tracing affected callers in [the general coding standard](../rules/general.md). The useful addition would be a short operational procedure that turns those principles into concrete choices before implementation, particularly checking existing code, standard facilities and native platform behavior. This is an inference from the upstream policy and the local standard, not a measured gain here.

Three deployment scopes should remain distinct:

1. **A trial in this repository:** refine the existing general coding standard in place. Its authority and pointer already exist, so this needs no new Skill, Feature, hook, or duplicate policy.
2. **An explicitly invoked workflow across projects:** a Skill could apply the procedure to a specified task, subject to the Collection's [normal Skill packaging and invocation contract](../rules/skills.md). The minimization behavior can be prose even though that contract requires the shared invocation shim and help surface. Mere availability does not guarantee loading in every coding session.
3. **An opt-in default across supported Harnesses:** a Feature could use the existing [`install_block`, `remove_block`, and `block_health` integration seam](../../skills/kntnt/library/scripts/integrations.py). That seam already owns blocks in Claude's global `CLAUDE.md`, Codex's global `AGENTS.md`, and OpenCode's global `AGENTS.md`. A static policy needs no new lifecycle process simply to exist there. Actual loading and subagent propagation still need verification for the chosen hosts. Feature ownership and Global-only enablement are governed by [the existing rules](../rules/skills.md).

Preserve the Collection's current acceptance criteria, readability, deep-module design and meaningful test requirements. Do not import blanket minimum-file or one-test rules that conflict with them. A pilot should compare completed implementations with the same behavior requirements and checks, reporting source size separately from tests and recording omitted requirements as failures. It should test the short policy against both today's instructions and the full upstream policy before claiming comparable effect.

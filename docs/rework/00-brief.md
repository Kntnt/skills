## Why this rebuild exists

Two problems drive it.

First, `/orchestrate` (`skills/code/orchestrate/`) — the skill that works `ready-for-agent` tickets in dependency waves — has grown into a 45 KB SKILL.md plus a ~4,500-line `run.py`. The bloat is structural, not accidental: builders work directly from raw tickets, so all interpretation, verification-gate resolution, decision-batching, and failure handling must happen at run time, and every one of those needs became a subsystem (frozen routing snapshots, amend counters, a five-state outcome taxonomy with dual bookkeeping, claim management). It works well enough today, which is why the ongoing work on `main` must not be disturbed — but Thomas has decided to replace it and delete it.

Second, the documentation confuses agents even on top-tier models (Opus 5, GPT 5.6). The repo has 80+ ADRs, many superseded by later ones, plus instructions spread across coding standards and other places. Deriving "what currently applies" requires legal archaeology across the pile, and every irrelevant instruction in context dilutes the binding force of the relevant ones. The root fault is the format: an ADR is an immutable historical record answering "why did it become like this?", but the pile is consumed as current law answering "what applies now?". Two incompatible functions live in one format.

## The target: a five-skill pipeline

The rebuild replaces /orchestrate and the planning front ends with five new skills forming one pipeline: `/frame` → `/to-slices` → per ticket `/compile` → `/dispatch` → `/land`. They will live under `skills/code/`. The governing insight: orchestrate's complexity is dispatch-time complexity, and the pipeline moves everything movable to compile time so the runtime part stays small. Do not re-add run-time subsystems that compile-time work makes unnecessary.

The design synthesizes two proven workflows: Matt Pocock's chain (grilling → to-spec → to-tickets → implement: interview-driven, decision-level durable artifacts, TDD at agreed seams) and shadcn's /improve (codebase-driven, self-contained executor plans, cheap executors in isolated worktrees, adversarial tech-lead review). The first moves information from the owner's head into the process; the second moves information from the codebase into the plan. The pipeline does both, plus three couplings neither has: uncertainty routing, just-in-time plan compilation, and test-authorship separation.

### /frame — adaptive front end

Maps a task by running codebase recon in parallel with an interview, routing every open point into one of three bins: codebase-answerable (a recon subagent fetches the answer — never a question to Thomas), technically decidable within the frames (frame decides itself and records the choice in a veto-able decision ledger — never a question to Thomas), or owner-owned (asked). Owner-owned means product behaviour, user experience, priorities, architecture direction, and trade-offs with cost or risk consequences. Questions are asked in frontier rounds with a recommended answer each, phrased as consequences for the owner ("choosing X gives users Y"), never as mechanism, and use established terms or the project's `CONTEXT.md` glossary — no invented vocabulary. Glossary terms and ADRs are written as decisions crystallise (sparingly: a decision earns an ADR only when it is hard to reverse, surprising without context, and the result of a real trade-off). A simple task yields an empty residual and passes straight through — the pipeline degrades gracefully instead of asking the human which steps to skip.

### /to-slices — durable decision layer

Synthesizes the framed understanding into a decision document plus tracer-bullet tickets: narrow vertical slices, each demoable on its own, each sized for a single fresh context window, each declaring its blocking edges. Wide refactors are sequenced expand–contract instead of forced into slices, and a ticket whose subject is a repository-wide invariant declares that it builds alone (rescued from orchestrate's solo-ticket concept). Each ticket carries a seam contract (what behaviour is verified, at which seam) and compilation hints (areas, exemplar patterns) but no code excerpts or line numbers — the durable layer must not rot. One human checkpoint: Thomas approves the breakdown and the blocking edges. Tickets publish to the repo's GitHub Issues.

### /compile — just-in-time plan compilation

Compiles a ticket into a fully self-contained executor plan against the current HEAD: exact files, fresh code excerpts, verification commands, scope boundaries, STOP conditions, machine-checkable done criteria — and the seam tests as finished, runnable files attached to the plan. Because compilation happens at dispatch time, drift between plan and code cannot arise, which deletes orchestrate's whole drift/reconcile apparatus. The plan has two registers: a binding contract (goal, scope, invariants, tests, done criteria, STOP conditions) and an advisory steps appendix — a weak executor follows the steps, a strong executor may ignore them and find its own way inside the contract. When compiling a batch, /compile pre-allocates serial resources (ADR numbers, migration numbers) from one shared counter and emits each plan's footprint: files in scope, files created, serial resources touched. A fresh-context subagent cold-reads every compiled plan before it is accepted. A ticket /compile cannot specify honestly is parked under `needs-info` with the question posted on the ticket; the rest of the batch continues.

### /dispatch — contained execution and integration

Runs compiled plans through cheap executors and lands the result on the branch where the command was given. Reads `skills/kntnt/library/references/delegation-mode.md` as its delegation doctrine — single source of truth, stated in no other words — and routes executors through model-selector's public route interface. The seam tests are the independent checker that doctrine requires, which makes cheap-first escalation safe by construction. Executors work in disposable worktrees forked from the current integration tip and may not modify the seam tests — the tests were authored at compile time, which removes the "executor games its own tests" failure class entirely. Review is the dispatcher's job, done like a tech lead: re-run every done criterion, enforce scope compliance (any out-of-scope file fails review), read the full diff, judge documented deviations on merit and undocumented ones as failures. Verdicts: APPROVE (merge, next), REVISE (max two rounds with the same executor), REBUILD (recompile against the new HEAD, fresh executor, once), PARK (needs a human). Merging is inside the scheduling loop, not a phase after it: approved work merges serially, each merge is verified with that ticket's seam tests plus the repo gate on the combined branch, and the next wave forks from the new tip. Executors never write shared append files (changelog, index); they leave proposed entries as notes and the dispatcher applies them serially (rescued from orchestrate's run-owned append files). A run journal records each ticket's state and holds in-flight work as patches, so worktrees are always disposable and an interrupted run resumes by re-invoking the same command. When a conflict needs Thomas, dispatch finishes everything not blocked by it, then stops with a precise handoff — what merged, what parked, the conflicted worktree left standing deliberately and named, and the exact question; Thomas resolves in the worktree or answers with an instruction, and the same invocation resumes, verifies, merges, and cleans. Exit invariant at completion, machine-checkable: `git worktree list` shows only the main tree(s), no dispatch branches remain, the journal is archived, every selected ticket is landed or explicitly reported parked. There is deliberately no separate /merge skill: merging is coupled to scheduling (fresh-tip forking is the conflict-minimization), unmerged worktrees are a decaying state, and the skill that creates worktrees is the one that removes them.

### /land — knowledge closure

Closes the loop on the tracker and in the docs after code has landed: closes tickets, verifies cheap done criteria on HEAD, refreshes downstream tickets whose assumptions the landed work changed, and — most importantly — harvests: decisions discovered during implementation (a seam that moved, a pattern that proved necessary) are written back as ADRs or glossary updates, so the durable layer compounds. Also absorbs orchestrate's `reconcile`: a ticket completed outside the pipeline is landed the same way, honestly recorded.

### Shared conventions across the five

All five are authored for a top-tier main model: goal, frames (invariants), and interface — never step-by-step recipes; the path stays free inside the frames. All five adopt `skills/kntnt/library/references/tldr-mode.md` as their voice toward Thomas, by file reference so one source governs: speak to the person who owns the outcome, lead with the conclusion, no invented jargon. `/compile`, `/dispatch`, and `/land` share one selection grammar: positional ticket refs (`#1 #2`), bare invocation = every eligible ticket after a yes/no confirmation, `--yes` answers yes; `/dispatch` adds `--at-once=<n>` (default 1, sequential) and `--dry-run` (shows the computed wave plan without starting). Eligibility per skill: compile → labeled ready without a fresh plan; dispatch → fresh plan and all blockers landed; land → merged but not closed, or completed outside the pipeline. Scheduling lives at dispatch runtime and nowhere else: semantic edges are declared in tickets (to-slices), footprints come from compiled plans (compile), and the wave plan is recomputed as verdicts land — a frozen schedule would need orchestrate's whole defensive apparatus. Rule of thumb: tickets are the programs, dispatch is the operating system.

## Orchestrate absorption map

What orchestrate does today and where it goes: `reconcile` → /land. Open-decision batching and `needs-info` parking → /compile (earlier and cheaper). Claims → /dispatch as two lines (assign on start, unassign on park), not a subsystem. Frozen routing snapshot → the journal records each routing decision append-only as it is made; resume reuses recorded decisions. Independent verifier subagent → replaced by something stronger and cheaper: compile-time seam tests plus the dispatcher's review. Five-state outcome taxonomy with dual bookkeeping → three states (landed, parked with reason, stranded); history lives in the journal archive. `--model` / `--deliberation` locks → dispatch flags passed as field-level overrides to route, semantics already defined in the delegation doctrine. Waves, solo tickets, and run-owned append files → rescued as described above. What deliberately dies: `run.py` (goal: no script runtime at all; if a deterministic helper proves necessary it must be small and do one thing), the frozen routing account, the outcome taxonomy, and run-start decision batching.

Deletion criterion for orchestrate: /dispatch has survived at least one real batch with `--at-once=2`, at least one merge conflict, and one pause-and-resume. Then delete `skills/code/orchestrate/` and update the SEE ALSO line in `skills/code/ready-for-agent-check/help.md` (the only cross-reference), plus whatever the Manager's manifest lists.

## The doc reform (phase 1 — precedes the skills)

Separate the two conflated functions. One small living rules document — the only doc agents load by default — where every line is current law phrased as a rule, with a pointer to its ADR for rationale; it is edited, never grown. The ADRs become an immutable, statused archive read on demand, never auto-loaded. Triage each of the 80+ existing ADRs mechanically: still binding and relevant to daily work → one line in the rules doc; still binding but rarely relevant → folded into a consolidation ADR; superseded or dead → deleted (git remembers); never a decision but an instruction → moved to the coding standard, ADR deleted. The consolidation ADRs are few, each explicitly names the ADRs it supersedes, and carries forward only the why-chains still alive. Expect many of the 80 to be how-texts disguised as why-documents; the bar going forward is domain-modeling's three criteria (hard to reverse, surprising without context, a real trade-off). The reform comes first because /compile must be able to inline "what binds here" into every plan cheaply — impossible against an 80-file derivation. Open decisions for phase 1 (settle with Thomas before executing): where the rules doc lives given the existing `docs/agents/` conventions, how many consolidation ADRs, what moves into the coding standard.

## Working conventions on this track

- Everything happens on `rework` in the worktree `../skills-rework`. Nothing rework-related touches `main` except the temporary AGENTS.md section.
- Commit and push to `origin rework` at your own discretion — standing authorization from Thomas (2026-08-25), no approval needed. This doubles as the recovery backstop against accidental local sweeps. Never push `main`.
- Rebuild tickets carry the scope label `rework` (always, never removed) and milestone "Skills 2.0". Ready state is the additional label `rework-ready-for-agent` — ready means both labels present. The other canonical lifecycle labels (`needs-triage`, `needs-info`, `ready-for-human`, `wontfix`) are reused as-is; only `ready-for-agent` has a rework variant, because it is the only label anything auto-sweeps (orchestrate's bare invocation). When creating tickets with `/to-tickets`, explicitly instruct it to apply `rework` + `rework-ready-for-agent` instead of its default `ready-for-agent`.
- Full bidirectional wall: rework sessions never touch `ready-for-agent` tickets or the ongoing work on `main`; ordinary sessions never touch `rework` tickets.
- When a fix that must survive the rebuild lands on `main` (e.g. in tldr or delegation), cherry-pick it to `rework` immediately, while it is fresh.
- Address Thomas from the owner's perspective in the register of `skills/kntnt/library/references/tldr-mode.md`: he owns the code, decides what is built and how the architecture and UX should be; he is technically capable but does not hold implementation state. Ask owner questions, decide technicalities yourself with visible recommended defaults.

## The endgame

When the rebuild is complete, `main` is not merged semantically — it is taken over, conflict-free by construction, with main's history preserved: `git checkout rework && git merge -s ours main -m "Reform tree takes over; main history absorbed" && git checkout main && git merge rework` (fast-forward). The final cleanup ticket then: deletes orchestrate as above, relabels remaining `rework-ready-for-agent` → `ready-for-agent`, drops the `rework` labels, closes the "Skills 2.0" milestone, removes the temporary AGENTS.md section, removes the worktree and branch, and deletes this `docs/rework/` directory.

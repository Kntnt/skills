# Rules — the collection's behaviour

Read before changing what the Manager does, or what any Skill of this collection promises about reaching a machine.

This module covers the collection's own behaviour: how it reaches a machine, what each of the Manager's verbs promises, how Dependencies are answered, how a Skill of this collection routes work it delegates, and the vocabulary those promises are stated in. It is not about the form of a Skill's shipped files, which is `skills.md`, nor about code form, which is `general.md`. A rule governing one Skill's own behaviour needs nothing here — that Skill's shipped documents are where a reader already meets it.

The capitalised terms — Catalog, Digest, Detected Harness, Enabled, Capability, and the rest — are defined in [`CONTEXT.md`](../../CONTEXT.md). That file says what a term means; this module says what is true of it.

The rules whose reasoning is settled in a decision record are named here in a phrase and cited to the record rather than argued again — the record is where the alternatives and their costs live, and a second telling of the argument is a second thing to keep true.

## The transport and the entry point

**The collection orchestrates the Transport rather than replacing it** (ADR-0001). Skill files move through `npx skills`, and the Manager fills only the gaps that leaves: a desired set in Global and in each Project, a report of what the Catalog has gained or lost, and the application of the chosen layer to every Detected Harness. The Manager installs no Dependency and is not a package manager.

**Adding the collection installs the Manager and nothing else** (ADR-0006). The rest of the collection is hidden from ordinary Transport discovery, because a user facing the Transport's picker and Select at once faces two selectors that can disagree. Select is the way a Skill becomes Enabled.

**The Manager is the collection's only namespaced entry point** (ADR-0002). It is the always-enabled Skill named `kntnt`, and its verbs are its subcommands; every other Skill is invoked by its own name — `/commit`, never `/kntnt commit`. A Category groups the rows of Select's list so related Skills are read together (ADR-0015); it is no part of a Skill's name and cannot be Enabled as a set.

**The collection ships Skills, never a Harness's `commands/` files** (ADR-0008). What is portable across every Harness is the Skill; a command file is one Harness's shape, and shipping one would make the collection behave differently depending on where it landed.

**Nothing is installed on the user's behalf** (ADR-0009). Select and Update put this collection's Skill files on disk and nothing more: no External, no binary, no runtime. Where a Dependency is Unsatisfied at use time the Skill does no work and gives the one instruction that satisfies it — check a collection Skill in `/kntnt select`, add an External through the Transport, install a binary with that binary's own command. Auto-installing would take rights the user never granted and would make the Manager the package manager ADR-0001 declines to build.

## Layers and targets

**Global is the default layer and `--project` selects the Project** (ADR-0004, ADR-0038). Every verb reads the flag the same way: absent or `--project=off` means Global, `--project` or `--project=on` means the working directory's Project layer. Global is the desired set that applies on this machine; a Project is a working directory with its own extra set, checked into that repository and travelling with it.

**A Project layer can only add** (ADR-0013). `select --project` unchecks a Skill Enabled in the Project layer and nothing else: a Skill Enabled only in Global has no copy in this layer to remove, and there is no subtractive overlay. The row says the Skill is already Enabled in Global instead, which is also what stops a second copy being Enabled into the repository by accident. The Project form shows the Project layer alone, because every row of a list a user answers must be a row they can change.

**One desired set per layer, never a matrix of Harnesses** (ADR-0005). Every Skill Enabled in a layer is applied to every Harness that layer targets; Project extras are never copied into Global.

**Targets are detected at each invocation and never recorded** (ADR-0035). A Harness is present in a layer when the parent of its skills directory exists — `~/.claude` for Global, `.claude` in the working directory for Project — so a Harness installed after the last run is reached by the next one with no configuration in between. Every call to the Transport names the full set of Detected Harnesses and never a subset, because the Transport cannot clear a shared directory while a Harness that reads it is left out of the call. With nothing detected the target is the shared `.agents/skills` directory alone, never every Harness the Transport knows of. In the Project layer a Harness whose skills directory is not hidden is never detected, its name being indistinguishable from the repository's own content.

**Nothing about where Skills go is remembered** (ADR-0003, ADR-0035). State is the user's remembered choices — which Skills are Enabled in Global and in each Project — and it is a reconstructable cache rather than an authority: a missing or corrupt State is rebuilt from the collection Skills on disk, and rebuilding deletes nothing.

## Disk as truth, and the disk as the report

**Enabled means present on disk in that layer** (ADR-0003). A Harness loads what its skills directory holds, so presence in each Detected Harness's directory for the layer is the whole of the definition, and Disabled is its absence. Select and Update compute the desired set for the targeted layer and apply the delta, so a second run with the same answers writes nothing.

**Partial is a fact about the disk and not a third state** (ADR-0043). A Skill whose files are in some of the layer's Detected Harnesses and missing from others is still Enabled or Disabled: nothing sets Partial, nothing stores it, and no answer of the user's can select it. Select shows such a Skill checked and marks it incomplete, and confirming the list repairs it.

**A change is reported from the disk, never from the plan** (ADR-0036). Every verb that changes what is on disk reads the disk afterwards, using the same presence test Select decides Enabled with, and reports what it finds: `intended` is what the verb set out to do, `confirmed` what the disk then showed, and `failed` the rest, each entry naming the Skill and the directories that contradict it. Any entry in `failed` exits non-zero even where other Skills succeeded, and the payload is emitted anyway, an exit code alone saying nothing about which Skill or which directory. A zero exit from the Transport is not evidence that files moved.

## The Catalog

**The Catalog is the collection's declared list of its Skills, their Dependencies and their Digests, authored in the repository and fetched from it at every invocation** (ADR-0039). A Skill the origin carries and this machine has never seen is listed, Disabled, and can be Enabled in the invocation that first showed it; a Skill the origin has dropped is not listed at all.

**A failed fetch falls back to the stored copy, and the verb says which list it is holding** (ADR-0039). A copy is stored beside the Manager and is what a verb reasons from when the origin cannot be reached; the payload carries `catalog_refreshed` so the report can say so. Only where there is neither an origin nor a stored copy does the fetch's own error stand — there is no Catalog to invent.

**Only Update replaces the stored copy** (ADR-0039). Update tells a new entry from a Withdrawn one by diffing the copy it last stored against what the origin now carries, so a verb that reports rather than changes reasons from the fetched Catalog and does not write it; adopting it would flatten the diff the next Update depends on. An Update with no stored copy has discovered nothing: the fetched list becomes the baseline rather than the whole collection being reported as new.

**The Catalog is resolved once per run and held** (ADR-0039). Every verb reads it many times over, and the origin is asked once.

**A new Catalog entry is reported and offered, never Enabled silently** (ADR-0007). Update names each new entry and asks whether to Enable it; `--yes` answers yes, and the cost of that — an unattended Update placing instructions the user has not read into every Detected Harness — is accepted deliberately in exchange for `--yes` meaning one thing everywhere. What is Enabled is the entry alone: an entry needing a Skill the layer does not hold is Enabled and reported Unsatisfied afterwards rather than dragging its closure in the way Select does.

**A Withdrawn Skill is removed without asking** (ADR-0037). Consent governs what enters the context and not what leaves it, and files no verb of the collection can still reach are not a Skill the user keeps. Update finds one by asking the disk rather than any stored list: a Skill directory in the targeted layer carrying `metadata` keys prefixed `kntnt.` that the current Catalog does not name is Withdrawn, whatever a local file remembers. The Manager is never Withdrawn, being no Catalog entry, and a directory with no marker belongs to another collection or to the user and is not this collection's to remove. Each withdrawn name is reported with what the disk then showed, on the same terms as every other change, and a failure belongs to that Skill rather than to the run, so the refresh still happens and the report still comes out. The sweep runs only where the origin answered: an Update that fell back reports no withdrawals at all, deleting nothing on the strength of a list it could not confirm.

## The Digest, and the word for a mismatch

**Each Catalog entry carries a Digest of that Skill's directory as the collection ships it** (ADR-0041). It is computed over the sorted relative paths and the contents of the files, so a rename, an edit, an added file and a removed file each change it, and it is generated when the Catalog is generated — no release depends on remembering to bump anything and no version number is introduced. The same computation over what is on disk answers the one freshness question the Manager can answer honestly: are these the same files.

**The ignore list is exactly `__pycache__/` and `*.pyc`, applied identically on the producing and the consuming side** (ADR-0041). This is a correctness requirement: disagree by a single artefact and every Skill shipping a script reports itself as Deviating forever.

**A mismatch is Deviating, and never *out of date*** (ADR-0041). The comparison sees two states and no history, so it cannot establish a direction, and outside a lagging Project copy the commonest cause is the user's own edit. Update refreshes what Deviates, and any offer to re-copy says in the same breath that local changes are overwritten.

**A fallback Catalog establishes no freshness verdict** (ADR-0041). Its digests describe the collection as of the last Update, so Select reports nothing as deviating or as current when the list came from the stored copy and offers no refresh on the strength of it, and Update refreshes nothing at all — the files would have to come from the origin the Catalog could not be fetched from.

## What the verbs promise

**Select shows what the collection has and changes it in the same gesture** (ADR-0043). It prints the Catalog grouped by Category, one row per Skill carrying a checkbox that is checked when the Skill is Enabled in the targeted layer, the Skill's one-line description, and any Capability it requires; the user answers in one sentence of plain text and confirms once, and nothing reaches the disk before that. Nothing about a row has to be looked up elsewhere, and any row can be read in full before the list is answered — the Skill's own `help.md` where it is Enabled, the collection's copy of it where it is not — so deciding never requires installing first. It replaced Status, Enable and Disable, and what was lost with them is a transcription step and the union view, both given up deliberately.

**Reading is never a side-effecting act** (ADR-0043). An answer that changes nothing writes nothing — no refresh, no repair, no touching of files to make the disk agree with a list somebody only wanted to look at.

**One verb is not one form** (ADR-0043). `--on=<skill>` and `--off=<skill>` name Skills directly, open no list, and apply a delta, so naming one Skill never silently Disables another. `--yes` opens no list either and Enables nothing that was not already Enabled: it answers the questions that are questions about the disk — refreshing what Deviates, repairing what is incomplete — and never *do you want this Skill*, which there was nobody present to be asked. The asymmetry with Update's `--yes` is intended: the unattended path that can add a Skill is the one the user pointed at the collection's own new entries.

**Update refreshes this collection's Skills and then checks every Dependency again** (ADR-0011). A Skill revision may add, drop, or replace a Dependency, so the gate is re-read after the files move, and an Unsatisfied one is answered as everywhere else in this collection. Without `--project` it applies Global, with `--project` the Project.

**Update re-adds what Deviates, and always the Manager** (ADR-0028). It calls the Transport's `add`, which empties and replaces the whole directory, rather than the Transport's own `update`, which compares `SKILL.md` alone and leaves every sidecar at whatever revision last touched that one file. It hands `add` every Enabled Skill whose files Deviate from its Catalog entry's Digest and leaves the rest alone, so the report says what moved rather than how many Skills are Enabled; the Manager is refreshed every time, being no Catalog entry and having no Digest to compare, and directly, because a call reaching the layer's Detected Harnesses need not reach the copy of the Manager being run. After one refresh, a file removed upstream is gone, a file changed upstream is replaced, and a file added upstream is present.

**Update does not refresh an External** (ADR-0011). An External is a Dependency whose source is another collection, and it is updated with the Transport.

**Uninstall takes this collection off this machine** (ADR-0040). It removes every Catalog Skill Enabled in Global from every Harness detected in the home directory, and then the Manager itself, last, in a Transport call of its own made only where the rest really left — a machine holding Skills with no verb left to remove them is worse off than one whose Manager outlives them by a run. `kntnt` among the confirmed is therefore the whole report. `--yes` is its gate: the verb refuses without it, as `select --off` does (ADR-0029).

**Uninstall has no `--project` form, and that is the decision rather than an omission** (ADR-0040). A Skill in a working directory is checked into that Project and travels with it, so it is never touched and the report says so: a user told the machine is clean, with a repository on it still carrying these Skills, has been told something false about the only thing they can check.

**Uninstall cannot promise completeness against a stale Catalog** (ADR-0040). The set it removes is what the Catalog names, so a run that fell back to the stored copy may leave behind a Skill the collection has since withdrawn; the verb reports which list it worked from, and the usual remedy of running it again is available only while the Manager is still installed.

**Bare `/kntnt` is Help** (ADR-0027). Somebody typing the Manager's name with nothing after it does not yet know what to type next, and a bare name should teach the interface rather than report the machine. Every subcommand is reached by its own name and none by the absence of one, so `/kntnt <command> --help` reaches that command's page directly. Help is not how another Skill's help is reached: a Skill the user has answers its own `--help` forms — what each Skill ships for that is in `skills.md` — and a Skill they do not have yet is read about in Select.

**`--yes` means no question is asked at all** (ADR-0029). Every question that could be answered yes or no is answered yes instead, so every yes/no question in the collection is worded so that *yes* ends it; a question whose yes opens another question has no unattended answer. Where a verb deletes files the user is choosing to delete, the flag is also the gate and the script refuses without it, a script having no way to prompt. Deleting a Withdrawn Skill is not such a choice and is not gated: there is no question to answer, so Update removes it either way.

## Dependencies

**A Dependency is a Skill or a runtime another Skill cannot work without, and the four kinds are answered by different parties.** A Dependency on a collection Skill is one Select can supply; a binary, an External and a Capability are not Select's to place and stay the checker's to answer when the Skill is used. Satisfied means present and usable — the Skill exists in the harness directory, the binary is on `PATH`, or the agent confirms the Capability of itself. Unsatisfied means the dependent Skill does no work and only says how to satisfy it (ADR-0009).

**A harness Capability is a Dependency the agent answers, not an install-time gate** (ADR-0030). A Skill needing something of the Harness itself is Enabled everywhere and refuses where the Capability is Unsatisfied — the alternative, a Catalog saying which Harnesses a Skill belongs on, is the per-Harness matrix ADR-0005 rejects. No script can test one, because the Manager cannot know which Harness invoked it; the checker reports each required Capability with a sentence to confirm and a way to check it, and the Skill's own instructions make answering them part of the check. Exit 0 with a non-empty capability list means *nothing missing that a script can see*, not *go ahead*. Every legal Capability name is defined in the script, so a misspelt one fails when the Catalog is generated rather than passing as a check that never runs.

**Dependencies are resolved before anything is written** (ADR-0047). A row is shown locked, naming what to check instead, where a Skill it depends on is Unsatisfied in the targeted layer and the row itself is not checked — a checked Skill whose Dependency has gone is a break to report, and locking it would tell the user they may not have what they already have. The structure between Skills is therefore visible before the answer is given. Where an answer implies Skills the user did not check, the closure is resolved by the script and costs one yes/no question naming exactly the additions, however deep the chain, and `--yes` answers it. What Satisfies a Dependency is what the Harness will load, so in the Project layer a Skill already Enabled in Global satisfies it without a second copy.

**Unchecking a Dependency is reported and allowed** (ADR-0047). The user is told what they left Unsatisfied and the run does it anyway; a Manager that quietly put the Dependency back would be answering for them, and the dependent Skill refuses at use time without the Manager ever having to forbid the state.

**A declaration the Manager cannot read is not a declaration of nothing** (ADR-0068). A Skill that invokes this collection's checker and whose Dependency declaration this Manager cannot parse is refused, not read as requiring nothing. The refusal is exit 2 with the reason on stdout, in the same three-key shape every Unsatisfied Dependency carries, exit 2 being the one non-zero answer every Skill's body documents a response to; what is Unsatisfied is the declaration itself, and the remedy is `/kntnt update`. The same marker answers a different question at the withdrawal sweep, where an unreadable or absent one means *not ours* rather than *ours, and unreadable* — a caller is one of ours by the act of calling. Update reports such a fault rather than refusing, its writes having already happened by the time the re-check runs.

## The Sandbox behind a dry run

**`--dry-run` is a real run against a Sandbox that is thrown away** (ADR-0042). The same code, the same Transport calls and the same reading of the disk afterwards, against a temporary home deleted when the run ends, so what comes back is an outcome and not a description of intent — there is no second account of the verb to disagree with the first. This rests on a measured fact: the Transport respects an overridden `HOME`, and the redirection has to cover the working directory too, since a Project layer is written there rather than under a home. After a dry run, no directory the layer would really have been written to has changed.

**The Sandbox is seeded with this collection's own files as they are now** — the Manager, plus every marker-carrying Skill found in each Detected directory of the layer being run, and of Global with it where that layer is a Project, and nothing else (ADR-0042). It must hold every layer the previewed run reads, not only the one it writes; without the seed a dry run reports installing what the user already has. Files belonging to other collections are left out deliberately, no verb of this collection touching them.

**A Sandbox has its own npm cache, and the report says so before the wait** (ADR-0042). The first dry run in a session downloads the Transport afresh and takes noticeably longer than the run it previews, and an unexplained pause in a command whose whole promise is *nothing will happen* is where somebody reaches for the interrupt.

**A dry run is the expensive full-fidelity preview, not a routine pre-flight** (ADR-0042). A verb still confirms before it writes, and that confirmation is not a dry run. The flag belongs to the verbs that have something to do with it, and a verb that has not refuses it rather than swallowing it (ADR-0059).

## The renderer boundary

**The script answers with structured data, the agent renders it as text, and the user replies in prose** (ADR-0045). No Skill of this collection may require a terminal: a script invoked from a Skill has no controlling terminal — no stream is a TTY, `/dev/tty` cannot be opened, and a script that reads stdin deadlocks and takes the session with it — while `TERM` is set and inherited, so anything deciding by the environment gets a false yes and then hangs. Even given a terminal the harness captures output rather than streaming it, and a widget belonging to one Harness would make the collection two Skills with one name.

**The script never asks; the questions live in the Skill body** (ADR-0045). The payload carries everything a correct rendering needs, and this is what makes `--yes` implementable at all — a flag can answer a question the agent asks and cannot answer one a blocked read is waiting on. What it costs is that a list's layout, a question's wording and a report's shape are prose reviewed as prose rather than code with a test.

## Routing and evidence

**A Skill that delegates execution routes through model-selector's public route Interface and reproduces none of its policy** (ADR-0083). That Interface alone validates exact points, mappings, availability, the complete main-seat ceiling, evidence class, bounded escalation, and Harness-native controls, and it returns a frozen snapshot binding the profile revision, evidence identity and vintage, Harness inventory, native mappings, commercial facts, main seat and override policy. Only a selection carries an exact Harness-native launch instruction; an inheritance audits why no override was safe and a refusal has a stable reason. A selected decision launches exactly as it says, a reported inheritance launches on the exact main seat and says optimisation was unavailable, and a refusal starts nothing (ADR-0085). A caller reads none of model-selector's private references. Portable deliberation is `low`, `medium`, `high`, `xhigh`, `max`, and a missing native mapping is unavailable rather than approximated.

**A verdict inherits the complete main seat exactly and is never routed** (ADR-0085). Judging work is authority rather than a decision that happened to come back inheriting, so no execution override, route result, repair or failure can downgrade that seat, and verdict work is never price-optimised.

**A routed attempt becomes evidence only where something outside it judged the attempt** (ADR-0089). An independent verifier, an objective checker, a frozen rubric, a declared failure signal, or the user saying so makes an outcome decisive; a builder's report and a subagent's confidence establish nothing, and an unchecked subjective success is left out rather than recorded as a weaker measurement. A decision nothing reached a verdict on is audit data and not an observation. The workflow's own failures — a mechanical hinder, an open product decision, a newly discovered dependency, a tracker failure, a merge collision — are retained as infrastructure errors and excluded from the success rate a frontier is built from.

**The observation is built by allow-list, and importing it is the user's act** (ADR-0089). Every field is copied by name, so prompts, responses, reasoning, ticket and source bodies, diffs, terminal output, secrets, transcripts and absolute paths are absent because they are never copied; a measurement the environment did not expose stays `null`, an absence read as zero making an unmeasured configuration the cheapest on the frontier. Model-selector owns emission as well as import, so a caller reaches it through the public Interface — `/model-selector observe` — and reimplements no sanitization, validation, or key derivation of its own. The artifact is written into caller-owned scratch and its path is named in the report the caller was already giving; no ledger, frontier, profile, repository file, tracker state, or lifecycle hook is touched by the work that produced it, and `/model-selector record` — which a person runs — is the only thing that imports one.

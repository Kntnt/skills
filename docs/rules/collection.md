# Rules — the collection's behaviour

Read before changing what a Manager verb promises, or how this collection reaches a machine.

This module covers the collection's own behaviour: how it gets onto a machine, what each of the Manager's verbs promises, how a Dependency is answered, and the vocabulary those promises are stated in. It is not about the form of a Skill's or a Feature's shipped files, which is `skills.md`, nor about code form, which is `general.md`. How a Skill routes work it delegates, and what may be filed as evidence about it, is `routing.md`. A rule governing one Skill's own behaviour needs nothing here — that Skill's shipped documents are where a reader already meets it.

The capitalised terms — Catalog, Digest, Detected Harness, Enabled, Capability, and the rest — are defined in [`CONTEXT.md`](../../CONTEXT.md). That file says what a term means; this module says what is true of it.

The rules whose reasoning is settled in a decision record are named here in a phrase and cited to the record rather than argued again — the record is where the alternatives and their costs live, and a second telling of the argument is a second thing to keep true.

## The transport and the entry point

**The collection orchestrates the Transport rather than replacing it** (ADR-0175). Skill files are acquired through `npx skills`, and the Manager fills only the gaps that leaves: a desired set in Global and in each Project, a report of what the Catalog has gained or lost, and the application of the chosen layer to every Detected Harness. The Manager installs no Dependency and is not a package manager. The Transport stays the acquisition boundary and is no longer the thing that writes an active installation, which is the refresh transaction below (ADR-0175).

**Adding the collection installs the Manager and nothing else** (ADR-0175). The rest of the collection is hidden from ordinary Transport discovery, because a user facing the Transport's picker and Select at once faces two selectors that can disagree. Select is the way a Skill becomes Enabled.

**The Manager is the collection's only namespaced entry point** (ADR-0175). It is the always-enabled Skill named `kntnt`, and its verbs are its subcommands; every other Skill is invoked by its own name — `/commit`, never `/kntnt commit`. A Category groups the rows of Select's list so related Skills are read together, and is no part of a Skill's identity: a Skill keeps its name when it moves between Categories, and `--on=<category>` is not a thing (ADR-0177).

**The Collection Library ships inside the Manager and is available to every Skill and every Feature of this collection** (ADR-0177). It is not itself a Skill, not a Catalog entry, and not something the user Enables separately, so a Skill installed without the Manager reaches nothing there and says so; what belongs in it, and what stays a Skill's own, is `skills.md`.

**The collection ships Skills, never a Harness's `commands/` files** (ADR-0177). What is portable across every Harness is the Skill; a command file is one Harness's shape with its own preprocessor, and shipping one would make the collection behave differently depending on where it landed.

**Nothing is installed on the user's behalf** (ADR-0175). Select and Update put this collection's Skill files on disk and nothing more: no External, no binary, no runtime. Where a Dependency is Unsatisfied at use time the Skill does no work and gives the one instruction that satisfies it — check a collection Skill in `/kntnt select`, add an External through the Transport, install a binary with that binary's own command. Auto-installing would take rights the user never granted and would make the Manager the package manager ADR-0175 declines to build.

## Layers and targets

**Global is the default layer and `--project` selects the Project** (ADR-0175). Every verb reads the flag the same way: absent or `--project=off` means Global, `--project` or `--project=on` means the working directory's Project layer (ADR-0175). Global is the desired set that applies on this machine; a Project is a working directory with its own extra set, checked into that repository and travelling with it.

**A Project layer can only add** (ADR-0175). `select --project` unchecks a Skill Enabled in the Project layer and nothing else: a Skill Enabled only in Global has no copy in this layer to remove, and there is no subtractive overlay. The row says the Skill is already Enabled in Global instead, which is also what stops a second copy being Enabled into the repository by accident. A mask that turned a Global Skill off in one directory was rejected and stays rejected: it would make what a Harness loads depend on the order the two layers are read in.

**The Project form shows the Project layer alone** (ADR-0175). Every row of a list a user answers must be a row they can change, and a row sourced from Global is not; a list whose checkboxes mean one thing in some rows and another in the rest teaches the user to distrust all of them. The Global form still lists every Catalog entry with its state on this machine, Disabled ones included. The Project form offers no Feature at all and carries the sentence saying why: a Feature owns only Harness Integrations, and the Project layer installs and removes none of them (ADR-0173). One payload serves both forms and names the layer it covers.

**One desired set per layer, never a matrix of Harnesses** (ADR-0005). Every Skill Enabled in a layer is applied to every Harness that layer targets, and Project extras are never copied into Global.

**Targets are detected at each invocation and never recorded** (ADR-0175). A Harness is present in a layer when the parent of its skills directory exists — `~/.claude` for Global, `.claude` in the working directory for Project — so a Harness installed after the last run is reached by the next one with no configuration in between. Every call to the Transport names the full set of Detected Harnesses and never a subset, because the Transport cannot clear a shared directory while a Harness that reads it is left out of the call. With nothing detected the target is the shared `.agents/skills` directory alone, never every Harness the Transport knows of. In the Project layer a Harness whose skills directory is not hidden is never detected, its name being indistinguishable from the repository's own content.

**Nothing about where Skills go is remembered** (ADR-0175). State is the user's remembered choices — which Skills are Enabled in Global and in each Project — and it is a reconstructable cache rather than an authority: a missing or corrupt State is rebuilt from the collection Skills on disk, and rebuilding deletes nothing.

## Disk as truth, and the disk as the report

**Enabled means present on disk in that layer** (ADR-0175). A Harness loads what its skills directory holds, so presence in each Detected Harness's directory for the layer is the whole of the definition for a Skill, and Disabled is its absence. A Feature places no files, so its Enabled state is read from what its Harnesses hold instead, which `skills.md` states (ADR-0173). Select and Update compute the desired set for the targeted layer and apply the delta, so a second run with the same answers writes nothing.

**Partial is a fact about what is there and not a third state** (ADR-0175). A Skill whose files are in some of the layer's Detected Harnesses and missing from others is still Enabled or Disabled: nothing sets Partial, nothing stores it, and no answer of the user's can select it. Select shows such a Skill checked and marks it incomplete, and confirming the list repairs it; a Feature installed into some of the Harnesses it serves and not the rest is marked and repaired the same way, one harness at a time rather than one directory at a time.

**A change is reported from the disk, never from the plan** (ADR-0175). Every verb that changes what is on disk reads the disk afterwards, using the same presence test Select decides Enabled with, and reports what it finds: `intended` is what the verb set out to do, `confirmed` what the disk then showed, and `failed` the rest, each entry naming the Skill and the directories that contradict it. Any entry in `failed` exits non-zero even where other Skills succeeded, and the payload is emitted anyway, an exit code alone saying nothing about which Skill or which directory. A zero exit from the Transport is not evidence that files moved. Presence remains the boundary for ordinary placement and removal; a staged refresh is also failed earlier, by acquisition, coherence, Digest, or publication verification (ADR-0175).

## The Catalog

**The Catalog is the collection's declared list of its entries, the Skills' Dependencies and every entry's Digest, authored in the repository and fetched from it at every invocation** (ADR-0175). A Catalog entry is a Skill or a Feature, carried as sibling groups and answered as one checked set (ADR-0173); what a Feature is and what it declares is `skills.md`. An entry the origin carries and this machine has never seen is listed, Disabled, and can be Enabled in the invocation that first showed it; an entry the origin has dropped is not listed at all.

**A failed fetch falls back to the stored copy, and the verb says which list it is holding** (ADR-0175). A copy is stored beside the Manager and is what a verb reasons from when the origin cannot be reached; the payload carries `catalog_refreshed` so the report can say so. Only where there is neither an origin nor a stored copy does the fetch's own error stand — there is no Catalog to invent.

**Only Update replaces the stored copy** (ADR-0175). Update tells a new entry from a Withdrawn one by diffing the copy it last stored against what the origin now carries, so a verb that reports rather than changes reasons from the fetched Catalog and does not write it; adopting it would flatten the diff the next Update depends on. An Update with no stored copy has discovered nothing: the fetched list becomes the baseline rather than the whole collection being reported as new.

**The Catalog is resolved once per run and held** (ADR-0175). Every verb reads it many times over, and the origin is asked once.

**A new Catalog entry is reported and offered, never Enabled silently** (ADR-0175). Update names each new Skill and asks whether to Enable it; `--yes` answers yes, and the cost of that — an unattended Update placing instructions the user has not read into every Detected Harness — is accepted deliberately in exchange for `--yes` meaning one thing everywhere. What is Enabled is the Skill alone: a Skill needing another the layer does not hold is Enabled and reported Unsatisfied afterwards rather than dragging its closure in the way Select does. A Feature new in the Catalog is not Enabled by `update --yes` the way a new Skill is: what it would write is instructions into a file the user owns and reads, and an unattended run must never place those. It is offered by Select instead, where what it writes is on the row beside the checkbox (ADR-0173).

**A Withdrawn Skill is removed without asking** (ADR-0175). Consent governs what enters the context and not what leaves it, and files no verb of the collection can still reach are not a Skill the user keeps. Update finds one by asking the disk rather than any stored list: a Skill directory in the targeted layer carrying `metadata` keys prefixed `kntnt.` that the current Catalog does not name is Withdrawn, whatever a local file remembers (ADR-0177). The Manager is never Withdrawn, being no Catalog entry, and a directory with no marker belongs to another collection or to the user and is not this collection's to remove. Each withdrawn name is reported with what the disk then showed, on the same terms as every other change, and a failure belongs to that Skill rather than to the run, so the refresh still happens and the report still comes out. The sweep runs only where the origin answered: an Update that fell back reports no withdrawals at all, deleting nothing on the strength of a list it could not confirm.

## The Digest, and the word for a mismatch

**Each Catalog entry carries a Digest of that entry's directory as the collection ships it** (ADR-0175). It is computed over the sorted relative paths and the contents of the files, so a rename, an edit, an added file and a removed file each change it, and it is generated when the Catalog is generated — no release depends on remembering to bump anything and no version number is introduced. The same computation over what is on disk answers the one freshness question the Manager can answer honestly: are these the same files.

**The ignore list is exactly `__pycache__/` and `*.pyc`, applied identically on the producing and the consuming side** (ADR-0175). This is a correctness requirement: disagree by a single artefact and every Skill shipping a script reports itself as Deviating forever.

**A mismatch is Deviating, and never *out of date*** (ADR-0175). The comparison sees two states and no history, so it cannot establish a direction, and outside a lagging Project copy the commonest cause is the user's own edit. Update refreshes what Deviates, and any offer to re-copy says in the same breath that local changes are overwritten.

**A fallback Catalog establishes no freshness verdict** (ADR-0175). Its digests describe the collection as of the last Update, so Select reports nothing as deviating or as current when the list came from the stored copy and offers no refresh on the strength of it, and Update refreshes nothing at all — the files would have to come from the origin the Catalog could not be fetched from.

**The Manager has no Catalog entry and a publication Digest of its own** (ADR-0175). The Catalog carries a top-level `manager_digest` over every file in the Manager's directory except the recursively generated `catalog.json`, which verifies a candidate but cannot establish that the active tree is already identical. So Update stages the Manager every time, and an identical staged candidate is proven directly and not republished.

## What the verbs promise

**Select shows what the collection has and changes it in the same gesture** (ADR-0175). It prints the Catalog in two groups — the Skills grouped by Category, and the Features under them — one row per entry carrying a checkbox that is checked when the entry is Enabled in the targeted layer and the entry's one-line description; a Skill's row also carries any Capability it requires, and a Feature's what it writes and where, the Harnesses it serves against those this machine has, and any single-valued setting another command already holds. The user answers both groups in one sentence of plain text and confirms once, and nothing reaches the disk before that. Nothing about a row has to be looked up elsewhere, and a Skill's row can be read in full before the list is answered — its own `help.md` where it is Enabled, the collection's copy of it where it is not — so deciding never requires installing first; a Feature carries no manpage, and what it writes stands on the row instead. It replaced Status, Enable and Disable, and what was lost with them is a transcription step and the union view, both given up deliberately.

**Reading is never a side-effecting act** (ADR-0175). An answer that changes nothing writes nothing — no refresh, no repair, no touching of files to make the disk agree with a list somebody only wanted to look at.

**One verb is not one form** (ADR-0175). `--on=<entry>` and `--off=<entry>` name a Catalog entry — a Skill or a Feature — directly, open no list, and apply a delta, so naming one entry never silently Disables another. `--yes` opens no list either and Enables nothing that was not already Enabled: it answers the questions that are questions about the disk — refreshing what Deviates, repairing what is incomplete — and never *do you want this Skill*, which there was nobody present to be asked. The asymmetry with Update's `--yes` is intended: the unattended path that can add a Skill is the one the user pointed at the collection's own new entries (ADR-0175).

**Update refreshes this collection's Skills and then checks every Dependency again** (ADR-0175). A Skill revision may add, drop, or replace a Dependency, so the gate is re-read after the files move, and an Unsatisfied one is answered as everywhere else in this collection. Without `--project` it applies Global, with `--project` the Project.

**Update refreshes what Deviates, and always the Manager** (ADR-0175). It asks the Transport for the whole directory rather than for the Transport's own `update`, which compares `SKILL.md` alone and leaves every sidecar at whatever revision last touched that one file. It refreshes every Enabled Skill whose files Deviate from its Catalog entry's Digest and leaves the rest alone, so the report says what moved rather than how many Skills are Enabled; the Manager is checked every time and directly, because a call reaching the layer's Detected Harnesses need not reach the copy of the Manager being run. After one refresh, a file removed upstream is gone, a file changed upstream is replaced, and a file added upstream is present.

**Update does not refresh an External** (ADR-0175). An External is a Dependency whose source is another collection, and it is updated with the Transport.

**Uninstall takes this collection off this machine** (ADR-0175). Every Feature Enabled in Global is torn down first, while the Manager they ship inside is still on disk to run them: a hook naming a script inside a deleted Manager is an entry the Harness runs at every session and nothing answers (ADR-0173). It then removes every Catalog Skill Enabled in Global from every Harness detected in the home directory, and then the Manager itself, last, in a Transport call of its own made only where the rest really left — a machine holding Skills with no verb left to remove them is worse off than one whose Manager outlives them by a run. `kntnt` among the confirmed is therefore the whole report. `--yes` is its gate: the verb refuses without it, as `select --off` does.

**Uninstall has no `--project` form, and that is the decision rather than an omission** (ADR-0175). A Skill in a working directory is checked into that Project and travels with it, so it is never touched and the report says so: a user told the machine is clean, with a repository on it still carrying these Skills, has been told something false about the only thing they can check.

**Uninstall cannot promise completeness against a stale Catalog** (ADR-0175). The set it removes is what the Catalog names, so a run that fell back to the stored copy may leave behind a Skill the collection has since withdrawn; the verb reports which list it worked from, and the usual remedy of running it again is available only while the Manager is still installed.

**Bare `/kntnt` is Help** (ADR-0175). Somebody typing the Manager's name with nothing after it does not yet know what to type next, and a bare name should teach the interface rather than report the machine. Every subcommand is reached by its own name and none by the absence of one, so `/kntnt <command> --help` and `/kntnt help <command>` reach that command's page directly. Help is not how another Skill's help is reached: a Skill the user has answers its own `--help` forms — what each Skill ships for that is in `skills.md` — and a Skill they do not have yet is read about in Select.

**`--yes` means no question is asked at all** (ADR-0029). Every question that could be answered yes or no is answered yes instead, so every yes/no question in the collection is worded so that *yes* ends it; a question whose yes opens another question has no unattended answer. Where a verb takes back something the user is choosing to give up, the flag is also the gate and the script refuses without it, a script having no way to prompt. Unchecking a Skill deletes its files and unchecking a Feature takes what it wrote back out of a Harness's own configuration, which is the user's file too, so each is gated in its own words rather than under one sentence about files that would be false of the other. Deleting a Withdrawn Skill is not such a choice and is not gated: there is no question to answer, so Update removes it either way (ADR-0175).

## Authorizing a real Global Update

**A real Global Update is authorized by the current Invocation Envelope or by a later response to its complete current plan, and by nothing else** (ADR-0175). Formal `--yes` in the current Formal Invocation is authorization in itself and keeps its collection-wide meaning. Without that flag the agent renders every Skill to refresh, every new entry a yes answer Enables, every Withdrawn Skill to remove, and every target directory, and then waits; only a user response arriving after that exact display authorizes the write. Contextual Instruction, Conversation Context, a response remembered from earlier in the task, a broad repair request, and an agent-authored handoff provide no authorization, however strongly they ask for a repaired machine.

**The engine binds that authorization to the plan itself, before the first write** (ADR-0175). Planning is read-only and resolves the layer, the refreshes, the already-current Skills, the removals, the Catalog's reachability and the target directories, with one opaque approval identity per answer — the one that accepts the proposed Enablements and the one that leaves them Disabled. A real Global apply resolves the complete plan again and refuses a missing, incomplete, contradictory, or changed approval identity before acquisition, Catalog replacement, publication, teardown, or any other write. The identity authorizes nothing by itself; it proves plan equality, and freshness stays the agent's obligation. A changed plan starts the interaction again, and the old answer is not carried forward.

**A dry run is outside the gate, and a Project Update is outside this record** (ADR-0175). A dry run's writes stay in the discarded Sandbox, so there is no real Global mutation to authorize; Project Update is unchanged, the incident and the Manager self-refresh boundary both being Global.

## Dependencies

**A Dependency is a Skill or a runtime another Skill cannot work without, and the four kinds are answered by different parties** (ADR-0175). A Dependency on a collection Skill is one Select can supply; a binary, an External and a Capability are not Select's to place and stay the checker's to answer when the Skill is used. Satisfied means present and usable — the Skill exists in the harness directory, the binary is on `PATH`, or the agent confirms the Capability of itself. Unsatisfied means the dependent Skill does no work and only says how to satisfy it.

**A harness Capability is a Dependency the agent answers, not an install-time gate** (ADR-0030). A Skill needing something of the Harness itself — spawning subagents, for one — is Enabled everywhere and refuses where the Capability is Unsatisfied; the alternative, a Catalog saying which Harnesses a Skill belongs on, is the per-Harness matrix ADR-0005 rejects. No script can test one, because the Manager cannot know which Harness invoked it; the checker reports each required Capability with a way to confirm it, and the Skill's own instructions make answering them part of the check. Exit 0 with a non-empty capability list means *nothing missing that a script can see*, not *go ahead*. Select names them on the Skill's row, so a user knows before choosing that a Skill may refuse to work where they are.

**Dependencies are resolved before anything is written** (ADR-0175). A row is shown locked, naming what to check instead, where a Skill it depends on is Unsatisfied in the targeted layer and the row itself is not checked — a checked Skill whose Dependency has gone is a break to report, and locking it would tell the user they may not have what they already have. The structure between Skills is therefore visible before the answer is given. Where an answer implies Skills the user did not check, the closure is resolved by the script and costs one yes/no question naming exactly the additions, however deep the chain, and `--yes` answers it. What Satisfies a Dependency is what the Harness will load, so in the Project layer a Skill already Enabled in Global satisfies it without a second copy (ADR-0175).

**Unchecking a Dependency is reported and allowed** (ADR-0175). The user is told what they left Unsatisfied and the run does it anyway; a Manager that quietly put the Dependency back would be answering for them, and the dependent Skill refuses at use time without the Manager ever having to forbid the state. The account is read off the layer after the run rather than off the answer, so a Dependency whose files never landed is reported absent rather than counted present because somebody named it (ADR-0175).

**A declaration the Manager cannot read is not a declaration of nothing** (ADR-0175). A Skill that invokes this collection's checker and whose Dependency declaration this Manager cannot parse is refused, not read as requiring nothing. The refusal is exit 2 with the reason on stdout, in the same three-key shape every Unsatisfied Dependency carries, exit 2 being the one non-zero answer every Skill's body documents a response to; what is Unsatisfied is the declaration itself, and the remedy is `/kntnt update`. The same marker answers a different question at the withdrawal sweep, where an unreadable or absent one means *not ours* rather than *ours, and unreadable* — a caller is one of ours by the act of calling. Update reports such a fault rather than refusing, its writes having already happened by the time the re-check runs.

## The refresh transaction

**The Transport never writes an active installation during a refresh** (ADR-0175). It empties a destination before it copies, which is correct after the call and unreadable during it, so the Manager redirects it to an isolated home and Project, asks it for the complete intended set, and verifies every candidate before publication begins. A Catalog Skill must match its selected Digest and the Manager candidate its `manager_digest`, and the candidate must then pass structural checks on its entrypoints, its structured data and its Python helpers; candidates acquired for several Harnesses must agree with one another. Acquisition or verification failure discards the isolated tree and leaves every active path untouched.

**Publication exchanges one complete directory for another in a single filesystem operation** (ADR-0175). A reader opening a Skill directory receives the complete old generation or the complete new one, never the Transport's empty interval or a partly copied tree. Logical paths are resolved to physical targets first, so two Harness paths reaching one tree publish once and a symlink stays the Harness-facing entry; stable parents are advisory-locked in sorted order, so concurrent Manager runs serialize without a lock file that can outlive either run. An atomic swap the host cannot provide is a publication refusal before an active tree moves.

**An identical verified candidate is no publication** (ADR-0175). The active and staged directories are compared with the collection's own directory Digest, ignores included, and equality preserves the directory entry, every inode and every timestamp.

**Publication is a transaction over the intended physical targets** (ADR-0175). A failure after an earlier exchange swaps every retained tree back in reverse order, and the complete prior collection remains installed. A Withdrawn Skill is an omission from the candidate generation, moved atomically inside the same transaction rather than deleted by the Transport afterwards; its integration-owning files are copied into the isolated root first, and teardown begins from that copy only after every filesystem target has committed. Every acquisition root, candidate, rollback copy and snapshot is removed on success or failure alike.

## The Sandbox behind a dry run

**`--dry-run` is a real run against a Sandbox that is thrown away** (ADR-0175). The same code, the same Transport calls and the same reading of the disk afterwards, against a temporary home deleted when the run ends, so what comes back is an outcome and not a description of intent — there is no second account of the verb to disagree with the first. This rests on a measured fact: the Transport respects an overridden `HOME`, and the redirection has to cover the working directory too, since a Project layer is written there rather than under a home. After a dry run, no directory the layer would really have been written to has changed. The acquisition and publication transaction runs inside that boundary, so a dry run needs no second implementation of it (ADR-0175).

**The Sandbox is seeded with this collection's own files as they are now** — the Manager, plus every marker-carrying Skill found in each Detected directory of the layer being run, and of Global with it where that layer is a Project, and nothing else (ADR-0175). It must hold every layer the previewed run reads, not only the one it writes; without the seed a dry run reports installing what the user already has. Files belonging to other collections are left out deliberately, no verb of this collection touching them.

**A Sandbox has its own npm cache, and the report says so before the wait** (ADR-0175). The first dry run in a session acquires the Transport afresh and takes noticeably longer than the run it previews, and an unexplained pause in a command whose whole promise is *nothing will happen* is where somebody reaches for the interrupt.

**A dry run is the expensive full-fidelity preview, not a routine pre-flight** (ADR-0175). A verb still confirms before it writes, and that confirmation is not a dry run. The flag belongs to the verbs that have something to do with it, and a verb that has not refuses it rather than swallowing it (ADR-0176).

## The renderer boundary

**The script answers with structured data, the agent renders it as text, and the user replies in prose** (ADR-0175). No Skill of this collection may require a terminal: a script invoked from a Skill has no controlling terminal — no stream is a TTY, `/dev/tty` cannot be opened, and a script that reads stdin deadlocks and takes the session with it — while `TERM` is set and inherited, so anything deciding by the environment gets a false yes and then hangs. Even given a terminal the harness captures output rather than streaming it, and a widget belonging to one Harness would make the collection two Skills with one name.

**The script never asks; the questions live in the Skill body** (ADR-0175). The payload carries everything a correct rendering needs, and this is what makes `--yes` implementable at all — a flag can answer a question the agent asks and cannot answer one a blocked read is waiting on. What it costs is that a list's layout, a question's wording and a report's shape are prose reviewed as prose rather than code with a test.

## Harness Integrations at the Manager's seam

**A Skill's own integrations are installed and removed at the seams that place and remove its files** (ADR-0179). Enabling a Skill that declares `metadata.kntnt.integrations` is the whole gesture: at every seam that already places or refreshes an Enabled Skill's files, the Manager says one word to that Skill and it installs what it owns; Disabling it is the whole undo, at the seam that already deletes its files. There is no second command and no second consent prompt, and install, repair and refresh are one convergence over whatever is on disk, so asking an already-installed Skill again changes nothing.

**The Manager asks the Skill to remove them while the Skill can still answer** (ADR-0179). Deleting a Skill's files is the moment its integrations become unreachable, so removal runs first, on the one seam every removal path passes through, and it is the Skill's own script that runs — the Manager learns no Harness's hook format. A teardown that fails is reported per Skill and never raised, because external state this collection does not own must not hold up the removal of files it does own. Inside the refresh transaction the ordering is the transaction's: the owner is staged while still active and invoked only after every filesystem target has committed (ADR-0175).

What such an integration may then do on the machine — what it may read, what it may write, and how its state is reported back — is `routing.md`.

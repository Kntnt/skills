# Coding standard — Skills

Read before adding a Skill or a Feature to this collection, or changing the files either one ships.

This module covers the form of a Catalog entry's own shipped files — a Skill's `SKILL.md`, its `help.md`, and what lives beside them, and a Feature's `FEATURE.md` — and the Collection Library shared among Skills and Features. It is not about what an entry does; it is about what every Skill and every Feature of this collection carries regardless of what it does and where shared implementation belongs. Read `general.md` first, and `python.md` too where the Skill, the Feature, or the Library ships an engine.

Much of what follows is enforced by the test suite, and where it is, the assertion that fails names the rule and points back here. Not all of it is, and where the suite holds less of a rule than the rule says — the README paragraph nothing compares against anything, a manpage section checked for its heading and not for the prose beneath it — this document says so where the rule is stated, rather than leaving a contributor to infer it from a green run. Read a green fourth check as *nothing the suite watches broke*, never as *the form is right*.

The rules whose reasoning is settled in a decision record are named here in a phrase and cited to the record rather than argued again — the record is where the alternatives and their costs live, and a second telling of the argument is a second thing to keep true.

## Why this is written down as well as asserted

A rule that lives in two places can disagree with itself, and this collection's own preference runs towards a single copy a reviewer can diff. The contract is written twice anyway, and deliberately, because the two copies are read at different moments by readers in different positions.

A contributor who has not yet written anything cannot be helped by an assertion message: nothing has failed, because nothing exists to fail. This document is for that moment. A contributor whose suite has just gone red cannot be helped by a document they did not know to read: they have a heading and a path, and what they need is the rule. The assertion message is for that moment, which is why every test enforcing a rule below fails with the rule and its reason in a phrase, and a pointer here or to the record.

The copies stay together because only one of them states the rule in full. The message names the rule and cites where it is stated; it does not restate the reasoning, and this document does not reproduce the tests. What can drift is the pointer, and a citation to a record number that resolves to nothing fails the suite.

## The collection's flag grammar

**A flag's meaning is uniform across the Skills that carry it; its presence follows its function** (ADR-0176). There is no collection-wide flag set every Skill is expected to offer. A Skill's grammar names a flag exactly where that flag has work to do in that Skill — `--yes` where the Skill asks at least one question answerable yes or no, and nowhere else — which is the same judgement the refusal makes per invocation rather than per Skill. What the flag then means is fixed for the whole collection and settled where the collection's promises are (ADR-0029); what is settled here is only whether a Skill writes it down at all. A Skill that carries no such flag documents no exception for it: the strict grammar refuses every undeclared flag alike, so a form nobody declared needs no reason of its own. The suite does not hold that last part — what a body argues about a flag it does not have is prose no assertion recognises — so it is held in review.

**A flag of this collection's own grammar that takes a value attaches it with `=`, written `--flag=value`, and the space-separated form is written nowhere** (ADR-0176). One spelling, on every surface: the `argument-hint`, the `## SYNOPSIS` and `## OPTIONS` of every root and subcommand manpage, the argument prose and steps of every Skill body, and every invocation of the collection's own Python engines a body constructs. The Skills have no parser of their own beyond the engine the Manager ships (ADR-0181), and the engine reads the grammar off these surfaces — so a grammar that varies by Skill is a grammar the engine cannot read.

A flag taking no value is untouched, and so is the bare spelling of a flag whose value is optional: `--project`, `--project=on`, and `--project=off` are all compliant, and the same value written after a space is not. In a manpage the attached form closes the bold run after the `=` and renders the metavariable with underscores, as `**--data=**_PATH_`, because `**--data=***PATH*` is not the markup it looks like.

**A third-party command line keeps its own tool's spelling.** A body constructing a `git`, `gh`, `uv`, or `npx` invocation writes whatever that tool documents; their grammar is not this collection's to normalise. The collection's engines stay permissive for the same reason they always were — `argparse` accepts both forms and nothing is gained by refusing one there — so the rule is held by the suite, which reads every file a Skill ships and the documents governed here, and fails on a valued flag written with a space.

## The collection's invocation order

**A Formal Invocation is written in one order: the command path, then the flags, then the operands, then the reserved separator and its optional Contextual Instruction** (ADR-0176). The three grammar surfaces agree about it as they agree about the flags they name — the `argument-hint`, the `## SYNOPSIS` of every root and subcommand manpage, and the `## OPTIONS` that describes what those forms may carry — and so do a Skill body's argument prose, its steps, the invocations of the collection's own engines it constructs, and every example in a manpage's `## EXAMPLES` and in the README.

The command path is the Skill name followed by the literal subcommand tokens that address a manpage, so a token belongs to the path exactly when a page under `help/` answers to it and is an operand otherwise (ADR-0176). Flags follow it, valued or not, in any order among themselves. Operands come last, and the order is strict: a flag the Skill declares that is written after an operand is out of order and refused rather than repaired, in the same shape as an undeclared flag and an incomplete form (ADR-0176), and each Skill's `DIAGNOSTICS` says so — `/commit fix the --yes bug` is refused, `/commit --yes fix the bug` is the form. A dash-prefixed word the Skill declares no flag for is text, so a free-text operand may contain one, and a Skill that declares no flag and no command path takes any dash-prefixed token as operand, and its `DIAGNOSTICS` says what the token is read as.

**Where a Skill's grammar carries no command path, the reserved separator is optional and the same guidance may be written as a bare operand** (ADR-0176). Such a Skill declares that free-text operand in its `argument-hint` and in every `## SYNOPSIS` form, beside the instruction suffix every form still ends with, and says in one sentence that the two slots carry one instruction; the two spellings are one invocation with one meaning. A dash-prefixed token inside that operand is part of the instruction rather than an undeclared flag, and the Skill's `DIAGNOSTICS` says so beside the flag-refusal rule every page carries. A Skill that later grows a subcommand or a flag acquires the ambiguity with it, and drops the operand in the same change.

Where a Skill offers the same choice as an operand and as a long-option alias, the flag spelling sits with the flags and the operand spelling with the operands, and no documented form is left ambiguous about which of the two it is using. A single form can then no longer make such a slot mandatory, because the slot appears in two regions of the line; state the exclusivity under `DIAGNOSTICS` instead. A `git`, `gh`, `uv`, or `npx` command line a body constructs keeps the order that tool documents, on the boundary ADR-0176 already draws for flag spelling.

The suite reads every `argument-hint` and every `## SYNOPSIS` line and fails where a flag follows an operand, or where a subcommand token answering to a page under `help/` follows a flag. An alternation naming both spellings of one slot — `[**scope**|**--scope**]` — is one unit rather than a sequence, and is allowed only where everything before it is path or flag and everything after it is operand.

## `SKILL.md`

### Frontmatter

The frontmatter is YAML and is read by a real YAML parser, so anything YAML accepts is what the field means (ADR-0177).

- **`name`** is the Skill's directory name, exactly. **`description`** is the only hook the harness has for deciding when a Skill applies (ADR-0177), and the Catalog carries both.
- **The fields a Skill may carry** are the six the Agent Skills specification defines, plus `argument-hint` and `disable-model-invocation`, which the collection ships knowingly (ADR-0180). A ninth field fails the suite until the record accepts it too.
- **Every `argument-hint` ends with `[-- <instruction>]`**, exposing the optional Contextual Instruction without making the reserved separator part of the Skill's Formal Invocation (ADR-0176). Existing formal free-text operands remain distinct and keep their own spelling before that suffix.
- **No alternative form of `argument-hint` offers a combination `## SYNOPSIS` forbids.** The hint is one line and may collapse forms the manpage spells out separately, so the two are not held to the same count of forms; what is held is that the flags of each alternative the hint separates with ` | ` fit inside a single synopsis form. The aggregate rule below compares the three surfaces as one set of names, which cannot see a combination at all — a hint advertising a scope flag and a confirmation flag alongside a status form that writes nothing satisfies it — and what the user meets is a refusal for a form the harness told them to type.
- **`disable-model-invocation` is written on every Skill**, `false` included, and the Codex sidecar mirrors it — see [`agents/openai.yaml`](#agentsopenaiyaml) below, where the pairing and its reason are stated.
- **Every `metadata` key carries the `kntnt.` prefix and every value is a string** (ADR-0177). The namespace is flat and shared with every other collection, so an unprefixed key is a key anybody may claim; a value in any other shape is coerced by a foreign reader rather than refused, and lost without a word. A list is one space-separated string, an empty list an empty string.
- **The four dependency lists** — `kntnt.binaries`, `kntnt.skills`, `kntnt.externals`, `kntnt.capabilities` — are written even when all four are empty, and `kntnt.internal: "true"` marks the Skill as this collection's. The lists are hard requirements only: the checker exits 2 on anything in them (ADR-0177), so nothing a Skill degrades gracefully without belongs there. All four are written even where they are empty because a key nobody wrote is read as an empty list, which is the answer a Skill requiring nothing gives — so an omission cannot be told from a declaration once the key is gone.
- **`kntnt.integrations`** names a script inside the Skill that the Manager asks, at the two moments this key exists for, to install or to remove whatever that Skill owns outside its own directory — a Harness hook, an adapter, anything a file deletion would not reach. Removal is the single word `remove-integrations`, asked while the owning files remain readable, at the seam that deletes a Disabled or withdrawn Skill's files; installation is its mirror word, `install-integrations`, asked at every seam that places or refreshes an Enabled Skill's files, and is idempotent — asking it again converges rather than repeats (ADR-0179). Both are answered with JSON and reported beside the removal or the placement itself. An ordinary removal invokes the active owner before deleting it; a transactional refresh first stages one copy per physical owner and invokes that copy only after filesystem publication commits, so rollback cannot restore a Skill whose external state was already torn down (ADR-0175). The value is a path relative to the Skill's own directory and may not climb out of it. Only a Skill that installs such a thing writes the key; its absence is the ordinary case and means deleting the files is the whole of the removal, and placing them installs nothing beyond themselves.
- **`compatibility` names exactly the binaries the dependency lists hold**, no more and no fewer, and the Capabilities likewise (ADR-0177). It is the one field a reader outside this collection knows to look at. A requirement the Skill degrades gracefully without is named there in prose and deliberately not in the lists — `/release` and `gh` is the only such case today. A Skill with nothing to state carries no `compatibility` field at all rather than an empty one.

### Body

The body carries only what the agent executes, which is why prose is the seam a Skill is held at (ADR-0177). What follows is what the body has to carry; how its prose is written is `/writing-for-agents`, and [`docs.md`](docs.md) states that rule beside the rest of what governs a document here.

- **Every body opens with the engine call, and nothing that asks the model to do the engine's work stands anywhere in it** (ADR-0181). After the one-line definition of `$HERE` — the directory that contains the `SKILL.md` — the body says where the Manager is, `$HERE/../kntnt/` if it exists and else `kntnt/` under a Global harness skills directory, names `npx skills add Kntnt/skills` as the fix where neither is found, and defines `$LIBRARY` as `library/` under that Manager, stopping with `/kntnt update` where an older Manager has none. Then it makes the call below with the payload on stdin: on exit 0 it answers the Capabilities the JSON's `dependencies` carries first — the half of the check no script can make, each `confirm` sentence true of the agent or its `how` given and the run stopped — and continues from the JSON; on any other exit it prints stdout verbatim and stops. That is the whole of what the Manager's body carries under its `## Invocation` heading, and the whole of what every other body carries before `## Arguments`, in three paragraphs. The dependency preamble, the `## Invocation` section that pointed at the Envelope contract and named the help routes, and the step that parsed the arguments are gone with the work they asked for: the engine makes the dependency check, splits the Envelope, routes help and holds the form before a step is read, and a body restating any of it asks the model to do the engine's work a second time. Every Skill therefore declares `uv` in `kntnt.binaries` and in `compatibility`, the engine running on it — which withdraws ADR-0177's exemption for a Skill with nothing else to declare, `uv` no longer being declared for nothing. What stays of the Envelope contract in a body is its semantic half, in one sentence beside the JSON's shape: the Contextual Instruction the JSON carries is applied under `$LIBRARY/references/invocation-envelope.md`, which no engine can judge. The three grammar surfaces a body used to argue against are unchanged, and so are the manpages: their `## INVOCATION ENVELOPE` pointer and `DIAGNOSTICS` still say what is done, the engine now doing it.
- **The Manager ships the invocation engine, and it executes the grammar rather than leaving the model to read it** (ADR-0181). It is called as `uv run "<manager>/scripts/kntnt.py" invoke --here="$HERE"` with the invocation payload — everything the user typed after the Skill name, verbatim, however many lines — on stdin, because the payload reaches the model as text and a multi-line Contextual Instruction does not survive a shell argument. In order it makes the dependency check `check --here` makes, so no body calls the checker on its own; splits the Envelope at the first standalone unquoted `--` as `$LIBRARY/references/invocation-envelope.md` states it; routes an exact help form — `--help`, `-h`, or `help` at the root, `<command path> --help` or `-h` where a page under `help/` answers to the path — to the addressed page, and refuses a Contextual Instruction beside one without rendering it; and holds the Formal Invocation to the grammar the Skill's own surfaces declare — the `argument-hint`, and the `## SYNOPSIS` and `## OPTIONS` of the most specific page the command path addresses — in the collection's one order. Three answers, told apart by exit status. On a valid form it exits 0 with JSON on stdout: `ok`, `path` (the command path as a list), `flags` (each flag written to `true` where it stood bare, to its attached value, or to a list of those where the page marks it repeatable), `operands` (in order; a last single slot takes the rest of the line, a repeatable slot one token each, and an operand or a flag value written in outer quotes arrives without them as that same file states), `instruction` (the Contextual Instruction, or `null`), and `dependencies` (the payload `check` prints, its `capabilities` the ones the agent must still answer). On an exact help form it prints the addressed page verbatim and exits 3. On an invalid form it prints the refusal in the collection's shape — what was wrong in one line, the addressed page's `## SYNOPSIS` verbatim, and that page's own `--help` route — and exits 2, which is also what an Unsatisfied Dependency exits with, the payload then being `check`'s. A body that calls it prints stdout verbatim and stops on either non-zero status, and begins its Steps from the JSON on 0. The engine checks the form of an operand — present, absent, one, many, and a literal the `## SYNOPSIS` names — and never its meaning: what a path, a URL, or an inline text is stays the Skill's. Flags come before operands, so a flag the Skill declares that is written after an operand is out of order and refused, as every page's DIAGNOSTICS states; a dash-prefixed word the Skill declares no flag for is text, and a Skill that declares no flag and no command path takes any dash-prefixed token as operand. An empty payload is the bare form, valid exactly where the `## SYNOPSIS` admits a form with nothing after the Skill name. The engine reads no grammar through `library/scripts/argument_grammar.py`, whose permissive split is the two JSON-refusing engines' and not this one's; a grammar surface it cannot read fails the suite, which runs it against every shipped page.
- **`## Arguments` states only what the engine cannot know** (ADR-0181). What an operand means once it is known to be one — a path, a URL, an inline text, a ticket reference, a version; a value vocabulary the `## SYNOPSIS` does not spell out, such as the six spellings `--in-place` accepts; an exclusion between two flags where the forms do not already draw it; what a flag means to the Steps that read it; and, for a Skill whose grammar carries no command path, the one sentence saying that the free-text operand and the Contextual Instruction carry one instruction (ADR-0176). The grammar line that opened the section, the sentence that made the order part of the form, the list of invalid forms and the refusal that closed it are the engine's, read off the `argument-hint` and the shipped pages and refused before a step is read, so the section names no help route, no synopsis and no refusal. A step that read a flag reads it from the JSON's `flags`, an operand from `operands`, a command path from `path`, and a flag handed on to one of the collection's own engines is handed on as it stood — a flag read as `true` as its bare name, one read with a value as `--flag=value`, one read as a list once per value.
- **An invalid form is refused by the engine, never repaired or ignored, and the body states no refusal of its own.** What a refusal does — name the error, print the `## SYNOPSIS` section of the most specific recognized command page verbatim, point at that page's own `--help` route, change nothing — is stated with the two refusal categories in `$LIBRARY/references/invocation-envelope.md`, together with the reason a flag with no work to do is refused rather than accepted and ignored (ADR-0176), and the engine performs it against the shipped pages before a step is read (ADR-0181). The body adds only what this Skill leaves undone when it stops — *correct nothing, write nothing* — and it adds that beside the one refusal the engine cannot make: a value whose form the page admits and whose meaning the Skill rejects, a `--max` that is not a non-negative integer, a genre nothing installs, a second Text Artifact in one operand. The step that settles that value refuses it as the Library file says, in the collection's shape, and says what the Skill then leaves undone; `## Arguments` states the constraint and never the refusal.
- **A file only this Skill opens when the situation arises lives under its `references/`** (ADR-0177). A reference or script with several Skill consumers lives in the Collection Library instead (ADR-0177). The published user pages — `help.md` beside `SKILL.md` and any subcommand pages under `help/` — stay outside `references/`; the Manager also keeps `catalog.json` and `steps/` at their published addresses. Every other Markdown file a Skill ships is agent reference material, which is how the suite finds it: by discovery rather than a maintained list.
- **An executable helper used only by this Skill lives under its `scripts/`** (ADR-0177). The directory is created when the first helper exists and omitted where none does; a Python file beside `SKILL.md` has lost the resource structure that tells a reader what it is.
- **Every pointer resolves.** `$HERE/<path>` is resolved from the directory holding `SKILL.md`, `$LIBRARY/<path>` from the Collection Library, and a Markdown link from the file the link sits in; all three are followed by the suite, in every Markdown file a Skill ships.

## Collection Library

The Collection Library is shared implementation shipped inside the Manager at `library/`; it is not a Skill, carries no `SKILL.md`, has no Catalog entry, and is never Enabled separately (ADR-0177).

- **The resource directories mirror a Skill's.** Agent reference documents live under `library/references/`, and executable helpers under `library/scripts/`. They start flat, with no concern directory added until present files need the grouping or would otherwise collide; empty directories state nothing and are not shipped.
- **Ownership follows consumers.** A reference or script with one Skill consumer stays local to that Skill. With several consumers it moves to the Library, so there is one authoritative copy without making one consumer the implementation owner of another.
- **The Invocation Envelope is stated once, at `library/references/invocation-envelope.md`.** Every Skill executes that contract and every manpage documents it, which makes it the most widely consumed thing the Library holds; a copy inside each Skill would be one contract in as many editable places as the collection has Skills, and the body and the manpage that both point here cannot come to disagree (ADR-0177, ADR-0176). The narrowing ADR-0176 made is written there too, and only there: unusable guidance is guidance with no addressable effect at all, while guidance a documented precedence has already settled against is suppressed rather than refused, the run continuing and the delivery naming the suppression where that belongs in the report.
- **An engine whose refusals are machine-readable parses the collection's one argument grammar** (ADR-0176). The Library engines that declare their command lines to `argparse` keep it. One that answers a line it will not run with a JSON refusal carrying a stable code, on exit 2, reads its arguments through `library/scripts/argument_grammar.py` instead, loaded by path from beside itself rather than by a bare import or an amended `sys.path`, and it declares which of its own flags carry no value: the grammar takes nothing from behind a flag an engine has named, so a valueless flag is a property of the engine that has it and never a token the parser compares against.
- **What may be filed as a Measurement without a person is one rule, and it is held where the append is** (ADR-0182). An outcome an independent verifier, an objective checker, or a declared failure signal established is what may be filed unasked; work never grades itself, and a builder's own report of how it went establishes nothing. Model Selector's own `record.py` is the one append, so a caller that judged something reaches it rather than writing a store of its own, and a refusal there is reported per row and stops nothing — the work the row describes is already done, and evidence is not a reason to fail it.
- **The editorial resources have a fixed shape.** `library/references/editorial/base.md` holds every normative outcome a first draft has to meet, once and in English, and names no Skill's options; `genres/` and `techniques/` beside it hold one file per selectable value, whose filename is its canonical spelling and whose directory is the only list of what is installed. A review half is a separate `<name>.review.md` beside its base half, so a Skill that only writes never loads it, and it restates no base rule (ADR-0178). `anti-slop.md` beside them is the collection's own condensed, language-independent adaptation rather than a dependency on an external Skill, it lives in the Library because more than one Skill applies that pass, and it carries the upstream notice inside the file, where a reader of an installed Skill receives it (ADR-0178). `mechanics.md` beside those holds the rules of objective correctness that do not depend on the language, so that none of them has to be written once per Language Resource where the copies could disagree; a Skill correcting mechanics loads it together with the resolved language's mechanics scope, and that scope is the more specific instruction wherever the two meet (ADR-0178). The language resolver's successful `list` and `resolve` payloads expose identity and requested scope content rather than the backing Language Resource paths, so the scoped content is a terminal result and never a pointer around the scope boundary (ADR-0178). The format page for all of them is [`skills/kntnt/library/references/editorial/README.md`](../../skills/kntnt/library/references/editorial/README.md), and the Language Resource format page sits beside it.
- **A genre a Skill infers is inferred from the installed filenames and the opening of each installed genre resource — the `# <Name>` heading and the paragraph under it — and from nothing further of any of them** (ADR-0178). Every Skill resolving a genre through the shared precedence states that licence in its resolution step, in the same words as its peers, with the bound written beside it; its loading step is unchanged by the licence and admits the genre that was settled on and no other. The opening is therefore a requirement on every genre and technique rather than a courtesy, and the format page above says so. Nothing enumerates the installed set anywhere else: an index would answer the same question and cost the property that makes adding a genre one file.
- **A genre's base half names the technique that genre is ordinarily written with, or states that it has none, and every genre in the directory states one or the other** (ADR-0178). It is a statement of practice rather than a requirement on the draft: each Skill that resolves a technique places it in its resolution order below everything the user or the material says — the invocation, a recognized map, an instruction, applicable Conversation Context, and inference — and above no technique at all, and says in its delivery which technique was resolved and where it came from. The statement sits below the resource's requirements, outside the opening a genre is inferred against, because a technique named in the opening would be read as evidence about which genre applies. Nothing infers a technique from a text: the genre carries a selection, and the prohibition on applying one because the material or the draft falls into its shape is untouched (ADR-0178).
- **A code sample is quoted material, so an editorial pass locates no finding inside one and changes nothing inside one** (ADR-0178). A fenced block, an indented block, and an inline code span are all read past rather than read against the rules, the docstrings, comments, and string literals inside them among what is read past; prose *about* code is ordinary prose and is read like every other sentence. Every Skill that runs a pass over a finished text states the rule in its pass step in the same words as its peers, every correction brief's preservation clause names code beside the quotations and formatting it already names, and every one of those Skills' manpages tells the reader that a code sample is quoted material. Three Skills stating one rule in three wordings would be three answers a run may pick between, and picking between them is the disagreement the record ends; the suite reads all three surfaces.
- **Peer internals are not an interface.** A Skill may follow another Skill's `SKILL.md` where it declares that Skill as a Dependency, but it never reads the peer's `references/` or runs its `scripts/`. A body using the Library defines `$LIBRARY` from the Manager directory it runs the engine from, and stops with `/kntnt update` when an older Manager has no Library. Every Skill uses it, the Invocation Envelope being stated there, so every body carries that definition beside `$HERE`. That withdraws what the Envelope rule used to promise, that a directly installed Skill's own manpage kept it self-contained (ADR-0176): such a Skill now stops with `/kntnt update` instead of reading the contract locally, which is the price of the contract being written down once.

## `FEATURE.md`

A Feature is a Catalog entry that owns Harness Integrations and nothing else (ADR-0173). It ships inside the Manager at `skills/kntnt/features/<name>/`, carries no `SKILL.md` and no manpage, is never a Dependency, and never travels through the transport.

- **`FEATURE.md` is its whole declaration and its whole page.** Its frontmatter carries `name` — which has to be the directory, because that is how the Manager addresses it — a one-line `description`, and the collection's own `metadata.kntnt.*` keys: `category`, `harnesses` as one space-separated string, `binaries`, `capabilities`, and `integrations` naming a script inside this Feature and nowhere else. `metadata` holds strings and nothing else (ADR-0177), which is why the sentences below are prose rather than a metadata list.
- **A `## Writes` section is required, one bullet per thing the Feature writes and where.** Catalog generation reads those bullets into the entry and Select puts them on the row and in the confirmation, because a row that edits a file the user owns and reads has to say so before it is checked. A Feature with no such section is refused at generation.
- **A name is unique across both entry types.** The list is answered as one checked set, so generation refuses a Feature that shares a Skill's name.
- **A Feature is Enabled at the Global layer alone, and its Enabled state is read rather than recorded** (ADR-0173, ADR-0179). An owned entry is keyed by its owner inside a Harness's own configuration, so a Project Enable and a Global one would write over and remove each other's; the layer question therefore has one answer for every Feature and nobody is asked it. A Feature places no files, so there is no disk a layer could be read off either: what its Harnesses actually hold is the whole of whether it is Enabled, which is what `health` is asked and why nothing keeps a record beside it.
- **The Manager's seam is three words, and every Feature's script answers them**, the two the Manager already says at its install and remove seams — `install-integrations` and `remove-integrations`, each taking `--harness` once per Detected Harness — and `health`, which is what Select reads a Feature's Enabled state from. What a Feature's script answers besides those is its own — the word its installed hook entry runs, or the one its installed instructions tell an agent to call — and the Manager says none of them. `install-integrations` and `health` also take `--replace`, the whole of the seam's vocabulary and never a flag of one Feature's own: it means *the user has confirmed, so you may take state another owner holds*, and a Feature holding nothing of that kind accepts the word and has no use for it. A Feature the Manager had to remember the argument list of would make the seam a table of exceptions. It reports per Harness in the shape `library/scripts/integrations.py` returns, one folded record per Harness however many things it owns there, so a reader told that two records disagreeing about one Harness is itself a finding never meets two records that are simply about two things.
- **Harness mechanics stay in the Collection Library** (ADR-0177). Which file a Harness reads its instructions from, how its hook table is written, and how a single-valued setting is taken or reported taken all live in `integrations.py`; a Feature supplies its owner identity, the command to run, and the moments it wants.
- **The ownership identity travels inside what is written.** A hook entry carries `--owner=` in its command; a block of prose is fenced by `<!-- <owner> begin -->` and `<!-- <owner> end -->`. Nothing keeps a register of what was installed, so install, repair and removal are one convergent operation over whatever is on disk, and a hand edit is a state to converge from.
- **A single-valued setting another command holds is a question, not a verdict** (ADR-0174). A table takes a second entry and a setting does not, so a Feature wanting one names what holds it on its row and writes nothing until the confirmation is answered — which `--yes` answers, along with everything else Select asks before it writes; no flag of its own is added for it. Nothing is kept of what is replaced: a private ledger goes stale the moment the user edits the setting by hand, so removal clears what this collection holds and restores nothing.
- **A Feature gets a `### <name>` section under the README's `## Features` heading**, on the same terms a Skill's section is written on.

## `help.md`

The root manpage ships as `help.md` beside its `SKILL.md` and is a file the Skill prints rather than prose it regenerates (ADR-0176). A Skill with subcommands also ships one page per command path under `help/`, mirroring nested paths as nested directories (ADR-0176). These pages are written for a reader deciding whether to Enable or use the Skill. Conventional installed manpages and brief terminal help are normally separate artifacts; this collection deliberately prints the complete addressed page for `--help`, `-h`, and top-level `help`, so each is a man-page-shaped Markdown reference rather than an installed roff page. The research behind the profile below, including its primary sources and the limits of the analogy, is in [`docs/research/manpage-help-conventions.md`](../research/manpage-help-conventions.md).

- **The title and fixed sections establish the page.** The file opens with `# <name>` as the Markdown analogue of a manpage's title metadata. `## NAME`, `## SYNOPSIS`, and `## DESCRIPTION` follow in that order. `## DEPENDENCIES` is the collection-specific section a reader deciding whether to Enable a Skill needs, including `None` where that is the complete answer, and `## SEE ALSO` closes the page. The suite holds those five sections present and in order on every manpage it finds; whether the prose under them is useful remains review judgement.
- **`NAME` is one line in the conventional form.** Write the invocation name, an ASCII hyphen, and a concise summary: `name - what it does`. Use the Skill name for its root page and append the complete space-separated command path for a subcommand page, such as `model-selector config add`. The summary is a phrase rather than a second description and carries no final period.
- **`SYNOPSIS` is the accepted grammar.** Give each genuinely distinct form its own paragraph rather than compressing incompatible forms into one line. Render literal commands and options in bold, replaceable metavariables in italics, square brackets around optional units, `|` between alternatives, and ASCII `...` after a repeatable unit. Examples and explanations live elsewhere. Every form ends with `[**--** *INSTRUCTION*]`, the optional Contextual Instruction suffix. Write every form in the collection's one invocation order — command path, then flags, then operands (ADR-0176). On the root page, the flags named in `argument-hint`, `## SYNOPSIS`, and `## OPTIONS` are one identical aggregate set, and the aggregate is silent about which of them may appear together — that is the per-form rule stated with `argument-hint` above; on every subcommand page, `## SYNOPSIS` and `## OPTIONS` are the identical set applicable to that path. When the set is empty, `## OPTIONS` is omitted and counts as empty. The standalone `--` is a separator, not an option, so `## OPTIONS` never lists it; `--help` is likewise the route into the manpage rather than a flag on a form and is named in none of the three.
- **`DESCRIPTION` starts with the normal case.** State observable behaviour, defaults, inputs, outputs, side effects, limits, and recovery needed to use the Skill correctly. Keep option-specific detail with the option and move architecture, implementation machinery, history, issue evidence, rejected alternatives, and decision rationale to the body, code, or ADR that owns them unless one fact prevents a likely misuse. Write short screen-sized paragraphs, normally one to three sentences, and split distinct decisions or outcomes instead of joining them into a monolithic paragraph.
- **Every page carries an `## INVOCATION ENVELOPE` section, and that section is a pointer.** It names the Contextual Instruction and the reserved separator, so a reader meets the `[**--** *INSTRUCTION*]` suffix every `SYNOPSIS` form ends with, and then sends them to `library/references/invocation-envelope.md` in the Collection Library for the contract in full — the quoted and attached forms, the Conversation Context rule, the semantic boundaries on applicable guidance, exact-help behaviour, both refusal categories with the narrowing ADR-0176 made to the second of them, selective propagation to nested Skills, and the absence of a mandatory acknowledgement on success (ADR-0176). No page restates that contract: a page that drifts from its siblings is one contract with two readings, and there are enough pages here that nobody would notice which had drifted. The path is written plainly rather than as `$LIBRARY`, a manpage being printed to a person who has no such variable. What `DIAGNOSTICS` says about an invalid form is not a restatement of it and stays where the bullet below puts it — that section names this page's own refusal, in this command's terms and pointing at this command's help route, which is the part no shared reference can write.
- **A command with subcommands carries `COMMANDS`.** List every immediate subcommand as a tagged term followed by a short description, with no accepted command omitted and no nested child flattened into its grandparent's list. Each listed path has its own page and direct `--help` route; a child that has subcommands repeats the rule on its page (ADR-0176).
- **All other sections are selected by content.** Use conventional uppercase headings and conventional order where they fit: `## COMMANDS`, `## POSITIONAL ARGUMENTS`, `## OPTIONS`, `## ENVIRONMENT`, `## FILES`, `## EXIT STATUS`, `## DIAGNOSTICS`, `## EXAMPLES`, `## NOTES`, then `## SEE ALSO`. A precise page-specific heading may replace a generic one where it improves retrieval. Omit an empty section instead of filling it with a statement that nothing is there; `DEPENDENCIES` is the sole local exception. `NOTES` is miscellaneous material, not a required home for details that belong elsewhere.
- **Arguments and options use tagged prose rather than generic lists.** Put the complete term on its own paragraph — literal tokens bold and metavariables italic — followed by its unbulleted description paragraph. State the default, constraints, repeatability, and important interactions where they matter. Put demonstrations under `EXAMPLES`, never in `SYNOPSIS`, and include only examples that resolve a non-obvious form, default, destructive boundary, or output shape.
- **The refusal is documented as well as performed.** Put invalid-form behaviour under `DIAGNOSTICS`, including that a flag with no work to do is refused rather than ignored, so strictness is reference information rather than miscellaneous commentary. End `SEE ALSO` with terse related invocations, not invented manual-section references.
- **Markdown carries the semantics, not roff syntax.** Use the uppercase section hierarchy and semantic emphasis above without roff macros, escapes, formatter spacing, or manual-section numbers. Every prose paragraph remains on one physical Markdown line under this repository's general standard, even though the Linux man-pages project uses semantic line breaks in roff source. Review the rendered page at a narrow terminal-like width as well as in source.

## `agents/openai.yaml`

Codex reads a Skill's user-facing name and its invocation policy out of this sidecar and out of nothing else, so the two facts the frontmatter already carries are written a second time, once per harness. The failure a missing sidecar causes is silent on the harness the Skill was authored against: it arrives in Codex nameless in the picker and implicitly invocable, whatever the frontmatter says. Both rules below are enforced by the suite, over every Skill the collection ships and the Manager among them.

- **`interface.display_name` and `interface.short_description` are present and neither is empty.** They are written for a person reading a list of Skills, which is why the sidecar carries its own rather than reusing the `description` — that field is the only hook a harness has for deciding when a Skill applies (ADR-0177), and a field written to be matched against a prompt reads as an instruction rather than as a label.
- **`policy.allow_implicit_invocation` is the negation of the frontmatter's `disable-model-invocation`, and both are written on every Skill**, `false` included where that is what the Skill means. Each harness defaults to allowing implicit invocation and neither default is leaned on: a Skill that writes nothing has not decided that a model may start it, it has only left the decision unwritten, and two files that each say nothing can come to disagree without either of them being edited. `$agents-md`, `$proofread`, and `$write` are the Skills here a model may start on its own (ADR-0177, ADR-0179; `$write` only on the literal token `/write` in a request or in an instruction it points at), and each says so in both files rather than in neither. Model invocation stays the exception, and a Skill that takes it writes a `description` narrow enough to be the whole of its trigger — the exclusions named as exclusions, because the model matches on what the Skill offers and no refusal can answer an invocation the user never typed (ADR-0177).

Codex accepts more than these two blocks — an icon, a brand colour, a default prompt, MCP dependencies — and this collection writes none of them. Nothing here has an icon, and a dependency declared there would be a second copy of the four lists the frontmatter already carries, kept true by hand and by nothing else.

## The README

A Skill gets a `### <name>` section under the README's `## Usage` heading, describing it to somebody deciding whether they want it. Keep this to one or two short paragraphs that establish the Skill's purpose and primary invocation; options, edge cases, implementation details, and full behaviour belong in its manpage. The suite fails when the Catalog names a Skill the README has no section for, and when a section names a Skill the Catalog does not.

The paragraph closing that part — which Skills need which binaries and which Capabilities — is prose, and nothing compares it against the dependency lists. Update it by hand when a Skill's requirements change, and expect no check to catch you if you do not.

## Refresh publication

Every shipped Skill is acquired and verified away from its active installation, then published as one complete directory entry (ADR-0175). A changed candidate atomically replaces the old tree, an identical candidate leaves its identity and timestamps untouched, and a Skill omitted from the selected generation is atomically retired with its old tree retained until the transaction succeeds. A failed acquisition, verification, replacement, or omission leaves the complete prior generation active. Logical paths resolving to one physical Skill tree produce one publication. The transport remains the acquisition boundary; the Manager owns active publication and removes every private staging or rollback artifact when the transaction ends.

Regenerate the Catalog when any authored file under `skills/` changed, including the Manager, and run the four checks. Both are in [`CONTRIBUTING.md`](../../CONTRIBUTING.md), together with how to compare a Skill against the specification's own reference validator.

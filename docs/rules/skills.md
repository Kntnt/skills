# Rules — what a Skill ships

Read before adding a Skill to this collection, or changing the files an existing one ships.

This module covers the form of a Skill's own shipped files — its `SKILL.md`, its `help.md`, and what lives beside them — and the Collection Library shared among Skills. It is not about what a Skill does; it is about what every Skill of this collection carries regardless of what it does and where shared implementation belongs. Read `general.md` first, and `python.md` too where the Skill or Library ships an engine.

Much of what follows is enforced by the test suite, and where it is, the assertion that fails names the rule and points back here. Not all of it is, and where the suite holds less of a rule than the rule says — the README paragraph nothing compares against anything, a manpage section checked for its heading and not for the prose beneath it — this document says so where the rule is stated, rather than leaving a contributor to infer it from a green run. Read a green fourth check as *nothing the suite watches broke*, never as *the form is right*.

The rules whose reasoning is settled in a decision record are named here in a phrase and cited to the record rather than argued again — the record is where the alternatives and their costs live, and a second telling of the argument is a second thing to keep true.

## Why this is written down as well as asserted

A rule that lives in two places can disagree with itself, and this collection's own preference runs towards a single copy a reviewer can diff. The contract is written twice anyway, and deliberately, because the two copies are read at different moments by readers in different positions.

A contributor who has not yet written anything cannot be helped by an assertion message: nothing has failed, because nothing exists to fail. This document is for that moment. A contributor whose suite has just gone red cannot be helped by a document they did not know to read: they have a heading and a path, and what they need is the rule. The assertion message is for that moment, which is why every test enforcing a rule below fails with the rule and its reason in a phrase, and a pointer here or to the record.

The copies stay together because only one of them states the rule in full. The message names the rule and cites where it is stated; it does not restate the reasoning, and this document does not reproduce the tests. What can drift is the pointer, and a citation to a record number that resolves to nothing fails the suite.

## The collection's flag grammar

**A flag of this collection's own grammar that takes a value attaches it with `=`, written `--flag=value`, and the space-separated form is written nowhere** (ADR-0096). One spelling, on every surface: the `argument-hint`, the `## SYNOPSIS` and `## OPTIONS` of every root and subcommand manpage, the argument prose and steps of every Skill body, and every invocation of the collection's own Python engines a body constructs. The Skills have no parser of their own — the agent reading these files is the whole of the enforcement — so a grammar that varies by Skill is a grammar that is guessed.

A flag taking no value is untouched, and so is the bare spelling of a flag whose value is optional: `--project`, `--project=on`, and `--project=off` are all compliant, and the same value written after a space is not. In a manpage the attached form closes the bold run after the `=` and renders the metavariable with underscores, as `**--data=**_PATH_`, because `**--data=***PATH*` is not the markup it looks like.

**A third-party command line keeps its own tool's spelling.** A body constructing a `git`, `gh`, `uv`, or `npx` invocation writes whatever that tool documents; their grammar is not this collection's to normalise. The collection's engines stay permissive for the same reason they always were — `argparse` accepts both forms and nothing is gained by refusing one there — so the rule is held by the suite, which reads every file a Skill ships and the documents governed here, and fails on a valued flag written with a space.

## The collection's invocation order

**A Formal Invocation is written in one order: the command path, then the flags, then the operands, then the reserved separator and its optional Contextual Instruction** (ADR-0097). The three grammar surfaces agree about it as they agree about the flags they name — the `argument-hint`, the `## SYNOPSIS` of every root and subcommand manpage, and the `## OPTIONS` that describes what those forms may carry — and so do a Skill body's argument prose, its steps, its refusal rules, the invocations of the collection's own engines it constructs, and every example in a manpage's `## EXAMPLES` and in the README.

The command path is the Skill name followed by the literal subcommand tokens that address a manpage, so a token belongs to the path exactly when a page under `help/` answers to it and is an operand otherwise (ADR-0077). Flags follow it, valued or not, in any order among themselves. Operands come last, which is what lets a free-text operand contain a word that looks like a flag: everything after the first operand is operand, and `/commit fix the --yes bug` needs no guess. The order is strict — an operand written before a flag is refused rather than repaired, in the same shape as an undeclared flag and an incomplete form (ADR-0059) — and each Skill's `DIAGNOSTICS` says so.

Where a Skill offers the same choice as an operand and as a long-option alias, the flag spelling sits with the flags and the operand spelling with the operands, and no documented form is left ambiguous about which of the two it is using. A single form can then no longer make such a slot mandatory, because the slot appears in two regions of the line; state the exclusivity under `DIAGNOSTICS` instead. A `git`, `gh`, `uv`, or `npx` command line a body constructs keeps the order that tool documents, on the boundary ADR-0096 already draws for flag spelling.

The suite reads every `argument-hint` and every `## SYNOPSIS` line and fails where a flag follows an operand, or where a subcommand token answering to a page under `help/` follows a flag. An alternation naming both spellings of one slot — `[**session**|**--session**]` — is one unit rather than a sequence, and is allowed only where everything before it is path or flag and everything after it is operand.

## `SKILL.md`

### Frontmatter

The frontmatter is YAML and is read by a real YAML parser, so anything YAML accepts is what the field means (ADR-0060).

- **`name`** is the Skill's directory name, exactly. **`description`** is the only hook the harness has for deciding when a Skill applies (ADR-0019), and the Catalog carries both.
- **The fields a Skill may carry** are the six the Agent Skills specification defines, plus `argument-hint` and `disable-model-invocation`, which the collection ships knowingly (ADR-0066). A ninth field fails the suite until the record accepts it too.
- **Every `argument-hint` ends with `[-- <instruction>]`**, exposing the optional Contextual Instruction without making the reserved separator part of the Skill's Formal Invocation (ADR-0078). Existing formal free-text operands remain distinct and keep their own spelling before that suffix.
- **No alternative form of `argument-hint` offers a combination `## SYNOPSIS` forbids.** The hint is one line and may collapse forms the manpage spells out separately, so the two are not held to the same count of forms; what is held is that the flags of each alternative the hint separates with ` | ` fit inside a single synopsis form. The aggregate rule below compares the three surfaces as one set of names, which cannot see a combination at all — a hint advertising a scope flag and a confirmation flag alongside a status form that writes nothing satisfies it — and what the user meets is a refusal for a form the harness told them to type.
- **`disable-model-invocation` is written on every Skill**, `false` included, and the Codex sidecar mirrors it — see [`agents/openai.yaml`](#agentsopenaiyaml) below, where the pairing and its reason are stated.
- **Every `metadata` key carries the `kntnt.` prefix and every value is a string** (ADR-0061). The namespace is flat and shared with every other collection, so an unprefixed key is a key anybody may claim; a value in any other shape is coerced by a foreign reader rather than refused, and lost without a word. A list is one space-separated string, an empty list an empty string.
- **The four dependency lists** — `kntnt.binaries`, `kntnt.skills`, `kntnt.externals`, `kntnt.capabilities` — are written even when all four are empty, and `kntnt.internal: "true"` marks the Skill as this collection's. The lists are hard requirements only: the checker exits 2 on anything in them (ADR-0012), so nothing a Skill degrades gracefully without belongs there. All four are written even where they are empty because a key nobody wrote is read as an empty list, which is the answer a Skill requiring nothing gives — so an omission cannot be told from a declaration once the key is gone.
- **`kntnt.integrations`** names a script inside the Skill that removes whatever that Skill installed outside its own directory — a Harness hook, an adapter, anything a file deletion would not reach. The Manager runs it with the single argument `remove-integrations` before it removes the Skill's files, which is the last moment those files can still say what they installed and where, and reports what it answered beside the removal itself. The value is a path relative to the Skill's own directory and may not climb out of it. Only a Skill that installs such a thing writes the key; its absence is the ordinary case and means deleting the files is the whole of the removal.
- **`compatibility` names exactly the binaries the dependency lists hold**, no more and no fewer, and the Capabilities likewise (ADR-0062). It is the one field a reader outside this collection knows to look at. A requirement the Skill degrades gracefully without is named there in prose and deliberately not in the lists — `/release` and `gh` is the only such case today. A Skill with nothing to state carries no `compatibility` field at all rather than an empty one.

### Body

The body carries only what the agent executes, which is why prose is the seam a Skill is held at (ADR-0046). This section governs what the body has to carry; how its prose is written is `/writing-for-agents`, which [`docs.md`](docs.md) states every body is authored under.

- **The dependency preamble is present exactly when the dependency lists are not empty.** A Skill with nothing to declare calls no checker, because the call could only ever report an empty list and would itself declare `uv` (ADR-0012). Where the preamble is present it invokes the checker as `check --here="$HERE"` and names `npx skills add Kntnt/skills` as the fix for a missing Manager.
- **An `## Invocation Envelope` section precedes `## Help` and Formal Invocation parsing.** It reads and follows the `## INVOCATION ENVELOPE` section of the Skill's own `$HERE/help.md`, applies Help and Arguments only to the separated Formal Invocation, and passes only that formal part to scripts or nested formal parsers. Before the first side effect, the Skill uses available read-only checks to identify unusable guidance; only a conflict that cannot be discovered until after a legitimate effect may stop later effects and report the exact partial outcome. The local page keeps a directly installed Skill self-contained while carrying the same caller-neutral split, validation order, semantic boundaries, refusal categories, Conversation Context rule, and selective propagation to nested Skills as every other page (ADR-0078).
- **A `## Help` section** routes `--help`, `-h`, and `help` to `$HERE/help.md`, printed verbatim (ADR-0044). A Skill with subcommands also routes `/<name> <command-path> --help` and its `-h` form to that path's page under `$HERE/help/`, stopping before normal work (ADR-0077). The heading is required and the routes sit under it: looked for anywhere in the body, their tokens prove nothing because the refusal clause names them again.
- **An invalid form is refused, never repaired or ignored.** The refusal names what was wrong, prints the `## SYNOPSIS` section of the most specific recognized command page verbatim, and points at that command's `--help` form; without a recognized command it uses `$HERE/help.md` and `/<name> --help`. The body states the rule with the clause *A flag is refused rather than ignored where it has no work to do here* and explains why accepting an ignored flag is misleading; the suite pins both.
- **A file only this Skill opens when the situation arises lives under its `references/`** (ADR-0063). A reference or script with several Skill consumers lives in the Collection Library instead (ADR-0076). The published user pages — `help.md` beside `SKILL.md` and any subcommand pages under `help/` — stay outside `references/`; the Manager also keeps `catalog.json` and `steps/` at their published addresses. Every other Markdown file a Skill ships is agent reference material, which is how the suite finds it: by discovery rather than a maintained list.
- **An executable helper used only by this Skill lives under its `scripts/`** (ADR-0063). The directory is created when the first helper exists and omitted where none does; a Python file beside `SKILL.md` has lost the resource structure that tells a reader what it is.
- **Every pointer resolves.** `$HERE/<path>` is resolved from the directory holding `SKILL.md`, `$LIBRARY/<path>` from the Collection Library, and a Markdown link from the file the link sits in; all three are followed by the suite, in every Markdown file a Skill ships.

## Collection Library

The Collection Library is shared implementation shipped inside the Manager at `library/`; it is not a Skill, carries no `SKILL.md`, has no Catalog entry, and is never Enabled separately (ADR-0076).

- **The resource directories mirror a Skill's.** Agent reference documents live under `library/references/`, and executable helpers under `library/scripts/`. They start flat, with no concern directory added until present files need the grouping or would otherwise collide; empty directories state nothing and are not shipped.
- **Ownership follows consumers.** A reference or script with one Skill consumer stays local to that Skill. With several consumers it moves to the Library, so there is one authoritative copy without making one consumer the implementation owner of another.
- **The editorial resources have a fixed shape.** `library/references/editorial/base.md` holds every normative outcome a first draft has to meet, once and in English, and names no Skill's options; `genres/` and `techniques/` beside it hold one file per selectable value, whose filename is its canonical spelling and whose directory is the only list of what is installed. A review half is a separate `<name>.review.md` beside its base half, so a Skill that only writes never loads it, and it restates no base rule (ADR-0095). `anti-slop.md` beside them is the collection's own condensed, language-independent adaptation rather than a dependency on an external Skill, it lives in the Library because more than one Skill applies that pass, and it carries the upstream notice inside the file, where a reader of an installed Skill receives it (ADR-0101). The format page for all of them is [`skills/kntnt/library/references/editorial/README.md`](../../skills/kntnt/library/references/editorial/README.md), and the Language Resource format page sits beside it.
- **Peer internals are not an interface.** A Skill may follow another Skill's `SKILL.md` where it declares that Skill as a Dependency, but it never reads the peer's `references/` or runs its `scripts/`. A body using the Library defines `$LIBRARY` from the Manager directory that contains its dependency checker and stops with `/kntnt update` when an older Manager has no Library.

## `help.md`

The root manpage ships as `help.md` beside its `SKILL.md` and is a file the Skill prints rather than prose it regenerates (ADR-0044). A Skill with subcommands also ships one page per command path under `help/`, mirroring nested paths as nested directories (ADR-0077). These pages are written for a reader deciding whether to Enable or use the Skill. Conventional installed manpages and brief terminal help are normally separate artifacts; this collection deliberately prints the complete addressed page for `--help`, `-h`, and top-level `help`, so each is a man-page-shaped Markdown reference rather than an installed roff page. The research behind the profile below, including its primary sources and the limits of the analogy, is in [`docs/research/manpage-help-conventions.md`](../research/manpage-help-conventions.md).

- **The title and fixed sections establish the page.** The file opens with `# <name>` as the Markdown analogue of a manpage's title metadata. `## NAME`, `## SYNOPSIS`, and `## DESCRIPTION` follow in that order. `## DEPENDENCIES` is the collection-specific section a reader deciding whether to Enable a Skill needs, including `None` where that is the complete answer, and `## SEE ALSO` closes the page. The suite holds those five sections present and in order on every manpage it finds; whether the prose under them is useful remains review judgement.
- **`NAME` is one line in the conventional form.** Write the invocation name, an ASCII hyphen, and a concise summary: `name - what it does`. Use the Skill name for its root page and append the complete space-separated command path for a subcommand page, such as `model-selector config add`. The summary is a phrase rather than a second description and carries no final period.
- **`SYNOPSIS` is the accepted grammar.** Give each genuinely distinct form its own paragraph rather than compressing incompatible forms into one line. Render literal commands and options in bold, replaceable metavariables in italics, square brackets around optional units, `|` between alternatives, and ASCII `...` after a repeatable unit. Examples and explanations live elsewhere. Every form ends with `[**--** *INSTRUCTION*]`, the optional Contextual Instruction suffix. Write every form in the collection's one invocation order — command path, then flags, then operands (ADR-0097). On the root page, the flags named in `argument-hint`, `## SYNOPSIS`, and `## OPTIONS` are one identical aggregate set, and the aggregate is silent about which of them may appear together — that is the per-form rule stated with `argument-hint` above; on every subcommand page, `## SYNOPSIS` and `## OPTIONS` are the identical set applicable to that path. When the set is empty, `## OPTIONS` is omitted and counts as empty. The standalone `--` is a separator, not an option, so `## OPTIONS` never lists it; `--help` is likewise the route into the manpage rather than a flag on a form and is named in none of the three.
- **`DESCRIPTION` starts with the normal case.** State observable behaviour, defaults, inputs, outputs, side effects, limits, and recovery needed to use the Skill correctly. Keep option-specific detail with the option and move architecture, implementation machinery, history, issue evidence, rejected alternatives, and decision rationale to the body, code, or ADR that owns them unless one fact prevents a likely misuse.
- **Every page carries an `## INVOCATION ENVELOPE` section.** It explains the Contextual Instruction and Conversation Context, the reserved separator and quoted/attached forms, the semantic boundaries on applicable guidance, exact-help behaviour, the syntax refusal for a malformed Envelope or Formal Invocation, the distinct context refusal for unusable guidance, selective propagation to nested Skills, and the absence of a mandatory acknowledgement on success (ADR-0078).
- **A command with subcommands carries `COMMANDS`.** List every immediate subcommand as a tagged term followed by a short description, with no accepted command omitted and no nested child flattened into its grandparent's list. Each listed path has its own page and direct `--help` route; a child that has subcommands repeats the rule on its page (ADR-0077).
- **All other sections are selected by content.** Use conventional uppercase headings and conventional order where they fit: `## COMMANDS`, `## POSITIONAL ARGUMENTS`, `## OPTIONS`, `## ENVIRONMENT`, `## FILES`, `## EXIT STATUS`, `## DIAGNOSTICS`, `## EXAMPLES`, `## NOTES`, then `## SEE ALSO`. A precise page-specific heading may replace a generic one where it improves retrieval. Omit an empty section instead of filling it with a statement that nothing is there; `DEPENDENCIES` is the sole local exception. `NOTES` is miscellaneous material, not a required home for details that belong elsewhere.
- **Arguments and options use tagged prose rather than generic lists.** Put the complete term on its own paragraph — literal tokens bold and metavariables italic — followed by its unbulleted description paragraph. State the default, constraints, repeatability, and important interactions where they matter. Put demonstrations under `EXAMPLES`, never in `SYNOPSIS`, and include only examples that resolve a non-obvious form, default, destructive boundary, or output shape.
- **The refusal is documented as well as performed.** Put invalid-form behaviour under `DIAGNOSTICS`, including that a flag with no work to do is refused rather than ignored, so strictness is reference information rather than miscellaneous commentary. End `SEE ALSO` with terse related invocations, not invented manual-section references.
- **Markdown carries the semantics, not roff syntax.** Use the uppercase section hierarchy and semantic emphasis above without roff macros, escapes, formatter spacing, or manual-section numbers. Every prose paragraph remains on one physical Markdown line under this repository's general rules, even though the Linux man-pages project uses semantic line breaks in roff source. Review the rendered page at a narrow terminal-like width as well as in source.

## `agents/openai.yaml`

Codex reads a Skill's user-facing name and its invocation policy out of this sidecar and out of nothing else, so the two facts the frontmatter already carries are written a second time, once per harness. The failure a missing sidecar causes is silent on the harness the Skill was authored against: it arrives in Codex nameless in the picker and implicitly invocable, whatever the frontmatter says. Both rules below are enforced by the suite, over every Skill the collection ships and the Manager among them.

- **`interface.display_name` and `interface.short_description` are present and neither is empty.** They are written for a person reading a list of Skills, which is why the sidecar carries its own rather than reusing the `description` — that field is the only hook a harness has for deciding when a Skill applies (ADR-0019), and a field written to be matched against a prompt reads as an instruction rather than as a label.
- **`policy.allow_implicit_invocation` is the negation of the frontmatter's `disable-model-invocation`, and both are written on every Skill**, `false` included where that is what the Skill means. Each harness defaults to allowing implicit invocation and neither default is leaned on: a Skill that writes nothing has not decided that a model may start it, it has only left the decision unwritten, and two files that each say nothing can come to disagree without either of them being edited. `/agents-md` and `/proofread` are the Skills here a model may start on its own (ADR-0018, ADR-0094), and each says so in both files rather than in neither. Model invocation stays the exception, and a Skill that takes it writes a `description` narrow enough to be the whole of its trigger — the exclusions named as exclusions, because the model matches on what the Skill offers and no refusal can answer an invocation the user never typed (ADR-0094).

Codex accepts more than these two blocks — an icon, a brand colour, a default prompt, MCP dependencies — and this collection writes none of them. Nothing here has an icon, and a dependency declared there would be a second copy of the four lists the frontmatter already carries, kept true by hand and by nothing else.

## The README

A Skill gets a `### <name>` section under the README's `## Usage` heading, describing it to somebody deciding whether they want it. The suite fails when the Catalog names a Skill the README has no section for, and when a section names a Skill the Catalog does not.

The paragraph closing that part — which Skills need which binaries and which Capabilities — is prose, and nothing compares it against the dependency lists. Update it by hand when a Skill's requirements change, and expect no check to catch you if you do not.

## Before opening the pull request

Regenerate the Catalog when any file under `skills/<category>/<skill>/` changed, and run the four checks. Both are in [`CONTRIBUTING.md`](../../CONTRIBUTING.md), together with how to compare a Skill against the specification's own reference validator.

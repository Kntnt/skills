# How an invocation is read

This record settles the invocation grammar in one place: how a caller's payload is split, what each half may do, what happens to a form the grammar does not allow, where a value attaches, in what order the parts are written, and how a reader reaches the page that documents any of it. It is a consolidation — it supersedes the eleven records named below, and carries forward what those records were for, which is the reasoning. What the rules are is stated in [`docs/rules/skills.md`](../rules/skills.md), which is the authority on them; the Envelope contract itself — the split, the boundaries, the refusal categories, the propagation rule — is stated once in the Collection Library, at [`invocation-envelope.md`](../../skills/kntnt/library/references/invocation-envelope.md), which every Skill executes and every manpage points at. This record argues rather than legislates, and where it needs a rule it cites the file that carries it rather than repeating it. A reader who wants today's law should be reading one of those two and not this. None of the eleven is annotated to say so: the duty that once had a later record reach back into an earlier one is retired, for the reason [`docs/rules/docs.md`](../rules/docs.md) gives, and each of them is read as of its own date until the sweep that removes it.

Two of the eleven contribute a correction to another rather than a subject of their own, and are carried inside the section of the record they correct rather than given one each: ADR-0122 narrows a single word of the Envelope's refusal rule, and ADR-0169 lifts an obligation from the invocation order without touching the order. Everything else below is reasoning a reader would otherwise have to reconstruct from evidence that no longer exists anywhere but in these records.

What a standing reframing mode selects for before it compresses words is ADR-0080's, which stays for the same kind of reason: no rules module holds it. Where a paragraph below needs either it names it and stops.

**Two chains run back through records the sweep deletes, and they are retold rather than pointed at.** ADR-0169 reasons from the record that gave `/brief` a closed grammar with no free-text operand, and ADR-0170 from the record that gave the same Skill's standing mode a session scope and a user scope written into a context file; both of those are binned `DROP`, being one Skill's own grammar and one Skill's own mode, stated on that Skill's own pages. Pointing at a file that is about to go would be a pointer into nothing, so the premise each of them leans on is written out where it is needed, in this record's own words.

## Why a payload has two halves at all

**Collection-wide strictness left a caller with the right facts and no way to hand them over** (ADR-0078, issue #87). Every part of an invocation was formal grammar, so guidance a Skill could have used — from a user, from a model that had just read the file in question, from an outer Skill that knew why it was calling — either had to be omitted or turned the invocation into a refusal. The Envelope answers that without spending the strictness: a Formal Invocation governed exactly as before, and one explicit channel beside it that every caller reaches the same way.

**The separator had to be reserved collection-wide, because a per-Skill one is a channel nobody can rely on** (ADR-0078). A caller composing an invocation for a Skill it has not read would have to know which token that Skill spends on context, which is the invisible Skill boundary strictness was adopted to remove. Reserving one token everywhere costs each Skill a token it can no longer take as formal data, and buys a channel every caller can use without asking. The exactness of the rule around it — one unquoted token, bounded, the first one only — is what keeps the cost that small: a payload that never writes the token is read exactly as it was before, later lines and paragraphs included.

**Reserving `--` is what costs the collection permutation, and the trade was made knowingly** (ADR-0078, ADR-0097). GNU tools use that token in the middle of a command line to end option processing, which is how they accept flags anywhere and still take free text; spending it here means that escape is not available, and the order rule below is what stands in its place. A caller needing a literal standalone `--` inside formal free text quotes or embeds it, which is the whole of what the reservation costs at the other end.

## What the second half may do, and what it may not

**A Contextual Instruction is read and used rather than parsed, ignored, or echoed** (ADR-0078). The alternatives were each available and each worse: accepting prose and ignoring it creates a channel with no semantics, inferring context from trailing prose is not portable across Harnesses and is ambiguous for every Skill whose formal grammar already takes free text, and letting each Skill decide whether prose is formal rebuilds the invisible Skill boundary that collection-wide strictness was adopted to remove.

**The boundaries are what keep an instruction from becoming a second grammar** (ADR-0078). Guidance is admitted where the Skill's contract left a choice open, and refused where honouring it would rewrite the contract — contradicting the formal half, widening what the Skill is answerable for, or standing a gate down. Without that line, prose would be able to reach anything the arguments cannot, and the strictness of the formal half would buy nothing at all. The same bounds hold guidance the session already carries, so a caller is never made to restate into the Envelope what the Skill can already read, and the channel does not become a ritual.

**Splitting before routing and before validation is what makes the two halves independent** (ADR-0078). The agent separates the Envelope first, selects a help route, validates the formal part, and only then interprets context — so a Skill cannot answer a syntax question with a semantic one, and prose can never be re-read as arguments to a form it was not part of.

**The two refusal categories are distinct because they send the user to different places** (ADR-0078). A malformed envelope or formal half is a syntax problem, answered with the synopsis of what was addressed; guidance that parses but cannot be honoured is not, and reporting it as syntax would tell somebody to fix a line that was already correct and send them to a page that could not contain the answer. The sharpest case is context arriving on an exact help route: the page's output is fixed, so there is nothing for the guidance to change, and the request is refused without the page being rendered at all — printing it and then refusing would answer half a request the Skill has just said it cannot take.

**One word of that second category was too wide, and a run refused a review nobody had written wrong** (ADR-0122, issue #146). An evaluation run met a text whose frontmatter settled the technique and the language, a genre flag on the invocation, and the instruction *Review it as a PAC piece in Swedish* — guidance every parameter of which a higher-precedence source had already resolved. The Envelope's *ineffective* reached it, so the run explained the precedence instead of doing the review, and it was obeying the collection: sixteen of eighteen fresh runs on the same text refused the same way. A ladder whose lower level exists to be overridden cannot make its own overriding an error, so *ineffective* now reaches guidance with no addressable effect at all and stops short of guidance a documented precedence has settled, which is suppressed while the run continues. The alternatives were worse in both directions — rewriting the editorial precedence would have left level 3 with no answer to what it is for, and a carve-out in the one Skill where it was observed would have left the same two rules disagreeing everywhere else and added a third rule only that Skill knew. What it costs is a judgement moved onto the agent: *no addressable effect at all* is narrower than *ineffective* and no more mechanical, and the failure it makes possible is the mirror of the one it fixes, guidance that genuinely reaches nothing quietly suppressed under the name of a precedence that never governed it. Naming the suppression in the delivery is what keeps that visible.

**Mixed guidance is not partially applied, and the read-only check is what makes that promise keepable** (ADR-0078, ADR-0122). Before the first side effect the agent uses whatever read-only checks are available to find out whether the guidance is usable, because a conflict discovered afterwards can no longer be answered by doing nothing. Where one is discovered anyway, later effects stop and the exact partial outcome is reported rather than silently rolled back — a rollback is a second thing that can fail, and a silent one leaves the user with a report that matches nothing on disk. That rule was written against guidance part of which is invalid, and it was never about a ladder resolving parameters one at a time: an instruction naming a technique the invocation left open and a language the artifact already settled is one ordinary invocation with one parameter landing and one suppressed.

**One Envelope belongs to one Skill, and a nested call gets its own** (ADR-0078). A Skill stays responsible for applicable guidance throughout its own work, including work it performs through another Skill, but it forwards only the relevant part as an explicit Contextual Instruction in the inner Skill's Envelope rather than copying context blindly. Blind copying would hand the inner Skill guidance addressed to a contract it does not have, which is the scope-widening the boundaries above already refuse. A successful run adds no mandatory acknowledgement of context; where a material choice the guidance changed belongs in the report, the report already names it.

## The guarantee the Envelope no longer makes

**The contract is now written down once, and the self-containment argument ended with the copies** (ADR-0078; issue #261, `a8c96ad`). Every shipped Skill executed the same contract and every one of them carried the text asking for it: an `## Invocation Envelope` section and a `## Help` section between the Skill's own description and its grammar, and a byte-identical 3.3 KB `## INVOCATION ENVELOPE` section in each of forty-seven manpages — a third of the smallest bodies, and one contract in as many editable places as the collection has Skills and pages, with nothing to say which copy was meant once two of them disagreed. The reason first given for those copies was that a Skill installed directly, without the Manager, still carried the caller-neutral split, the validation order, the semantic boundaries, both refusal categories, the Conversation Context rule and the selective propagation locally. The contract moved to one Collection Library reference; every body reaches it through `$LIBRARY`, the two Skills that had declared no dependency at all included, and a Skill installed without the Manager stops with `/kntnt update` rather than reading the contract locally.

**What each surface keeps is the part no shared reference could write.** A body names its own help routes, because which pages exist is the one thing a file shared by every Skill cannot know, and its `## Arguments` adds only which page a refusal addresses where the Skill has several and what the Skill leaves undone when it stops. A manpage's section names the separator a reader meets in that page's own `SYNOPSIS` forms and then gives the contract's plain path — plain, because a manpage is printed to a person who has no `$LIBRARY` — and what its `DIAGNOSTICS` says is no restatement either, naming that command's own refusal in that command's terms.

**That guarantee is therefore not part of what this record carries forward.** It stopped being true of this collection, and a consolidation repeating it would put a dead promise back into the archive as current argument. The rule that replaced it, with the price named as a price, is the **Peer internals are not an interface** bullet under `## Collection Library` in [`docs/rules/skills.md`](../rules/skills.md).

## Strictness, and the flag that made the seam visible

**Two tolerances passed silently on the collection's surface, and the second one is what exposed the first** (ADR-0059, issue #21). A subcommand the Manager did not have was re-read as `help`, so `/kntnt updat --yes` ran a different verb and the rest of the line became that verb's arguments; and a flag a verb had no use for was accepted and ignored, so `/kntnt help --yes` succeeded and did nothing. Both are errors, answered with the error, the synopsis of the thing actually addressed, and a pointer to `--help` — and with nothing else: no guess at which verb was meant, no half of a run, and nothing done with the rest of a line whose first word was wrong.

**The tell is `--force`** (ADR-0059, ADR-0029). `/kntnt help --force` already failed while `/kntnt help --yes` succeeded, and the only difference between them was that `--yes` happened to mean something on another verb. Nobody outside the script could see that difference, so what the surface taught was that some meaningless flags are errors and others are not, with no rule available to say which. The line had been drawn at *misleading* — `uninstall --project` refused because accepting it would state something false about the disk, `help --yes` tolerated because nothing could be misread — and the line does not hold, because tolerating it teaches exactly what that same record says must never be taught, that flags sometimes do nothing.

**Validity is judged per invocation, not per skill, and that is what fixes the scope** (ADR-0059). A flag is allowed where it has a function on *this* run, not where it has one somewhere in the Skill, so `/kntnt help --yes` and `delegation status --yes` are the same case. Settling them differently would have left the Manager strict and every other Skill lax, which is the seam again with a Skill boundary drawn through it. A Skill with no script has no parser to make strict either, so the rule has to be stated where the agent reads it and enforced there: strictness is a rule of the collection, not of the Manager.

**Presence follows function, which is the same judgement made one level up** (ADR-0059). There is no collection-wide flag set every Skill is expected to offer: a Skill's grammar names a flag exactly where that flag has work to do in that Skill — `--yes` where the Skill asks at least one question answerable yes or no, and nowhere else. A Skill that carries no such flag therefore documents no exception for it, because the strict grammar refuses every undeclared flag alike and a form nobody declared needs no reason of its own. The alternative was a body arguing the absence of a flag it does not have, which is a sentence every Skill would eventually be expected to carry about every flag it lacks, and which no assertion can recognise as prose — so that last part is held in review rather than by the suite.

**The fallback goes with the tolerance, and the second half matters as much as the first** (ADR-0059). A mistyped verb is an error, and whatever followed it is ignored rather than re-parsed — a line the user meant for `update` carries flags that would mean something to whatever the typo landed on.

**One error path, not two** (ADR-0059, issue #32). `uninstall --project` had a bespoke message naming the machine it clears, and the message went with the distinction that produced it: once every disallowed flag is an error, a message that exists because one of them was the misleading kind has nothing left to mark. Nothing is lost that the user cannot reach — the verb's own page carries the reason in full, and the pointer at the end of every refusal is what leads there. A special case in the code for one flag is the same shape of seam the rule exists to remove.

**What the strict rule re-opened is named rather than argued away** (ADR-0059, ADR-0029). The tolerance had been written to end a real failure: `argument-hint` advertised `--yes` on `/kntnt` while `apply enable --yes` died on `unrecognized arguments`, so the Skill was documented into a crash and only luck decided whether the model forwarded the user's own flag. Strictness re-opens that failure wherever the grammar and the parser disagree, and what answers it is a settled flag table both are read from — the test that reads the manpages also reads the parser, so a verb documented to take a flag it would reject fails in the suite rather than in somebody's session. The dependency gate is the sharpest edge, `check --here` running first in every Skill, and its call sites are pinned flagless for that reason.

## Where a value attaches

**The collection spelled a flag's value two ways and nothing decided between them** (ADR-0096). `model-selector` attached every value with `=`, every other Skill separated it with a space, and the Manager's optional-valued `--project` took both because the attached form is the only spelling an optional value has. All of it was legal and all of it was documented, which is the problem rather than the excuse: a reader who learns one Skill's grammar learns the wrong thing about the next.

**The attached form is chosen for three reasons that do not turn on taste** (ADR-0096). It is the only spelling an optional value has, so keeping the space form for the required flags would mean two rules where the collection can have one. It is unambiguous where a value begins with `-` or is empty, which the space form is not — `--model -mini` and a value nobody typed are both readable as the next argument. And it makes a flag and its value one token, which matters most here, because these Skills have no parser of their own: the agent reading `SKILL.md` and the manpage beside it is the whole of the enforcement, and an invocation is composed by a model into a free-text payload rather than split into `argv` by a shell, where two tokens are two things to keep beside each other through every reordering, truncation and quoting mishap.

**The space form was the alternative, and it was the smaller diff** (ADR-0096). It is the commoner spelling in hand-written terminal help and it is what most of the collection already wrote. It cannot express an optional value, so adopting it would have kept both spellings and settled only which one was usual — which is not a rule an agent can apply without knowing, per flag, which kind it is holding.

**The boundary is ownership rather than syntax** (ADR-0096). A `git`, `gh`, `uv`, or `npx` command line a body constructs keeps whatever that tool documents; rewriting it would assert a form those tools do not have. The collection's own engines stay permissive for a related reason — the only writer of those command lines is a Skill body in this repository, and a second parser built to refuse a spelling would be a second grammar to keep true — so the rule is held where the writing is, by a check that reads every file a Skill ships and fails on a valued flag written with a space.

**The registry that check reads was hand-written, and the price came due within one run** (ADR-0105, issue #121). The first two Skills added after the spelling was settled introduced six valued flags between them; none entered the list, and nothing failed, because every use in those Skills happened to be attached already. The registry had silently stopped answering for the newest part of the collection and would have gone on not answering until somebody wrote one of those six with a space and nobody noticed.

**The valued set is derived instead, from declarations the collection already holds to completeness** (ADR-0105). Every flag a shipped manpage's `## OPTIONS` declares with a value, unioned with the flags the engines declare as taking one: the pages name every flag any Skill surface offers a user, since a flag documented nowhere is a flag no user can write, and what the pages cannot name is the flag only a Skill body writes into an engine invocation, which the engines declare themselves. Neither source has to be complete on its own.

**A declaration is read in every spelling a declaration can be written in, the forbidden one included** (ADR-0105). Reading only the compliant spelling would put the flag written space-separated on every surface outside the derived set — and that flag is exactly the violation the rule exists to catch, so the derivation would be blindest in the one case it is for. The cheap alternative fails on the same spot: a staleness check that forces a flag into a hand list the moment an attached spelling is seen would have caught five of the six, and cannot see the sixth, a flag written space-separated everywhere and attached nowhere.

**What this costs is a suite that parses the engines' Python** (ADR-0105). An engine whose source cannot be parsed fails the derivation, and a future engine declaring its options through some seam neither `argparse` nor the hand-rolled one is a set quietly short of a flag — a derivation goes stale when the collection grows a new way of declaring an option, where a list went stale every time anybody added one. The derived set is also only as good as the declarations it reads: a manpage documenting a valued flag as though it took none puts that flag outside the rule. One small hand-written table remains beside it, naming the flags whose value is optional and the vocabulary each accepts; it decides nothing about what is valued and exists only to tell an operand behind a bare flag from a value, which no declaration states.

## One order, because of the operand at the end

**Every Skill wrote its operands before its flags and nowhere was that stated as a rule** (ADR-0097). It was inherited by imitation, so the next Skill inherited it too and a Skill quietly doing the opposite would have read as a variation rather than a defect. It was also the one part of the grammar nothing could judge: the suite compares the flags named in `argument-hint`, `## SYNOPSIS`, and `## OPTIONS` as a set, and a set has no order.

**The order is POSIX's, bounded by the one thing POSIX never had to answer for** (ADR-0097, ADR-0077). These Skills have command paths, so the rule has three parts rather than two. The path boundary is not a judgement about which words feel like commands: a token is part of the path when a page under the Skill's `help/` answers to it and an operand otherwise, which a builder can test against the shipped tree rather than argue about.

**The reason is the free-text operand, not symmetry** (ADR-0097). `/commit fix the --yes bug` has no reading that is both strict and useful while a flag may follow an operand: either the Skill guesses which `--yes` was meant, or it refuses a message a user had every reason to type. With the flags in front, everything after the first operand is operand, and the grammar stops depending on whether a word in the middle of a sentence happens to look like a flag. It is the same defence the reserved separator gives at the other end of an invocation, applied to the end that had none.

**Permuting was the alternative, and it fails on the operand that matters** (ADR-0097). Accepting flags anywhere is what most tools do, it would have cost no diff at all, and it is what a user expects — but permutation and free text are the same ambiguity seen from two sides, because a parser willing to find `--yes` after the message is a parser unable to accept a message containing `--yes`. GNU resolves this with `--` in the middle of the line, and this collection has already spent that token on the Contextual Instruction. The choice was therefore between free text and permutation, and free text is the thing users type.

**What the strictness costs is real and is not hidden** (ADR-0097, ADR-0059). The form every Skill documented until then stops working — `/commit "fix the parser" --yes` and `/release minor --yes` were the spelling in the manpages, and both are now refused rather than repaired. A user whose habits come from `git` or `gh` meets a refusal where either would have permuted the arguments and carried on. The collection accepts that because it already trades permissiveness for a grammar that reads the same way in every Skill, and an order enforced in one Skill and repaired in another is exactly the invisible boundary strictness was adopted to remove.

**An operand with a long-option alias keeps both spellings, and pays for it under `DIAGNOSTICS`** (ADR-0097). The flag spelling sits with the flags and the operand spelling with the operands, so neither documented form is ambiguous about which of the two it is using; the cost is that a single synopsis form can no longer make such a slot mandatory, the slot appearing in two regions of the line, and the exclusivity is stated where the rest of that grammar's exclusivity already lived.

**Where a grammar offers nothing for a leading word to shadow, the separator stops being an obligation** (ADR-0169, issue #250). A Skill whose whole grammar is its own name and an instruction has no subcommand and no flag, so prose after the name has exactly one reading, and the sentence about the shared channel was the only thing asking a user to type three characters. `/tldr bara säkerhetsdelen` and `/tldr -- bara säkerhetsdelen` are one invocation with one meaning. The ambiguity that forced a closed grammar on `/brief` — a bare `on` shadowing a legitimate instruction, so that `/brief on the security part` had no reading that was both strict and useful — is a property of the grammar and not of free text: it needs something for a leading word to be mistaken for, and a grammar with no command path and no flag offers nothing. A dash-prefixed token inside such an operand is part of the instruction for the same reason, obeyed as guidance or refused as guidance, never refused as an undeclared flag.

**What moves is the obligation and not the channel** (ADR-0169). The `argument-hint` still ends with the instruction suffix and every `## SYNOPSIS` form still ends with its marked-up equivalent, exactly as on every other Skill here, so a habit carried from any Skill to any other keeps working and a user who omits the separator is understood too. Keeping it mandatory everywhere would have bought uniformity of obligation at the price of a refusal with no ambiguity behind it, and strictness here is justified by a refusal the user can act on rather than by another Skill having needed one. Letting each Skill decide for itself is the state this ends: two Skills with identical grammars answering one payload differently is a thing a user would have to learn per Skill, which is the cost the reserved channel exists to remove. The condition is testable against the grammar — is there a command path, is there a flag — rather than an author's preference. What it costs is a page that documents one instruction in two slots and has to say in a sentence that the duplication is intended, a Skill that later grows a subcommand acquiring the ambiguity with it and having to drop the operand in the same change with nothing able to check that, and a user who learns the shorter form meeting the refusal on the next Skill that does not offer it.

## Where help lives, and how it is addressed

**`/kntnt help commit` asked the user to hold the wrong fact** (ADR-0044). It required knowing that `commit` had arrived through this collection — the Skill was in front of them, it answered when they typed its name, and the one thing they could not ask it was what it does. So the manpage ships beside the `SKILL.md` and the Skill prints it, and *where is the help* has one answer whether the thing being asked is a Skill or a subcommand.

**Help regenerated from a Skill's own instructions drifts silently** (ADR-0044). It falls behind the first time the instructions change and nobody re-reads the output, and there is nothing to diff, so nobody finds out. A file is a thing a reviewer can read and a thing the Skill can print without deciding anything.

**Reading about a Skill one does not yet have moved to where the decision is actually made** (ADR-0044). Select is where that route was really being used from, and the path is derivable rather than published anew — `category` is already a Catalog field, so the list reads an installed Skill's page from disk and fetches the collection's copy for one that is not installed. With that in place the older `/kntnt help <skill>` route was withdrawn rather than kept beside it: a second way to the same text is a second thing to keep true, and that one asked the user to remember the wrong fact. None of it makes the Manager the owner of a Skill's documentation; it never was, it was only the address.

**A root page cannot stay a usable reference for a Skill whose subcommands grow** (ADR-0077). `model-selector` demonstrated the failure with fourteen command paths on one page while `/model-selector recommend --help` was rejected outright and the user had to search that page for the relevant paragraphs. Every public subcommand has an addressable page under `help/`, mirroring command paths as nested directories, so the hierarchy is preserved without inventing filename separators.

**Every command with subcommands lists its immediate children and flattens none of them** (ADR-0077). The root page lists root children, a child with children repeats the rule on its own page, and the page tree and each `COMMANDS` section are checked against one another — so adding a page without listing it and listing a command without a page both fail.

**The help route is selected before ordinary validation, which is what lets an exact path be incomplete** (ADR-0077, ADR-0078). `config edit --help` needs no record identifier, because the request addresses documentation rather than the operation. The mirror of it is that an invalid normal invocation uses the most specific recognized page's `SYNOPSIS` and points at that path's own help route, keeping the error beside the grammar it violated.

**The pages stay authored rather than extracted** (ADR-0077). Extraction would either reproduce the overgrown root page or introduce a second renderer whose output can drift, which is the failure ADR-0044 removed in the first place. What it costs is more authored pages and some repeated background, bounded by command-specific usefulness: shared orientation stays on the root page, each command page carries what is needed to use that path, and the structural tests hold addressing and command discovery while prose quality stays a reviewer's job.

## The engines that read their own command line

**Two Library engines read their own arguments, and they were carrying copies of each other's parser** (ADR-0152, issue #220). The value reader was byte-identical between them, docstring included, and the normaliser that separates operands from options was the same loop twice, diverging in one token: one knew that `--yes` takes no value and the other had no notion of a valueless flag at all. Nothing exercised the difference, because the engine that had lost it has no such flag — so the copy that did not know they exist would have swallowed the operand behind the first one anybody added, and answered *needs one path* to a caller who had supplied one.

**Shared implementation has no honest owner among its consumers, and that holds between two Library modules as it holds between two Skills** (ADR-0152, ADR-0076). One module beside them is the whole of how this collection's command lines are read where `argparse` does not read them: a value written apart from its flag is joined to it, because these engines stay permissive about the attached spelling the collection writes everywhere else, and the operands are separated from the options whichever order the caller wrote them in, because the Skills write the flags first while these parsers read their own operand first.

**Which of an engine's flags carry no value is the engine's own fact, declared to the grammar rather than compared against a literal** (ADR-0152). A parser that compares a token against a name it has hard-coded is correct for exactly one caller and silently wrong for the next, which is the defect above written as a rule. Each engine names its valueless flags — one its `--yes`, the other an empty set, because it has none — and the grammar takes nothing from behind a flag that was named, so the first valueless flag either of them grows is parsed correctly by construction rather than by somebody remembering.

**Migrating both to `argparse` was the alternative, and their refusal contract is what it could not carry** (ADR-0152). Every line these engines will not run is answered with a JSON body carrying a stable code, on exit 2, on stdout — which is what their callers parse and what the Skills render — where `argparse` answers with a usage dump on stderr and an exit status of its own. An `argparse` migration would have had to reproduce every code in both invocation orders before it was even equal to what stood, and the three Library engines that already use it are untouched precisely because they have no such contract to reproduce. The parsing seam turns on whether an engine's refusals are machine-readable, not on taste.

**What this costs** (ADR-0152, ADR-0076). A third module in a Library that had five, and two engines that now fail at import where the Library is incomplete rather than at the first command line they are given — the same revision coupling shared implementation already priced, one file wider. A declaration is also a thing that can be left unwritten: a valueless flag its engine forgets to name is parsed as though it took a value, which is today's behaviour rather than a new failure, and it is the one part of this the suite cannot see for an engine whose flag does not exist yet.

## A mode is typed into a conversation, and the conversation is its whole scope

**A standing mode with a persisted scope answers for windows that never asked** (ADR-0170, issue #251). `/brief on` once held in a session scope or in a `--user` scope written as a managed block into the Harness's global context file, and almost all of the Skill's weight was that persistence: the target file, the block and its markers, the confirmation before writing, the staleness comparison, the two-blocks-in-one-file case, and a `status` that had to report which of two scopes won — 28.5 KB across eight files against a 2.2 KB payload. The mode is now adopted for the conversation it is typed in and nothing is written anywhere, so two windows open on the same project hold independent states and no later session starts with the mode on.

**The scope is the conversation because the mode is a property of the work in front of you, not of the person** (ADR-0170). A window where a long design discussion is running wants the perspective; a window where a build is being driven wants the file-level detail the perspective removes. Both are open at once, on the same project, and any scope wider than the conversation forces one answer on both — which is what the `--user` scope could not avoid, turning the mode into a standing default nobody chose per conversation and making *off* in one window a write to a file every other window read.

**An Output Style cannot carry this, and that is on the record so it is not proposed a third time** (ADR-0170). It has been asked for and declined twice, and the reasons already given hold — only one Harness has them, the route into them moved, and they are read once at session start, so a flag cannot change the conversation it was typed in. The decisive one is newer: an Output Style is read from a settings file, one per user or per project, so two windows on one project read the same file and get the same state, and giving them different states is the whole requirement. The managed block fails the same way from the other end, living in the global context file every session loads.

**A bare `/brief` is an invalid form rather than a toggle** (ADR-0170, ADR-0080). It is refused the way every other invalid form here is, because that Skill's bare invocation was the reframing command for as long as the Skill had existed and a user typing it out of habit would silently get a state change instead of the answer they meant — where a sibling Skill's bare form has one obvious reading and does toggle. Every form now names the state it produces, and the muscle memory is caught by the root page's `SEE ALSO`. What the mode selects for before it compresses words is untouched and stays where it was decided.

**What this costs** (ADR-0170). A user who wanted the mode on by default sets it in their own configuration and the Skill will not do it for them, which is the honest division — a standing default across sessions is a preference the user owns rather than something a Skill writes into a hand-curated file. Two windows that should agree have to be told twice, compaction can drop the instruction with nothing to detect it and retyping as the repair, and the Skill can no longer answer *is it on somewhere else*, because this conversation is all there is.

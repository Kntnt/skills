# What a Skill ships

This record settles the form of a Skill in one place: what kind of artifact the collection publishes, what its frontmatter has to carry and who the fields are written for, what belongs in the body and what does not, where the files beside it live, where implementation with several consumers goes, and when a model may start a Skill without being asked. It is a consolidation — it supersedes the twelve records named below, and carries forward what those records were for, which is the reasoning. What the rules are is stated in [`docs/rules/skills.md`](../rules/skills.md), and for the two that are promises of the collection rather than of a Skill's form in [`docs/rules/collection.md`](../rules/collection.md); those modules are the authority on them. This record argues rather than legislates, and where it needs a rule it cites the module rather than repeating it. A reader who wants today's law should be reading the module and not this.

## The records folded into this one

- ADR-0008 — Portable skills only; no harness command files
- ADR-0012 — Each skill declares its dependencies; the catalog is generated; checks are shared
- ADR-0015 — The collection repo groups skills by category
- ADR-0018 — `agents-md` is a Model-invoked skill with a safe write set
- ADR-0019 — The `agents-md` description is the only hook
- ADR-0046 — The skill body carries only what the agent executes
- ADR-0060 — Frontmatter is read by a real YAML parser, and the price is the offline cold start
- ADR-0061 — The collection writes one flat, prefixed `metadata` namespace
- ADR-0062 — `compatibility` states the environment, and names no product
- ADR-0063 — On-demand files live under `references/`
- ADR-0076 — Shared implementation belongs to the Collection Library
- ADR-0094 — A model starts a Skill only inside a description that bounds the trigger

**Two of the twelve contribute less than a whole record's worth, and where that is so it is said rather than padded.** ADR-0018's safe write set is one Skill's own behaviour, stated in `agents-md`'s shipped documents where a reader already meets it, so nothing of it is carried here beyond the half that generalised — why a Skill of that kind is model-invocable at all. ADR-0015's grouping is a one-line rule about a repository layout the Transport already discovers; what is carried from it is the part with a consequence, that a Skill's identity is its name rather than its path. Everything else below is reasoning a reader would otherwise have to reconstruct from evidence that no longer exists anywhere but in these records.

## The artifact is a Skill, and that is a portability stance

**Claude Code distinguishes a slash-command file from a Skill, and no other Harness implements the difference** (ADR-0008). A `commands/*.md` file is preprocessed — `$ARGUMENTS`, `@file`, `!shell` — and a collection shipping one would behave differently depending on where it landed: working as written in one Harness, and arriving as inert text with unexpanded placeholders in the next. What the user starts by name is therefore a user-invoked Skill, a static `SKILL.md` the model carries out with its own tools, everywhere. The rule is in [`docs/rules/collection.md`](../rules/collection.md), with the collection's other promises about how it reaches a machine, because it is a statement about what the collection publishes rather than about the files any one Skill carries.

**A Skill's identity is its name and not its path** (ADR-0015). A flat directory of Skills stops being readable past a handful, so the repository groups them by Category and the Transport discovers that layout already — but `/grill-me` stays `/grill-me` when it moves from one Category to another, and Category names are free to change for exactly that reason. A Category is not itself something to check: the user answers one Skill at a time, and `select --on=wordpress` is not a thing. That rule is in [`docs/rules/collection.md`](../rules/collection.md) too, beside Select's list, which is the only place a Category is visible to anybody.

## The frontmatter is read by a parser everybody else uses

**The hand-rolled parser existed to keep the script dependency-free, and the premise did not hold** (ADR-0060). About eighty lines read maps, lists of scalars, and quoted and bare scalars, while `uv` was already a hard dependency the Manager's own `SKILL.md` states in as many words and every script in the collection runs through — with the PEP 723 block that declares what the script needs sitting empty. A real parser was one line and one dependency `uv` installs unasked, measured at 0.42 s on a cold cache with the network up and 0.06 s warm.

**What the subset bought was a narrow window, and it is spent deliberately rather than discovered later** (ADR-0060). With a cold `uv` cache *and* no network, a script declaring a dependency does not start at all — the resolver has nothing to resolve from and fails before the first line runs — where the same script with an empty dependency list runs fine. That is not a small window to walk into blind: `check --here` is the first thing every Skill of the collection runs, so in that state every Skill with a dependency dies before doing anything and the message the user meets is `uv`'s resolver rather than the collection's. One run with the network up warms the cache for good, and every one of those Skills already requires `uv` to be installed at all.

**What is bought back is the class of bug the subset was** (ADR-0060, issue #48). The parser is what reads *other people's* files: the marker check is an untrusted boundary by design, any bytes at all from a directory the collection did not write, and a hand-rolled parser that silently mis-reads unknown input is exactly where a defect hides with nothing to catch it. That defect was found by hand rather than by a test, which is the point, because the next one would be too. A parser everybody else uses does not have that class of bug and is exercised by more users in a day than this collection will see.

**A parser that reads more also refuses more, and the boundary absorbs that** (ADR-0060). Malformed YAML raises where the subset skipped the line it could not read, so the parse error joins what the marker check swallows alongside a missing file and undecodable bytes: a file the collection did not write may be anything at all, none of it can claim to be this collection's, and none of it may take a run down with a traceback in place of the report.

**Adopting the format widened what a Skill may look like, and that is recorded rather than left to pass in silence** (ADR-0060). A folded `description: >` had yielded the indicator itself under the subset, so Catalog generation refused it to keep a lone `>` out of a field that is a Skill's entire help text until it is Enabled; that refusal was never a design decision, only a limitation with a courteous error attached, and it went with the limitation. What survives of the record's own correction to `/tldr` — which ADR-0061 later left nothing to correct — is the principle behind it: the format is followed rather than accommodated, and a branch admitting one wrong value is the same accommodation one step down.

## One flat namespace, because the reader is a stranger

**A foreign reader does not refuse the wrong shape, it coerces it** (ADR-0061, issue #52). The specification defines `metadata` as a map from string keys to string values, one level, strings on both sides; what every Skill carried was neither — a boolean, and a nested map holding four lists — so a standard reader answered with the Dependency lists flattened into a Python repr and the marker's value as the word `true`. Nothing warned, because a string is a legal value and coercion produced one. That is the failure mode this whole section is written against: the copy nobody in this collection reads is the copy nobody in this collection notices breaking.

**Space separation follows the specification's own precedent, and the alternative is a second format** (ADR-0061). `allowed-tools` is a space-separated string for exactly this reason, a list having to survive in a map whose values are strings; encoding JSON into the value is a second thing to parse and the same repr problem wearing better punctuation. A Dependency name has no spaces in it, so splitting on whitespace is lossless, and an empty list is an empty string — unambiguous under any parser, which is what a nested block never was.

**The marker is the prefix rather than a block, which ends the trap the block was** (ADR-0061). A Skill with nothing to declare writes its four lists empty and is marked by that, a shape a foreign parser can neither lose nor mistake; there is no value left that means *marked and empty* only to a parser that reads a block whole.

**Prefixing `internal` is a real cost paid on purpose** (ADR-0061). The namespace is flat and shared with every other collection, so a bare key is one anybody may claim, and prefixing means a reader looking for a bare `internal` to keep a Skill out of ordinary discovery no longer finds one here. Nothing in this collection reads the key — it is written for readers elsewhere — and a key any collection may claim is not one this collection could rely on either way, so correctness under the specification is worth more than a convention only some readers honour.

**`compatibility` is a third copy of a fact, justified by the reader it is for** (ADR-0062, issue #53). The requirements were already stated twice, in the body's prose and machine-readably in the dependency lists the checker refuses on, and both copies only speak to a reader that already knows this collection: the private namespace is one nothing outside is obliged to decode, and the body's paragraph is invisible until the Skill has been loaded and activated. `compatibility` is the one field a foreign consumer — another Harness, a registry, a validator — knows to look at, and a blank one says a Skill needs nothing. So the copy that can drift is pinned rather than trusted, by a test that holds every binary in a Skill's dependency block against that field from both sides.

**It also holds what the dependency lists deliberately cannot** (ADR-0062). Those lists are hard requirements only, the checker exiting non-zero on anything in them, so a requirement a Skill degrades gracefully without has nowhere else to go — `/release` needs `gh` for one step and reports the pushed tag without it. Such soft requirements are stated in `compatibility` and reviewed by eye, because no list holds them to be checked against.

**No `compatibility` names a Harness product** (ADR-0062, ADR-0008). The specification's own example names one, and that is exactly what this collection is not: one set across many Harnesses. Where a Skill needs something of the Harness it names the Capability rather than the product that has it, so the field stays true wherever the collection is installed. The mirror rule holds as it does for the checker: a Skill with nothing to state carries no field at all, and gains one the day it gains a requirement.

## The lists are the Skill's, and the check is the collection's

**A Skill's own `SKILL.md` is the source of its Dependency list, because the Skill has to be able to refuse when the Catalog is not there** (ADR-0012). The Catalog is generated from those files so Select and Update can see the graph, rather than being a second authored list that can disagree with the Skill it describes. Every Skill calls the same checker in the Manager, so the Unsatisfied message stays one instruction instead of a different paragraph in each Skill.

**A Skill with nothing to declare calls no checker** (ADR-0012). The check could only ever report an empty list, and running it would mean declaring `uv` for the sole purpose of letting the check that proves there are no dependencies execute. The mirror is the rule for the next author: the day a Skill declares its first Dependency it gains the check alongside it, in the same shape as every other, so the message stays one instruction wherever there is something to be unsatisfied about.

## The body is paid on every invocation

**Every line of a body is paid on every invocation, and a line the agent does not act on buys nothing** (ADR-0046). Help left `SKILL.md` because it drifted, and it should have left for this second reason, which binds more than help: a description of a flag is not an instruction, it is documentation that happens to be stored where the instructions are, and the Harness reads the whole file to find out what to do. Audience decides placement inside a Skill exactly as it decides placement inside a repository — the body points, it does not copy.

**The test is whether removing a passage changes what the agent does** (ADR-0046). A section describing flags the Steps already act on fails it, the Steps saying *wait unless `--yes`* and the description above them saying the same thing to nobody who will act on it. Parse rules pass it, because the step that carries them out has nothing to carry out without them — and that distinction is the whole rule.

**The record's own count claim is outrun, and the rule is why rather than despite** (ADR-0046, ADR-0059, issue #66). It first measured itself in Skills that lost an `## Arguments` heading and one that kept it; once every Skill had to state the grammar it accepts and the one refusal that answers everything else, the heading came back in every body — carrying rules rather than descriptions, a grammar line the agent parses against and a refusal it carries out. What those Skills lost they have not got back: the per-flag bullets are gone, each Step carrying in full what its bullet said. The heading was never what the record measured; the passage under it was.

**What this costs is a reader who opens a `SKILL.md` alone** (ADR-0046). They no longer find out what the Skill takes, which is deliberate — the body is not written for that reader, and the file that is sits next to it. The drift traded into is a manpage that can fall behind the Steps, which is a file a reviewer can diff, rather than a regenerated text nobody can.

## The directories say what a file is for

**A flat Skill root says nothing about which of its files a user reads and which the agent opens when a situation arises** (ADR-0063, issue #54). You had to already know that the manpage is the manpage and a gates document is not. `references/` is the convention that says it, and it says the same thing here as in any other collection, to a reader who has never seen this one; `scripts/` holds a Skill's executables, as it already did. `assets/` has nothing to hold, and an empty directory is not a statement. The specification calls these recommendations rather than requirements, and that is established without appeal to any external validator — the reference validator rejects every Skill this collection ships, and did then, over frontmatter fields no directory layout touches (ADR-0066).

**The manpage stays in the Skill's root because its address is published** (ADR-0063, ADR-0044). Select fetches it from the origin for a Skill the user does not have yet, at a path derived from the Catalog's own `category` field, and moving it would change a published path to buy nothing — the one thing a manpage never needs is a directory explaining that it is one.

**The Manager's `steps/` is not documentation; it *is* the steps** (ADR-0063, ADR-0046). Folding it into `references/` would erase the line between what a Skill executes and what it consults, which is the line the collection is built on. The same line answers a brief handed to a subagent: it is read at one step of the caller's own procedure, filled in, and given to somebody else — consulted, not executed. What was once a Manager-only `help/` exception is now the manpage tree of any Skill with subcommands (ADR-0077), while `steps/` remains the Manager's own.

**The Manager's published data files stay where they are for the same reason as the manpage** (ADR-0063). An installed Manager fetches the Catalog from a fixed path in the origin, so that path is a contract rather than internal layout; moving it would break the fetch for every installation already out there, and the verb that would deliver the repair is the one verb that cannot run without the Catalog it could no longer find.

**Two things spelled the same are kept apart** (ADR-0063). A *References* line is a pointer written into an `AGENTS.md`, one line per file with the class of work that should open it; a `references/` directory is a place inside a Skill. Neither rule reaches the other, and the words are near enough that a record letting them blur would be read as saying that a Skill's `references/` is written by `agents-md`, or that a References line points into one.

**What holds the layout is a test rather than the convention** (ADR-0063). A layout only moves once every body naming a file agrees, so the suite follows both pointer shapes the collection uses and fails on the first that resolves to nothing. That is what makes the directories safe to adopt: the cost of a move is a rewrite of every pointer into the moved files, paid once, and a half-done rewrite is caught there rather than in somebody's session.

## Shared implementation has no honest owner among its consumers

**Putting a shared file under one consumer makes every other consumer reach through that Skill's private layout, and duplicating it makes one rule several things to keep true** (ADR-0076). So a reference or script with several consumers lives in the Collection Library, and one with a single consumer stays where its consumer is. The Library mirrors a Skill's resource structure and starts flat: a subdirectory is introduced when present files need the grouping or would otherwise collide, never to predict a second domain that does not exist.

**A peer Skill is an interface, never an implementation address** (ADR-0076). Reaching into a peer's own resource directories would make the Dependency graph describe incidental reuse — where one consumer happened to keep a file — instead of behaviour the user can Enable, and it would freeze that consumer's private layout into somebody else's contract. Declaring the peer's behaviour and following its `SKILL.md`, as `push` follows `commit`, is the version of the same reuse that survives the peer rearranging its own files.

**The Manager is the Library's transport, which is what keeps the Library from becoming a Skill** (ADR-0076). The initial transport installs only the Manager, Update refreshes it, and Uninstall removes it last, so shipping the Library inside it introduces no separately Enabled support Skill and no second installation mechanism. A consumer resolves the Library beside the dependency checker it has already found, and where an older Manager has no Library it stops and names `/kntnt update` rather than reaching into a peer Skill as a fallback.

**What this costs is a coupling no Catalog edge expresses** (ADR-0076). A consumer and the Library are revision-coupled: the refusal makes the first migration explicit, and a later change to a shared file has to ship with the Manager and with every consumer whose expectations it changes. That is the price of one authoritative implementation without turning implementation details into user-selectable Skills — and it is the price the collection has since chosen to pay for its most widely consumed contract, the Invocation Envelope, whose one statement now lives there. The rule, and the guarantee that move withdrew, is the **Peer internals are not an interface** bullet in [`docs/rules/skills.md`](../rules/skills.md).

## When a model may start a Skill

**A Skill's `description` is the whole of the hook, so a second hook is meaning in two places** (ADR-0019). Where a Skill is started by a model rather than by a user typing its name, the description is what the decision is made from; adding a pointer to an always-loaded file beside it would duplicate that meaning and spend always-loaded lines for nothing.

**That is also why the Codex sidecar does not reuse the description** (ADR-0019). The sidecar carries a Skill's user-facing name and its invocation policy for the one Harness that reads them from nowhere else, and the label it shows a person browsing a list is not the field a model matches a prompt against: a `description` written to be matched reads as an instruction rather than as a name. So the sidecar is written with its own short line, and the two facts the frontmatter already holds are written a second time, once per Harness — a duplication paid because the failure it prevents is silent on the Harness the Skill was authored against. What each file has to carry, and the pairing that keeps them from disagreeing, is stated in [`docs/rules/skills.md`](../rules/skills.md).

**The risk model invocation carries is not that the Skill runs when it should not have** (ADR-0094). It is that a Skill runs against a request its own contract refuses, and there is no invocation for the refusal to answer. A user who types the Skill's name on a request it does not cover can be told so; a model that reached the same Skill from *make this better* has already decided, and the Skill either does the narrow thing the user did not ask for or the wide thing it promised not to do. Both are worse than never having been reached.

**A Skill a model may start bounds its trigger inside its own description** (ADR-0094, ADR-0019). For the collection's second such Skill the bound is a conjunction — a specific text is at hand, *and* the request either uses a proofreading term or is unambiguously limited to mechanical language errors — because neither half is sufficient alone: a proofreading term in a question about what proofreading is names no text, and a text alone names no request.

**The exclusions are written as exclusions rather than left to be inferred** (ADR-0094). A model reads what a Skill offers and matches a prompt against it, so a description that describes only what the Skill does leaves *edit*, *rewrite*, *polish*, *improve*, and *review* to be judged as near misses of a good description rather than as the different requests they are. Named, they are answers rather than inferences. It costs a longer description than a user-invoked Skill would need, which is the right place to spend length: the description is read by the thing making the decision.

**Invocation by name stays available on every such Skill, and is what makes the narrow trigger affordable** (ADR-0094). A trigger tight enough to exclude the ambiguous cases will fail to fire on requests that genuinely wanted it, and typing the name is what that user reaches for. A Skill whose only route in was a model's judgement would have to widen the trigger to stay usable, and widening it is exactly what the contract cannot survive.

**Two exceptions with no stated rule would be a habit rather than exceptions** (ADR-0094, ADR-0018). The first Skill of this kind was model-invocable for a reason of its own — its work belongs after other work, and nobody would think to ask for it — and the rule was written about that Skill. The second is the opposite case, a Skill people ask for constantly in ordinary language about a text already in front of them, which is what made the general question unavoidable. The collection therefore names the Skills a model may start, and the suite reads the set off the frontmatter, so it cannot grow by omission. What the suite cannot judge is whether a given description is actually narrow: it holds the exclusions present and the two invocation fields in agreement, and whether the prose bounds the trigger is a reviewer's reading. That limit is why this is reasoning and not only a test — an author adding the third such Skill needs the argument, not a list of substrings to include.

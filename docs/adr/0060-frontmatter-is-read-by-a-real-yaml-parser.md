# Frontmatter is read by a real YAML parser, and the price is the offline cold start

The Manager read a skill's frontmatter with about eighty hand-rolled lines: maps, lists of scalars, quoted and bare scalars, and nothing else. That subset existed to keep the script dependency-free, and the premise does not hold. `uv` is already a hard dependency — the Manager's own `SKILL.md` says so in as many words, and every invocation of every script in the collection goes through `uv run` — while the PEP 723 block that declares what the script needs sat empty. A real parser was one line and one dependency `uv` installs without the user doing anything: measured on the maintainer's machine, 0.42 s on a cold cache with the network up, 0.06 s warm. **`parse_frontmatter` reads through `yaml.safe_load`, and the subset is gone.**

**What the subset bought, and what is being given up.** With a cold `uv` cache *and* no network, a script that declares a dependency does not start at all — the resolver has nothing to resolve from and fails before the first line runs — where the same script with `dependencies = []` runs fine. That is not a small window to walk into blind: `check --here` is the first thing every skill of the collection runs, so in that state `agents-md`, `delegation`, `commit`, `push`, and `release` all die before doing anything, and the message the user meets is `uv`'s resolver rather than the collection's. The window is narrow — one run with the network up warms the cache for good, and every one of those skills already requires `uv` to be installed at all — but it is the whole of what the subset was worth, and it is spent deliberately here rather than discovered later.

**What is bought back is the class of bug the subset was.** The parser is what reads *other people's* files: `carries_marker` is an untrusted boundary by design, any bytes at all from a directory the collection did not write, and a hand-rolled parser that silently mis-reads unknown input is exactly where a defect hides with nothing to catch it. Issue #48 was that defect, and it was found by hand rather than by a test — which is the point, because the next one would be too. A parser everybody else uses does not have that class of bug, and it is exercised by more users in a day than this collection will see.

**A parser that reads more also refuses more, and the boundary absorbs that.** PyYAML raises on malformed YAML where the subset skipped the line it could not read, so `yaml.YAMLError` joins what `carries_marker` swallows alongside `OSError` and `UnicodeDecodeError`. The rule there is unchanged and is the rule of issue #5: a file the collection did not write may be anything at all, none of it can claim to be ours, and none of it may take the run down with a traceback in place of the report. `parse_frontmatter` itself keeps its contract — it splits on the `---` fence, and a file with no frontmatter or an unterminated one answers `{}` — and raises for a closed fence holding something unreadable, which is a caller's decision rather than the parser's.

**`description: >` becomes valid, and that is a widening of what a Skill may look like.** The subset had no block scalars, so a folded description yielded the indicator itself and Catalog generation refused it to keep a lone `>` out of a field that is a skill's entire help text until it is Enabled. That refusal was never a design decision, only a limitation with a courteous error attached, and it goes with the limitation: a description may now run over lines. This is recorded rather than left to pass in silence, because it changes what a contributor may write and what the Catalog may carry.

**The format is followed rather than accommodated.** A bare `kntnt:` is `null` in YAML, not an empty mapping; `{}` is how an empty mapping is spelled. The subset read the bare key as `{}` and `/tldr` was written to that reading, with a comment explaining that the standard spelling could not be used. So `/tldr` is corrected to `kntnt: {}` and the comment goes with it, rather than `collection_block` being taught to accept `null` as an empty block. That check still requires a mapping and still refuses `null` with the message issue #48 gives it — `kntnt: true` and `kntnt: some-string` are errors under any parser, and a branch admitting one wrong value would be the same accommodation one step down.

**Two of the four checks name the package themselves.** `uv run` gives the script what its PEP 723 block declares, so nothing that goes through the script has to know about PyYAML. The type check and the test run do not go through it — `uvx mypy` runs in an environment of its own and needs the stubs, and the suite imports the script into the interpreter pytest is running under — so both name it in the command. That is a cost of the dependency and is written down here so it is not mistaken for incidental tooling drift.

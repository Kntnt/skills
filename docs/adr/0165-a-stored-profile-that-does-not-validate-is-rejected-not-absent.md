# A stored profile that does not validate is rejected, not absent

`_read_profile` answered `None` for three different situations — no file, a file it could not read, and a file that failed the profile contract or its reference integrity — and every caller downstream saw the same thing. Route inherited on every request with `missing_profile`, the audit's `profile_revision` was null, and the machine that had run `setup` and had three configured channels and eight configured selections on disk was routed as though nothing had ever been configured. It was reachable: `profile.schema.json` was written after the profile on the maintainer's own machine, which fails it at eighteen paths, and the user's only symptom was that runs worked, on the strongest seat available, forever. What that costs is not a degraded selection but the whole of routing — with no mappings and no adapters an exact `--model` override has nothing to be honoured against and an evidence ledger of any size reaches no decision.

This record narrows ADR-0136, which stated a missing or invalid profile as one thing that inherits.

**Absence is the file not existing, and nothing else.** A `config.json` that is present and cannot be read, cannot be decoded, decodes to something other than an object, fails the profile contract, or holds a selection that does not resolve to exactly one configured access channel was written by somebody and discarded by this command. Reporting it as a profile nobody wrote is the defect, so `_read_profile` splits `FileNotFoundError` out of the clause that caught every read failure together, and what remains in that clause is rejection. The reading answers with which of three states it met, and the frozen context carries the answer: an absent profile is the `null` it always was, a validated one is its revision, and a rejected one is a `rejection` naming what rejected it.

**A rejected profile inherits, and its reason is its own token.** Route already discriminated the two states and answered the second with a refusal carrying the stable code `invalid_profile`. Nothing ever reached it — the derivation wrote `valid: true` whenever it wrote the member at all — so the branch was unreachable from every real profile, and it is the branch that gives way rather than the decision to distinguish the states. Orchestrate reads a route refusal as *start nothing*, so a profile gone stale would cost an unattended run every ticket in it, where inheritance costs that run its optimisation and nothing else. The distinct reason, `rejected_profile`, is what tells the developer which of the two happened. `invalid_profile` is retired entirely rather than left dead beside its replacement: from the decision path, from the public Module's list of stable refusal codes, and from the suite.

**The rejection rides in the frozen snapshot, and carries no revision it did not read.** `freeze_context()` is the context plus an identity, so anything under `context.profile` is already in the snapshot; putting the detail only in the context response would mean adding a member to a request artifact whose top level admits none, or stripping it inside the shared freeze — both work done to lose information. So the request contract admits it, `revision` leaves the accepted shape's company rather than being invented, and `snapshot_identity` moves with the detail as it moves with every other frozen fact. Where the contract is what rejected the profile the detail is the shared schema interpreter's own error text, the failing path beside the constraint it broke; the other shapes name the read or decode failure, the value that is not an object, and the selection that resolves to no configured access channel. None of them reads a value out of the profile, so none carries the user's plans, tiers or fees into an artifact a caller may print.

**No migration is written, and that is the decision rather than an omission.** The stored profile that produced this record fails at every access channel and at a model selection besides, and the divergence is structural: a nested `recurring_fee` where the contract expects flat members, `sources` as objects where it expects strings, and two members — `allowance_amounts` and `model_specific_quota_rules` — the contract has no place for at all. No transformation bridges those two shapes without inventing facts nobody wrote down. The profile is a short interview `setup` recreates in minutes, so a migration framework for a shape this Collection has documented exactly one version of would be code kept alive for a case that ends the first time the user re-runs `setup`. The rejection names `setup` as the way back instead, in the detail itself rather than in a document the user would have to already be reading. The empty in-memory migration hook goes with the decision rather than standing beside it as a seam for a transformation this record refuses: an abstraction kept for a need that has been ruled out is a promise the next reader has to disprove.

**Context still reports and returns, in all three states.** It starts no setup, performs no network access, and writes nothing — which is what makes reporting the rejection the whole of the remedy this command may apply. `evidence` is read before and independently of the profile branch, so a populated ledger survives a rejected profile intact and is not emptied alongside the selections.

**What this costs.** The `profile` member of the frozen snapshot has two shapes where it had one, and a consumer that read `valid` reads the presence of `rejection` instead. A stable refusal code leaves a published Module, which is a contract change a caller pinning the old list would notice; this Collection has one user and the code was unreachable, so it goes rather than being kept as a name nothing answers to. And a user whose profile predates the contract still has to re-run `setup` — the change does not restore their routing, it tells them that it stopped and why, which is the difference between a defect that hides and one that reports itself.

# A Catalog entry is a Skill or a Feature

ADR-0090 gave a Skill the right to own what it writes into a Harness's own configuration, and every narrowing since has been about *how* that is installed: the owner identity inside what is written, the Collection Library holding the Harness mechanics, the seams where the Manager says install and remove, the trust gate reported gated. What none of them settled is *what a Catalog row is*. The one integration this collection shipped never exposed the gap, because capture rides on `model-selector` — a real Skill with a real purpose of its own, whose row the user was already reading for other reasons. The integration was a consequence of that row, never the point of it.

Two things the collection now wants have no such host. A session-cleanup integration is a block of prose and a lifecycle hook, and there is no Skill it belongs to. A Claude Code status line is a shell script and a settings key, and there is no Skill it belongs to either. Attaching each to an invented Skill purely to obtain a checkbox would bend the model to fit the user interface: a Skill nobody invokes, whose `SKILL.md` exists so that something else can be installed beside it, is a lie told to the Catalog to get past the fact that the Catalog only had one shape.

**The Catalog gains a second entry type. A Catalog entry is a Skill or a Feature, and a Feature is an entry that owns Harness Integrations and nothing else.** No Harness loads it, the transport never moves it, it has no directory in any skills tree, and it is never a Dependency of anything. What it has is exactly what ADR-0090 gave a Skill — an owned integration it installs, converges, and removes — and nothing besides. Select lists Features as a second group under the Skills, they are answered in the same checked set, and they install and tear down at the same two seams that already place and remove an Enabled Skill's files.

**There is no new verb, and ADR-0010 still holds.** A separate `setup` was considered and rejected: it would split *what do I have enabled* across two places, which is the whole of what ADR-0043 exists to prevent. ADR-0010 survives because its own reason survives — nothing is left for a setup step to collect. A Feature asks the user nothing; it only writes. The line to hold is that **`setup` is for asking and `select` is for choosing**. The day a Feature has to interview a user — which tracker, which paths, which variant — that premise breaks and a setup verb earns its place. Until then, anything that only writes belongs at the seam that already writes.

**A Feature ships inside the Manager.** It has no files a Harness reads, so there is nothing for the transport to place in a skills directory, and the hook it installs has to name a script that is on the machine for as long as the Feature is enabled. The Manager is the one directory that is always installed and always addressable, so `skills/kntnt/features/<name>/` is where a Feature's `FEATURE.md`, its declared script, and whatever it ships beside them live. Its Catalog entry carries a Digest of that directory, so a locally edited Feature reads as Deviating on its row exactly as a Skill does. Its Enabled state is not a file test: it is what the Feature's own script reports its Harnesses actually hold, which is the same convergence over disk everything else here already stands on (ADR-0003).

**A Feature's row states what it writes, before it is checked.** ADR-0160 could leave this to `help.md`, because what capture wrote was its own store and a hook entry. A Feature writes into `~/.claude/CLAUDE.md`, into `~/.codex/AGENTS.md`, into a settings key the user chose the value of — files the user owns, reads, and edits by hand. So the Catalog entry carries `writes`, one line per thing and where, generated from the Feature's own page, and Select puts those lines in the single confirmation question it already asks before writing anything. A row that edits a file the user reads must say so before the checkbox, never after the run.

**A Harness a Feature cannot serve is reported, never hidden.** A Feature declares the Harnesses it serves; a Detected Harness outside that set is one it cannot reach. Where no Detected Harness is one it serves, the row is locked and says so in the words every unmet Harness requirement is already said in (ADR-0030). This is the Manager's own answer rather than an agent's, because which Harnesses this machine has is precisely what the Manager knows and the agent does not — a Capability stays what only the agent can answer for itself.

**The Global layer alone, for ADR-0160's reason exactly.** An owned entry is keyed by owner inside a Harness's own configuration, so a Project-layer Enable and a Global one would write and remove each other's single entry. A Feature is a property of the machine and not of a working directory. `select --project` therefore offers no Feature at all and carries the sentence saying why, rather than a checkbox that could never change anything.

**Update re-converges an Enabled Feature and never adopts a new one.** A Feature ships inside the Manager, so a refresh replaces the tree its script and its installed block both come from; without re-converging, a Harness would go on reading last release's prose from a file nothing had touched. But a Feature new in the Catalog is not enabled by `update --yes` the way a new Skill is, because what it would write is instructions into a file the user reads, and an unattended run must never place instructions the user has not read (ADR-0043). A new Feature is offered by Select, where what it writes is on the row beside the checkbox.

**Uninstall tears every Feature down first, while the Manager is still there to do it.** A Feature's hook names a script inside the Manager's own directory. Removing the Manager before the Feature would leave every Harness running an entry that names a path that is gone — an integration nothing can remove, because the thing that removes it was what got deleted.

**This amends ADR-0090.** That record's premise throughout is that the owner of a Harness Integration is a Skill: "a skill owns the harness integrations it installs." The owner is now a Catalog entry, which is a Skill or a Feature. Every mechanism ADR-0090 states is unchanged and now has a second kind of owner — the owner identity inside what is written, the Collection Library holding the Harness-specific mechanics, install and removal as one convergent operation over whatever is on disk, and a failed installation reported per owner rather than raised. ADR-0160's rule that an integration follows its owner's own Enabled state is what a Feature is made entirely of.

**What this costs.** The Catalog is no longer one list, and every reader of it — the Manager's verbs, the Select steps, the manpages — carries a second case. A name now has to mean one entry across both groups, so generation refuses a Feature that shares a Skill's name, and the collection has given up the freedom to reuse a name across the two kinds. Enabling a Feature writes into files the user maintains by hand, which no Enable did before: the fenced block and the ownership marker are what keep that surgical, and a hand edit inside the fence is overwritten by the next run rather than merged, because convergence has no way to tell an improvement from damage. What it buys is that the collection can ship something that is not a Skill without pretending it is one, and that the user still has exactly one place to see and change everything this collection has put on their machine.


What this record leaves to each Feature — what happens when the state it wants is already somebody's — is narrowed by ADR-0174 for the one case where the state cannot hold two: a single-valued setting another command holds is a question Select puts to the user and never a verdict a script reaches on its own.

# A withdrawn skill is removed without asking

The repository is the truth about what the collection provides. A skill withdrawn from it is withdrawn everywhere: it can no longer be updated, supported, or reasoned about, and the Catalog entry that named it is gone, which is what Select builds a row from and resolves an `--on` or `--off` name through. Leaving the files behind does not leave the user a skill — it leaves instructions no command of the collection can reach, and the only way out is deleting a directory by hand. So Update removes it, in the layer it is acting on, and does not ask.

The asymmetry with ADR-0007 is the point of this record rather than a wrinkle in it. Adding a skill silently would inject instructions the user has never read into every Harness's context, so a new Catalog entry is named before it can be Enabled: Update reports it, the offer names it, and a user who says no keeps it Disabled (ADR-0007). Removing one injects nothing. It takes away something the collection has already stopped shipping, and asking would only offer a choice that cannot be honoured — *keep it* means keeping an orphan. Consent governs what enters the context, not what leaves it.

**The withdrawn set is resolved from the disk, not from a diff.** A skill installed from this collection carries `metadata.kntnt` in its own frontmatter — the block it declares its Dependencies in, and a key nothing outside this collection has reason to write. On Update, every skill directory in the targeted layer that carries that marker and is not in the current Catalog is a skill the collection has withdrawn, whatever any local file remembers. Two things are never swept: the Manager, which is exempt by name because it is no Catalog entry and judging it by the Catalog alone would delete the verb doing the sweeping, and a skill with no marker, which belongs to another collection or to the user and is not this collection's to remove (ADR-0011). The cost is reading each installed SKILL.md in the layer once per Update.

A diff cannot carry this, and the reason is not subtle. The record it compares against is `catalog.json` beside the Manager — a sidecar of the Manager, so any run of the transport that re-copies `kntnt` replaces it, including a run of Update that refreshed it and then died, and including `npx skills update` invoked by hand. Once that file no longer names a skill, nothing can establish the skill was ever ours: the diff is empty forever and the files are stranded with no command of the collection able to reach them. That is the sequence issue #5's own fix went through, and issue #20 is what it cost. Provenance has to live somewhere the transport does not overwrite, and the only such place is the skill itself. The Catalog diff stays for reporting *new* entries, which is ADR-0007's half and is not in question; only removal changes hands.

The sweep runs only where the origin answered. ADR-0039 lets every verb fall back to the stored copy when the collection cannot be reached, and a report made from a stale list is worth having — but deleting files on the strength of one is not. So an Update that fell back reports no withdrawals at all, rather than deleting whatever that copy has since stopped naming, and its `catalog_refreshed: false` is what tells the user to run it again when the collection is reachable.

This is why Update fetches the Catalog before it decides anything. Resolving the work first meant resolving it against the list the collection had already moved on from: the withdrawn skill was still Enabled, so it went into the refresh, the transport was asked for a name the source no longer carried, and the run died with the transport's raw error and no report at all (issue #5). Adopting the Catalog first makes *only what the current Catalog carries* the thing that is refreshed, and gives the sweep the one list it is entitled to judge a marked skill against.

Removal goes through the same wrapper Select takes a skill off the disk with. The collection has one way to delete skill files, and a second one would be a second thing to get wrong in a place where being wrong means deleting the wrong directory. What Update adds around it is per-skill reporting on ADR-0036's terms: each withdrawn name is reported with what the disk then showed — removed, or failed with the directories its files survive in. There is no third verdict for a skill that was never here, because the sweep never found one to report. A failure belongs to that skill and not to the run, so the refresh still happens and the report still comes out; and, being a change the disk does not show, it exits non-zero like every other.

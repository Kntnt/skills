# Capture follows the Skill's own Enabled state

ADR-0090 made capture an opt-in of an Enabled Skill rather than a consequence of enabling one, and it was right that both are decisions: writing into a Harness's own configuration and handling local session metadata are choices a user should make knowingly. What it did not price is that a decision nobody makes is a feature that does not exist. Automatic capture shipped weeks before this record and never ran once, anywhere, including on the maintainer's own machine: the Skill was Enabled, eight validated model selections sat in the profile across three Harnesses, and there was no capture store and no owned entry in any Harness's configuration, because opting in was a second gesture behind an already-Enabled Skill, gated behind a `capture` command with its own on, off, and status forms, a consent statement to read, and a Harness and a Seat to name by hand. `recommend` went on answering from the shipped seed rather than from the maintainer's own work, for exactly that reason.

**Capture follows the Skill's own Enabled state, and asks for nothing beyond it.** Enabling model-selector through the Manager is now the whole gesture: at every seam that already places or refreshes an Enabled Skill's files, the Manager asks a Skill declaring `metadata.kntnt.integrations` to install what it owns, the mirror of the word it already sends a Disabled or withdrawn one to remove them. Disabling the Skill is the whole undo, at the same seam that already deletes its files. There is no third command, no consent prompt, and no question asked at any point — install, repair, and refresh are the same convergence over whatever is already on disk, so asking an already-installed Skill again changes nothing.

**What the second opt-in bought was a feature that never started.** A user who has already decided to Enable a Skill has made the only decision this collection asks of an Enable anywhere else; asking again, behind a second command with its own grammar, produced not a more considered choice but no choice at all. The maintainer's own machine is the evidence: eight weeks Enabled, zero sessions captured, because the second gesture was never made. A decision a user is asked to make twice is a decision most users make once, by never reaching the second asking.

**The disclosure moved to the one surface a user reads before answering.** The Manager's Catalog carries a Skill's name, category, description, digest, and dependency kinds; a Select row carries the checkbox, the description, its declared Capabilities, freshness, closure, and lock state. Neither carries what a Skill's own integrations install or retain, and teaching either to would be a Manager schema change of its own, which this record does not make. What Select already offers is a Skill's own `help.md` in full, readable before the list is answered, fetched from the collection for a Skill not yet Enabled and read locally for one that is. `help.md`'s `DESCRIPTION` now states, in one short paragraph, that Enabling this Skill installs session lifecycle integration into each supported Detected Harness of the Global layer, names what is retained — the Seat, usage counts, timestamps, and opaque identifiers, never prompts, responses, reasoning, file contents, or paths — and states that Disabling removes every entry and keeps what was measured. A user who reads that page before checking the box has read the whole of what checking it does; a user who does not has still Enabled nothing more than a Skill.

**The price is that Enabling this Skill now writes into a Harness's own configuration.** That was always ADR-0090's own price for capture existing at all — this record does not add to it, it only stops asking a second time for something the first gesture already authorizes. Only a Harness the Collection Library has an adapter for is ever attempted, and everything else is reported as a single count naming the supported set rather than one row per Harness this collection cannot reach: `harness-paths.json` names dozens of Harnesses, the Library's adapters cover three, and a report enumerating the rest would bury the outcome that matters. Only the Global layer is written: an owned entry is keyed by owner inside a Harness's own configuration, so a Global and a Project Enable of the same Skill would write and remove one another's single entry, and measurement is a property of the machine rather than of a working directory. A failed installation is reported per Skill and per Harness and never raised, exactly as a failed removal already was.

**This record supersedes ADR-0090's opt-in paragraph.** The paragraph beginning "Capture is an opt-in of an Enabled Skill, never a consequence of enabling one" no longer holds: enabling a Skill that declares an owned integration now installs that integration, not only the Skill's own files. Every other paragraph of ADR-0090 stands — the owned-entry model, the Manager asking the Skill to remove its integrations while its files are still readable, the Collection Library holding the Harness-specific mechanics, the fail-open bounded hook path, and the narrowings later records made to it.

**What this costs.** Enabling model-selector is no longer a decision that can be made without also deciding to measure ordinary work in every supported Harness this machine runs — a user who wants the Skill's routing and recommendations but not its measurement can no longer have one without the other short of Disabling the Skill entirely. What that buys back is the thing the second opt-in never delivered: a feature that actually runs, evidence that replaces public priors with the maintainer's own work, and one surface — `help.md` before Select answers — where what Enabling does is stated in full rather than split across a consent prompt nobody reached.

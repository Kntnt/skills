# An unknown subcommand and a disallowed flag are both errors

Two things pass silently on this collection's surface today. A subcommand the Manager does not have is re-read as `help`, so `/kntnt updat --yes` runs a different verb and the rest of the line becomes that verb's arguments; and a flag a verb has no use for is accepted and ignored, so `/kntnt help --yes` succeeds and does nothing. **Both are errors from here on.** An error is answered with the error, the synopsis of the thing that was actually addressed, and a pointer to `--help` — and with nothing else: no guess at which verb was meant, no half of a run, and nothing done with the rest of a line whose first word was wrong.

**The meaning of invocation in this record is narrowed by ADR-0078: the strict grammar here governs the Formal Invocation inside an Invocation Envelope, while an optional Contextual Instruction is separated from it and is never reinterpreted as arguments or flags.**

**The tell is `--force`.** `/kntnt help --force` already fails while `/kntnt help --yes` succeeds, and the only difference between them is that `--yes` happens to mean something on another verb. Nobody outside the script can see that difference, so what the surface shows the user is that some meaningless flags are errors and others are not, with no rule available to say which. ADR-0029 drew the line at *misleading* — `uninstall --project` refused because accepting it would state something false, `help --yes` tolerated because nothing could be misread — and the line does not hold, because tolerating it teaches exactly what that same record says must never be taught: that flags sometimes do nothing. The simpler rule has no such seam. **A flag with no function on this verb is not a flag of this verb**, and that is the rule story 41 of issue #21 asked for in the first place.

The user-facing verbs, settled by the flag table this record makes binding:

| | `--dry-run` | `--yes` | `--project` |
|---|---|---|---|
| `help` | – | – | – |
| `select` | yes | yes | yes |
| `update` | yes | yes | yes |
| `uninstall` | yes | yes | – |

`select` additionally takes `--on <skill>` and `--off <skill>`, documented in its manpage. `--force` is accepted by no verb, as it never has been (ADR-0023's `--force` on `agents-md` is a different flag on a different skill and is untouched).

**The rule has no exceptions.** It binds every subcommand the script has, including `manpage`, `check`, and `catalog`, which no user types. Exempting them would rebuild the same invisible seam one layer down — a surface strict where somebody is looking and lax where nobody is — and it buys nothing measurable, since no call site in the collection passes a meaningless flag to any of the three. `catalog` keeps `--dry-run` by genuinely acting on it where it writes, which is the only way anything keeps a flag under this record: by having a use for it.

**One error path, not two.** Every disallowed flag is refused the same way, `uninstall --project` included. That one flag was given a bespoke message naming the machine it clears (issue #32), and the message goes, along with `refuse_project_on_uninstall`, the check that produced it ahead of the parser. Nothing is lost that the user cannot reach: `help/uninstall.md` carries the reason in full, and the pointer at the end of every error is what leads there. A special case in the code for one flag is the same shape of seam this record exists to remove — a difference between two refusals that only somebody reading the source can account for. The shape is already in use elsewhere: `/tldr --user` without its state is refused with the synopsis and nothing changed (ADR-0048), so a skill has one failure behaviour rather than one per kind of mistake.

**Validity is judged per invocation, not per skill.** A flag is allowed where it has a function on *this* run, not where it has one somewhere in the skill. `/kntnt help --yes` and `delegation status --yes` are the same case — a flag with nothing to do on the path it was given — and settling them differently would leave the Manager strict and every other skill lax, which is the seam again with a skill boundary drawn through it. This is also what forces the scope: a skill with no script has no parser to make strict, so the rule has to be stated where the agent reads it and enforced there. **Strictness is a rule of the collection, not of the Manager.**

**The fallback goes with the tolerance.** Sending an unknown subcommand to the help step is the same tolerance in the other half of the grammar: a typo is answered by silently running a different verb, and everything after it is re-read as arguments to a verb the user did not name. A mistyped verb is an error, and whatever followed it is ignored rather than re-parsed — the second half matters as much as the first, because a line the user meant for `update` carries flags that would mean something to whatever the typo landed on.

**What this withdraws from ADR-0029.** Two clauses go. *A meaningless flag is tolerated* is reversed outright by the rule above. *Every verb of every collection script accepts the flag, including the verbs that ask nothing* goes with it, and with it the pass-through it licensed: a skill may no longer forward the user's arguments unread on the assumption that a flag can never be the thing that breaks a run. What was true when that was written is still true — argparse is not the surface the user meets — but the answer is no longer to make the parser swallow everything; it is to make the parser and the documented grammar the same grammar. Issue #32's bespoke refusal of `uninstall --project` is withdrawn with them, being the other half of the same distinction: once every disallowed flag is an error, a message that exists because one of them was the misleading kind has nothing left to mark.

**What stands, and stands unchanged.** `--yes` means assume yes wherever a collection skill can ask something answerable yes or no, one flag with one meaning across the collection; every yes/no question is worded so that *yes* ends it, because the flag answers rather than defers; and where a subcommand deletes files the user is choosing to delete, the flag is also the gate and the script refuses without it. ADR-0042's sentence granting `--dry-run` to every subparser of the script rested on the clause withdrawn here and is corrected with it, rather than being left to contradict this record.

**What this costs, stated plainly.** ADR-0029 was written to end a real failure: `argument-hint` advertised `--yes` on `/kntnt` while `apply enable --yes` died on `unrecognized arguments`, so the skill was documented into a crash and only luck decided whether the model forwarded the user's own flag. Strictness re-opens that failure mode wherever the grammar and the parser disagree. What was missing then and exists now is a settled flag table, so the defence is to make one table drive both: the test that reads the manpages also reads the parser, and a verb documented to take a flag it would reject is a failure in the suite rather than in somebody's session. The dependency gate is the sharpest edge — `check --here` runs first in every skill, so a stray flag reaching it would kill the skill before it did anything — and a test pins those call sites flagless so the drift is caught in the suite rather than in a broken `/commit`.

**The ordering hazard is real and is accepted.** This record lands before the code, because both halves of the code contradict clauses that are written down and true until they are unwritten. The Manager and the skills are then two pieces of work, and between the first landing and the second the Manager is strict while the skills are lax — which is the very seam the rule removes. That is not a regression: the skills in that window behave exactly as they do today, and a user meets a surface no worse than the one they have. It is a reason not to ship, and no version is released in that window.

# Update re-adds what deviates; the transport's `update` is not a refresh

`npx skills update` compares `SKILL.md` and skips a skill whose `SKILL.md` is unchanged. It exits 0 and reports everything up to date, while every sidecar in that directory — `catalog.json`, helper documents, scripts — stays at the revision that last happened to touch `SKILL.md`. A collection whose skills are mostly sidecar therefore could not be updated at all: `delegation` was added to the Catalog in 0.3.0, and no `/kntnt update` could deliver it, because `skills/kntnt/SKILL.md` had not changed since 0.1.0.

Update calls the transport's `add` instead, which empties and replaces the whole directory and is idempotent (ADR-0003). Update also writes the Catalog to the running Manager's own directory. `add` reaches the Harnesses detected in the targeted layer, and those need not include the copy of the Manager being run right now — an `add --project` never refreshes a Manager invoked from `~/.claude/skills` — so the layer the Manager itself sits in has to be refreshed directly or it stays frozen.

**What has changed is which skills are handed to `add`.** Update no longer re-adds everything Enabled; it re-adds every Enabled skill that Deviates from the Digest its Catalog entry carries, and always the Manager, which is no Catalog entry. ADR-0130 later gave the Manager a top-level publication Digest that excludes its recursively generated Catalog, so it verifies a candidate but cannot preselect a fully identical active tree. Gating Catalog Skills on their Digests is safe for the same reason `add` was chosen in the first place: a Skill whose Digest matches is already byte-identical to what the collection ships, so skipping it cannot strand a sidecar. This is the opposite of the transport's own skip, which compares one file and infers the rest of the directory from it.

What the gate buys is a report that carries information. *Twelve of twelve refreshed* said only that twelve skills were Enabled; it said the same thing on a machine where nothing had moved and on one where everything had. What is refreshed now is what moved, and a run with nothing to do says that instead.

**The test double has to model the wipe.** `add` empties the directory before it copies: a file added under an installed skill and an edit made to one of its files were both gone after a re-`add`, verified against the real transport. That is what makes *files removed upstream gone, files changed upstream replaced, files added upstream present* true of every refreshed skill after one call, which is now the stated postcondition of a refresh rather than a happy accident of it. A double that leaves extra files in place is less capable than the thing it stands in for, and a correct test would fail against it. This record's own lesson is the mirror image: the double once copied unconditionally, which is why the suite was green while the collection could not be updated. A double that differs from the real thing in either direction tests nothing.

The premise that this wipe happens in the active installation is superseded by ADR-0130, which runs the faithful wipe in isolation and atomically publishes its verified result.

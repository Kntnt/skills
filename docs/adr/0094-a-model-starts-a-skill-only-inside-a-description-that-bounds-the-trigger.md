# A model starts a Skill only inside a description that bounds the trigger

Until now one Skill in the collection could be started by a model rather than by a user typing its name, and the rule that allowed it was written about that Skill (ADR-0018). Proofread is the second, and it is a different kind of case: `agents-md` is model-invocable because its work belongs after other work and nobody would think to ask for it, while Proofread is model-invocable because people ask for it constantly, in ordinary language, about a text already in front of them. That makes the general question unavoidable, because a second exception with no stated rule is no longer an exception — it is a habit.

The risk model invocation carries is not that the Skill runs when it should not have. It is that a Skill runs against a request its own contract refuses, and there is no invocation for the refusal to answer. A user who types `/proofread` on a request to improve a draft can be told that improving is not what this does. A model that reached the same Skill from *make this better* has already decided; the Skill either does the narrow thing the user did not ask for, or the wide thing it promised not to do. Both are worse than never having been reached.

**A Skill a model may start bounds its trigger inside its own `description`, because the description is the whole of the hook (ADR-0019).** For Proofread the bound is two conditions at once: a specific Text Artifact is at hand, and the request either uses a proofreading term or is unambiguously limited to mechanical language errors. Neither half is sufficient alone — a proofreading term in a question about what proofreading is names no text, and a text alone names no request — and the conjunction is what keeps the ordinary editorial request outside.

**The exclusions are written as exclusions rather than left to be inferred.** A model reads what a Skill offers and matches a prompt against it, so a description that describes only what the Skill does leaves *edit*, *rewrite*, *polish*, *improve*, and *review* to be judged as near misses of a good description rather than as the different requests they are. Named in the description, they are answers rather than inferences. This costs a longer description than a user-invoked Skill would need, which is the right place to spend length: the description is read by the thing making the decision.

**Invocation by name remains available on every such Skill, and is the reason the narrow trigger is affordable.** A trigger tight enough to exclude the ambiguous cases will fail to fire on requests that genuinely wanted it, and `/proofread` is what that user reaches for. A Skill whose only route in was a model's judgement would have to widen the trigger to stay usable, and widening it is exactly what the contract cannot survive.

**The collection names the Skills a model may start, and the suite reads the list off the frontmatter.** The standard's sidecar section carries the names; a Skill shipping `disable-model-invocation: false` and missing from that sentence fails, so the set cannot grow by omission. What the suite cannot judge is whether a given description is actually narrow — it holds the exclusions present and the two invocation fields in agreement, and whether the prose bounds the trigger is a reviewer's reading. That limit is why this is a record and not only a test: an author adding the third such Skill needs the reasoning, not a list of substrings to include.

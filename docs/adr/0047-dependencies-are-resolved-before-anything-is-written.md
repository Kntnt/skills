# Dependencies are resolved before anything is written, and unchecking is reported

A Catalog is a graph, and a list that hides the edges asks the user to answer a question the manager already knows the answer to. Select shows them. A row whose Dependency is unchecked is **locked** and names the Dependency, so the user reads why they cannot have that skill yet and what to check instead in the same glance that shows them the checkbox.

**The closure is resolved before the write, not after it.** Where the answer implies Skills the user did not check, `plan select` has already carried the resolved closure on the row that needs it, and the agent asks one yes/no question naming exactly what would be added. One question for the whole closure, whatever its depth: `release` pulling in `push` and `commit` is a single yes rather than three, because the user made one decision and being asked three times about it is the same decision charged three times over. Nothing reaches the disk until that question is answered, and `--yes` answers it — which is only sound because the question is worded so that yes ends it and opens nothing further. ADR-0131 strengthens the same before-write boundary for a real Global Update: its later Apply also proves that the answer belongs to the exact complete plan shown.

**The closure is resolved by the script and rendered by the agent.** A three-deep chain walked in prose is a chain walked differently on a bad day, and the failure would be silent: a Skill Enabled without something it needs looks exactly like one that has everything. So the walk is `dependency_closure`, the row carries `requires` and the `unsatisfied` part of it, and the rendering names what the payload names (ADR-0045). What Satisfies a Dependency is what the Harness will load, so in the Project layer a Skill already Enabled in Global satisfies it without a second copy (ADR-0013).

**Unchecking is reported, not blocked.** A user who unchecks a Skill that a checked one depends on is told what they left Unsatisfied, and the run does it anyway: the answer is the whole checked set for the layer, and a manager that quietly put the Dependency back would be answering for them. `apply select` carries the same account under `unsatisfied`, read off the layer after the run rather than off the answer, so a Dependency whose files the transport never placed is reported as absent instead of counted as present because somebody named it (ADR-0036). This is ADR-0009's rule read from the other end — say what is wrong and let the user act — and it is why the dependent Skill can refuse at use time without the Manager ever having to forbid the state.

# TL;DR mode is a standing instruction, not an output style

Issue #43 asked for `/tldr --output-style`: a flag that makes the agent answer briefly from the outset, so the summary never has to be requested afterwards. Output styles are the obvious mechanism and are the wrong one, for three reasons that compound.

**Only one harness has them.** Output styles are a Claude Code feature. OpenCode, Codex, and the rest have nothing equivalent, so the flag would work where it was tested and silently do nothing everywhere else — which is the failure ADR-0005 and ADR-0008 exist to prevent. A skill that is a mode in one agent and a no-op in another is two skills with one name.

**The route into them has just moved.** The standalone `/output-style` command was deprecated in Claude Code v2.1.73 and removed in v2.1.91. What remains is the `/config` menu or writing `outputStyle` into a settings file — neither of which a portable skill should be reaching into.

**And they cannot take effect when asked for.** An output style is part of the system prompt, read once at session start. `/tldr --on` would therefore be unable to change the conversation it was typed in; the best it could say is *run `/clear` and it will apply*, which is not what the flag promises.

So the mode is built the way `delegation` is built: `mode.md` is the single source of truth for the text, and that text is written verbatim as a managed block into whatever context file the running harness already loads. It is portable, it takes effect on the turn that switches it on, and the pattern is already reviewed. What it costs is that a block is a user message rather than a change to the system prompt, and its tokens are paid on every turn while it is on — which is why the block is seven lines of prohibitions and not an essay.

**The scopes are `session` and `user`, and the absence of `project` is the deliberate part.** `delegation` has all three because it describes a *working method* a team might reasonably share. Brevity is not that. It is how one person likes to read, and a managed block in a committed `AGENTS.md` that makes every agent terse for everyone who clones the repository is imposing a reading preference on collaborators — it would land in a pull request as exactly that. Anyone who wants it everywhere sets `user`. A second consequence is welcome: with two scopes and no committed file, the verdict is single-valued by construction.

**No session state file, and this is the second departure from `delegation`.** That skill writes `kntnt-delegation.json` into a scratch directory so a compaction cannot silently lose the session state. The failures are not comparable. A lost delegation setting is invisible — nothing tells you a subagent was not spawned — whereas a lost TL;DR mode announces itself in the very next reply, and the repair is retyping four characters. Paying a write branch, a read branch, and a no-scratch-directory fallback would buy protection against a failure that reports itself.

**One skill, and the mode reached by flags rather than by bare words.** The summariser accepts a free-form tail: anything after `/tldr` that is not a flag is an instruction in any language, obeyed as written. That grammar is what rules out `/tldr on`, since `on` would become a reserved word shadowing a legitimate instruction and `/tldr on the security part` would be genuinely ambiguous. A flag can never be mistaken for prose. Two skills would have cost a second name for what the issue correctly treats as one idea.

**`/tldr` is the second skill in the collection with paired arguments, and that is why `/tldr --user` alone is an error.** Only `delegation` had a scope that needed a state beside it; every other skill takes independently optional arguments and therefore has no incomplete form to get wrong. An incomplete form is refused the way a disallowed flag is — the synopsis, and nothing changed — so the skill has one failure behaviour rather than two. Under the ask rule `/tldr --user --yes` would have had no answer at all, the question having three outcomes, which ADR-0029 says is not asked under `--yes` in the first place. The same correction is owed to `delegation`, whose own Steps already stop where its Arguments section says ask; it is tracked on issue #47.

# A delegated start inherits the caller's permission level

On 2026-09-19 an Orchestrate run could not use the launch instruction it had been given. `plan` in `skills/models/model-selector/scripts/launch.py` had always decided the Codex sandbox by itself: `read-only` where the caller said the work wrote nothing, and `workspace-write` everywhere else. On this machine `workspace-write` is not enough for a building role. Tried that day against codex-cli 0.155.1 in a scratch repository: `git commit` fails with `fatal: Unable to create '…/.git/index.lock': Operation not permitted`, so a builder cannot commit what it built; the network is closed, so `uv sync` cannot fetch a dependency and `curl` returns status `000`; `~/.cache/uv` cannot be written, `touch` answering `Operation not permitted`; and neither `-c sandbox_workspace_write.writable_roots=[…]` nor `-c sandbox_workspace_write.network_access=true` opened either of them. The calling session was running under Claude Code's `bypassPermissions` at the time and the user's own `~/.codex/config.toml` sets `sandbox_mode = "danger-full-access"`, so the planned launch was stricter than both the caller and the user's own default, with nobody having asked for that. The run answered by substituting `-s danger-full-access` for `-s workspace-write` in the command it had been handed — which is exactly what a planned launch exists to make unnecessary, and what makes a launch instruction unaccountable the moment it is not run as it stands.

The fault was not the value chosen. It was that a planner with no way to know what its caller was running under was choosing at all. Model and Deliberation have never worked that way: an explicit choice wins, silence means inheritance, and the caller says which. Permission is the same kind of fact, so it gets the same treatment. `selection.py` and `run.py route` take `--permissions=<level>`, the level travels into `launch.plan`, and it comes back spelled the way the CLI being started spells it. The alternative — leaving the planner to decide and letting callers patch the argv afterwards — is what produced the field failure, and it moves the launch translation, which `ADR-0182` puts in this module alone, into every caller that ever finds a start too weak.

The vocabulary is the module's own and Harness-neutral, because the two Harnesses spell the same intent differently and a level named in one tool's words cannot be carried into the other's. It is six, closed at this writing: `bypass`, `auto`, `edits`, `never-ask`, `manual`, `plan`. Those are exactly the six values `--permission-mode` takes in Claude Code 2.1.278, so that side is one-to-one in both directions and a caller reads its own level off its transcript and maps it back with no ambiguity. The Codex side is not one-to-one, and that is the interesting half. Read from `codex exec --help` in codex-cli 0.155.1 on 2026-09-20: `bypass` is `--dangerously-bypass-approvals-and-sandbox`; `auto` is `--approve-for-me`; `edits` and `never-ask` are both `-s workspace-write`; `manual` and `plan` are both `-s read-only`.

Two pairs therefore coincide on the Codex side, for one reason in both cases: these starts are unattended, and nobody is there to answer an approval. `codex exec` does have an approval flag — `--approve-for-me`, which the help describes as routing approval requests through automatic review using the workspace-write sandbox — and that is what `auto` is, the faithful counterpart of Claude Code's `auto`, where the decisions are likewise made automatically rather than by the person. It cannot hang on anybody, because there is no person behind it; tried on 2026-09-20, a start carrying it printed `approval: on-request` and `sandbox: workspace-write [workdir, /tmp, $TMPDIR]` in its own banner, ran what it was given, reported the outcome and exited 0 without stopping for an approval. It is also mutually exclusive with the sandbox flag: `codex exec --approve-for-me -s read-only` exits 2 with `error: the argument '--approve-for-me' cannot be used with '--sandbox <SANDBOX_MODE>'`, before anything runs, so `auto` is the one Codex row carrying no `-s`. Nothing else in this CLI means *ask a person first*. The approval policy reachable through `-c approval_policy=` is not it: `untrusted` is refused outright by this version — `approval_policy = "untrusted" is no longer supported; remove this setting`, tried the same day — and `on-request` or `on-failure` set that way have no automatic reviewer behind them, so either can leave an unattended start waiting on an approval nobody can answer, which `docs/research/model-lifecycle-2026-09.md` had already found. No level of this vocabulary sets an approval policy, and no command the module builds contains `-c approval_policy=`. So `manual` becomes `-s read-only`: the faithful outcome of a level that would have asked, in a start with nobody to ask, is a start that cannot write. `manual` is therefore a faithful inheritance and no promise of progress — tried against Claude Code 2.1.278 on 2026-09-20, a headless start on the `haiku` model, under `--permission-mode manual` and with the shell as its only tool, given a prompt asking for a write through that shell, answered `The command was denied — output redirection via bash is blocked in this environment.`, exited 0, and waited for nobody. About Codex under `manual` this record says nothing beyond which command the level gives, that being a fact about the command rather than about a run nobody has made. `edits` and `never-ask` coincide from the other side of the same point: with no policy set, the sandbox is the whole of what decides an unattended `exec`.

Silence stays silence, and that is the second decision. A call naming no level produces a command with no permission flag at all, so the started CLI follows whatever the user configured for it — `~/.codex/config.toml` for Codex, `permissions.defaultMode` for Claude Code where one is set, and otherwise that tool's own headless default, which its documentation gives as manual on every plan for `-p`. Silence is inheritance from configuration and no promise of write access. This is worth stating because the machine this was found on has both files set permissively, which makes silence look like a working default when it is only a working default here. A role that has to write is given a level by its caller; a caller that cannot read its own level off itself omits the flag and takes what the configuration gives. Defaulting silence to something writable instead was rejected: it would put the planner back to choosing a permission nobody asked for, which is the whole of what went wrong.

Nothing sniffs. The level is stated by the caller for the same reason `--harness` and `--seat` are — only the session knows, and a script guessing at it would be a script guessing at the one fact it cannot observe. The cost is that the read-off has to be written down in prose for the sessions that make the call, which it is, in Model Selector's own body, in Delegation's mode reference and in Orchestrate's route step. A value outside the vocabulary is answered as silence with a note naming it, never as a refusal, which is the interface's standing promise (ADR-0182): a caller that could not read its own level is exactly the caller that still needs an answer. A read-only request outranks every level, so the grader's judge is started with the command it always was, byte for byte. The built-in Claude Code subagent path and the inheritance floor are untouched, a subagent already running in its parent's mode.

The last piece is the caller's side of the bargain, and it is a rule rather than a change. A caller runs the argv it was handed as it stands — none of its flags added, exchanged or removed, sandbox and permission flags included — and a start that cannot do the work it was given is wrongly routed rather than wrongly worded, reported as a defect instead of repaired at the terminal. At 68f2b6e2 no prose under `skills/` named a sandbox or permission flag at all, searched for `workspace-write`, `danger-full-access`, `--permission-mode` and `bypassPermissions`, so the substitution made on 2026-09-19 was a decision taken in the moment and codified nowhere. It is now said once, in the dispatch step that was the one to take it.

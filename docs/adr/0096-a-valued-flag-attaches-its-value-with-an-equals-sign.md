# A valued flag attaches its value with an equals sign

The collection spelled a flag's value two ways and nothing decided between them. `model-selector` attached every value with `=`; every other Skill taking a valued flag separated it with a space; and the Manager's `--project`, whose value is optional, took both, because the attached form is the only spelling GNU long-option syntax gives an optional value. Both forms are legal, both were documented, and that is the problem rather than the excuse: a reader who learns one Skill's grammar learns the wrong thing about the next. These Skills have no parser of their own. The agent reading `SKILL.md` and the manpage beside it is the whole of the enforcement, so a grammar that varies by Skill is a grammar that is guessed, and the guess is made in the one place nothing checks it — the free-text payload a model composes at invocation time.

**A flag of this collection's own grammar that takes a value attaches it with `=`, written `--flag=value`, and the space-separated form is written nowhere the collection owns.** That covers every `argument-hint`, the `## SYNOPSIS` and `## OPTIONS` of every root and subcommand manpage, the argument prose and steps of every Skill body, every invocation of the collection's own Python engines a body constructs, and the flag prose in the README, in `CONTEXT.md`, and in the records here.

**The attached form is chosen for three reasons that do not turn on taste.** It is the only spelling an optional value has — `--project` already needs it, and keeping the space form for the required flags would mean two rules where the collection can have one. It is unambiguous where a value begins with `-` or is empty, which the space form is not: `--model -mini` and a value nobody typed are both readable as the next argument. And it makes a flag and its value one token, which matters most here, where an invocation is composed by a model into a free-text payload rather than split into `argv` by a shell — two tokens are two things to keep beside each other, and the pairing survives no reordering, truncation, or quoting mishap.

**The space-separated form was the alternative, and its cost is the one just paid.** It is the more common spelling in hand-written terminal help, it reads a shade lighter, and it is what most of this collection already wrote — adopting it would have been the smaller diff. It cannot express an optional value, so the collection would have kept both spellings and settled only which one was usual, which is not a rule an agent can apply without knowing per flag which kind it is holding. That is the same knowledge the space form already requires at parse time, and the reason a normalisation was worth doing at all.

**A third-party command line is out of scope.** A body constructing a `git`, `gh`, `uv`, or `npx` invocation keeps whatever spelling that tool's own documentation uses. Their grammar is not this collection's to normalise, and rewriting it would assert a form those tools do not document. The boundary is ownership rather than syntax: the rule reaches a flag this collection defines, wherever it is written, and stops at every flag it does not.

**The engines stay permissive, and the suite is the enforcement.** Their parsers accept both forms because that is what `argparse` does, and there is no cheap way to refuse the space form there — nor anything to gain by it, the only writer of those command lines being a Skill body in this repository. A second parser built to refuse it would be a second grammar to keep true. So the rule is held where the writing is: a check that reads every file a Skill ships and every document the coding standard governs, and fails on a valued flag of the collection's own grammar written with a space, naming the rule and pointing at the standard. The check carries a sample of its own that it must still find violations in, so an empty result means compliance rather than a pattern that stopped matching.

**What the rule does not reach is stated rather than left to be inferred.** A flag taking no value is untouched, and so is the bare spelling of `--project`, which is already compliant as `--project`, `--project=on`, or `--project=off`. An `argv` list built programmatically — a test invoking an engine, a `subprocess` call assembling a list of strings — has no spelling to settle: the separation there is the list itself and not a character in a line, and holding it to this rule would be enforcing punctuation on something that has none. And history is not rewritten: the changelog, the closed tickets, and the plans kept beside the repository record what was true when they were written, so the check does not read them.

**What this costs.** Every surface naming a valued flag was rewritten at once, which is a wide diff over files that were each individually correct before it. The manpage rendering of an option term becomes slightly more awkward — a bold flag ending in `=` followed by an underscored metavariable, `**--data=**_PATH_`, because the bold run has to close after the `=` and `**--data=***PATH*` is not the markup it appears to be. And the flag table the check reads is maintained by hand: a valued flag added to an engine and never named there is a flag the rule does not reach, which is the price of a scan that does not have to parse Python to know what takes a value.

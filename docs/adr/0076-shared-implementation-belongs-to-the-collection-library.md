# Shared implementation belongs to the Collection Library

A reference or script used by several Skills has no honest owner among its consumers: putting it under one makes every other consumer reach through that Skill's private layout, and duplicating it makes one rule several things to keep true. Shared implementation therefore lives in the Collection Library, shipped inside the always-enabled Manager, while a file used by one Skill stays in that Skill. This record amends ADR-0063 only where it assigned every on-demand file to the Skill that opened it; its distinction between `references/`, `scripts/`, manpages, and executable steps otherwise stands.

**The Library mirrors a Skill's resource structure.** Markdown an agent consults on demand lives under `library/references/`, and executables live under `library/scripts/`. Both directories start flat: `changelog.md` and `ship.py` need no `ship/` directory that would repeat the script's name and predict a second domain that does not exist. A subdirectory is introduced only when present files need the grouping or would otherwise collide.

**A peer Skill is an interface, never an implementation address.** A Skill may follow another Skill's `SKILL.md` where the other Skill's behaviour is the Dependency it declares, as `push` follows `commit` and `release` follows `push`. It never reads that peer's `references/` or runs its `scripts/`; implementation with several consumers moves to the Collection Library instead. The Dependency graph then describes behaviour the user can Enable, rather than incidental reuse of where one consumer happened to keep a file.

**The Manager is the Library's transport.** The collection's initial transport installs only the Manager (ADR-0006), Update refreshes it, and Uninstall removes it last, so putting the Library inside it introduces no separately Enabled support Skill and no second installation mechanism. A Library consumer resolves it beside the dependency checker it already found; where an older Manager has no Library, the consumer stops and names `/kntnt update` rather than reaching back into a peer Skill as a fallback.

**What this costs.** A consumer and the Library are now revision-coupled even though no Catalog edge expresses that relationship. The missing-Library refusal makes the first migration explicit, and subsequent changes to a shared file have to be shipped with the Manager and every consumer that changes its expectations; that coupling is the price of one authoritative implementation without turning implementation details into user-selectable Skills.

# A setting somebody holds is a question, not a verdict

A Harness's hook table takes a second entry beside the first, so an owned integration installs into it without ever having to decide what happens to anybody else's. A single-valued setting has no room beside its value. Claude Code's `statusLine` names one command, and the `statusline` Feature shipped with the first draft of the second entry type answered that by refusing: finding another command there, it reported the slot as taken, wrote nothing, and told the user to take the setting out themselves and enable the Feature again.

That was the wrong shape, and the maintainer said so from the list. Checking the row **is** the user saying they want this status line. Answering it with *no, something is already there* hands them an outcome they did not ask for and no way forward from the surface they are standing in — a checkbox that stays unchecked however often it is checked, a report that names a file and a JSON key and asks them to go and edit it by hand, and a run that has just told them what they could have been asked. The refusal protected them from an overwrite they might not have wanted, at the cost of never letting them have the thing they said they wanted.

**A single-valued setting another command holds is a question put to the user, and never a verdict a script reaches on its own.** This narrows ADR-0173, which left to each Feature what happens when the state it wants is already somebody's. Select's row names the command that holds it, before the checkbox is answered. The one confirmation Select already asks before writing anything asks the second thing in the same breath: this command holds the setting, may it be replaced. Only a yes writes anything.

**`--yes` is that answer, and no flag of its own is added.** A first draft gave the question a `--replace` of its own, on the reasoning that replacing something the user wrote is a different kind of question from placing files. It is not a different kind of question; it is one more thing asked in the one confirmation Select already asks, and `--yes` is what this collection has always meant by *answer yes to what you are about to ask me*. A second flag for one Feature's one setting would be grammar grown to carry a distinction the user does not make, and ADR-0059's own test refuses it: a flag earns its place by having work no existing flag does.

What keeps `--yes` from replacing a status line nobody meant to replace is that it never enables anything on its own. `select --yes` with no name is `--as-is`: it Enables nothing that was not already Enabled, so a held setting is not in the answer and is never reached. A held setting is replaced only where the same invocation also names the Feature — at the list, where the user checked the row and answered the question, or in the no-list form, where they typed the name and the flag together.

**A held Feature is reported apart from a failed one.** Nothing was attempted and nothing broke: the run was simply given no answer. Folding it into `failed` would move an exit code that means *a change the disk does not show* onto a question nobody was asked, and would tell an unattended caller that something is wrong with a machine that is fine. So the outcome carries `held` beside `failed`, naming what holds the setting, and the exit code stays where it was.

**Nothing is kept of what is replaced.** This is the half of the earlier decision that survives, and ADR-0090's own reason is why: a private ledger of displaced values goes stale the moment the user edits the setting by hand, and a removal restoring a value they have since replaced is worse than one that restores nothing. Disabling the Feature therefore clears the setting where this collection holds it and restores nothing. That is exactly why the question has to say so before it is answered, and why the record of what was replaced is in the run's own report rather than in a file this collection would have to keep honest forever.

**What this costs.** A user can now lose a status line they wrote, in one answer, with nothing to put it back. The whole of the mitigation is that the question names the command before they answer it and says plainly that no copy is kept — which is a real bound and not a safety net, and it is what an irreversible action is honestly offered as. What it buys is that checking a box does what checking a box means, and that a collection which writes into the user's own files asks them about their own files instead of deciding for them in either direction.

# The requirement is the whole thread, not the body

`/orchestrate` briefed a subagent with a ticket's body and nothing else. The tracker's unit of record is not the body, though — it is the thread, and in this project the difference is not academic. The `/triage` skill posts its agent brief, by instruction, as a **comment**: the settled decision, the desired behaviour, and the acceptance criteria. So a triaged ticket reached a builder as its untriaged self, ending in the open questions triage had already answered, and reached the verifier the same way — told to check every acceptance criterion in a ticket that, as it saw it, had none. Nothing refused and nothing warned. Two of seven tickets in one run were built that way before it was noticed.

**So the brief carries the ticket as the tracker now holds it**: the body it was filed with, followed by what has been said on it since, in the order it was said, each comment attributed and dated. Both subagents get the same account, from the same field of the same plan entry, because a criterion the builder was given and a criterion the verdict is taken against have to be the same criterion. Where a comment contradicts the body, the later text stands, and both templates say so — otherwise a builder reading "What triage must decide" above an answer to it has a contradiction and no rule for resolving it.

**This does not reopen the engine's boundary stance, it draws the line the stance was always about.** `record` writes its outcomes as marked comments and reads them back off the tracker (ADR-0051), on the reason that a comment is prose anybody can write and only a marker this engine knows how to record settles anything. That reason is right about markers and was never a claim about requirements. The line is between two different acts. **A marker is read only where the engine wrote it** — an outcome naming an outcome this engine records, or the note it leaves before a rebuild — and everything else a comment carries is left uninterpreted. **Prose is relayed rather than interpreted**: the engine does not summarise a comment, rank it, judge whether it is requirement or chatter, or let it change a plan. It hands the thread to a subagent, and the subagent is what reads it. Nothing the engine decides is a function of what a comment says; the only thing that changed is what a subagent is handed.

**What the run wrote itself is left out.** An outcome marker and a rebuild note are the engine talking to its next self, and a builder that reads them learns only that this ticket failed once — which is not requirement and is a fair way to bias a session. They are recognised by exactly the two patterns that write them, so a marker naming an outcome this engine never records stays in the thread: it is somebody else's writing, and somebody else's writing is what gets relayed.

**The alternative was to teach `/triage` to edit the body**, and it was rejected. `/triage` lives outside this repository and is one of several ways a requirement lands on a ticket — a maintainer answering a question in the thread is filing requirement whether a skill wrote it or a person did. Fixing the writer fixes one writer; reading the thread fixes every one of them, and makes the comment-writing convention harmless rather than merely tolerated.

**What this costs.** A plan carries every ticket's thread, so the JSON a wave is briefed from grows with the conversation on its tickets — and a long argument on a ticket reaches a builder whole, including the parts that went nowhere. That is the price of not interpreting: the engine cannot tell a settled decision from a passing remark without becoming the thing this record says it must not be, and a builder reading one paragraph too many is a far cheaper failure than a builder guessing at a decision that was made hours ago. A ticket with no thread is briefed exactly as it was before this record, which is the whole of the behaviour that did not change.

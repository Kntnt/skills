# Orchestrate routes execution and inherits verdicts

ADR-0074 established that Orchestrate may delegate building down while its own seat owns every verdict, and had the orchestrator judge each builder's model from the ticket's own text. Two things about that turned out to be wrong rather than merely narrow. A model name is not an execution configuration: the same model exposes materially different deliberation controls, and a builder-only model override left that half unstated. And a judgment made from prose cannot be reproduced — the same run, resumed the next morning against changed profiles, aliases, prices, evidence, and Harness mappings, would judge again and reach somewhere else, with nothing in the account saying it had.

**Orchestrate delegates every execution role through model-selector's public route Interface, and freezes the snapshot that Interface returns before the first claim.** Initial builds, amends, collision repairs, rebuilds, replacement claims, and mechanical wave fixes are execution and are each decided from that one snapshot, in a request of their own, before they run. The Interface alone validates exact points, mappings, availability, the complete main-seat ceiling, evidence class, bounded escalation, and Harness-native controls; this Skill reproduces none of those rules and reads none of model-selector's private references (ADR-0083). A selected decision launches exactly as it says; a reported inheritance launches on the exact main seat and says optimisation was unavailable; a refusal starts nothing.

**Every verdict inherits the complete main seat exactly, and is never routed.** Ticket verification, amend verification, repair verification, and wave checking use the orchestrating session's exact model and deliberation configuration. Inheritance here is authority rather than a decision that happened to come back inheriting, so there is no request to make for a verdict at all — and the engine refuses to freeze one, because a decision that cannot be persisted cannot reach a verifier. No execution override, automatic decision, route result, repair, or failure can downgrade that seat. Independent verdicts, not builder reports, still decide the existing five Ticket Resolutions.

**Route before claim is an invariant of the run, not a step on its opening path.** The frontier a plan names is routed as one ordered batch, in plan order, and so is every frontier after it: a wave the last one unblocked returns through the same preflight rather than jumping to the claim, and a replacement considered after a claim collision is decided before its own claim. The claim verb enforces it, refusing a ticket the frozen account holds no acceptable decision for; the amend verb enforces it per attempt. A rule the workflow only asks for is one a later edit can move a paragraph and lose.

**The frozen routing is the one thing a run cannot rebuild.** ADR-0051 put every outcome on the tracker and ADR-0052 made the invocation the resume, both resting on the same property: what a run remembers of itself is a note of what the tracker and the branch already say, so it may be absent without changing an answer. That property does not extend here. No tracker and no branch holds the profile revision, evidence identity and vintage, Harness inventory, native mappings, commercial facts, main seat, and override policy a decision was made from, and the current versions of all of that are a different context rather than a recovered one. So it lives in a file of its own beside the ordinary state, absence and damage are different answers where that state answers both as *no state*, and a run whose account is gone while its claims stand stops rather than deciding the rest of itself from what is current. The invocation's own `--model` and `--deliberation` locks are frozen with it: a re-invocation that changes or drops either is a second run reporting as the first.

**Portable overrides are independently exact.** `--model` locks only the building model and `--deliberation` locks only the building portable deliberation value (`low`, `medium`, `high`, `xhigh`, or `max`). Omission leaves that one dimension automatic. An unavailable, ambiguous, unmappable, or above-main explicit point refuses before claims and never falls through to a neighbour. A launch that goes away after the ticket was claimed is a condition of the environment and nothing about the work, so it is triaged as the mechanical hinder it is and takes the workflow's existing single repair — never a quality failure, never a new attempt, and never a quiet substitution of the point the developer named.

**What this costs.** Each run preserves a larger account — snapshot, exact decisions, evidence and selection facts, native controls, exclusions, and reasons — and cannot optimise where the frozen data cannot make a safe decision. A run that loses that account stops where it would once have carried on, which is the price of the report being true about what decided what. In return, unattended execution is reproducible across resumption while its strongest seat remains the final authority.

# `compatibility` states the environment, and names no product

The Agent Skills specification defines `compatibility` as the field a skill states its environment requirements in, and every skill of this collection that has one left it blank. The requirements were stated twice already — in the body's **Dependencies** paragraph, and machine-readably in `metadata.kntnt.binaries`, where the checker refuses on them (ADR-0012) — and both copies only speak to a reader that already knows this collection. `metadata.kntnt.*` is a private namespace nothing outside is obliged to decode (ADR-0061), and the body's paragraph is invisible until the skill has been loaded and activated. **Every skill with an environment requirement now states it in `compatibility`, and a skill with none carries no field** (issue #53).

**A third copy of a fact is justified by the reader it is for.** `compatibility` is the one field a foreign consumer — another harness, a registry, a validator — knows to look at, and a blank one says a skill needs nothing. That is the drift the objection is really about, so the copy that can drift is pinned rather than trusted: a test holds every binary in a skill's dependency block against its `compatibility`, from both sides, so dropping a binary from either one fails the suite.

**It also holds what the dependency block deliberately cannot.** The block is hard requirements only — the checker exits 2 on anything in it — so a requirement a skill degrades gracefully without has nowhere else to go. `/release` needs `gh` for step 9 alone and reports the pushed tag without it, and the Manager needs `npx` and a reachable network for the transport and the Catalog fetch, neither of them a binary a run may be refused on. These soft requirements are stated in `compatibility` and reviewed by eye, like the body paragraph, because no list holds them to be checked against.

**No `compatibility` names a harness product.** The specification's own example is *Designed for Claude Code (or similar products)*, and that is exactly what this collection is not: one set across many harnesses (ADR-0005, ADR-0008). Where a skill needs something of the harness it names the Capability rather than the product that has it (ADR-0030) — `/delegation` and `/orchestrate` say `subagents` — so the field stays true wherever the collection is installed.

**The mirror rule of ADR-0012 holds here.** `/tldr` has no binary, no Capability, and no collection Dependency, so it carries no `compatibility` for the same reason it calls no checker; the day it gains a requirement it gains the field alongside it.

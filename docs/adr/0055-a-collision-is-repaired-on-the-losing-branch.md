# A collision is repaired on the losing branch, and a rebuild is the only rerun

Two tickets built at the same time can touch the same code, and the second one will not merge onto the branch the first is already on. Neither ticket is wrong: both were built alone, both passed verification alone, and what failed is the assumption that they were independent. Somebody has to decide what the merged code should say, and there is no human in the run to ask.

The cheap repair is worth trying, because two added imports should not cost a full rebuild. But a repair is a guess until something checks it, and the thing it can silently get wrong is the worst thing this Skill can report: one ticket's acceptance criteria kept by quietly dropping the other's, which reads perfectly well in a diff. **So a resolution is verified against both tickets' acceptance criteria by a session that did not make it, and a resolution that cannot be verified is not a resolution.**

**The repair happens on the losing ticket's own branch, never on the run branch.** The run branch is merged *into* the ticket's working tree and settled there. Only then, and only on a verifier's pass, is that branch merged onto the run branch — where it cannot collide, because it now contains the very commits it collided with.

The obvious alternative is to settle the collision where it happened, on the run branch, and revert the merge if it does not verify. That inverts the property the whole Skill rests on: nothing reaches the branch the developer comes back to until a verifier has passed it. It also puts the run branch into a half-merged state that an interruption can freeze — the developer wakes to a repository mid-merge — and makes the undo a reset of the branch's own tip rather than the discarding of a scratch branch nobody depends on. Repairing on the losing branch costs one extra merge commit and buys back both.

**Where the repair does not verify, the ticket is built again from nothing, on top of the work it collided with.** The failed resolution is discarded with the working tree that holds it, so no second builder can read it as work already done. What comes back is code somebody meant rather than a stitched-together guess, and it cannot collide again, because it was built on the code it would have collided with.

**A rebuild is the only rerun the Skill performs, and it happens at most once per ticket.** A failed ticket is never retried, because the conditions of a rerun would be identical and so would the outcome. A rebuild is not that: the conditions genuinely changed, the branch now carrying work that was not there when the ticket was built. That is the whole of the exception, and it is bounded to one attempt so that a ticket which keeps colliding is recorded and reported rather than built over and over through the night.

**The bound is kept on the tracker, not in the run.** The ticket carries a note from the moment its rebuild starts, for the same reason every outcome does (ADR-0051): a run interrupted mid-rebuild must come back and find the bound where it left it, rather than with its one rebuild unspent.

**A collision that is not repaired is reported with the ticket it collided with.** That pair names a blocking edge the ticket breakdown was missing, which is the one thing a failed integration is genuinely good for — the files alone would leave the developer to work out whose work they had run into. The branch itself is what answers it: each merge a run makes carries a marker naming the ticket it brought, so the commits a conflicting file came from can be read back off the branch rather than remembered.

**What this costs.** A collision the resolver could have settled in place is settled twice — once in the ticket's working tree, once as a merge commit onto the run branch — and a repair that fails costs a full build of the losing ticket on top of the merge attempt that preceded it. Both are paid in machine time overnight, which is the resource this Skill has most of.

# How the collection reaches a machine

This record settles the distribution model in one place: how this collection's Skill files get onto a machine, and why each promise the Manager makes while they do is the promise it is. It is a consolidation — it supersedes the twenty-five records named below, and carries forward what those records were for, which is the reasoning. What the rules are is stated in [`docs/rules/collection.md`](../rules/collection.md), which is the authority on them; this record argues rather than legislates, and where it needs a rule it cites that module rather than repeating it. A reader who wants today's law should be reading the module and not this.

- ADR-0006 — Transport installs only the manager
- ADR-0007 — A new Catalog entry is offered, and `--yes` accepts it
- ADR-0009 — Skills refuse when a dependency is unsatisfied; they never install
- ADR-0011 — Update re-checks dependencies; it does not refresh externals
- ADR-0013 — A Project cannot hide a Global skill
- ADR-0027 — Bare `/kntnt` is Help
- ADR-0028 — Update re-adds what deviates; the transport's `update` is not a refresh
- ADR-0030 — A harness requirement is a Dependency the agent answers, not an install-time gate
- ADR-0035 — Target directories are detected at each invocation, never recorded
- ADR-0036 — A change is reported from the disk, never from the plan

**Not all twenty-five had an argument left to carry, and the ones that did not are absent below rather than summarised.** ADR-0002's naming, ADR-0004's default layer and its flag spelling, and ADR-0011's re-check after a refresh are one-line rules whose reasoning nobody would have to rediscover; they are stated in the rules module and appear nowhere below. ADR-0038's reading of that same flag is another, and only its second half — the argument for showing one layer rather than a union — is carried. ADR-0005 and ADR-0027 each say in their own text that a later decision removed the alternative they argued against, so what is carried from them is the reason the collection never grew that alternative, and not the argument against it. Everything else below is reasoning a reader would otherwise have to reconstruct from evidence that no longer exists anywhere but in these records.

## The transport boundary, and why the Manager is not a package manager

**The collection orchestrates a transport it did not write, because writing one buys nothing and forks the collection from the ecosystem its users already stand in** (ADR-0001). Users install collections with `npx skills add`; a second installer would duplicate the multi-harness paths, the update logic and the discovery, and would have to be kept correct against every Harness independently. What was left over once that scope line was drawn is the whole of the Manager's job, and every decision below is downstream of the line having been drawn where it was.

**The transport's own picker had to be shut out of the collection, or the user faces two selectors that can disagree** (ADR-0006). A Transport picker listing every Skill, beside a Select list that also lists every Skill, gives two answers to *what do I have* with no rule for which wins. Hiding the rest of the collection from ordinary Transport discovery leaves one selector, and Select is it.

**Not installing anything on the user's behalf is the same decision read from the machine's end** (ADR-0009). Auto-installing a binary or an External takes rights the user never granted, and it rebuilds exactly the package manager ADR-0001 declined to build — the multi-platform install paths, the upgrade logic, the failure modes — inside a Manager whose whole claim is that it does not have them. What stands in its place is the answer this collection gives to every kind of shortfall: say what is wrong, give the one instruction that fixes it, and do no work until it is fixed.

## Where Skills go stops being a choice

**Recording the targets was the obvious design and the rejected one** (ADR-0035). It costs a verb to ask the question, a file to remember the answer and a failure state for when the file is missing, and it buys less than the Transport's own default gives away free — while going stale the day another Harness is installed. Detection has no such day: a Harness installed after the last run is reached by the next one with nothing in between, because presence is resolved from the disk in front of the verb rather than from a memory of an earlier disk. What this costs was accepted rather than argued away: there is no longer any way to say *I have this Harness and do not want the collection's Skills in it*, and the remaining control is coarser and sits one level up — leave the Skill unchecked altogether, for anywhere.

**Naming every Detected Harness in every call is a defect that was observed rather than a tidiness** (ADR-0035, issue #7). Leave one Harness that reads a shared skills directory out of the call and the Transport will not clear that directory at all, so a Manager that ever names a subset can ask for a removal that silently does not happen. A Manager that always names all of them cannot make that request at all.

**All means all present, never all the Transport knows of** (ADR-0035). The Transport has the right rule and also a wrong fallback: detecting nothing, it targets every agent it has heard of, which would create skills directories for Harnesses the user has never installed — litter in a home directory and vandalism in a repository. With nothing detected the answer is the shared directory alone, the one the largest group of Harnesses reads. The Project layer needs a second guard for the same reason: `skills`, `data/skills` and `agent/skills` are things a repository has for its own purposes, and a rule that claimed them on the strength of a name would write this collection into somebody else's source tree.

**A Capability is a Dependency rather than a placement, which is this rule applied one level up** (ADR-0030, ADR-0005). A Skill that needs something of the Harness itself invites the obvious fix — let the Catalog say which Harnesses it belongs on — and that fix is the per-Harness matrix: the desired set differs per Harness, Select needs a row per Harness, and the drift the collection exists to prevent comes back through the door. Letting a Skill be Enabled everywhere and refuse where it does not fit keeps one desired set and one layer model. Since targets stopped being chosen at all, no dimension is left for a set to differ along, which is why ADR-0005 records its own rule as having become trivially true.

## A layer can only add

**The mask was rejected and stays rejected** (ADR-0013). A Project able to turn a Global Skill off would make what a Harness loads depend on the order the two layers are read in, and would surprise anyone who Enabled a Skill once on the machine and then found it gone in a directory they had never Disabled it in. A layer that can only add is one a user can reason about from either end, and one whose result does not change when the reading order does.

**The union view left the collection with the verb that reported it** (ADR-0038, ADR-0043). Status changed nothing, so it could read the flag as a question and answer it with everything Enabled in Global plus everything Enabled here. Select is where the user acts as well as where they read, so every row of its list has to be a row they can change — and a row sourced from Global is not one, there being no copy in this layer to remove and no subtractive overlay to make one. A list whose checkboxes mean one thing in some rows and another in the rest teaches the user to distrust all of them. What the union was actually needed for at the moment of choosing survives at row level, as a mark on a Skill already Enabled in Global, so nobody Enables a second copy into a repository by accident.

## Disk is truth, and the disk is the report

**Presence in the layer's Detected Harness directories is the whole of Enabled, because that is the whole of what a Harness reads** (ADR-0003). This is the invariant the rest of the distribution model rests on. Any second notion of presence — a manifest, an install log, a remembered answer — is a thing that can disagree with the disk, and the disk wins every such argument by construction, so the second notion can only ever be a source of wrong answers. It is what makes apply idempotent, what makes State a cache that may be thrown away and rebuilt from the Skills on disk rather than an authority that can be corrupted, and what gives every verb a delta to compute instead of a history to reconstruct.

**Reporting the plan rather than the disk was tried, and it lied** (ADR-0036, issue #7). A run that unchecked two Skills reported both as changed, exited 0, and left both on disk, where the next Select contradicted it. A Transport that removes nothing and exits 0 is indistinguishable from one that did the work, so a zero exit is not evidence that files moved. Reading the disk afterwards — with the same presence test Select decides Enabled with, in the same directories, with no cache and no second notion of presence — is the invariant above applied to reporting what was done rather than to deciding what to do.

**It is a safety net rather than a fix for one Transport defect** (ADR-0036). The particular defect behind issue #7 became unreachable the moment every call named every present Harness; what reading the disk afterwards buys is the *next* silent failure, from any cause, arriving as a legible error instead of as a contradiction the user finds later. It earns most where the Manager removes itself, because afterwards there is nothing left to contradict a false report of success.

**What presence cannot see is named rather than papered over** (ADR-0036). A refresh that overwrote nothing looks exactly like one that did, the files being in place either way. Update is verified on the presence test regardless, which catches the case that matters — a Harness detected since the last run, which the refresh is supposed to reach — and a stronger check would require a second notion of presence, which is precisely what the invariant forbids.

## The Catalog is asked, and only Update remembers the answer

**A Catalog that only Update refreshed answered the wrong question** (ADR-0039, issue #3). It said what the collection contained when this machine last updated, not what the collection contains. A Skill published upstream was invisible until the user ran Update — the one thing nothing gave them a reason to run, because nothing had told them there was anything new — and a Skill the collection had withdrawn went on being offered as though it could still be Enabled. Both halves were observed on a real installation, two withdrawn Skills among them.

**A failed fetch may not take a read verb with it** (ADR-0039). The origin is unreachable often enough — offline, blocked, down — that a Select exiting non-zero on it would be worse than a stale one, so a stale answer beats no answer, provided the user is told which they are holding. The floor is where nothing has ever been stored, and there the error is allowed to stand: a list of what the collection contains is the one thing that cannot be guessed at. That is the collection's standing answer applied to a list rather than to a Dependency — say what is wrong and let the user act, rather than fail or guess.

**Confining the stored copy to Update is not the rule that a read should have no write side effect** (ADR-0039). Telling a new entry from a Withdrawn one is a diff, and a diff needs a *before* that only one verb is allowed to move. Any other verb adopting what it fetched would flatten it, so the next Update would report no new Skills and — the real cost — leave a Withdrawn Skill's files exactly where they were. The price of the choice is that the offline fallback is only ever as fresh as the last Update, which is what a fallback is for.

## Consent governs what enters the context, and not what leaves it

**Offering a new entry and deleting a withdrawn one unasked are one rule read from two ends** (ADR-0007, ADR-0037). Enabling a Skill silently would put instructions the user has never read into every Detected Harness's context, so a new entry is named before it can be Enabled. Removing one puts nothing anywhere: it takes away something the collection has already stopped shipping, and asking would offer a choice that cannot be honoured, since *keep it* means keeping files no verb of the collection can still reach and whose only remaining removal is deleting a directory by hand.

**The consent trade was overturned deliberately, and the cost is real** (ADR-0007). `--yes` means no question is asked at all, so an unattended `update --yes` — a cron job, a provisioning script, a Skill passing the user's arguments through unread — can place instructions the user has not read into every Detected Harness. That is precisely the harm the earlier decision was written to prevent, and it is accepted rather than argued away. What buys it is a flag that means one thing everywhere: the alternative was a flag that answers every question except this one, which is not a rule a user can hold, since they would have to carry a list of the questions it does not reach, and a flag with an exception lies about the rest. It was also unenforceable at the edge where it mattered, a Skill forwarding the user's arguments unread having no way to know which of them the Manager would decline to honour. Whoever reopens this should reopen it as *is one coherent flag worth an unattended install of unread instructions*, which is what was actually decided, and not as *should new Skills be silent*, which was not decided either then or now.

**What an offer Enables is the entry alone, because of what the user was asked** (ADR-0007, ADR-0047). At Select's list the user is choosing a set, so resolving the closure answers a question they are in the middle of. At Update's offer they are answering *do you want the thing the collection just added*, and a Skill they have already chosen to leave Disabled is not that question's to reverse. What they lose is a new Skill that works on arrival; what they get is a report naming exactly what it lacks, and Select as the way to supply it.

**Provenance had to move to where the Transport cannot overwrite it** (ADR-0037, issues #5 and #20). Withdrawal was once decided by diffing a Catalog copy stored beside the Manager — a sidecar of the Manager, so any Transport run that re-copies it replaces the copy, including an Update that refreshed it and then died, and including a bare `npx skills update` run by hand. Once that file no longer named a Skill, nothing could establish the Skill had ever been this collection's: the diff is empty forever and the files are stranded with no verb able to reach them. So withdrawal is decided from the disk, by the marker each installed Skill carries in its own frontmatter, and the Catalog diff keeps only the half it can still be trusted with, which is reporting new entries. The cost is reading each installed `SKILL.md` in the layer once per Update.

**A report from a list that could not be confirmed is worth having; a deletion from one is not** (ADR-0037). That is where the fallback stops, and it is the same shape as the freshness verdict a fallback Catalog cannot support.

**Fetching before deciding is what keeps a withdrawn Skill from killing the run** (ADR-0037, issue #5). Resolving the work first meant resolving it against a list the collection had already moved on from: the withdrawn Skill was still Enabled, so it went into the refresh, the Transport was asked for a name the source no longer carried, and the run died with the Transport's raw error and no report at all.

## Freshness is a comparison, not a version

**A version number answers a question nobody asked** (ADR-0041). *Which release did this come from* is not *are these the same files*, and a version cannot see a truncated install or a hand edit at all, both of which leave the number exactly where it was. A digest over the sorted relative paths and the contents sees all four kinds of difference — a rename, an edit, an added file, a removed file — and it is computed when the Catalog is generated, so no release depends on remembering to bump anything and there is no number to bump.

**The ignore list is a correctness requirement rather than a convenience** (ADR-0041). The generator walks a working tree carrying the maintainer's own bytecode cache; the consumer walks an installed directory that made its own the first time the Skill ran. Neither side has a git to ask which files are the collection's, so the two can agree only through one explicit list, defined once and used by both. One artefact the two sides disagree about is enough to make every Skill that ships a script report itself as Deviating for good — and a signal that never turns off is one nobody reads, which would cost the digest the only thing it is for.

**The vocabulary carries the honesty so that no rendering has to remember it** (ADR-0041). The comparison sees two states and no history, so *out of date* would name a direction it cannot establish, and outside a lagging Project copy the commoner cause of a mismatch is the user's own edit an hour ago. Deviating says exactly what was seen and nothing more, which is why every offer to re-copy can say in the same breath that local changes are overwritten.

**A freshness verdict from a fallback Catalog would be a verdict about the past** (ADR-0041). Those digests describe the collection as of the last Update, so a Skill matching them may Deviate from what the collection carries now and one differing from them may be exactly current. Update goes further and refreshes nothing at all, for a reason that is not about digests: the files themselves would have to come through the Transport from the same origin the Catalog could not be fetched from, so a careful decision about what to refresh would be followed by a fetch that cannot happen.

**The Transport's own `update` is not a refresh, and a collection of sidecars is what proved it** (ADR-0028). It compares `SKILL.md`, skips the Skill whose `SKILL.md` is unchanged, exits 0 and reports everything up to date, while every sidecar in that directory stays at whatever revision last happened to touch that one file. `delegation` was added to the Catalog in 0.3.0 and no `/kntnt update` could deliver it, because `skills/kntnt/SKILL.md` had not changed since 0.1.0. Calling the Transport's `add` instead — which empties and replaces the whole directory — is what makes *removed upstream is gone, changed upstream is replaced, added upstream is present* a stated postcondition rather than a happy accident. Gating on the digest is safe for the same reason `add` was chosen in the first place: a Skill whose digest matches is already byte-identical to what the collection ships, so skipping it cannot strand a sidecar. That is the opposite of a skip that compares one file and infers the rest of the directory from it. What the gate buys is a report that carries information — *twelve of twelve refreshed* said the same thing on a machine where nothing had moved and on one where everything had.

**A test double that differs from the real thing in either direction tests nothing** (ADR-0028). That `add` empties the directory before it copies was verified against the real Transport, a file added under an installed Skill and an edit to one of its files both being gone afterwards. A double that leaves extra files in place is less capable than the thing it stands in for, and a correct test fails against it; the mirror image is this record's own lesson, the double having once copied unconditionally, which is why the suite was green while the collection could not be updated at all.

## One verb where three stood

**Three verbs put a transcription step between somebody and a decision they had already made** (ADR-0043). Status printed a list, Enable and Disable took names, so the everyday act of changing what is Enabled was *read a list under one verb, then retype names from it under another*, and the list the user had just read was not the thing they acted on. What was given up with those verbs is the transcription and the union view, and nothing else.

**Reading may not be a side-effecting act, or the verb cannot carry the reading half of its job** (ADR-0043). Somebody who opens Select to remind themselves what they have must be able to leave knowing they changed nothing. A Select that refreshed or repaired on the way past would put the collection back to three verbs with one of them renamed.

**Partial was modelled as a state and should not have been** (ADR-0043). A Skill present in some of a layer's Detected Harnesses and missing from others is a fact about the disk, not a third thing anybody chose. Modelling it would have put a value in the payload that no answer of the user's could ever set, and made the list ask a question with no honest answer available.

**Naming a Skill directly applies a delta rather than assigning a set** (ADR-0043). A machine being provisioned has nobody to read a list, and treating the named Skills as the whole answer would silently Disable everything a script did not happen to mention.

## Taking the collection off the machine

**Removal existed only as a side effect of editing a list, and once the list was retired even that way in was gone** (ADR-0040). Installing was one command and removing was none, which is what the verb answers.

**Having no Project form is the decision rather than an omission** (ADR-0040). Those files are the repository's: a teammate who clones it receives them, and whether they stay is that project's decision rather than this machine's. Uninstall answers *take your collection off my machine*, which no working directory is part of. The report has to say as much out loud, the alternative being a user who has been told the machine is clean while a repository on it still carries these Skills — a false statement about the one place they can go and check.

**Splitting the Manager's own removal off is what leaves a retry available** (ADR-0040). Losing the verb before the files it removes strands a machine full of Skills nothing can reach, which is a worse place to stop than one run short of finished — and the retry that ordering exists for has to be a retry the code actually leaves available. Deleting itself is also why the run reads its path table once and holds it: the table ships beside the Manager, and the run still has to verify the removal and name the directories it happened in after the file it would have read that from is gone. Neither pass raises on the other's behalf, both reading their verdict off the disk instead.

**The usual remedy for a stale Catalog is the one remedy this verb cannot leave behind** (ADR-0040). Everywhere else a run made from the stored copy is simply run again once the origin is reachable; after Uninstall there is no Manager left to run it with, so a run that fell back may strand a Skill the collection has since withdrawn and nothing can be done about it afterwards. That is what the verb naming the list it worked from is for.

## What a bare name should teach

**Binding the bare word to a report was the alternative, and the reason for rejecting it outlived the alternative** (ADR-0027). A report of what is on the machine answers a question the beginner has not asked; the person who types the Manager's name and stops there is the person who does not yet know what comes after it, so the bare form teaches the interface instead. The binding also made one subcommand reachable two ways, an asymmetry with nothing behind it. Status no longer exists, so there is nothing left for the bare form to mean and the rule is trivially true; what is left of the record is the reason the collection never grew that shape.

## The dependency gate, and the parties who answer it

**A Capability cannot be tested by a script, because the script cannot know which Harness invoked it** (ADR-0030). An environment sniff would be a guess, and a wrong guess refuses a Skill that works. The agent knows, because the agent *is* the Harness, so the check is split between them and the script's clean exit stops meaning *go ahead*. The names are closed rather than free text for the same reason the split exists at all: a check that never runs passes forever, and a misspelling is how one quietly becomes one.

**A chain walked in prose is a chain walked differently on a bad day, and the failure would be silent** (ADR-0047). A Skill Enabled without something it needs looks exactly like one that has everything, so the closure is resolved by the script and only rendered by the agent. It costs one question however deep the chain, because the user made one decision and being asked three times about it is the same decision charged three times over — and one question is a question `--yes` can answer, which is only sound because it is worded so that yes ends it and opens nothing further.

**Showing the edges before the answer is what makes the graph the user's to reason about** (ADR-0047). A list that hides them asks the user to answer a question the Manager already knows the answer to, so a row whose Dependency is unchecked is locked and names what to check instead. A row the user did check is never locked, a checked Skill whose Dependency has gone being a break to report rather than a permission to withhold.

**Unchecking is reported and allowed** (ADR-0047). A Manager that quietly put the Dependency back would be answering for the user. Saying what was left Unsatisfied and doing it anyway is the same *say what is wrong and let the user act* the collection answers everything else with, and it is why the dependent Skill can refuse at use time without the Manager ever having to forbid the state.

**A gate that admits when it should not is never found at all** (ADR-0068, issue #68). The gate answered exit 0 with two empty lists for a Skill whose declaration it could not parse — which is exactly what a Skill genuinely requiring nothing answers — so an unreadable declaration was indistinguishable, to everything downstream, from nothing to declare. Each Skill's body treats exit 0 as the go-ahead, and the Capability half is worded so that exit 0 is not a go-ahead until every Capability is answered, which an empty list satisfies vacuously. A gate that refuses when it should not is found the first time somebody runs it; this one could not be found at all.

**What kept the fail-open shape alive is that the same marker answers a second, opposite question** (ADR-0068). Asking a directory the collection did not write whether it is this collection's, an absent marker means *not ours*, and a rule of the form *refuse where the marker is missing* would refuse every Skill on the machine this collection did not write. The two states come apart at the caller: the sweep asks about a stranger's directory, while the gate asks a Skill that invoked the checker itself what it declares — and nothing but a Skill of this collection invokes the checker, the instruction to run it being written in the collection's own bodies. A caller is one of ours by the act of calling. One predicate answers both questions, and the two callers read its answer differently because they asked different things.

**The refusal channel was chosen for what a Skill's body already documents** (ADR-0068). Exit 2 is the one non-zero answer every body says what to do with, so a fault reported that way reaches the user through a channel that exists; a raised error exits 1 to stderr, and a Skill told only what to do with exit 2 would stop with nothing to say. For the same reason the entry carries the shape every Unsatisfied Dependency carries — an entry of another shape reaches the user through no documented channel at all.

**What the fix buys is the next shape change, not the one that produced it** (ADR-0068). The code that fails open is the installed Manager's, so a machine that Enables a Skill through Select without first running Update still gets the new shape beside an old Manager, and that Manager answers exit 0 with two empty lists. The generation-time gate was described as the whole of the guarantee; it was the whole of the guarantee about the repository, and never about a machine holding two revisions at once.

## The Sandbox behind a dry run

**A plan is a second account of the verb, kept true by remembering to keep it true** (ADR-0042). It is composed before the Transport has been asked for anything, so it cannot report what the Transport did with the files, and the run that follows is the first time anybody finds out. When the two disagree the user is shown the wrong one and nothing in the run can notice. Executing the verb against a Sandbox removes the second account: what comes back is the verb's own report, read off a disk, because there is no other report for it to disagree with.

**It rests on a measured fact rather than an assumption** (ADR-0042). The Transport respects an overridden `HOME`: an install with `HOME` redirected to a temporary directory landed entirely inside it, and the real home was untouched. Had that not held, the flag would have had to be a description after all. The guarantee is therefore stated in terms of the disk rather than of the mechanism, which is also what forces the redirection to cover the working directory as well as the home: a Project layer is written there, and a guarantee about a home would have missed it entirely.

**The seed exists because a preview that starts from an empty world reports installing what the user already has** (ADR-0042). The Sandbox has to hold every layer the previewed run *reads* and not only the one it writes to: what Satisfies a Project's Dependency is Global's copy as much as its own, so a Sandbox holding the working directory alone would read a machine with nothing on it and offer a second copy of every Dependency the user already has. The union runs one way only — a Sandbox standing in for Global holds Global alone, a Global run reading no Project, and a seeded Project would be a directory the real run never looked in. Other collections' files are left out deliberately: no verb of this collection touches them, so copying them in buys nothing, and if the Transport ever did touch one, that is a defect to be observed in reality rather than absorbed by a Sandbox that had made room for it.

**Full fidelity has a measured price, and it is announced rather than hidden** (ADR-0042). The npm cache lives under the home that was redirected, so the first preview in a session pays for a fresh download of the Transport and outlasts the run it is previewing. An unexplained pause in a command whose entire promise is *nothing will happen* is exactly the moment somebody reaches for the interrupt — and a preview that costs this much is one to reach for deliberately rather than before every write.

## The agent is the renderer

**A picker is the natural way to build a list with checkboxes, and every part of it is unavailable here, which is why this is a record and not a habit** (ADR-0045). A script invoked from a Skill has no controlling terminal, measured rather than assumed: no stream is a TTY, `/dev/tty` cannot be opened at all and answers `Device not configured`, and a script that reads stdin does not fail but deadlocks and takes the session with it. `dialog`, `whiptail`, `gum` and `fzf` each fail on exactly that open, so no dependency buys a way around it.

**`TERM` is set and inherited, and that is the trap** (ADR-0045). Anything deciding whether it has a terminal by reading the environment gets a false yes and then hangs on the read. A check that tests the file descriptor answers correctly; a check that tests an environment variable answers confidently and wrongly, and the failure it produces is a hang rather than an error.

**Even given a terminal it would not work, and this is the second and independent reason** (ADR-0045). The Harness captures a script's output rather than streaming it, so nothing drawn mid-run reaches the user until the run is over, by which time a picker has nothing left to pick. And a widget belonging to one Harness would break the rule that the collection behaves the same everywhere: a Skill that is a menu in one agent and a wall of text in another is two Skills with one name.

**The trade is that everything the user actually sees is prose** (ADR-0045). The suite can pin that the payload carries what a correct rendering needs, and it can pin nothing about the rendering. It is not a close trade: the alternative on offer was never a tested picker, it was a hung session.

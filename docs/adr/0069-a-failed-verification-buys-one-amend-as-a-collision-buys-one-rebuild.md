# A failed verification buys one amend, as a collision buys one rebuild

Two overnight `/orchestrate` runs, interviewed after the fact, lost their nights to verification failures whose fixes were bounded, named, and already written down — by the verifier itself. One run had a ticket fail on a single contradiction left standing in one documentation file, a three-line edit away from its pass. The other recorded three tickets failed on one clause in a README, one field-routing change, and one `lock()` moved inside a `try`/`finally` — and when the developer came back in the morning and said *fix them*, all three were fixed in minutes, each fix shaped exactly by the verdict that had failed it. The rule that stopped both runs is ADR-0055's: a failed ticket is never retried, because the conditions of a rerun would be identical and so would the outcome. That reasoning is sound, and its premise is what an amend changes.

**So a ticket that fails verification is amended once: a fresh builder, in the same working tree, is briefed with the ticket and the verifier's verdict, and a third session verifies what it did.** A pass integrates and records the ticket exactly as a first-time pass does. Anything else — the amender stopped, or the third verdict is a fail — records the ticket failed, exactly as today, and it is not touched again.

**An amend is not the retry ADR-0055 refuses, because the conditions are not identical.** The verdict names the command that failed or the criterion that is not met, which is information the first builder never had. A rerun from the same brief would walk the same path to the same failure; a build handed the failure is a different build. This is the same argument that already licenses the rebuild: the one rerun the run performs is the one whose conditions genuinely changed.

**The bound is one amend per ticket, recorded on the tracker at the moment the amend starts.** The reasons are ADR-0055's own, unchanged: bounded to one attempt so a ticket that keeps failing is recorded and reported rather than worked over and over through the night, and written on the ticket (ADR-0051) so a run interrupted mid-amend comes back and finds the bound where it left it rather than with its one amend unspent. The amend and the rebuild are separate bounds: a ticket may spend each once, because they answer different failures at different moments — the rebuild answers a collision at integration, the amend answers a verdict before it — and folding them into one shared attempt would leave a collided ticket's repair story dependent on whether its verifier had earlier found a typo.

**The third session is briefed like a first verifier, not like a reviewer of the amend.** It gets the ticket, thread and all, and the working tree; it runs the project's full verification itself and checks every acceptance criterion. It is told nothing the amender said and nothing the first verifier said beyond what the repository now shows — a verdict formed by checking the fix against the complaint would inherit the first verdict's blind spots, and the failure mode this Skill guards against is a report it cannot support.

**What this costs.** A failed ticket now costs up to two builds and two verifications before it is recorded failed, paid in machine time overnight, which is the resource the run has most of. The genuine fail is delayed by one cycle. And a verifier's verdict becomes load-bearing in a second way — it is now also a brief — which is pressure in the right direction: a verdict that names what failed was already the standard (`verify.md` demands the failing command or the unmet criterion by name), and the amend is simply the first machinery that collects on it.

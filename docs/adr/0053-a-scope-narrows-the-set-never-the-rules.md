# A scope narrows the set, never the rules

A run is aimed: at one ticket, at one spec's children, or at nothing in particular. The question a reference raises is not which tickets it selects — that part is arithmetic — but whether being named changes what happens to a ticket once it is in. **It does not. A reference narrows the set the same questions are asked of, and every rule that governs a ticket in a bare run governs it in an aimed one.**

**Two rules are where the pressure is.** A ticket carrying a recorded outcome is settled and never offered again (ADR-0051), and a ticket whose blockers are unmet is not workable. Both are tempting to relax for a ticket the developer named by hand: naming it looks like new information, and the retry a reference exists to make cheap is exactly the case where the old outcome is in the way.

**Relaxing either turns one flag into two engines.** The rules would then be a function of how the run was started, and the plan a developer reads on a bare invocation would no longer describe what a named invocation would do to the same ticket. Worse, both relaxations fail quietly rather than loudly: a ticket rebuilt on top of a blocker that does not exist produces a verification failure nobody can read, and a recorded failure re-offered under the same conditions produces the same failure again — which is the whole reason it was not retried the first time.

**A recorded outcome is therefore cleared on the ticket, not overridden by an argument.** That is one deliberate gesture on the tracker, where the outcome lives and where the developer is already looking, rather than a flag whose meaning has to be remembered. It costs the retry a step and buys every other invocation the property that the tracker alone says what is settled.

**A blocking edge out of the aim still holds.** A ticket named alone whose blocker is open comes back as work this run cannot reach, which is what the graph already calls a blocker outside the scope. The developer asked which ticket to work, not for the work it depends on to exist.

**What the reference does decide is which of two things it named.** A ticket the tracker files children under is a spec and scopes the run to those children; it is never itself built, even where it carries the ready label, because a spec is the shape of other work rather than work. Where the tracker files no children, a ticket in scope naming this one as its parent says the same thing — the same relation-then-body order every other edge is read in. Everything else the tracker can answer for is a ticket, worked alone. A reference nothing can resolve is named and nothing is started, because both ways of guessing are wrong in a way nobody would see: dropping it works the whole tracker under an argument that asked for part of it, and picking a reading works tickets the developer never named.

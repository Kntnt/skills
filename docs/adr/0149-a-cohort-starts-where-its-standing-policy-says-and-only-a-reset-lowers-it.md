# A Cohort starts where its Standing Policy says, and only a reset lowers it

Routing had no memory of where it should begin. Every unmeasured request took the same cold start — the weakest complete candidate, or the strongest where the work was irreversible and unchecked — and every run that learned the weakest one could not do the job learned it again the next night, because nothing carried the lesson forward. The only escalation that existed was per attempt: one Rung after one externally verified failure, discarded with the attempt. A collection whose stated purpose is finding the cheapest configuration that holds quality was re-deriving its starting point from nothing, forever (issue #195).

**A Standing Policy is per Cohort, and the Cohort key is the request's own.** The policy is keyed by the literal `workload_cohort` string, byte for byte, which is the same identity the evidence ledger groups a frontier by. Nothing translates, normalises, or matches it loosely: a request naming no Cohort routes under the shipped default and can never receive an override or move one, because a row comparable within nothing cannot teach anything either. Each Cohort carries its own integer revision, `0` while the shipped default is the whole of its policy and `1` from its first override onward, and that revision is what an audited decision reports.

**It ships working, and version 1 exposes no dial.** `starting_rung: "cold_start"`, `floor: "weakest_enabled"`, `ceiling: "main_seat"`, a failure threshold of two failures in a window of four, and an exploration budget nothing yet spends. There is no `set`: a user never edits a policy to get a working system, and the only two writes are a threshold trip, which stores an exact starting Rung, and `config policy reset`, which removes one. Floors, ceilings, thresholds, epsilons, and budgets stay exactly as shipped, so the store holds one field and the contract has one moving part.

The claim that these are the only two writes is narrowed by ADR-0159, which gives `config reset --evidence` a second downward write: discarding the whole store and its history at once, rather than restoring one Cohort's shipped default.

**The shipped values are symbolic, and they resolve per request.** They are never materialised into the user's file merely because routing read them. `weakest_enabled` and `main_seat` mean the two ends of the candidate ladder that individual request already reaches, after every hard filter, lock, adapter check, and both main-seat ceilings — so under the shipped policy the bounds are the ladder's own ends and nothing is excluded, which is exactly the property that lets this land without changing a single measured winner. `cold_start` means the cold-start heuristic this contract already had, `cold_start_strongest` or `cold_start_weakest` by the request's own safety facts; it is unrelated to `override_policy.cold_start`, which decides whether an unmeasured start may happen at all and is untouched here.

**Bounds are read on the Rung order, and a carried control is compared on the model dimension alone.** The order is `model_capability` and then position on the portable scale, both ends inclusive, which is ADR-0146's ladder read as an interval rather than as a step. A point whose deliberation the Harness carries by inheritance launches at the seat's own control, so the deliberation dimension is not its to exceed and only its model is compared. An otherwise eligible point outside the range is excluded as `standing_policy_out_of_bounds` and is gone from every later step — selection, the frontier, and adjacency alike — which is why the ceiling needs no second implementation inside escalation: the pool escalation reads is already the bounded one.

**A stored Rung is a measurement, not a promise, so an unreachable one falls back and says so.** Configuration changes: a model is removed, a Harness stops offering a surface, a request locks a dimension, the seat moves down. The derivation does not mutate the policy to match, and routing does not clamp the stored Rung to the nearest survivor or guess a replacement — either would silently answer a question nobody asked. It takes the cold start and audits `standing_policy_start_unavailable`, so the fallback is visible in the same block that says what the policy wanted.

**Every selected or inherited execution decision carries the policy it ran under.** `audit.standing_policy` names the Cohort, its revision, and the resolved `starting_rung`, `current_rung`, `floor`, `ceiling`, and `next_rung_up` as concrete Rungs, with the `start_fallback` beside them. An inheritance reports the seat as the current Rung and nothing above it; an inheritance with no surviving candidate reports the Cohort and revision and every Rung as `null`, because a symbol with no ladder to resolve against has no honest concrete value. A verdict carries no block at all: it inherits by authority, not by policy. The threshold evaluation that will move a policy reads this block and adds nothing to it.

**The store lives in the Collection Library, not under either Skill that reads it.** Three callers share one file — the context derivation that freezes it, the `config policy` adapter that renders and restores it, and the evidence import that will evaluate its threshold inside the Library's own `record` — and a peer Skill's `scripts/` is not an interface any of them may reach into. The shipped defaults are constants in that module rather than a data file: the Library ships only `references/` and `scripts/`, and the threshold evaluation reads the same two numbers from the same place the store writes them against. The policy is script-owned throughout, never agent-edited, so the profile's `config.lock` protocol does not apply to it and no lock is taken for a file no interview writes.

**It ratchets up only.** Nothing lowers a Cohort by itself. A threshold trip raises it; a user's reset restores the shipped default and appends a row saying so. The alternative — de-escalating after some run of successes, with a minimum dwell — is self-correcting in the same breath as it is surprising: a policy that moves in both directions without a person asking can oscillate around a boundary and will do so most where evidence is thinnest. The one downward path that will exist is a budgeted exploration attempt, which is a deliberate purchase of information rather than a policy drifting.

**It enters the snapshot, so it can never reach a running run.** The policy is frozen into `override_policy.standing_policy` by the context derivation and is covered by the snapshot identity like every other frozen fact (ADR-0083, ADR-0085). Changing it is therefore a new snapshot: an escalation lands at the next run's freeze, a delegation session re-freezes per call, and a night that started under one policy finishes under it. This is also why the projection carries the whole store rather than only the Cohorts a particular batch happens to name — the identity should move when the policy moves, never because a batch was composed differently.

**What this costs.** The snapshot and every audit identity change in this release, deliberately: routing now freezes a fact it did not freeze before, and no persisted routing account from before this ticket loads. The frozen block is larger than it needs to be for one request, carrying every moved Cohort so that identity tracks the store. A policy is per Cohort and per user, so a Cohort whose work is not homogeneous will average its lesson across the work it contains and start everything in it at the same Rung. And a stored Rung ages: it is the measurement of a profile that has since changed, and the only thing standing between a stale Rung and a wrong start is a reachability check and one audited fallback. In return, what one run pays to learn, the next run starts from.

# A Project cannot hide a Global skill

`--project` mutates only the Project layer. Global stays untouched. `select --project` can uncheck a skill that was Enabled in the Project layer and nothing else: a skill Enabled only in Global has no copy in this layer to remove, and the row says so rather than offering a checkbox that would do nothing.

The alternative — a mask that turns a Global skill off in one directory — was rejected and stays rejected. It would make what a Harness loads depend on the order the two layers are read in, and it would surprise anyone who Enabled a skill once on the machine and then found it gone in a directory they had never Disabled it in. A layer that can only add is one a user can reason about from either end, and one whose result does not change when the reading order does.

**What is struck is the reporting half.** This record used to say that a verb reports the union of both layers, and that *Effective* was the collection's name for it. That a Harness in a Project loads both layers is a fact about Harnesses and is still true; what no longer holds is that any verb of this collection reports it. `select --project` shows the Project layer alone, because that is the layer the answer will be written to and a list whose checkboxes mean different things in different rows misleads worse than a narrower list informs (ADR-0038). What the union was needed for at the moment of choosing survives at row level: a skill already Enabled in Global is marked as such, so nobody Enables a second copy into a repository by accident. *Effective* leaves the domain language with the report that carried it.

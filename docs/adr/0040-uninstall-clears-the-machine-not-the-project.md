# Uninstall clears the machine; a Project's copies are the Project's

Installing is one command. Removing was none: the behaviour existed — dropping a Harness cleared this collection's whole set from it, the Manager included — but only as a side effect of editing a list, and once that list was retired (ADR-0035) even that way in was gone. `/kntnt uninstall` gives it a verb. It removes every Catalog skill Enabled in Global from every Harness present in the home directory, and then the Manager, through the transport like every other file move (ADR-0006). Afterwards the Harness's own uninstall has nothing left to do.

There is no `--project` form, and this is the decision rather than an omission. A skill in a working directory is checked into that repository and travels with it: a teammate cloning the project receives it, and whether it stays is that project's decision, not this machine's. Uninstall answers *take your collection off my machine*, which no working directory is part of. So Project copies are never touched, and the report says so — a user told the machine is clean, with a repository on it still carrying these skills, has been told something false about the only thing they can check.

The set is resolved by detection at the moment the verb runs, for the same reason every other verb resolves it that way, and with one consequence particular to removal: the transport only clears a shared skills directory when the call names every Harness that reads it, and a call that always names all of them cannot get that wrong (ADR-0035).

`--yes` is the gate, as on Disable: the verb deletes files the user is choosing to delete, and a script cannot prompt (ADR-0029).

Two things follow from the Manager deleting itself. The path table is read once per run and held, because it ships beside the Manager and the same run still has to verify the removal and name the directories it happened in. And the Manager goes last, in a transport call of its own, made only where the rest of the collection really left — a machine holding skills with no verb left to remove them is worse off than one whose Manager outlives them by a run, and the retry the split exists for has to be a retry the code actually leaves available. Neither pass raises on the other's behalf; both read their verdict off the disk, which is what ADR-0036 requires and matters most here, where afterwards there is nothing left to contradict a false report of success. `kntnt` among the confirmed is therefore the whole report: the Manager is gone only when everything it was asked to remove went with it.

What Uninstall cannot promise is completeness in one respect: the set it removes is what the Catalog names, so a Catalog read from the stored snapshot rather than the origin may leave behind a skill the collection has since withdrawn. The verb reports which of the two it worked from — `catalog_refreshed`, as everywhere else — and the skill body says what a false means, because the usual remedy of *run it again with the origin reachable* is only available while the Manager is still installed.

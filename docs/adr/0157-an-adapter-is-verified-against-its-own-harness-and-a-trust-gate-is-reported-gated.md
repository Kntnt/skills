# An adapter is verified against its own Harness, and a trust gate is reported gated

ADR-0090 already said a Harness whose supported lifecycle cannot carry the contract reports an Unsatisfied capability rather than being quietly skipped, because a feature that believes it is installed where it is not is worse than one that knows it is not. Two of the three shipped adapters were doing exactly the thing that sentence forbids, though the Codex adapter's actual fault turned out narrower than first suspected: its owned hook table under `SessionStart`, `Stop`, and `SessionEnd`, in the same nested matcher group Claude Code's `settings.json` holds, is confirmed live against the installed binary (`codex app-server`, `initialize` + `hooks/list`) to be exactly what Codex's own `hooks.json` — deserialized through its `HookEventsToml` — reads; the camelCase, flat `handlerType`/`command` shape once suspected of being the Harness's own belongs to a different surface, the app-server protocol's own `HookEventName`, the normalized runtime view `hooks/list` itself reports back, and is silently dropped rather than read when written into the config file. What the adapter actually got wrong is the trust review: Codex holds a newly written hook back from ever running until a human clears it, and installation reported success regardless, so a written-but-inert integration was indistinguishable from one Codex was actually acting on. The OpenCode adapter ran its owned command with `--event=<type>` and no payload at all, discarding the only place the session identity ever appears, while leaving Bun's shell to hand the child process this session's own standard input by default — confirmed by reproducing the hang directly — which a hook that reads standard input to end-of-file can block on for as long as that session's own stdin stays open. Verification read the file back and confirmed only that the Library had written what it meant, never that the Harness would act on it.

**An adapter is verified against what its own Harness actually reads, established from the Harness as installed.** Event names, entry shape, and file location are read off the Harness on the machine building the adapter rather than assumed from a sibling's — and, confirmed rather than assumed, Codex's own config file turns out to accept the very shape a first pass at this adapter suspected it did not: PascalCase keys, the same nested `hooks` matcher group Claude Code's table holds. `codex app-server generate-json-schema`'s flat `command`-handler variant, requiring `command` and `handlerType` directly on the entry, is the app-server protocol's own shape, not `HookEventsToml`'s — the schema generator alone conflates the two easily, which is exactly what a build that stopped there did, and exactly what re-deriving live against `hooks/list` catches. Where a fact cannot be established this way, the honest answer is Unsatisfied, exactly as ADR-0090 already requires for a Harness outside the supported set — a guessed shape that happens to parse is not a verified one.

**A Harness that gates a new integration behind a user's trust is reported gated, never healthy.** Codex reviews a hook that is new or changed before it will run it — its own `HookTrustStatus` names the state directly (`managed`, `untrusted`, `trusted`, `modified`), and its CLI's own startup copy says as much in words ("Hooks need review... Trust all and continue... Continue without trusting (hooks won't run)"). This collection forges no trust decision and writes no trust record on the user's behalf; a gate is the Harness's, and the honest report is the whole of this collection's answer to it. So a Codex integration that is fully and correctly written is reported `gated` — present on disk, not yet active, naming what the user does next — rather than `healthy`, which stays reserved for a Harness this collection can observe is actually acting on what it installed. `gated` sits as a third state in `health`'s own field, between `absent` and `healthy`, and is carried through `install`'s `detail` at the moment of writing rather than deferred to a later check.

**The field this state was added to is the one that already exists.** The per-Harness integration presence section `/model-selector status` is meant to carry belongs to a lifecycle ticket (#223) that has not landed, and whether a Harness supplies measurements belongs to a ticket that reads the finished session (#225), which has not landed either. This record adds nothing to either: `gated` is added to `health`'s existing `status` field, surfaced unchanged through `capture.py`'s `status()`, because that is the field that exists today. When #223 lands its own presence section, `gated` moves with the rest of that vocabulary; this record does not pre-empt what shape that section takes.

**The OpenCode plugin redirects the event onto the invoked command's own standard input.** `${event}` carries the session identity OpenCode itself nests inside it — `session.idle`'s directly as `properties.sessionID`, `session.created`'s and `session.deleted`'s inside the session record at `properties.info.id` — so the plugin still interprets nothing (ADR-0090) and simply hands the whole event on, unlike the entry-and-normalization split Codex and Claude Code need. The redirect is `< ${new Response(JSON.stringify(event))}`, verified against Bun 1.4.0 directly: an unredirected `$` command inherits this process's own standard input by default and a hook reading it to end-of-file blocks for as long as that input stays open, reproduced and then cleared by the same redirect. `capture.py` unwraps that envelope once, at the hook, rather than asking every caller of its own allow-list to know OpenCode's event shape.

**What this costs.** Codex's own hook-invocation payload — the exact field its command receives the moment's name under, as opposed to `hooks/list`'s own `eventName` — was not directly observable: every attempt to drive a hook to fire, trust bypassed or not, ran into Codex's session and auth lifecycle before the hook itself, never into a shape error. `eventName` is carried into `capture.py`'s own event-field fallback as the same convention Codex uses everywhere else its JSON API names a moment, not as a confirmed reading of that one payload — a decision a later session with working Codex credentials can settle outright. Codex's own OS-level activation — the moment a `gated` integration is observed to become `healthy` once a human clears the review — is likewise something this collection cannot drive from here and does not attempt to detect; `gated` is the ceiling this adapter reports for Codex until a future ticket has the Harness's own contract for that transition in hand.

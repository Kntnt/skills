# A ledger row becomes evidence only inside its own Cohort

ADR-0089 made external judgement a precondition for routed-work evidence, ADR-0137 let Orchestrate import that evidence at a verdict, and ADR-0136 made the Collection derive the routing context instead of asking each session to assemble one. What none of them settled is how a ledger row becomes a fact a later decision can use. `context.evidence.records` was shipped empty, the route module classified over records nothing produced, and thirteen imported observations left every following decision `heuristic`. This decision names what turns the accounting into evidence.

**A routed attempt carries the Cohort of the request it answered.** An observation gains `stage`, `workload_cohort`, and `workload_tags`, copied verbatim from the route request, admitted by the emission allow-list as identities, and travelling as one: an attempt naming only some of them names none, and all three are emitted null. They are optional, because every row written before them is still a row and automatic capture observes work nobody routed. `benchmark_key` stays the identity of the check and is not the Cohort.

The automatic-capture clause here is narrowed by ADR-0156: capture no longer writes a ledger row at all, routed or not, so no row in this ledger is ever an automatically captured one again.

**A frontier is the exact tuple, not the benchmark key.** A derived frontier is identified by `benchmark_key`, `stage`, `workload_cohort`, and sorted `workload_tags` together, and rows differing on any member are never compared as one. A projected evidence record carries exactly one value for each of those identities, so grouping by less than all four would let it assert a stage the runs behind it never shared. `derived-frontiers.json` keys each entry by a digest of the four and carries all four inside it; `record` reports the same four per rebuilt frontier. A row naming no Cohort is comparable within nothing: it stays in the ledger and enters no frontier.

**The projection emits records and classifies nothing.** One record per fingerprint point of one frontier, of the shape the route request schema already defines: the exact routed point from the ledger rows, the Cohort from the frontier, `representative` true because the group is that exact match, `coverage.decision_relevant` true where both bounds exist, `stale` false, `quality` the judged success rate, and `uncertainty` the two-sided 95% Wilson interval the point's judged runs establish. A point with no decisive run emits nothing, because the numeric quality and interval a record requires do not exist for it. The route module remains the only classifier (ADR-0083), and `measurement_based` goes on meaning what the frozen `override_policy.quality_floor` says — which is where *too few runs* comes from without any observation count being written down anywhere.

**The context derivation is the only consumer.** It writes `context.evidence.records` from the projection for every route request, digests them into `evidence.identity`, and takes `evidence.vintage` from the newest instant behind them. No user step stands between a verdict and the next decision, which is what makes `/orchestrate` a self-learning path rather than a bookkeeping one. A ledger row the schema will not admit refuses itself rather than the artifact it would sit in.

**Orchestrate's Cohort comes from the request name alone.** The engine reads `stage` as the role token of the request name and `workload_cohort` as `orchestrate/` plus that role's workload stratum, with empty tags, and freezes all three in the routing account beside the decision; the Skill body states the same rule for the request the agent writes. Two derivations of one fact from one name is what lets the request the module routes and the observation the ledger keeps name the same Cohort without either checking the other — the request name is already trusted the same way.

**What this costs.** A routing account frozen before this change cannot be resumed after it, as everywhere in this collection. Every ledger row written before it names no Cohort and is evidence about nothing, so the loop starts from an empty frontier rather than from history, and a `derived-frontiers.json` written under the old identity is discarded on the next rebuild rather than migrated — the file is a summary of rows nothing deleted. An attempt observed twice across the change is a conflicting identity rather than a duplicate. In return, a run's own verdicts are what the next run's decision is made from, and the class a decision reports is a reading of the ledger rather than of a hand-written record nobody wrote.

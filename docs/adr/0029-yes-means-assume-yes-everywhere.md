# `--yes` means assume yes, on every skill and every verb

Wherever a collection skill can ask something answerable yes or no, `--yes` answers it yes instead of asking. One flag, one meaning, across the collection — a user who learns it on `/commit` has learned it on `/kntnt` and `/agents-md`.

**It means no question is asked at all**, which constrains how questions may be written and not only how they are answered. Every yes/no question is therefore worded so that *yes* ends it. A question whose yes opens a second question has no unattended answer: either the run stalls where nobody can reach it, or the flag has to mean *yes, and yes to whatever that opens*, which is a promise no user can read off four characters. Where a decision has more than two outcomes it is not asked under `--yes` at all; the verb does the part that needs no permission and reports the rest (ADR-0043).

The confirmation itself lives in the skill, because a script run non-interactively cannot prompt. **This record originally added that every verb of every collection script accepts the flag, including the verbs that ask nothing, so that a skill could pass the user's arguments through unread; that clause is withdrawn by ADR-0059.** What it was written to end was real and is worth keeping in view: `argument-hint` advertised `--yes` on `/kntnt` while `apply enable --yes` died with `unrecognized arguments` — the skill was documented into a crash, and only luck decided whether the model forwarded the user's own flag. The defence against that is now a settled flag table that the documented grammar and the parser are both read from, rather than a parser that swallows whatever arrives.

**A meaningless flag is tolerated; a misleading one is refused — withdrawn by ADR-0059, which makes both an error.** The reasoning is kept because it is what the reversal answers. These are not the same permission, and the difference is what the user could come to believe. `help --yes` changes nothing anyone could misread: there was no question, and the run is the run they asked for. `uninstall --project` would let a user believe the machine was spared, and they would find out otherwise only by looking at a disk they had been told was clean. So a verb accepts a flag that has no work to do for it, and refuses one whose acceptance would state something false about what happened. The rule is that *where a flag is accepted it always means the same thing* — not that every verb accepts every flag, which is a different rule and a worse one: a flag accepted and ignored teaches that flags sometimes do nothing. That last sentence is what undid the clause it sits in. `help --yes` is a flag accepted and ignored, so tolerating it teaches the very thing this paragraph refuses to teach, and the line between *meaningless* and *misleading* turned out to be invisible from the user's seat: `help --force` fails and `help --yes` does not, and nothing outside the script explains why. What survives here is the accepted-means-the-same rule; what replaces the tolerance is that a flag with no function on a verb is not a flag of that verb (ADR-0059).

Where a subcommand deletes files the user is choosing to delete, the flag is also the gate: the script refuses without it. Uninstall removes this collection from the machine, so requiring `--yes` there means the confirmation cannot be skipped by accident, only on purpose. Verbs that add or refresh take the flag and are not gated by it: it answers their questions, and its absence is not a refusal.

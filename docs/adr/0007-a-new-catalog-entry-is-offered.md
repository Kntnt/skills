# A new Catalog entry is offered, and `--yes` accepts it

Update reports each new Catalog entry and asks whether to Enable it. `--yes` answers that question yes, as it answers every other yes/no question in the collection (ADR-0029), so an unattended Update Enables what the collection has added since the last one.

**The original reasoning stands where a human is there to read.** An Update that silently Enabled a new skill would inject instructions the user has never read into every Detected Harness's context. Consent governs what enters the context — the same asymmetry ADR-0037 turns on — so nothing is Enabled without being named first: the entry is reported, the question names it, and a user who says no keeps it Disabled. What changed is not that consent was dropped but where it is asked for. Before, Update did not ask at all; the user learned there was something new and had to reach for a second verb to act on it, at a moment when they had already been given the reason to. The question is now asked while they are still thinking about the collection.

**The trade is overturned deliberately, and the cost is real.** `--yes` means no question is asked at all, so an unattended `update --yes` — a cron job, a provisioning script, a skill passing the user's arguments through unread — can place instructions the user has not read into every Detected Harness. That is precisely the harm the earlier record was written to prevent. It is accepted here, not argued away.

**What buys it is that `--yes` means one thing everywhere.** The alternative was a flag that answers every question except this one, and that is not a rule a user can hold: they would have to carry a list of the questions the flag does not reach, and a flag with an exception is a flag that lies about the rest. The exception was also unenforceable at the edge it mattered — a skill forwarding the user's arguments unread cannot know which of them the Manager will decline to honour, so the guarantee would have held only where somebody already knew it existed. Whoever reopens this should reopen it as *is one coherent flag worth an unattended install of unread instructions*, which is the question that was actually decided, and not as *should new skills be silent*, which was not decided either then or now.

**What is Enabled is the new entries, and nothing behind them.** An entry that needs a Skill the layer does not hold is Enabled alone and reported Unsatisfied afterwards, rather than dragging its closure in the way Select does (ADR-0047). The difference is what the user was asked. At the list they are choosing a set and the closure is part of that choice, so resolving it answers a question they are in the middle of; here they are answering *do you want the thing the collection just added*, and a Skill they have already chosen to leave Disabled is not that question's to reverse. What they lose is a new Skill that works on arrival; what they get is a report naming exactly what it lacks and `select` as the way to supply it, which is the same *say what is wrong and let the user act* this collection answers every Unsatisfied Dependency with (ADR-0009).

`select --yes` is the counterweight, and its asymmetry with this record is intended: it opens no list and Enables nothing that was not already Enabled (ADR-0043). The unattended path that can add a skill is the one the user pointed at the collection's own new entries, and every name it added is in its report.

# A run works the branch it was left on

`/orchestrate` refused to start on the repository's default branch, and refused again before it merged a ticket into it, on the reason that an unattended night must never land there. No record ever stated that rule. This repository is developed on `main`: every commit in its history is on `main`, and no branch policy puts a ticket anywhere else — so the rule protected the project from no mistake it was going to make, and made the Skill unusable in it without first inventing a branch that exists only to satisfy the check and merging that branch back by hand afterwards. The invented branch is not a safety measure. It is the same commits, on the same line of history, one step later.

**So the refusal goes, both halves of it.** A run plans, builds, integrates, and reports on whatever branch is checked out, the default branch included; and a repository where nothing can say which branch its default is is worked rather than refused, there being nothing left for that answer to gate. The developer's choice of branch is not the Skill's to second-guess.

**A flag was rejected rather than overlooked.** A run is unattended by design and reads its own flags, so a refusal a flag lifts is a rule that is never enforced: the developer who works on `main` writes the flag into the invocation once and never sees the refusal again. What the gate would buy is the appearance of a safeguard, plus a flag to remember, plus prose explaining both.

**`/release`'s opposite polarity is not a contradiction.** `/release` refuses to bump anywhere *but* the default branch, and that requirement is untouched. The two read together once you ask what each one publishes. `/release` commits, pushes, tags, and cuts a GitHub release: it puts work where other people fetch it, so it must ship from the published line, and a version cut off a side branch is a version nobody can find. A run publishes nothing — it commits, and nothing it does is pushed, tagged, or released — so where it commits stays the developer's business until they push it themselves.

**What a failure on the default branch costs, concretely.** An overnight run of seven tickets that fails on the fourth at a ceiling of one leaves three tickets' commits on the branch, the fourth ticket's unverified work in the working tree, and a stopped run. Nothing was pushed, so the branch is local commits ahead of its remote and `git reset --hard origin/<default>` puts it back — the same position any ordinary bad commit leaves. A failed ticket's work is still never reverted, which is on purpose and is also why the run stops at the first failure. The uncommitted-work refusal (ADR-0056) is what still stops a run whose tree it cannot account for, at both of its call sites, and it is now the only thing a run refuses about the state it starts in.

**The bound this forfeits.** ADR-0058 bounds the closed half of a report by the fork point from the default branch, and that bound is already nothing where the branch in hand *is* the default one. So a run on the default branch asks the closed question whole every time, backed only by the guard that refuses a full page. That works now, and it refuses the report outright once this project has ever closed two hundred `ready-for-agent` tickets. It is a real price for working the default branch, and it belongs in the record rather than in a surprise one night. The default branch is still detected and still reported in the plan; it simply no longer gates anything.

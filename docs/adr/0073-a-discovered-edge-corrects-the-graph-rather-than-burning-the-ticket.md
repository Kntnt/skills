# A discovered edge corrects the graph rather than burning the ticket

An overnight run built a ticket whose builder discovered, mid-build, that one acceptance criterion could not be delivered: it depended on a question another ticket held open — a ticket parked behind `needs-info`, outside the run entirely. The graph had not said so; the ticket's one recorded blocker was already merged. The builder had two moves in its vocabulary, build or stop-and-fail, and it invented a third: it built everything else and committed under a `Closes` trailer with the scope quietly narrowed. The verifier caught precisely that — *the scope was redefined inside the commit rather than raised on the ticket, which is exactly the case this verdict exists to catch* — and the ticket was recorded failed. Every actor behaved correctly, and the outcome was still wrong: what the builder had found was a true blocking edge the ticket breakdown missed, the one kind of finding the run's own report calls the point of reporting a collision, and the run's answer was to burn the ticket and let the report read as a build that could not be built. The developer diagnosed it in the morning and wrote the edge by hand.

**So a builder that finds its ticket depends on open work the graph does not name stops and names the blocker, and the run records a corrected edge rather than a failure.** The engine takes it as an outcome of its own: recorded blocked on the named ticket, it writes the dependency to the tracker the same way the breakdown would have, releases the claim, and leaves the ticket open and unbuilt. The next plan — the same night's next wave, or the next run's first — reads the graph as corrected: the ticket waits exactly as it would have waited had the edge been filed with it, comes back workable when its blocker closes, and is built then on top of the work it actually needed.

The closure-based unblocking premise in this record is superseded by ADR-0079, which requires a done Ticket Resolution before the work is treated as complete.

**The boundary against ADR-0070 is whether the missing thing has a number.** A dependency on an open ticket is an edge, and this record's mechanism writes it. A dependency on an answer no ticket carries is a question, and it parks the ticket under ADR-0070 instead — the question written on the ticket, the label returned to triage. The builder reports what it found; which of the two it is, the orchestrator reads off whether there is a ticket to point at.

**The half-built work is discarded with the working tree, exactly as a refused repair is.** When the blocker closes, the ticket is isolated afresh from the branch that now carries the blocker's work and built whole on top of it, which is ADR-0055's rebuild reasoning in a new position: what comes back is code somebody meant, built on the code it needed, rather than a torso completed around a hole. Keeping the torso would also leave the run unable to say what the working tree holds — work toward a ticket whose requirement, by the builder's own finding, could not yet be met.

**The report keeps its five lists.** A blocked ticket carries no failure and no commit; once its edge is written it is simply a ticket waiting on open work, which the report already accounts for — stranded where the blocker is the run's own failed work, never-on-the-frontier where the blocker lives outside the run. What changes is only that the account is now true: the ticket appears as waiting, with the edge on the tracker saying on what, instead of as failed with a verdict that reads as the builder's fault.

**What this costs.** A builder can name a wrong edge, and a buildable ticket then idles for the night behind work it never needed — but the edge is on the tracker, in the breakdown's own vocabulary, where the developer removes it in one gesture; the opposite error stood a whole diagnosis away. The build spent before the discovery is thrown away with the tree, paid in overnight machine time. And the engine takes on a write it did not have — an edge on the tracker — which is one more thing a run does that a developer reading the morning's graph has to know a run can do; the recorded outcome on the ticket is where it says so.

# A Skill owns the Harness integrations it installs

ADR-0089 made routed work produce importable evidence and left the ordinary case where it was: a user works all day in a Harness and nothing is measured, because measuring is a thing they have to remember to do. Closing that gap means the Harness calling us rather than the user invoking us, which means writing into the Harness's own configuration — the first thing this collection installs that is neither a Skill file nor removed by deleting one.

**Capture is an opt-in of an Enabled Skill, never a consequence of enabling one.** ADR-0010 made Select place files and nothing else, and that is the promise being kept here: enabling a Skill installs a Skill. Persistent lifecycle integration and the handling of local session metadata are a second decision, made with the first opt-in, which states what is installed, what is retained, how it is cleaned up, and how to stop it — before anything reaches disk. A Skill that started capturing because it was Enabled would make every future Enable a question about what else it might turn on.

**The integration is owned, and the owner travels in what is written.** Every entry carries a stable ownership identity inside the command it runs, rather than beside it in a key the Harness's own schema does not define. That makes removal surgical without anything having to be remembered: the disk is read, our entries are found by their owner, and everybody else's survive untouched (ADR-0003). Nothing keeps a private ledger of what was installed, so a hand-edited, externally repaired, or half-removed Harness is a state the next run converges from rather than one nothing can account for. Install, repair, update, and remove are therefore all the same operation applied to whatever is actually there.

**The Manager asks the Skill to remove them, while the Skill can still answer.** Deleting a Skill's files is the one moment its integrations become unreachable — after it, nothing on the machine knows what was installed or where. So removal runs first, on the one seam every removal path already passes through, and it is the Skill's own script that runs: it declares `metadata.kntnt.integrations`, the Manager says one word to it, and the Manager learns no Harness's hook format in the process (ADR-0012). A teardown that fails is reported per Skill and never raised, because external state this collection does not own must not hold up the removal of files it does own. Making the Skill Disabled is thus sufficient to stop capture, and there is no second shutdown step to forget.

The premise that teardown always runs from the active tree before its files move is narrowed by ADR-0130: a transactional refresh stages each physical integration owner while it is readable, commits the filesystem generation, and only then invokes the staged copy, so a publication rollback leaves both the prior tree and its integrations unchanged.

**Harness-specific mechanics belong to the Collection Library.** Three Harnesses, three shapes: two owned hook tables and one plugin file named for its owner. That knowledge is not one Skill's private business, so it lives in the Library where a second consumer finds it rather than reaching into the first (ADR-0076). Which Harness is running is still the agent's to say and never a script's to sniff (ADR-0030), and a Harness whose supported lifecycle cannot carry the contract reports an Unsatisfied capability rather than being quietly skipped — a feature that believes it is installed where it is not is worse than one that knows it is not.

**Captured ordinary work is the same observation, under the stratum it belongs to.** Nothing routed it, so it is recorded as the inheritance that actually happened: the exact main seat the session ran on, fingerprinted from that seat, with `route_status` still reading `inherit` so that no part of it reads as a choice somebody made, and provenance naming the captured environment because there was no routing snapshot to freeze. It is a seventh stratum rather than a second representation — ADR-0089's envelope, validation, refusals, idempotency, and conflict rules answer for it unchanged, and `record` remains the only thing that writes the ledger.

**Nothing inside the work may grade the work.** The rule ADR-0089 set for routed attempts holds here with less to lean on: there is no independent verifier in an ordinary session, so an objective checker, a frozen rubric, a declared failure signal, or the user's own confirmation establishes an outcome, and nothing else does. Unjudged work waits in bounded pending review for a human rather than becoming weak evidence, an abandoned session is reconciled into that same waiting state instead of into a result, and an infrastructure error keeps its own outcome so a bad environment cannot make a configuration look bad.

**The hook path is fail-open, bounded, and local.** It runs inside somebody's session, so it does local metadata I/O and nothing else — no network request, no model call, no test run, no repository-wide hashing, no transcript scan, no long-lived work — and every failure in it is swallowed. Capture that breaks a session is worse than no capture, and a user who has to weigh measurement against their Harness working will turn measurement off. Notifications are debounced and user-facing for the same reason in reverse: a measurement reminder placed where the model reads it would change the configuration being measured.

**What this costs.** The collection now writes outside its own directories, and a machine whose Harness config was hand-edited between an install and a removal can be left holding an entry we no longer recognise — reported, but the user's to delete. Retention is a bound rather than a promise: pending captures older than thirty days, beyond a hundred drafts, or past a mebibyte are removed oldest-first, so evidence nobody reviewed is evidence that eventually goes. And sessions in an unsupported Harness, or with no checker and no answer from the user, produce nothing at all. In return the evidence that should replace public priors is produced by the work itself, in the shape the ledger already accepts, with an off switch that is the same switch as the Skill's own.

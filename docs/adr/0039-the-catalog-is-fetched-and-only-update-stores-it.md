# The Catalog is fetched at every invocation, and only Update stores it

The Catalog shipped as a file beside the Manager and was replaced only by Update. So the list the Manager showed, and the list it validated a name against, answered *what did the collection contain when this machine last updated* rather than *what does the collection contain*. A skill published upstream was invisible until the user ran Update — the one thing nothing gave them a reason to run, because nothing had told them there was anything new — and a skill the collection had withdrawn went on being offered as though it could still be Enabled. Both halves of that were observed on a real installation, two withdrawn skills among them (issue #3).

So every verb resolves the Catalog by asking the origin, and reasons from the answer. A skill the origin carries and this machine has never seen is listed, Disabled, and can be Enabled in the same invocation that first showed it. A skill the origin has dropped is not listed at all.

**A fetch that fails must not take a read verb with it.** The origin is unreachable often enough — offline, blocked, down — that a Select which exited non-zero on it would be worse than a stale one. The failure falls back to the stored copy and the payload carries `catalog_refreshed`, the same boolean under the same name Update already reports, so the skill body can tell the user which of the two lists they are holding. Only where there is neither an origin nor a stored copy does the fetch's own error stand: there is no Catalog to invent. This is ADR-0009's shape applied to a list rather than to a Dependency — say what is wrong and let the user act, rather than fail or guess.

**Only Update writes the file.** This was the open question, and the answer is not merely that a read verb should not have a write side effect. Update tells a new Catalog entry from a Withdrawn one by diffing the copy it last stored against what the origin now carries, and the whole of ADR-0007 and ADR-0037 rests on that difference: the first reports the new entry and offers to Enable it, the second deletes files off the disk. A Select that adopted the fetched Catalog would flatten the diff, and the next Update would report no new skills and — the real cost — leave a Withdrawn skill's files exactly where they were. Detecting withdrawal from the disk instead would make the write safe, but that is a change to Update and not to the source of the list, which is what this record is about. The price of the choice is that the offline fallback is only as fresh as the last Update, which is what a fallback is for. Its other consequence is that a Manager can now reach Update with no stored copy at all, and a run with no *before* has discovered nothing: the fetched list becomes the baseline rather than the whole collection being reported as new entries.

The Catalog is resolved once per run and held. Every verb reads it many times over, and the origin is to be asked once, not once per reader.

ADR-0007 is untouched by this record. A newly discovered skill is reported, and nothing about becoming visible enables anything: what Enables it is the offer Update makes and the answer that offer is given. What changes is that discovery no longer waits for Update, so the instruction to run Update in order to find a skill leaves the Select guidance and the README with nothing left to do.

# A ticket asserts only what stays true until it is built

The `/orchestrate` run that closed issues #45 to #55 and #61 to #62 hit eleven instances of one failure: a ticket asserted something that was true when it was written and false by the time an agent built it. Every instance was caught — by a builder stopping to flag it, by a verifier, or by hand mid-run — and none of them reached a release. Each cost real work anyway, and one class of it recurred five times. The tickets were not careless; the gap is a property of the workflow. Filing and building are separated by hours or days, sibling tickets land in between, and an unattended run builds whatever the ticket said with nobody in the loop to notice that the ground moved. **So a ticket claims nothing about this repository that a sibling ticket can falsify while it waits: it names no record number, cites symbols rather than line numbers, quantifies over the collection rather than enumerating it, and says which commit it was written against** (issue #67). The four rules are convention, each carried by the finding that produced it, because a rule without its reason is a rule the next author talks themselves out of.

**Never name a record number.** Write *the next free number at the time of writing*, and require the commit to say which number was taken. A number in a ticket is a claim about a shared resource nobody has reserved, so a ticket that names one is racing every other ticket in the same wave — and losing that race is invisible until integration.

Five collisions from three tickets, and #54 is the instructive one: triage had already spotted its first collision and reassigned the ticket to a number that was also taken, and it was corrected twice more mid-run as sibling tickets consumed the next two numbers in turn. Three corrections to one ticket, none of which stuck, because each one named a number and the wave kept consuming numbers.

**Cite symbols, not line numbers.** Name the function and the file — `collection_block` in `skills/kntnt/scripts/kntnt.py` — rather than the file and a line in it. Where a line number genuinely helps a reader locate something, mark it as of a named commit, so a reader who finds something else there knows to re-derive it rather than to doubt themselves. Issue #48 cited three line numbers in the manager for two functions; issue #52 cited two ranges and its builder found the same functions some fifty lines lower, because #51 had landed in between; issue #45 cited a line in the test suite. Nothing broke — every agent found the symbol anyway — but each one had to notice the discrepancy, decide whether it mattered, and say so. That is the cost even in the good case, and the bad case is an agent that trusts the line and edits what happens to be there.

**Quantify over the collection rather than enumerating it.** Write *every shipped skill* rather than a table of names, and where a table is genuinely needed for the reasoning, say whether it is exhaustive or illustrative so a builder is not left inferring it. Three tickets carried a list or a table that omitted `orchestrate`, which had shipped in 0.9.0 shortly before they were filed: #50 named five skills, #53 tabulated six while its own reasoning said all seven, and #54 stated flatly that `orchestrate` had no flat sidecars when it had five. Three builders independently widened the work to the skill the ticket had missed, and three verifiers independently upheld them. That it came out right three times is luck plus good agents, not a property of the tickets.

**State the ticket's own vantage point.** One line naming the commit the ticket was written against. It is the cheapest of the four and it repairs the other three when they fail: a builder who can see what the author saw can tell drift from error, instead of guessing which of the two they are looking at and how much else in the ticket to distrust. This record was written against `9fc3af0`.

**Nothing enforces this, and that is the decision rather than an omission.** The first rule is the only mechanically checkable one — a test could fail on a record number appearing in an open ticket body — but the check would mean the test suite reaching the tracker over the network, which nothing else in this repository does, for one rule out of four. The suite already refuses a number two records claim and a citation with no record behind it, which is the harm that matters: a collision that reached the tree. The residual risk is stated plainly. A ticket filed with a doomed number, a moved line, or a stale enumeration is caught only by a builder or a verifier noticing, hours later, at the cost of a correction or a rebuild — exactly as the eleven instances were — and rules two to four are not checkable at all. What is bought instead is that the collection has one place saying what a ticket may assert, and a ticket may cite it.

**This record is itself an instance of what it documents.** It and the record that became ADR-0066 were both told to take the next free number, and both would have taken the same one had they been built in the same wave. They were built in different waves only because triage made one a blocker of the other on the tracker — the fix that a ticket which names no number would not have needed. Its own number was derived by reading `docs/adr/` at the moment the file was written, where *next free* means one above the highest: the gaps at 0031 to 0034 are legitimate and do not make a lower number free. There is one thing this record cannot do, and the reason is the rule it carries: the suite fails on any record number in this directory that no record answers to, so the mistake cannot be illustrated with a made-up number. It has to be described in prose, which is the same discipline the first rule asks of a ticket author.

**No closed ticket is rewritten to comply.** Issues #45 to #55 and #61 to #62 are closed, and the drift in them is recorded in their bodies and in the commits that closed them. That drift is the evidence these rules rest on; retrofitting the tickets would leave the rules reading as taste, with nothing left to show they were findings.

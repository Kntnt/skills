# Failed serial work is preserved locally and taken off the branch

A run of `/orchestrate` in `Kntnt/briefsmith` on 2026-09-19 worked one ticket at a time. Issue #13 was built once and amended twice, and all three independent verdicts were a fail. The engine recorded the Run Outcome as `failed` and deliberately left the ticket open — and the three commits `d221733`, `6d83ae0` and `89a431c` were already on `main`, because at a ceiling of one the builder commits straight onto the branch the developer is standing on. The next `/push` published them. ADR-0200 settled one consequence of that push: the `Closes` trailer in those commits closed the ticket. This is the other one, which that record left explicitly outside its scope — code three verifiers refused was on the branch, and went out with it.

Above a ceiling of one this cannot happen. Each ticket gets a working tree and a branch of its own (ADR-0054), only a passed ticket goes through `integrate`, and failed work stands in its own tree for the developer to look at, having never reached the run's branch. At exactly one there is no isolation, by the same record's design: the work "lands on the branch the developer is on", and it lands there before any verdict exists. Step 9 of the Skill then said of a terminal failure that the work is left "where it stands", which with a working tree means a tree off to one side and without one means the developer's own branch. The same three words covered two very different places.

Three things followed from that, and isolation prevents all three. Unverified code is published by the next push with nothing on the way saying it was refused. A later ticket in the same repository is built on top of it, and its verifier reads a branch that already carries it. And the invocation's closing branch gate — which at a ceiling of one is the only whole-branch reading there is — runs the project's verification over work the run itself has just condemned. A ceiling of one is not an odd mode: it is the small run ADR-0054 describes, and it is the only mode a session that is itself inside an isolated working tree can run in at all.

**So the engine preserves the work locally and puts the branch back.** At a terminal serial failure, `record --outcome=failed` writes the ticket's commits under a preservation ref, writes whatever the build left uncommitted — the index, the working tree, and untracked files, with the staging difference intact — under a second one, and only then returns the branch, the index and the working tree to the commit that build began on. The original commits keep their own identity; nothing is squashed, rewritten or discarded. What the repository ignores is not work and is not touched. Nothing is published, and nothing is pushed: the recovery is local, so the material is in that clone and in no other.

**The price is a new authority, and the conditions on it are what make it bearable.** Until now the engine never moved the top of the developer's branch. It now may, and only where four things hold at once: `HEAD` is the branch the record names and is not detached, the start point resolves to a commit this repository holds, the branch still descends from it, and no commit between them has more than one parent. Ownership comes out of that persistent record and nowhere else. No commit is ever examined for its author, its message or its time to decide whose it is — that inference is exactly what an unattended run must not make, and a run that made it would be guessing about a developer's own commit.

**The record is written at the attempt boundary, not at the claim.** Step 4 claims every ticket in the frontier and step 5 isolates them afterwards, so at claim time no ticket has a working tree and the two paths cannot be told apart; a record written there would be written for every concurrent ticket too, and every ordinary concurrent failure would then look contradictory. `attempt-start` runs immediately before each dispatch, already carries the ticket number, and is the point at which a serial build's first commit is still in the future — and `plan` has just refused the branch if the working tree was dirty, so the head at that moment is a boundary nothing has moved. The two paths are told apart there by asking git for this run's own working trees, which is the question the engine already asks elsewhere, rather than by a flag or by the ceiling: a ticket with such a tree is isolated and opens no episode, and a ticket with an open record and no tree is the serial one.

**An episode nothing closed is closed by the next ticket's attempt boundary.** An invocation interrupted between dispatch and `record` leaves its record standing across the invocation boundary. A later invocation can build and integrate another ticket on the same branch, apply its notes, and only then come back to the interrupted one — at which point the stretch from the old start point to the head contains a passed ticket's verified work. Closing every other ticket's record at `attempt-start` is what stops the recovery reaching back over it, and it needs no fifth history condition, no tracker call, and no reading of who wrote what. What it costs is that the interrupted ticket's earlier commits stay on the branch: its next episode begins above them. That is what already happens to a parked ticket's work, and it loses nothing — the commits are there and reachable.

**Two directions were rejected.** Requiring a working tree even at a ceiling of one would close all three consequences, but it removes the mode ADR-0054 exists to keep: a tree, a branch and a merge for a single ticket, and no way at all for a session that is itself in an isolated tree to run. Reporting the failed commits and leaving them would let the next push publish them and the branch gate read them, which is two of the three consequences untouched, and an unattended run has nobody reading the report before it carries on.

**What cannot be recovered is refused rather than forced.** An index with unmerged stages, a merge, cherry-pick, revert, rebase or bisect in progress, and a path the preserving cannot read are states rather than work: nothing holds them whole, so preserving them would preserve an appearance and lose the rest. A refusal leaves `HEAD`, the branch, the start point, an earlier run's preservation, the index and every file in the working tree exactly as it found them. It is never a refusal to record the outcome — the comment is written and the exit stays zero, because the engine decides what is settled on the Ticket Resolution alone, and a `failed` that never reached the tracker would leave the ticket open for the next plan to offer and build on top of the very work this is about.

**So a refusal writes one ref, and that ref is what holds the branch.** It says the recovery is unfinished. While it stands, `plan` starts nothing and names both doors out: repeating the same `record` continues the recovery from wherever it stopped, and `git update-ref -d` on the named ref releases the branch by hand where nothing can. That is the "hand" this decision asks for when the ground is missing, and the run states the command rather than leaving it in the code. Neither a fresh session directory nor a tracker that already carries the failure gets past it, the refusal being read off the repository rather than off either.

**The refs live outside `refs/heads/`, under the engine's own namespace.** `git branch` does not list them, the one gesture in the run that deletes a branch cannot reach them, a collection cannot take away what they point at, and they never collide with the branch names the isolated path forms. Preserved work is kept for good; the engine removes a preservation ref never, and the unfinished-recovery ref only when the recovery finishes.

This narrows ADR-0054, which said the ceiling-one mode leaves work on the branch with nothing to clean up: that is now true of passed work and of a ticket whose episode an interruption closed, and untrue of a terminal failure. It does not touch ADR-0056, whose refusal of a working tree the run cannot account for is what makes the start point trustworthy in the first place — the tree was clean when the plan ran, so every untracked file at `record` is the run's own and goes with the preserved work. And it leaves ADR-0064 intact: the run still works whatever branch it was left on, and still publishes nothing. What changes is that the local commits a developer would otherwise have to find and reset away themselves are taken off by the run that made them.

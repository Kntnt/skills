## Findings considered and rejected

Recorded so nobody re-audits them.

- **`KNTNT_SOURCE` flows into the Catalog fetch URL (`kntnt.py:308-313`) and `KNTNT_TRANSPORT` through `shlex.split` into a subprocess command (`kntnt.py:487-488`)**: not a finding. Both are test and development hooks read from the process environment, which is already trusted ground — no privilege boundary is crossed, and an attacker who can set them can run commands directly.
- **`npx --yes skills` executes a package fetched at run time (`kntnt.py:487`)**: by design. The transport is a deliberate architectural choice, recorded in `docs/adr/0001-orchestrate-the-transport.md` and `docs/adr/0006-transport-installs-only-the-manager.md`.
- **Setup removing a Harness deletes only the Global layer (`kntnt.py:798-799`), leaving Project-layer copies on disk**: not a defect. `CONTEXT.md:78-80` defines Global as the layer that applies to the machine, and Setup owns exactly that layer.
- **`check` exits 0 with a non-empty `capabilities` list, which could read as a go-ahead**: settled, not a finding. The split is deliberate and documented three times over — `kntnt.py:958-965`, `docs/adr/0030-harness-capability-is-a-dependency.md`, and each declaring skill's own Dependencies paragraph.
- **`fetch_catalog` reads an HTTP response without a size limit (`kntnt.py:312-313`)**: not worth doing. The origin is a pinned constant, the response is a small JSON file, and a malicious response requires already controlling either GitHub or the user's environment.
- **`README.md:22-27` lists four external collections as "Essential skills on which Kntnt Skills depends", while every Catalog entry declares `"externals": []`**: a real inconsistency, HIGH confidence, but **deferred by the maintainer** rather than rejected. Either the README overstates the dependency or the skills under-declare it; the `externals` machinery is fully implemented and unused (`kntnt.py:932-940`). Worth deciding, not worth a plan until the direction is chosen.

## Direction findings — not planned, for the maintainer to weigh

Options, not problems. No plans were written for these.

- **Two channels ship the same skills.** The machine this audit ran on has `kntnt-code-skills:commit`, `:push`, `:release` and `kntnt-skills:agents-md` available as Claude Code plugin skills alongside this collection's `commit`, `push`, `release`, and `agents-md`. This repository also carries empty `skills/text/` and `skills/wordpress/` directories (untracked, so local-only) while `kntnt-text-skills` and `kntnt-wp-skills` exist as separate plugins. The evidence is the harness's skill list rather than this repository, so treat it as a question: if both channels are live, the collection's premise — one set, no drift between harnesses (`docs/adr/0005-one-set-many-harnesses.md`) — is undercut by drift between *channels*. Worth deciding explicitly which supersedes which.
- **There is no supported way to remove the collection.** `cmd_apply_setup` refuses an empty Harness list (`kntnt.py:777-778`), so uninstalling means working out which directories hold what and deleting them by hand. Install is one command. The removal machinery already exists — `remove_skills(drop, removed, global_layer=True)` at `kntnt.py:798-799` does exactly this per Harness — so a `/kntnt uninstall --yes` is close to free and closes an obvious one-directional gap against `npx skills add`.
- **Status cannot tell a user their Catalog is stale.** `skills/kntnt/status.md:12` says to run `/kntnt update` when an expected skill is missing, which requires already knowing it exists. `README.md:67` admits a skill added upstream "appears only after you run it". Update already computes `new` and `removed` (`kntnt.py:848-850`); teaching Status to compare against the origin would let it say "3 new skills upstream" instead of leaving the user to guess.

# orchestrate

Read the tracker, and work the `ready-for-agent` tickets it holds on the branch the developer is already on: a wave at a time, each ticket built by its own subagent, verified by a second one that did not build it, and integrated into that branch as its wave completes.

**Dependencies.** Checker: `$HERE/../kntnt/scripts/kntnt.py` if that file exists, else `kntnt/scripts/kntnt.py` under a Global harness skills directory (`~/.claude/skills`, `~/.config/opencode/skills`, or wherever another Harness keeps them). Run `uv run "<checker>" check --here "$HERE"`. Exit 2: emit stdout and stop. If no checker is found, tell the user to install the Manager (`npx skills add Kntnt/skills`).

The payload's `capabilities` are the half of the check no script can do — you are the harness, so you answer. For each one, say whether its `confirm` sentence is true of you. Any that is not: give its `how`, do no work, install nothing, stop. Exit 0 is not a go-ahead until every one is answered.

`$HERE` is the directory that contains this SKILL.md.

## Invocation Envelope

Before help routing or formal validation, read the `## INVOCATION ENVELOPE` section of `$HERE/help.md` and follow it. Pass only the Formal Invocation to scripts and nested formal parsers. Apply Help and Arguments below only to the Formal Invocation.

## Help

If the arguments are `--help`, `-h`, or `help`, print `$HERE/help.md` verbatim and stop. If they are `reconcile --help` or `reconcile -h`, print `$HERE/help/reconcile.md` verbatim and stop.

## Arguments

`/orchestrate [#<ticket-or-spec> ...] [--dry-run] [--at-once <n>] [--model <name>] [--yes]` or `/orchestrate reconcile #<ticket> [--commit <commit>] [--yes]`, and nothing else. A run may be aimed at as many tickets and specs as the user cares to name. Reconciliation names exactly one ticket. `--state-dir` is yours to pass rather than the developer's to type, and step 1 says where it comes from.

Anything else is an invalid form. For an invalid recognized `reconcile` form, name in one line what was wrong, print the `## SYNOPSIS` section of `$HERE/help/reconcile.md` verbatim, and point at `/orchestrate reconcile --help` for the page in full. Without that recognized subcommand, print the `## SYNOPSIS` section of `$HERE/help.md` verbatim and point at `/orchestrate --help` for the page in full. Then start nothing and stop. A flag is refused rather than ignored where it has no work to do here, because a flag accepted and ignored teaches that flags sometimes do nothing.

## Steps

Where the Formal Invocation starts with `reconcile`, follow this paragraph and stop before the numbered run steps. Run `uv run "$HERE/scripts/run.py" reconcile --ticket <number>`, adding `--commit <commit>` when the maintainer supplied one. Exit 0 is the complete Reconciliation; report whether it was newly recorded, already agreed, or repaired after interrupted lifecycle cleanup, together with the unsuccessful Run Outcome, the done Ticket Resolution, and the completion commit from stdout. When no commit was supplied and stderr says no unique completion commit can be established, ask the maintainer for the commit and rerun with their answer; under `--yes`, ask nothing and report the refusal. Any other nonzero exit is a refusal: show stderr and stop. Never close or reopen the ticket, edit an earlier outcome, or describe the rescued work as built or independently verified by Orchestrate.

Every command below takes `--state-dir <directory>`. Pass whatever per-session scratchpad or temporary directory your harness gives you, the same one on every call, so what this run has claimed survives a compaction. The engine keeps what it remembers in a subdirectory of that directory rather than at its root, so a subagent writing or clearing scratch of its own has nothing of the run's to catch. Where your harness gives you none, leave the flag off: its absence is not an error, and the engine rebuilds what it needs from the tracker and the branch. There is no resume flag and none is wanted — re-invoked with the same arguments, this Skill continues an interrupted run rather than restarting it.

1. Run `uv run "$HERE/scripts/run.py" plan`, passing the user's `--dry-run`, `--at-once`, `--model`, and `--yes` through. Where the user named any tickets or specs, pass what they named too, verbatim and as one value: `--scope "<what they wrote>"` — all of it, however many references it holds and in the order they wrote them. Never resolve a reference yourself, and never widen or narrow what they named, or drop one you cannot make sense of — the engine reads the tracker and decides, reference by reference, which of the two each one is. Done when stdout is the JSON plan; anything else on stdout means the engine refused the arguments, so show stderr and stop.
2. Where `ready` is false: go to step 12, having started nothing. `reason` is why no run may start, and a dry run is one of those reasons. Done when you have stopped or `ready` is true.
3. Before anything is claimed, read every ticket in `tickets` — body and thread alike, both already in the plan — for a decision the text leaves open: a deferred value, a choice named as the maintainer's, two designs left standing. The label promises there is nothing to ask, but the label is a claim, and triage sometimes gets it wrong. Where nothing is open, go on to step 4. Otherwise, without `--yes`: ask the developer everything you found in one batch, now, while the developer who typed the command is still there — after this step they are not addressed again until the report — and write each answer as a comment on its ticket with `gh issue comment <number> --body "<the answer>"`, which is how it reaches the builder: the brief carries the whole thread, so an answer on the ticket is an answer in the brief. Under `--yes` there is nobody to ask, and the flag cannot answer an open question — it answers yes/no, and *which default?* is not one — so park each such ticket instead: write the question on the ticket with the same comment command, then `uv run "$HERE/scripts/run.py" park --ticket <number>`, which replaces `ready-for-agent` with `needs-info` and releases any claim of this run's; keep each parked ticket's number, title, and question for step 12. Exit 2 there means the ticket already carries a recorded outcome and is settled — nobody's to park, so leave it as it stands. Never park for anything else, and never answer an open question yourself: a run still creates no ticket and decides no ticket's substance. Where anything was written or parked, run step 1's `plan` command again and return to step 2 with what it answers — the answers are now in each ticket's thread, so the briefs will carry them, and a parked ticket has left the scope the way an unlabelled ticket was never in it. Done when no ticket in scope leaves a decision open, every answer being on its ticket or the ticket that deferred it parked.
4. Claim every ticket in `starting`, which is the frontier cut to the ceiling the developer set: `uv run "$HERE/scripts/run.py" claim --ticket <number>` for each. Exit 2 means another session or a person already has it — leave it untouched, record nothing, drop it from this wave, and claim the next ticket in `workable` that the wave does not already hold, so the ceiling stays filled. A ticket `resuming` names is one an earlier invocation of this run claimed and was interrupted before recording: it is in `workable` like any other and claiming it succeeds, the claim being already this run's own. Done when the wave is the tickets you claimed, or nothing could be claimed and you go to step 12.
5. Where `worktrees` is true, give each ticket in the wave what the wave would otherwise share: `uv run "$HERE/scripts/run.py" isolate --ticket <number>`. It answers with the `worktree` that ticket is built and verified in, the `branch` it is built on, the `scratch` directory made for it beside that tree, and the `reservations` it holds — one record number in each of the repository's numbered registries, so two tickets creating a record at once cannot mint the same number. A ticket picked up again gets all four back rather than a second set of them. The briefs carry the last two to every subagent this ticket gets: the scratch is the only place outside the working tree any of them may write, and the reserved number is what a builder creating a record takes instead of reading the directory. Where `worktrees` is false the wave is one ticket and there is nothing to isolate: it is built in the repository as it stands, on the branch already checked out, it takes the next free number in any registry it adds a record to — nothing is being built beside it to read that directory at the same moment — and the scratch its briefs name is one you make for it in a subdirectory of the session's own scratch, never that directory's root. An engine refusal here — exit 1, with the reason on stderr — is a ticket this run has nowhere to build: drop it from the wave, build nothing for it, record nothing against it, and leave its claim where it is; step 12's report accounts for it as a ticket that was never on the frontier. Done when every ticket in the wave has somewhere to be built.
6. Build the wave, one subagent per ticket, each with its own context window. Where `model` names a model, every builder runs on it and no judgment is made — the flag is the override. Where it names none, choose per ticket, from the ticket's own text, the cheapest model you may give its builder that you judge able — a mechanical rename is not a redesign — and never above your own, the orchestrating session being the run's most capable seat. Start them together rather than one after another — working the frontier concurrently is what the ceiling is for, and a ticket that waits on an unrelated ticket is a run slower than its graph requires. Before the first wave is briefed, name the run's own files: the changelog, and whatever else this repository's own ground rules make every ticket append to — a guide's list of references, a worklog, an index of records. Read those rules to answer it, and hold the answer for the whole run rather than asking it again each wave; which files those are is a reading of prose rather than something a script can compute, which is why the naming is yours and not the engine's. A builder never edits one of them, so every brief carries the list together with the note path its builder writes an entry to instead, and step 8 applies what the wave's notes hold. Where this repository has no such file, the list is empty and `brief.md` says how it is filled in then. Resolve the gate then too, once for the run: read the project's contributing guide and write down the commands it names for verifying a change, verbatim; where no guide names any, write down the whole test suite and whatever lint, format, and type checks the project is configured for, as the concrete commands those resolve to. Hold that list for the whole run and fill it into every brief that asks for verification — the list is the gate wherever it is carried, all of it and nothing in its place, so the strictness travels while the resolving happens once: resolved by every subagent instead, the same phrase was read nine times over one tree, and one open-ended reading found and ran a twenty-five-minute rig no guide had named as a gate. Read `$HERE/references/brief.md`, fill it in per ticket from that ticket's entry in `tickets`, from what step 5 answered for it, and from the run's own files you named, and give each subagent the filled-in brief and nothing else. Never build a ticket in this context: a ticket built here is a ticket whose builder and verifier are the same session, and the run would be reporting on itself. A subagent that ends its turn waiting on a command it started has neither finished nor failed: it is resumed with that command's result rather than recorded, its stop being the mechanical kind and the repair a resumption. A subagent that stopped and reported instead is triaged before anything is recorded, and one question sorts the stop: whether fixing what stopped it decides anything about the work. A mechanical hinder — a condition of the environment, not a question of the requirement: the path slightly wrong, the directory missing, the number it wanted already taken — decides nothing, so repair the condition yourself and dispatch the same brief once more. Once: a hinder that survives its repair is recorded as the failure it now is, this bound being one for the same reason the amend's and the rebuild's are. A genuine decision — an ambiguity the ticket does not settle, a requirement it does not state, a design the spec leaves open — parks the ticket exactly as step 3 parks one: write the question on the ticket with the same comment command, run the same `park` command, which returns the label to triage and releases the claim, record no outcome, and keep the number, title, and question for step 12; the wave carries on without it, and its working tree, where it has one, stands like a failed ticket's. A builder that stopped because its ticket depends on unresolved work the graph does not name found a missing edge, and what sorts that stop is whether the missing thing has a number: an answer no ticket carries is a genuine decision and parks as above, while a ticket without a done Ticket Resolution is an edge the breakdown missed — run `uv run "$HERE/scripts/run.py" record --ticket <number> --outcome blocked --blocked-by <blocker>`, passing `--blocked-by` once per ticket the report names. That writes the corrected edge to the tracker the way the breakdown would have, releases the claim, leaves the ticket open with a note saying what happened and on what, and discards its working tree and branch, the half-built work with them, exactly as a refused repair is discarded and without spending the ticket's one rebuild; the wave carries on without it, and a plan offers the ticket again when its blocker has a done Ticket Resolution — tonight, where a later wave reaches it — isolated afresh from the branch that by then carries the blocker's work and built whole on top of it. The engine refuses a blocker with a done Ticket Resolution because that resolution establishes the required work; tracker closure without that resolution does not end the wait. Where `worktrees` is false a parked or blocked ticket has no tree of its own, so the wave carries on only where its subagent left the working tree as it found it — leavings there stand on the branch itself, and the run goes to step 12 rather than build the next ticket on top of them, exactly as step 11 stops on a failure. Anything else a stop reports is work tried and found wanting: the ticket stays in the wave and is verified like any other, its failure path being step 8's — the one the amend fronts. The same triage is every stopped subagent's — building, verifying, amending, or repairing. Done when every subagent has finished or its stop has been triaged, a parked ticket having left the wave.
7. Verify each ticket in a second subagent that has not seen the building session, and that is told nothing the builder said. Read `$HERE/references/verify.md`, fill it in from the same entry, the same working tree, the same scratch directory, and the gate you resolved before the first wave was briefed, and give it that. It runs on your own model, whatever the builders ran on, as every verdict in this run does — this one, the amend's, the repair's, and the wave check's — because the saving is never taken at the last thing that would catch a mistake. Its verdict decides; the builder's report is evidence of nothing. No argument, flag, or circumstance skips this step. A verifier that ends its turn waiting on a command it started is resumed with that command's result too, rather than recorded: a verdict that was not reached is not a fail. A verifier that stopped and reported is triaged as step 6 triages a stop: a mechanical hinder repaired and the same brief dispatched once more, once; a genuine decision parking the ticket, which leaves the wave wanting no verdict; anything else standing as the fail it is. Done when every ticket still in the wave has a verdict.
8. Integrate the wave, ticket by ticket in the order `starting` names them, and record every outcome as you go.
   - A ticket that passed, where `worktrees` is true: `uv run "$HERE/scripts/run.py" integrate --ticket <number>`. Exit 0 merges it into the run branch and takes its working tree away — record it with `record --ticket <number> --outcome done --commit <the commit it answered with>`, which closes the ticket. Exit 2 is a collision with work already on the branch: the branch is left as it was and the working tree stands, so go to step 10 with what it answered — its `collisions`, the files the merge could not settle, and its `collided_with`, the tickets whose merged work is on the other side of them.
   - A ticket that passed, where `worktrees` is false: its work is already on the branch, so record it done with `--commit "$(git rev-parse HEAD)"`. Exit 1 is the engine refusing to call it done — the working tree still holds work nothing committed, so the commit named does not carry it: record the ticket `--outcome failed` instead, change nothing in the working tree, and go to step 11 with a failure. There is no verdict to amend from here — the verifier passed the ticket, and what refused it is the tree.
   - Anything else is work tried and found wanting — a failed verdict and only that, every stop having been triaged in the step it happened in: go to step 9 with it before anything is recorded. Where the amend does not deliver a pass, the ticket is recorded `--outcome failed` and no `--commit`, which leaves it open and claimed so nothing touches it again. Nothing integrates it, so its working tree stays where it is for the developer to look at.

   Then write the wave's entries into the run's own files, once every ticket in the wave carries an outcome. Every ticket whose work reached the branch left its entries there at `.kntnt-orchestrate/<number>.md`, its own number in the name: take those notes one ticket's worth at a time, in the order this step integrated them, add each entry to the file it names where that file's own convention puts it, then remove the notes from the branch and commit that. Sequential appends cannot collide, which is why these files are the run's to write rather than a builder's, and the entries land before step 11 reads the branch, so the run's own writing is verified exactly like the work it describes. A wave that left no note has nothing to apply here.

   Done when every ticket in the wave carries an outcome and the wave's notes have been applied and taken off the branch, a failed verdict having gone through step 9 first and a collision through step 10.
9. Amend each ticket whose verdict was a fail through at most two verifier-informed amends, each decided by another fresh verdict. The initial verdict changes the first amender's conditions, and attempt 1's fresh verdict changes them again when it names a different defect or a regression; no attempt 3 exists, so the repair path stays finite.
   - The ticket entry's `amends_spent` and `amend_state` are the append-only phase ledger. `amends_spent` is zero before an amend, one during or after attempt 1, and two during or after the continuation. `amend_state` carries that `attempt`, its exact `phase` — `building`, `verifying`, `passed`, or `failed` — and the complete `verdict` at a builder dispatch or failed-verifier boundary. Every phase is appended before the work it fronts, so the tracker alone says what a fresh invocation safely does next. A legacy unnumbered marker appears as one spent attempt with phase `legacy`; it leaves only the continuation available and requires the current session to supply the latest failed verdict because the old marker could not persist one.
   - For a failed verdict with an opportunity left, write that verdict verbatim to a file inside this ticket's scratch directory, then run `uv run "$HERE/scripts/run.py" amend --ticket <number> --attempt <1-or-2> --phase building --verdict-file <path>`. The initial verdict spends attempt 1; the `failed` state and persisted verdict from attempt 1 spend attempt 2. Exit 0 appends the phase before dispatch, or returns the same attempt and phase with `newly_recorded` false when an interrupted caller repeats the exact event already written; both cases resume that recorded attempt without minting the next. Exit 2 refuses an attempt above the hard bound. An engine refusal — exit 1 with the reason on stderr — is a skipped or stale phase, a mismatched verdict, or an amend that did not happen, so stop rather than pair the wrong verdict with a marker. Never call `amend` with a different attempt for the same verdict.
   - For either attempt in phase `building`, read `$HERE/references/amend.md` and fill it from the ticket's whole entry in `tickets`, from what step 5 answered for it, from the gate resolved before the first wave, from the recorded `attempt`, and from the immediately preceding verifier's verdict pasted whole — never a summary or an accumulation. Give it to a fresh building subagent, on a model chosen as step 6 chooses a builder's: amending is building, and a ticket back for an amend has demonstrated it was harder than it looked. Both attempts reuse the same working tree, scratch directory, reservations, run-owned-file rules, and plan entry; at a ceiling of one the working tree is the repository and current branch. Nothing from one ticket's amend enters a sibling's brief, scratch, reservations, notes, or working tree. When that builder completes, append the verifier boundary with `uv run "$HERE/scripts/run.py" amend --ticket <number> --attempt <1-or-2> --phase verifying` before dispatching its verifier.
   - For either attempt in phase `verifying`, dispatch a fresh verdict subagent from `verify.md` unchanged at `$HERE/references/verify.md` and filled exactly as step 7 fills it, on your own model as every verdict runs. It receives the ordinary ticket verification brief and no builder report, earlier verdict, or amend history. It runs the full fixed gate and checks the whole ticket: pass only when every gate command and acceptance criterion passes, however concrete or numerous the remaining findings are. Before acting on a pass, append it with `uv run "$HERE/scripts/run.py" amend --ticket <number> --attempt <1-or-2> --phase passed`. Before acting on a fail, write its verdict verbatim to the ticket scratch directory and append it with `uv run "$HERE/scripts/run.py" amend --ticket <number> --attempt <1-or-2> --phase failed --verdict-file <path>`.
   - Resume strictly from `amend_state`: `building` resumes or dispatches that attempt's builder from its persisted verdict; `verifying` resumes or dispatches its ordinary fresh verifier; `passed` integrates and records the ticket exactly as step 8 does, with a collision going to step 10; `failed` on attempt 1 starts attempt 2 from that persisted verdict; and `failed` on attempt 2 records the terminal failure. Attempt 1 never exhausts the verification-repair path: if attempt 1's fresh verdict is a fail, keep that complete verdict as the latest one and spend attempt 2 through this same loop. A pass after either attempt integrates normally. Repeating a recorded phase is the only replay; do not infer completion from a vanished subagent report or append a later phase until the work immediately before it has completed.
   - An amending builder or verifier that stops is triaged as step 6 triages a stop at either attempt: a waiting subagent resumes, a mechanical hinder is repaired once, a genuine decision parks the ticket with its spent marker, and a discovered dependency follows its existing edge path rather than becoming an automatic retry. Only an attempt 2 amend that was independently tried and found wanting, or a failed final verification after attempt 2, exhausts the verification-repair path: record `--outcome failed` and no `--commit`, leave the work where it stands, and offer no attempt 3. At a concurrency ceiling of one, no later ticket starts until this continuation has a passing verdict or that terminal outcome; with worktrees, unrelated completed tickets may still be accounted for while this ticket stays inside its own allocation.

   Done when every failed verdict has passed after either bounded amend, exhausted both attempts and been recorded failed, or left the wave through the existing stop triage.
10. Repair each collision, and where the repair does not hold, build that ticket once more on top of the work it collided with. Two tickets that touched the same code should not cost a full rebuild over two added imports, so the cheap repair is tried first — and it is verification that decides, because a resolution nobody can verify is not a resolution.
   - Read `$HERE/references/repair.md`, fill it in from the losing ticket's entry in `tickets`, from what `isolate` answered for it, from the run `branch`, from the gate you resolved before the first wave was briefed, and from the collision's `collisions` and `collided_with` — one block per ticket named there, each carrying that ticket's whole body from `tickets`. Give it to a subagent, on a model chosen as step 6 chooses a builder's — repairing a collision is building. It merges the run branch into the ticket's own branch, inside that ticket's working tree, and settles the collision there. Nothing is settled on the run branch: what a verifier has not passed does not reach the branch the developer comes back to.
   - Verify that repair in a second subagent that has not seen it, from `$HERE/references/repaired.md`, filled in the same way, and on your own model, as every verdict runs. It checks both tickets' acceptance criteria against the repaired working tree and runs the project's full verification itself. Its verdict decides.
   - A pass: `uv run "$HERE/scripts/run.py" integrate --ticket <number>` again. It merges, the ticket's branch now carrying the run branch it collided with, so record it done on the commit it answers with, exactly as step 8 does.
   - A repair subagent that stopped and reported is triaged as step 6 triages a stop — a mechanical hinder repaired and the same brief dispatched once more, once; an open decision in the losing ticket's own requirement parking it, no outcome recorded. The disagreement the two tickets do not settle is neither of those: the rebuild below is the run's answer to it, the ticket built afresh on the very work it disagreed with.
   - Anything else — a stop the triage neither cleared nor parked, the verdict is a fail, or the merge collides a second time: `uv run "$HERE/scripts/run.py" rebuild --ticket <number>`. Exit 0 discards that working tree and its branch, the failed resolution with them, and the ticket may be built once more: isolate it as step 5 does, build it alone from `brief.md` as step 6 does, verify it from `verify.md` as step 7 does, and integrate and record it as step 8 does, whatever the outcome. Built on the very code it would have collided with, it cannot collide again. Exit 2 means this ticket has already spent its one rebuild: record `--outcome conflicted`, passing `--collided-with <number>` once per ticket in `collided_with`, and leave its working tree where it stands.
   - An engine command that refuses anywhere in this step — exit 1, with the reason on stderr — is a repair that did not happen: record the ticket `--outcome conflicted` with its `collided_with` as above, and leave it. A ticket leaves this step with an outcome or parked with none, and a collision nobody could record is one the report would lose.
   - Never ask the developer how to resolve a collision, and never rerun anything else here. The rebuild is the one rerun a collision buys, and it happens at most once per ticket; the verifier-informed amends a failed verdict buys are step 9's, and their two-attempt bound is independent of the one rebuild.

   Done when every collision has been repaired, rebuilt, recorded conflicted, or its ticket parked.
11. Where `worktrees` is true and anything was integrated, check the integrated branch in a subagent on your own model, as every verdict runs, from `$HERE/references/wave.md`, filled in with the gate you resolved before the first wave was briefed and a scratch directory of its own like any other subagent's. It runs the project's full verification and reads the branch for coherence — the branch agreeing with itself — and its verdict has three shapes. Two tickets that pass alone and fail together are caught here and nowhere else, and so is a branch that no longer agrees with itself, a ticket forked before a sibling's work landed being unable to see that work at all. A clean pass: run step 1's `plan` command again and go to step 4 with what it now returns — the outcomes you just recorded are what change it, a done Ticket Resolution unblocking whatever waited on it and an unsuccessful Ticket Resolution stranding whatever waited on that. Never carry a ticket forward from an earlier plan; the plan you act on is always the one you just read. Mechanical findings: read `$HERE/references/fix.md`, fill it in with the findings pasted whole and a scratch directory of its own, and give it to a fresh subagent, never the checking one — the finder is never the fixer, and what licenses the fixer's commit ahead of a verdict is that the check that demanded it reads the result. When the fixer has committed, run this step's check again from `wave.md` unchanged — gate and coherence both, on the branch as it now stands — and act on that verdict exactly as this step acts on the first, because this class of defect never comes alone. The loop ends when a round finds nothing, and it stops the run when a round changes nothing — the same findings back with no fix made is the non-mechanical case wearing the mechanical one's clothes: go to step 12 as a stop. A stop — the gate failed, or a finding is a choice between two tickets' intents: go to step 12, saying which wave it was and that the run stopped rather than spend the remaining hours building on broken code or on a disagreement merged onto the branch. Where `worktrees` is false, there is nothing integrated to check: on a pass go to step 4 with a fresh plan as above, and on a failure go to step 12, the ticket's unverified work being on the branch itself and the next ticket otherwise built on top of it — a failure reaching here having exhausted both verifier-informed amends, so the run stops rather than build another ticket on work that failed three independent verifications. Done when a wave's check has ended in a clean pass or a stop, a ticket has failed on a branch of its own, or no ticket is workable.
12. Report the run in one go, rather than as a running commentary, and render it from what the engine returned rather than from your own account of the session. It is the first time since step 3 the developer is addressed, and it asks nothing: what the run had standing to do on its own account it has already done, between waves, and what it had not it states — findings as a list of statements, never as questions awaiting answers. Lead with what is done and with what is left for the developer to do; the account below follows. Where nothing started, that account is the last plan's `reason` together with its `waves`, `workable`, `starting`, `claimed`, `resuming`, `recorded`, `stranded`, and `never_workable` — which is what a dry run is read for — and you are done. Otherwise run `uv run "$HERE/scripts/run.py" report`, passing the same `--scope` you passed in step 1 so the account covers what the run was aimed at, and give the developer what it emits: its `branch` and the `base` its work sits on top of, then every ticket in scope under the outcome it fell to — `done`, `failed`, `conflicted`, `stranded` behind a failure, and `never_on_frontier`, which is every ticket this run never had on its frontier, whether held by a cycle, by work outside the run, by another session's claim, or by the run stopping before its wave came round. Name each ticket by number and title from `tickets`, and give its `commit` where the outcome carries one, its `collided_with` where it is conflicted — that pair being the blocking edge the ticket breakdown was missing, and the whole point of reporting a collision rather than only a failure — and its `worktree` where the machine kept one, that being where a failure stands and how it is looked at. Render every ticket's `run_outcome`, `is_reconciled`, and `amends_spent` provenance as well. For a failed ticket, two spent amends mean its exhausted verification-repair path failed its final independent verdict; zero or one means it failed before an available continuation amend completed, so never describe the latter as exhaustion.

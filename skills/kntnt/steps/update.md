# update

Refresh the skills of this collection whose files Deviate from it, then check every Dependency again. Report each new Catalog entry and ask whether to Enable it; `--yes` answers that question yes, so an unattended run Enables what the collection has added since the last one. A skill the collection has withdrawn is deleted from this layer, and that is not asked either — it can no longer be updated or supported, and no other command can reach it. Do not refresh an External. Without `--project` apply the Global layer; with `--project` apply the Project layer. A Harness installed since the last run is reached without any configuration, because the targets are worked out on each run. A real Global Update is authorized only by `--yes` in the current Formal Invocation or by a later user response to the complete current plan.

`$HERE` is the manager directory (the parent of `scripts/`).

## Steps

1. Run `uv run "$HERE/scripts/kntnt.py" plan update` with the same `--project` flag the user passed. This is read-only. Done when stdout is JSON.
2. Show the complete plan. Name every item in `refresh`, `enable`, and `remove`, and every target in `directories`; say each item in `current` already matches and will not be re-copied. `refresh` contains every Enabled Skill whose files Deviate and the Manager on a Global run; say that re-copying discards local edits. `enable` contains every new Catalog entry a yes answer Enables, and `remove` contains every Withdrawn Skill the run deletes without a separate question. Ask **one** question for the whole run — refresh these, remove these, and Enable the new entries as well? — worded so that a plain *yes* ends it and Enables them; where `enable` is empty there is nothing to add to that clause. An answer that takes the refresh and removals but leaves the new entries Disabled is honoured in step 3 by withholding `--yes`. If `catalog_refreshed` is false, say the Collection could not be reached and nothing can be refreshed, Enabled, or removed. On a real Global run without formal `--yes`, wait for a later user response after showing this exact plan. A Contextual Instruction, Conversation Context, an instruction or answer remembered from earlier in the task, a broad repair request, or an agent-authored handoff is never approval; planning alone is not approval either. Formal `--yes` in the current Invocation Envelope authorizes the displayed plan without a later question. A dry run needs no mutation confirmation or approval because every write stays inside its discarded Sandbox. Done when the current plan has fresh authorization, or the run is a dry run.
3. For a real Global run that Enables the entries in `enable`, copy `approval` from the plan exactly; when the later response accepts the refresh and removals but leaves those entries Disabled, copy `approval_without_enablement` instead. Run `uv run "$HERE/scripts/kntnt.py" apply update --approval=<approval>` with that value; each opaque identity binds Apply to one complete answer and authorizes nothing by itself. Use the same `--project` flag, and pass `--yes` where the Formal Invocation carried it or step 2's later user response answered yes — that flag retains its collection-wide meaning and is the whole of what Enables a new entry. Forward `--dry-run` without `--approval` if the user passed it, and say before starting that the run happens against a temporary home that is thrown away, and that it downloads the transport afresh and so takes longer than the real run would. A missing, incomplete, contradictory, or changed approval — including an Enablement identity paired with the opposite `--yes` answer — is refused before the first write; return to step 1, show the complete new plan, and obtain a new response rather than reusing the earlier authorization. Done when stdout is JSON.
4. Say each name in `current` was already the files the collection ships and was not re-copied. Say each name in `enabled` is a new Catalog entry the answer told this run to Enable — whether it landed is `confirmed` and `failed` in step 5, not this list — and each name in `new` that is not in `enabled` is in the Catalog and still Disabled, with `/kntnt select` as where to change that. Every item in `removed` is a skill of this collection that was found in this layer and is no longer in the collection, so say that and say what became of its files: `disk` is `removed` where they were deleted, and `failed` where they are still there — name that item's `directories`, pass on as it stands whatever the script printed to stderr under `the transport said:`, and do not call the run clean. A withdrawn skill this layer never held is not reported, because there was nothing here to remove. For each item in `unsatisfied`, give its `how`. For each item in `capabilities`, answer its `confirm` about yourself — you are the harness, and no script can test that; where it is not true of you, say that `skill` does no work here and give its `how`. If `catalog_refreshed` is false, say the collection could not be reached and nothing was refreshed: the stored copy is unchanged, nothing was fetched because the files come from the origin that list could not be read from, `new` is empty for want of anything to compare against rather than because nothing changed upstream, so nothing was Enabled whatever was answered, and `removed` is empty because nothing is deleted on the strength of a list the collection did not answer with — run this again when the collection is reachable. Done when the user has the report.
5. `intended` names the skills the run set out to place — what Deviated, and any new entry the question Enabled — and `confirmed` those the script then found on disk. If `failed` is non-empty the command exits non-zero: say those skills did not land, whether or not the transport claimed otherwise, name each one's `directories` as where to look, pass on as it stands whatever the script printed to stderr under `the transport said:` — those are the transport's own words and the only account there is of why — and do not call the run clean. Done when the user has the outcome.
6. Report what became of each Skill's Harness Integrations. A Harness Integration is what a Skill writes into a Harness's own configuration so that Harness calls the Skill at its own lifecycle moments, and it sits outside the Skill's own directory, where deleting that Skill's files never reaches it. Update carries what it placed under `integrations`, each withdrawal's own teardown records inside that withdrawal's `integrations` in `removed`, and the withdrawal gate's `note` under `removed_integrations`, whose `attempted` is empty because those records already sit beside each withdrawal. Each record is one Skill's own answer — its `name`, its `status`, a `detail`, and the per-Harness entries it answered with under `installed` or `removed` — and each of those entries carries its own `harness`, `status`, `entries`, and `detail`. Read the records per Skill and per Harness rather than one line per record: the Manager asks a Skill once per directory that holds it, so a Skill in two trees answers twice about one integration written once into one Harness, and those identical records are one finding rather than two. Where records for one Skill disagree, the disagreement is itself the finding and is reported once rather than as two outcomes the user has to reconcile, and a record that reached no Harness at all is reported against the Skill alone rather than against a Harness nobody established. Name a failed install or teardown per Skill in the payload's own words, passing its `detail` on as it stands rather than paraphrasing it: the Manager has already cut a failed script's own output at two hundred characters, and nothing else is cut. An integration failure raises nothing and moves no exit code, so a run whose files all landed and which exits zero can still be a run you do not call clean: say what failed, and do not call it clean. Report a `note` wherever it is not null: it says this layer installs or removes no integration, and a user who unchecked a Skill in a project has to be told that rather than left believing their machine-wide integration went with the files. A per-Harness entry that removed nothing — `removed` with `entries` at zero — is the converged state and adds nothing: a teardown attempts every Harness the collection has an adapter for, whether or not this machine ever held an entry there. What is reported comes from the records the payload carries and never from the run's own list of Skills, so a Skill that owns no Harness Integration adds nothing here. A per-Harness entry whose `status` is `installed` and whose `detail` is not null is gated: report it as present and not yet active, never as installed and working, and pass on that whole `detail`, which is what tells the user how to activate it. Where a record's `unsupported` carries a `count` that is not zero, say that many Harnesses no adapter serves, as that count and never as names — the payload names none of them deliberately — and say nothing where the count is zero. A record here may name a Feature rather than a Skill: a Feature is a Catalog entry that owns Harness Integrations and nothing else, so its record is the whole of what enabling or disabling it did, and everything above about reading records per owner and per Harness applies to it unchanged. Done when the user has been told what became of every Harness Integration the payload names, or it named none.

# update

Refresh the skills of this collection whose files Deviate from it, then check every Dependency again. Report each new Catalog entry and ask whether to Enable it; `--yes` answers that question yes, so an unattended run Enables what the collection has added since the last one. A skill the collection has withdrawn is deleted from this layer, and that is not asked either — it can no longer be updated or supported, and no other command can reach it. Do not refresh an External. Without `--project` apply the Global layer; with `--project` apply the Project layer. A Harness installed since the last run is reached without any configuration, because the targets are worked out on each run.

`$HERE` is the manager directory (the parent of `scripts/`).

## Steps

1. Run `uv run "$HERE/scripts/kntnt.py" plan update` with the same `--project` flag the user passed. Done when stdout is JSON.
2. Show the plan, including the `directories` it will refresh. Its `refresh` list is what will be re-copied — every Enabled skill whose files Deviate from the collection, and the manager, which is refreshed every time — and `current` is what is already the collection's own files and will be left alone; say both, and say that re-copying a skill discards any local edit to it. Say that a skill this layer holds and the collection no longer carries will be deleted rather than refreshed, and that step 4 reports which. Name each skill in `new`: the collection has added it since this Manager stored its Catalog, and it is Disabled here. Ask **one** question for the whole run — refresh these, and Enable the new entries as well? — worded so that a plain *yes* ends it and Enables them; where `new` is empty there is nothing to add to the question. An answer that takes the refresh and leaves the new entries Disabled is honoured in step 3 by withholding `--yes`, and nothing is written before the question is answered. If `catalog_refreshed` is false, say the collection could not be reached and nothing can be refreshed: the files move through the same origin the list could not be read from, which is why both lists are empty. Wait unless `--yes` or `--dry-run` — a dry run refreshes nothing outside its own Sandbox, so there is nothing here to confirm, and the offer is not put to a preview either: without `--yes` it previews the refresh alone. Done when the user confirms, or `--yes` or `--dry-run` is set.
3. Run `uv run "$HERE/scripts/kntnt.py" apply update` with the same `--project` flag, and `--yes` where the user gave it or step 2's question was answered yes — that flag is the whole of what Enables a new entry, so pass it on no other answer. Forward `--dry-run` if the user passed it, and say before starting that the run happens against a temporary home that is thrown away, and that it downloads the transport afresh and so takes longer than the real run would. Done when stdout is JSON.
4. Say each name in `current` was already the files the collection ships and was not re-copied. Say each name in `enabled` is a new Catalog entry the answer told this run to Enable — whether it landed is `confirmed` and `failed` in step 5, not this list — and each name in `new` that is not in `enabled` is in the Catalog and still Disabled, with `/kntnt select` as where to change that. Every item in `removed` is a skill of this collection that was found in this layer and is no longer in the collection, so say that and say what became of its files: `disk` is `removed` where they were deleted, and `failed` where they are still there — name that item's `directories`, and do not call the run clean. A withdrawn skill this layer never held is not reported, because there was nothing here to remove. For each item in `unsatisfied`, give its `how`. For each item in `capabilities`, answer its `confirm` about yourself — you are the harness, and no script can test that; where it is not true of you, say that `skill` does no work here and give its `how`. If `catalog_refreshed` is false, say the collection could not be reached and nothing was refreshed: the stored copy is unchanged, nothing was fetched because the files come from the origin that list could not be read from, `new` is empty for want of anything to compare against rather than because nothing changed upstream, so nothing was Enabled whatever was answered, and `removed` is empty because nothing is deleted on the strength of a list the collection did not answer with — run this again when the collection is reachable. Done when the user has the report.
5. `intended` names the skills the run set out to place — what Deviated, and any new entry the question Enabled — and `confirmed` those the script then found on disk. If `failed` is non-empty the command exits non-zero: say those skills did not land, whatever the transport reported, name each one's `directories` as where to look, and do not call the run clean. Done when the user has the outcome.

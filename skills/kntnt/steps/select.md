# select

Show what the collection has and change it in the same gesture. The list is the Catalog, one row per skill with a checkbox that is checked when the skill is Enabled in the targeted layer; the user answers it in one sentence of plain text. Targets Global unless `--project` or `--project=on` is given, and reaches every Harness present in that layer. Reading is never a side-effecting act: an answer that changes nothing writes nothing.

`$HERE` is the manager directory (the parent of `scripts/`).

## Steps

1. Read the arguments before running anything. `--on <skill>` and `--off <skill>` — either of them, as often as the answer has names — and `--yes` given with neither of them open no list at all: follow **Without the list** below and stop. Everything that follows is the list form. Done when you know which form this is.
2. Run `uv run "$HERE/scripts/kntnt.py" plan select` with the same `--project` flag the user passed. Done when stdout is JSON.
3. Print the list. Group the rows by their key in `categories` and give every skill a row of its own, in this shape: a checkbox — checked where `checked` is true — the skill's `name`, its `description`, and, where `capabilities` is non-empty, the Capabilities it requires of the harness, said as a warning that it may refuse to work where the user is. Name the `directories` the list covers. Done when every row the payload carries is on screen.
4. Mark the rows the payload marks. `incomplete` true: the skill's files reached only some of the directories, so it is shown checked and marked incomplete, and confirming the list repairs it. `freshness` is `deviating`: say the files differ from the ones the collection ships — **deviating**, never *out of date*, because the comparison sees two states and no history, and a local edit is as likely a cause as a lagging copy. `current` needs no remark and `unknown` means there was nothing to compare. `locked` true: show the row locked and name its `unsatisfied` Dependencies as what to check instead, so the user can see why they cannot have it yet. A row with a non-empty `unsatisfied` that is not locked is one the user already has and something it needs has gone: say what it lacks. Done when the marks are made.
5. Say which Catalog the list came from, taking it from `catalog_refreshed`. `true` needs no remark. `false` means the collection could not be reached and the list is the copy stored beside the manager: say so, say it may be missing skills published since, and report no skill as deviating or as current — those digests describe the collection as of the last update, so offer no re-copy on the strength of them. Done when that is said, or the list was fetched.
6. Close with `withdrawn` where it is non-empty: say how many skills on disk carry this collection's marker and are no longer in the Catalog, and that `/kntnt update` is what takes them off. Done when that is said, or the list is empty.
7. Take the user's answer as the whole checked set for this layer, not a list of changes. Done when you have that set.
8. Resolve the closure before anything is written. Every checked skill's `requires` names the whole chain it needs, so work out the additions: each name in those chains the checked set does not carry, that the user did not just uncheck — a skill whose row came back `checked` and the answer leaves out is an uncheck, and putting it back would answer for them — and, in the Project layer, that a row whose `in_global` is true does not already supply, since Global's copy Satisfies it and a second one buys nothing. Add those to the checked set. Done when you have them, or there were none.
9. Work out what confirming the resolved set would do: a skill checked that is unchecked, incomplete, or deviating is placed; a checked skill they unchecked is deleted from this layer. Show both and name the `directories`. Name exactly what step 8 added and why, in **one question** for the whole closure however deep the chain it came from — `release` pulling in `push` and `commit` is a single yes, never one question per level. Where a deviating skill is among the placements, say in the same breath that re-copying overwrites the local changes. Where the answer unchecks a skill that a checked one depends on, name what it leaves Unsatisfied and go on: that is reported, not refused, and it is never repaired by re-checking what the user just unchecked. Ask once, and write nothing before it is answered; `--yes` answers it. Done when the user confirms, or the run ends having written nothing.
10. An answer that leaves nothing to place and nothing to delete is not applied at all: say nothing changed and stop. Done when it is said.
11. Run `uv run "$HERE/scripts/kntnt.py" apply select` with the same `--project` flag, every name in the resolved checked set, and `--yes`. Forward `--dry-run` if the user passed it, and say before starting that the run happens against a temporary home that is thrown away, and that it downloads the transport afresh and so takes longer than the real run would. Unchecking deletes files, so the script refuses without `--yes`; reaching this step means step 9 settled it. Done when stdout is JSON.
12. Report the outcome the payload carries, not the answer. `intended` names the skills the run set out to change, `placed` and `removed` say which way each of them went, `confirmed` names those the script then found the disk agreeing about, and `noop` those the run left alone — already exactly as answered, or carried by a delta that never named them. `unsatisfied` names each skill the answer left without a Dependency and what it lacks: report it as the state the user chose, not as a failure of the run. If `failed` is non-empty the command exits non-zero: say those skills did **not** change, whatever the transport reported, name each one's `directories` as where to look, and do not call the run clean. Done when the user has the outcome.

## Without the list

The list is what a person reads, and these forms are for a run with nobody at it. Print no list in either of them, and report the payload the script answers with. A skill the user did not name is not written for at all — not Enabled, not Disabled, and not re-copied because its files deviate — since the offer to overwrite a local edit is the list's, and there is no list here to make it.

1. `--on` and `--off` apply a delta and never mean *make this the whole set*: the script starts from what the layer already holds, so a skill nobody named keeps the state it had, and it brings what a named skill needs along with it. Where `--yes` was not given and a name given with `--on` needs a skill the layer does not have, settle that first: run `uv run "$HERE/scripts/kntnt.py" plan select` with the same `--project` flag, read the `requires` and `freshness` of each `--on` name without printing the list, and ask **one** yes/no question naming exactly what would come with them. Where a named skill is already on disk and `deviating`, say in the same breath that re-copying it overwrites the local changes. Write nothing before it is answered. Done when the user confirms, there was nothing to add, or `--yes` answered it.
2. Run `uv run "$HERE/scripts/kntnt.py" apply select` with every `--on` and `--off` the user gave, the same `--project` flag, and `--yes` if they gave it. Forward `--dry-run` as the list form does, saying the same thing about it first. Unchecking deletes files, so the script refuses an `--off` without `--yes`: report that refusal as it stands and stop, rather than supplying a `--yes` the user did not give. Done when stdout is JSON.
3. `--yes` with neither `--on` nor `--off` puts what the user already has into good order and does nothing else: run `uv run "$HERE/scripts/kntnt.py" apply select --as-is --yes` with the same `--project` flag, and forward `--dry-run` as step 2 does. It Enables no skill that was not Enabled already — what deviates is refreshed and what is incomplete is repaired — because an unattended run must never place instructions the user has not read. Done when stdout is JSON.
4. Say where the Catalog came from before reporting a refresh. `catalog_refreshed` false means the collection could not be reached and the run reasoned from the copy stored beside the manager: nothing on such a list can be judged deviating, so say that nothing was refreshed and why. Done when that is said, or the Catalog was fetched.
5. Report the outcome as step 12 does. Done when the user has it.

## Notes

`--project` shows the Project layer alone. A row whose `in_global` is true is a skill this working directory does not carry and the machine does: say so on the row, because checking it makes a second copy and unchecking it does nothing — this layer holds none of that skill to remove.
